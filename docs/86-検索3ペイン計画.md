# 検索 3 ペイン計画

検索画面を、広い画面でだけ「左: 仮想フォルダー / 右上: 検索結果一覧 /
右下: 選択したノート」の 3 ペインにする。主戦場のスマホは現行 UI を
一切変えない — 3 ペインは広い画面のときの上乗せであって、置き換えではない。

## §1 フォルダーは作らない (仮想に徹する)

フォルダーのテーブルもノートの所属列も作らない。材料は既に揃っている:

- **タグ = フォルダー**。`Item.tags` は保存のたびに作り直す派生キャッシュで、
  フォルダーのクリック = 検索窓に `#タグ` を入れるのと同じ動作にする。
  正本は今の検索一本のまま。
- **特殊フォルダー**: すべて / 未分類 (tags が空) / 最近 (accessedAt 順) /
  ゴミ箱。いずれも既存の検索・並び順・/trash へのリンクにすぎない。
- **ピン留め検索 = スマートフォルダー**: `SearchQuery` (検索履歴) に
  kind を 1 つ足すだけで「保存した検索」が作れる (Phase 3)。

こうしておけばフォルダーとノートの所属がずれる同期問題は構造的に起きない —
フォルダーは常に検索結果のエイリアスだから。

## §2 選択ノートは URL で持つ (intercepting routes)

右下のペインは「`/item/<番号>` へのソフトナビゲーションを検索画面の中で
受け止めた物」として作る。Next の parallel routes + intercepting routes
(公式のフォトモーダルの型。node_modules/next/dist/docs の
parallel-routes.md §Modals) をそのまま使う:

```text
src/app/(search)/
  layout.tsx                     … children と detail スロットを並べるだけ
  @detail/default.tsx            … 未選択 (ハードロード時) は null
  @detail/(.)item/[itemNo]/
    page.tsx                     … ペインの中身 (ItemView を再利用)
    loading.tsx                  … ペインの骨組み
```

- **一覧の行リンクは今のまま** (`buildItemUrl` が組む /item/… への Link)。
  ソフト遷移だけが横取りされ、URL は /item/… のまま右下に出る。
  共有・リロード・QR シールからの直リンクは従来どおり全画面の /item に
  自然フォールバックする (ハードロードは横取りされない仕様)。
- **parallel routes だから一覧セグメントは再レンダーされない**。無限
  スクロールの読み込み済みページとスクロール位置がそのまま保たれる。
  `?peek=` のような searchParams 方式を採らないのはこれが理由 —
  あちらは選択のたびに検索本体が再実行され、buildSearchUrl を使う全箇所
  (打鍵・ページ送り・並び替え) に選択状態の持ち回しが要る。
- **@detail/page.tsx は置かない**。スロットは「合わない URL へのソフト遷移
  では前の中身が残る」仕様で、これを利用して AutoLoadMore の
  `replace(/?page=N)` や打鍵での URL 書き換えでペインが閉じないようにする。
  null を返す page を置くと、ページ送りのたびにペインが消える。
- 閉じるのは `router.back()`。**Esc は持たせない** — モーダル類 (draw・
  スキャナ・検索パネル…) がそれぞれ自前の Esc を持つ流儀で、ペインが
  window で先に拾うと、開いているモーダルより先に画面ごと閉じてしまう。

## §3 accessedAt はプレビューでは進めない

「最近見た順」(docs/37) の記録 `RecordAccess` を横取り側の page には
**置かない**。一覧で ↑↓ や連続タップで流し見するたびに accessedAt が
動くと、並びが「最近触った順」ではなく「最近カーソルが通った順」になる。

進めたいとき (本当に開く) の口は 2 つ:

- ペインの「開く」— `<a href>` のハード遷移。横取りを抜けて素の /item に
  到達し、そこで初めて RecordAccess が働く。ソフト遷移では横取りから
  逃げられないので、ここだけは意図的に `<a>` を使う。
- ItemView 内の「編集」— /edit は横取り対象外なので普通の Link のまま。

## §4 ペインの見た目 (PreviewPane)

中身は全画面の /item と同じ `ItemView` + `ItemListNav` (前後ナビ。リンクは
また横取りされるので、ペインの中だけで前後に歩ける)。器だけ新設する:

- **lg 未満**: ヘッダーの下いっぱいのオーバーレイ (§4-5 のとおりヘッダーは
  覆わない)。見た目は従来の画面遷移とほぼ同じで、戻る = router.back() で
  一覧に帰る。横取りは画面幅では止められないので、狭い画面では「ペイン」
  ではなく「全画面」として描く、が正しい畳み方。
- **lg 以上**: 画面下半分に固定 (`--preview-pane-h`、既定 45dvh)。中で
  独立にスクロールする。下端は下部操作バーのぶん (`--bottom-bar-h`) 上で
  止め、スキャン等のボタンを塞がない。
- 選択中の行は「いまペインに出ている番号」でハイライトする (§4-4)。
  画像表示のタイル (ImageMasonry) にも同じ印を降ろす。
- 一覧の行の文字はノート本文と同じ大きさ (0.875rem)。一覧とノートが
  並んで見える画面で、片方だけ大きいと視線がそちらに引かれる。

## §4-3 ペイン 2 は自分でスクロールする

lg 以上では一覧の器 (`main`) が**そのままペイン 2** になり、スクロールバーも
その中に出る。当初は「一覧は window スクロールのまま、ペインのぶんだけ
padding-bottom で底上げ」で作ったが、実機で破綻した:

- ウィンドウのスクロールバーが画面の右端を上から下まで貫き、プレビュー
  ペイン自身のバーと 2 本並ぶ。どちらがどこを送るのか見て判らない。
- フォルダーペインは fixed で場所を取らないので、**一覧の左側がペインの
  下に潜る**。小表示で顕著で、テキストサイズ (docs/61) を上げるほど器が
  広がって早く重なる。半透明の地色だと、その潜った行が透けて読めた。

作り (globals.css。フックは検索ページにだけ在る `[data-folder-pane]`):

- `body` を flex 縦積み + `height:100dvh` + `overflow:hidden`。ヘッダーの
  高さを決め打ちせずに済む (テキストサイズで伸びても追随する)。
- `main` は `flex:1` + `min-height:0` + `overflow-y:auto`。下部バーと
  (開いていれば) プレビューペインのぶんは **margin-bottom** で外に置く —
  padding だとスクロールバーだけがペインの外まで伸びる。
- 器はペイン 2 の領域いっぱいに広げ (`max-width:none` + `margin-inline:0`。
  `mx-auto` を残すと flex の子が中身幅に縮んでバーが画面の中ほどに出る)、
  読み幅は中身 (`[data-results-pane]`) が `max-width:42rem` で持つ。
- フォルダーが居るときは `padding-left` でそのぶん右へ寄せる (§4-9)。
  ペイン 2 の中身はペイン幅いっぱいに広げる (§4-8)。
- モバイル (lg 未満) は素通し。従来どおり window スクロールで、
  PullToRefresh もそのまま効く (内側スクローラができる lg 以上では、
  PullToRefresh 自身の `hasScrollableAncestor` が働いて出ない)。
- AutoLoadMore は IntersectionObserver が祖先の overflow で切り取られた
  可視領域を見るので、内側スクロールでもそのまま働く (実測: 底まで送ると
  次ページが継ぎ足され、位置も保たれる)。

## §4-2 境界はドラッグで動かす

ペインの境界 (`PaneResizer`) を掴んで、フォルダーの幅とプレビューの高さを
変えられる。**動かすのは CSS 変数 2 つだけ** — ペイン自身の寸法も、一覧の
底上げ padding も、カード一覧の広幅補正も、もとから同じ変数を見ているので
(§4)、変数を書き換えれば全部が追随する。

| 境界 | 変数 | 単位 | 既定 | 範囲 | 刻み (キー) |
| --- | --- | --- | --- | --- | --- |
| フォルダーの右端 (xl 以上) | `--folder-pane-w` | rem | 14 | 9〜28 | 1 |
| プレビューの上端 (lg 以上) | `--preview-pane-h` | dvh | 45 | 20〜80 | 5 |

- **単位が違うのは意図的**。フォルダーは rem — テキストサイズ (docs/61) を
  上げると中の行も伸びるので、幅も一緒に伸びないと文字が詰まる。
  プレビューは dvh — ウィンドウの高さが変わっても「画面の何割」が保たれる
  (px で持つと、小さい画面に持ち込んだとき一覧が潰れる)。
- 寸法・上下限・刻み・CSS 変数の綴りは `src/lib/paneSize.ts` の表 1 つが
  正本。ポインタ→寸法の計算 (どちらの端から測るか) も同じ file に置く —
  掴む場所を決める CSS と対なので、離すとずれる。
- 保存は localStorage、初回描画前の反映は layout.tsx の `<head>` に置く
  インラインスクリプト。テキストサイズと同じ作りで、サーバは寸法を知らない。
  **上下限をスクリプトに書き写さない** (表から組み立てる) のが要点 —
  書き写すと、読み込み直後だけ古い上限で clamp される端末が生まれる。
- ドラッグ中は state を更新しない (ref と CSS 変数だけで進める)。1 フレーム
  ごとに再描画すると、一覧に数百行ある状態で引っかかる。
- キーボードでも動かせる (`role="separator"` の window splitter): 矢印で
  1 刻み、Home / End で端まで、Enter で既定へ。ダブルクリックも既定へ戻す。

## §4-4 ペイン構成はヘッダーで切り替える

ヘッダー右端 (ユーザー名の左) の色付きアイコン + 数字を押すと、
**3 → 2 → 1 → 3** と構成が回る。

| 構成 | 出る面 | ノートの畳み方 |
| --- | --- | --- |
| 3 | フォルダー + 検索結果 + ノート | **常に出す** (幅に関係なく §4-9)。開いていなければ先頭を選ぶ |
| 2 | 検索結果 + ノート | **ペインの間 (lg 以上) は 3 と同じ**で常に出す。狭い画面は開いたときだけ |
| 1 | 検索結果だけ | 開くと全画面 (スマホと同じ畳み方) |

- 置き場は cookie (`panes`)。表示モード (docs/23 §5) と同じ理由で、
  「どう見たいか」という端末ごとの好みだから。**サーバが描画前に読める**
  ことが要で、フォルダーを出すかどうかの判断もサーバで済む — クライアントで
  隠すだけだと、出さない構成でもタグの集計を引いてしまう。
- ヘッダーは左右に振り分ける。器を `max-w-2xl` で中央に寄せていた頃は、
  3 ペインにするとハンバーガーもユーザー名も画面の中ほどに集まり、左の
  フォルダーとも右のノートとも揃わなかった。
- ボタンは**どの幅でも出す** (§4-9)。3 ペインは幅に関係なく 3 ペインなので、
  狭い画面で隠すと選んだ構成から抜ける手段が無くなる。
- アイコンは**いまの構成そのものを描く** (押した先ではない)。3 つのペインを
  青 (フォルダー) / 緑 (検索結果) / 琥珀 (ノート) で塗り分け、形・色・数字の
  3 通りで同じことを言う。送信中は送った先を先に見せる (docs/62 §3-1)。

### 「必ずノートを出す」作り (3 / 2 ペイン)

2 つの出どころを使い分ける (`PaneModeProvider` が両方を見張る):

- **横取りスロット (@detail)** … 利用者が自分で選んだノート。ペインとして
  出ている間は URL が /item を離れても閉じない (検索語の打ち替え・ページ送りで
  消えない)。「閉じる」も出さない — 押しても閉じられない物をボタンにしない
  (2 ペインの狭い画面はノートが全画面 = 閉じられるので、そこだけ出す)。
- **自動のノート (`AutoNotePane`)** … まだ何も選んでいないときに、検索結果の
  先頭を検索ページ側が server render して出す。横取りスロットがノートを
  持った時点で引っ込む。

**URL は動かさない。** `router.replace` で `/item/<先頭>` へ飛ばす手もあるが、
それだと再読み込みした瞬間に横取りの外 (全画面のノート) へ着地して 3 ペインが
消える。検索ページ側で描けば URL は検索のまま保てる。

- 自動のノートは `SearchResults` の**外**に置く。あちらはカード表示で
  breakout の `transform` を持ち、transform のある要素は `position: fixed` の
  包含ブロックになる (下部バーを nav の外へ出しているのと同じ罠)。中に入れると
  ペインが一覧の幅の中へ縮んで浮く (実測で発覚)。
- 一覧の行・画像タイルのハイライトは pathname ではなく context の
  `shownItemNo` を見る。3 ペインでは URL が /item から離れてもノートが
  出たままなので、URL だけでは「いま何が出ているか」が決まらない。

## §4-5 ヘッダーは常に見えている

- ノートを全画面で開く場面 (1 ペイン・lg 未満) でも、**ヘッダーは覆わない**。
  上端は必ず `--header-h` の下から始める。メニュー・ホーム・ペイン構成は
  ノートを開いている間も押せる必要がある。ペインは z-10 / z-0 で、
  ヘッダー (z-20) には必ず譲る。
- 帯は lg 以上では 1 行の高さに詰める (44px のタップ目標を外す)。
  スマホでは 44px のまま — 指で狙う画面だから。
- `--header-h` は**実際の帯より小さめ**に置くこと。ペインはヘッダーより
  下の層なので、足りない分は帯の下に潜って見えない。逆に大きいと隙間が開く。

## §4-6 ペイン 2 の中で送るのは一覧だけ

検索窓・件数・進捗はペインの上に留まり、**一覧 (と特性表・ページ送り) だけ**が
内側でスクロールする。スクロールバーもその器に付くので、一覧の右端に沿う。

積み方は flex の縦 3 段 (`main` → `[data-results-pane]` → `[data-search-results]`
→ `[data-results-scroll]`)。どの段にも `min-height: 0` を置くこと — flex の子は
中身より縮まないのが既定で、1 つでも抜けると内側のスクロールが働かず、器が
下へ伸びるだけになる。

下端の空きは器の `margin-bottom` が持つので、文書の流れで空けていた分
(下部バーぶんの spacer と `pb-safe`) は畳む。残すと一覧の下に同じ幅の死んだ
余白ができる (実測で発覚)。

## §4-7 表示は 小 / 中 / 大 / 画像 の 4 段

一覧の密度を 1 段増やした (docs/23 の表示モードに `medium` を足す)。

| 表示 | 行 | タグ | サムネ |
| --- | --- | --- | --- |
| 小 | 1 行 (#番号 + タイトル) | 出さない | 1 行ぶん (24px) |
| 中 | 2 行 (+ タグ) | 出す | 2 行ぶん (40px) |
| 大 | カード (+ 本文 3 行) | 出す | 5 行ぶん (96px) |
| 画像 | タイル | タイルの下 | 画像そのもの |

- 小からタグを落とすのは、**1 ノート 1 行に詰めるため**。タグは中・大・
  ノート本体・フォルダーペイン (§5) で見られるので、いちばん密な表示から
  外しても行き止まりにはならない。
- サムネと縮小プレビューの枠は行の高さに合わせる。プレビューは
  「キャンバス × 縮小率 = 枠」の組を崩さないこと (docs/71 §2) —
  小は 10rem × 0.15 = 1.5rem、中は 10rem × 0.25 = 2.5rem。
- 器を広げるのはカードと画像だけ (`usesWideResults`)。1 カラムの小・中は
  読み幅を保つ。**判定は viewMode.ts に置く** — 検索とゴミ箱の 2 か所で
  同じ式を書くと、表示を足した日に片方だけ広いままになる。

## §4-8 ペインの中身はペイン幅いっぱい

lg 以上でペインとして出ているときは、検索結果もノートも**ペインの幅
いっぱい**に広げる。3 ペインは既に画面を縦横に割ってあり、その中でさらに
読み幅 (42rem) に絞ると、ペインの左右が空いて何のために割ったのか判らなくなる。

- 検索結果 … 器 (`[data-results-pane]`) の max-width を外す。カード表示の
  広幅 breakout (`WIDE_RESULTS_CLASS`) も**要らなくなるので外した** —
  あれは「中央 42rem の器からはみ出す」ための道具で、器がもうペイン幅
  いっぱいなら二重に効いて中心がずれる。
- ノート … 下部ペインのときだけ `lg:max-w-none`。全画面 (1 ペイン・狭い
  画面) では読み幅に収めたまま — 画面の端から端まで続く行は目で追えない。

## §4-9 3 ペインは幅に関係なく 3 ペイン

構成を選んだ以上、ブラウザ幅で勝手に畳まない。

| 構成 | フォルダー | ノートの器 |
| --- | --- | --- |
| 3 | 幅に関係なく出す | 幅に関係なく下部のペイン |
| 2 | 出さない | lg 以上はペイン、狭い画面は全画面 |
| 1 | 出さない | 幅に関係なく全画面 |

- **既定は 2**。3 はどの幅でも 3 ペインで通すので、既定にするとスマホの
  初回表示がフォルダーで埋まる。2 ならこの機能が入る前とまったく同じ
  見た目 (広い画面ではノートのペイン、狭い画面では全画面) になる。
  3 ペインは端末ごとに 1 度選べば cookie が 1 年覚えている。
- ヘッダーのボタンは**どの幅でも出す**。狭い画面で隠すと、選んだ構成から
  抜ける手段が無くなる。
- CSS のペインの積み方 (§4-3) は**同じ宣言を 2 か所**に置いてある:
  `@media (min-width: 64rem)` と `body:has([data-panes="3"])`。CSS には
  「幅 or クラス」の or が書けないため。**必ず対で直すこと。**
  1 / 2 ペインの狭い画面を従来の文書スクロールのままにするのは、
  引っ張って更新 (docs/47) が内側スクローラでは出せないから。
- ノートのペイン (下部) は **z-0**。下部バー (z-10) より下に置く —
  バーの長押しメニューはバーの上へせり上がるので、ペインと同層だと
  DOM 順で負けて隠れる (実機で判明)。全画面のときだけ z-10 でバーごと覆う。

## §4-10 境界は濃いグレイの線で見せる

ペインの継ぎ目が判らないと、どこを掴めば動かせるのかも判らない。

- 線を描くのは**掴む帯 (`PaneResizer`) の中の 2px** で、ペイン側は枠線を
  持たない。両方に持たせると二重線になる。
- 色は既定でグレイ (`gray-400`)、触れている間と掴んでいる間は青。
  「いまどの境界を動かしているか」がその色で判る。
- 帯そのもの (8px) は塗らない。塗ると太い色帯になって、線ではなく面に見える。

## §4-11 一覧に効く操作は一覧の頭に置く

表示 (小/中/大/画像)・並び順・選択は**検索結果の見出し行**(件数の右) に置く。
画面下端のバーに残るのはスキャンと画像検索だけ。

- 3 ペインではバーが画面のいちばん下 = ノートのペインの下にあり、そこに
  一覧の操作があると**どのペインに効くのか判らなかった**。操作は効く対象の
  そばに置く。
- 中身は下部バーとまったく同じ部品 (`ViewSlot` / `SortSlot`) の `variant`
  違い。循環・長押しメニュー・JS 無効での送信は `BarSlot` に置いたまま
  共有する — 書き写すと必ずずれる (docs/67 で一度踏んだ)。
- 見出し行のメニューは**下向きに開く** (`SlotMenu` の `side`)。上へ開くと
  検索窓を覆う。
- 件数の行は `<p>` から `<div>` に変えた。中にフォームを持つので、段落の
  中に置くと HTML として不正になる。
- ゴミ箱のバー (`TrashActionBar`) は従来どおり表示・並び順を帯に持つ —
  あちらは 1 画面 1 一覧で、取り違えようがない。

## §4-12 fixed のペインは親の余白を打ち消す

ペインも境界も `position: fixed` だが、**margin は効く**。絶対配置の位置は
「上端 + margin + 高さ + margin + 下端 = 器の高さ」で解かれるので、親から
margin を配られるとその分だけずれる。

自動で選ぶノート (`AutoNotePane`) は検索結果の器 (`space-y-2`) の子として
描かれるため、`margin-top: 8px` が付いて**ペインが 8px 上へ浮き、一覧の
最下部と重なっていた** (実機で報告。`main` の底は margin-bottom で
正しい位置にあるので、ペイン 2 が境界からはみ出して見える)。

対策はペイン側と境界側に `m-0` を持たせること。fixed の面が流れの余白を
受け取る理由はないので、打ち消すのが正しい。**器の DOM 位置に依らない**
のが要点で、置き場所を変えても壊れない。

## §4-13 浮かせる物はペインの外へ出す

ペインの器は `overflow: hidden` / `auto` なので、**中から浮かせた物は切られる**。
検索窓の候補一覧が下半分を失っていた (実機で報告)。

- 候補一覧は `position: fixed` にして、窓の位置を実測して置き直す。
  fixed は祖先の overflow に切られない (包含ブロックを作る祖先が無いことは
  実測で確認済み)。開いている間だけ `scroll` (capture で祖先の内側
  スクロールも拾う) と `resize` を購読して追従させる。
- 重なりは z-30 — ノートのペイン (z-0) と下部バー (z-10) より上。
  実測: 画面が低いときに候補がペイン 2 の下端を 42px 越え、最終行が
  ノートのペインの上でも押せる。
- 行の高さは本文 1 行ぶん (約 24px)。候補は「1 画面にいくつ並ぶか」が
  そのまま使い勝手になる場所なので、40px のタップ目標より一覧性を優先する
  (フォルダーペインの行と同じ判断)。

同じ罠は下部バーの長押しメニューでも踏んでいる (§4-11 の `side`)。
**浮かせる物を足すときは、必ずペインの器の外に出ているか確かめること。**

## §5 Phase 2: フォルダーペイン

- `(search)/layout.tsx` の左に `FolderPane` (サーバーコンポーネント)。
  出すかどうかは構成が決める (§4-9) — 3 ペインを選んだ端末では幅に
  関係なく出る。モバイル用のドロワーは作らない — タグ補完と検索履歴が
  既にあり、重複投資になる。
- タグ集計は `unnest(tags)` の生 SQL 1 本。数百件規模の seq scan で足りる
  (title / task_todo と同じ判断で索引は張らない)。
- 各フォルダーは単なるリンク: タグ → `/?q=%23タグ`、最近 → `/?sort=accessed`、
  ゴミ箱 → `/trash`。現在の URL と一致する物をハイライトする。
- 地色は**不透明**。fixed で場所を取らない以上、下には一覧が通っている
  (§4-3)。半透明にすると行が透けて読めた。
- 行の高さは本文 1 行ぶん (約 24px)。44px のタップ目標は取らない —
  このペインは xl 以上、つまりポインタで狙う画面にしか出ないので、
  指の的より一覧性を優先する。
- 縦はヘッダーと下部バーの間まで。`z-0` で、バー (z-10)・ヘッダー (z-20)
  には譲る (テキストサイズで帯が伸びた日にボタンへかぶらないため)。

## §6.5 レビューで確認した割り切り

- ペインの下端は下部バーの高さ 49px (44px スロット + 余白 4px + 枠 1px) を
  決め打ちで避ける。テキストサイズ拡大 (docs/61) でバーは最大 1.3 倍まで
  伸び、ペインの下端 15px ほどに重なるが、そこはペイン内側の pb-20 の

  (実測で確認)。RecordAccess・保存トーストとも従来どおり全画面側で働く。
  (search)/default.tsx は、それでも圏外からのソフト遷移で横取りが起きた
  場合に 404 にしないための安全網として置いてある。
- 一覧の行は memo 化しない。プレビュー選択での全行再レンダーは、打鍵の
  たびに起きている既存の再レンダーと同規模で、memo 化は per-row callback
  (スワイプ) の作り直しを伴い割に合わない。
