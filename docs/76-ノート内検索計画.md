# ノート内検索計画

編集中のノートの中を**探して置き換える**。長いノート (問題集・部品メモ) で
「あの語をどこに書いたか」を探す手段が、いまは画面をスクロールすることしか
無い。全文検索 (docs/04) はノートを**見つける**ための道具で、開いた 1 枚の
中を歩く道具ではない。

土台は既に載っている。`basicSetup` が `searchKeymap` を既定で入れているので、
PC では今も `Ctrl+F` で CodeMirror 標準のパネルが開く。足りないのは
**スマホで使える UI** と**置換の安全策**の 2 つで、この計画はそこだけを足す。

§8 の 1〜6 まで実装済み。ローカルのブラウザで一巡確認した (検索・前後送り・
置換 1 件・全置換・元に戻す・`Ctrl+F`・`Enter`・`Escape`・閉じるとライブ
プレビューが戻ること)。実機 iPhone の追試 — 特に §6 のキーボード追従 — が残り。

`@codemirror/search` は `package.json` に**明示していない** (@uiw/react-codemirror
が連れてくる物に相乗りしている)。直接 import しているので、次に依存を触るときに
`npm i @codemirror/search` で立てておくとよい。

## §1 対象は編集画面だけ — 閲覧はブラウザに任せる

閲覧画面 (`/item/:no`) には手を入れない。ページャーは隠したページも DOM に
残してある (`NotePager.tsx` の冒頭コメント) ので、ブラウザのページ内検索が
既に全ページに当たる。自前のハイライトを重ねると、`react-markdown` が描いた
木に手を入れることになり、割に合わない。

`:::details` の中は閉じていると Safari が拾えない、という穴は残る。ここは
別途 (§7)。

## §2 下部バーを検索バーに差し替える

入り口は編集の下部バー (`EditToolbar`) に「検索」を 1 つ足す。**タップで検索、
長押しで置換つき**で開く (docs/62 の長押しの流儀)。開いている間、バーの中身は
検索バーに**入れ替わる** — 並べると帯が 2 段になり、狭い画面で本文が潰れる。

```text
検索だけ (1 段)
┌────────────────────────────────────┐
│ 🔍[ 抵抗            ] Aa 3/12  ∧  ∨  ⇄  ✕ │
└────────────────────────────────────┘
                                  ↑置換を開く

置換つき (2 段)
┌────────────────────────────────────┐
│ 🔍[ 抵抗            ] Aa 3/12  ∧  ∨  ⇄  ✕ │
│ ⇄ [ レジスタ         ]   置換    すべて(12) │
└────────────────────────────────────┘
```

- 件数 `3/12` は常時出す。0 件は入力欄と件数を赤くするだけ (アラートは出さない)。
- `∧ ∨ ✕` は親指の届く右端に固める。`Enter` = 次、`Shift+Enter` = 前、
  `Escape` = 閉じる。PC の `Ctrl+F` はこのバーを開く側へ奪う (標準パネルは
  ハイライトの都合で使わない。§3)。
- 開くとき、選択範囲があればそれを検索語の初期値にする。無ければ直前の語を
  復元して全選択する (同じ語を続けて探すことが多い)。
- 大小の区別は `Aa` の 1 つだけ。既定は**区別しない** — 日本語の本文では
  ほとんど効かない設定なので、既定で有効にすると「打った語が見つからない」
  だけの罠になる。

## §3 ハイライトは自前で描く (標準のものはパネルが無いと描かない)

`@codemirror/search` の `searchHighlighter` は

```js
highlight({ query, panel }) {
  if (!panel || !query.spec.valid) return Decoration.none
```

と、**パネルが開いているときしか**装飾を作らない。バーを下部バーへ portal
する (= CodeMirror のパネルを開かない) この設計では、検索語を入れても
ハイライトだけが出ない、という形で出る。

なので `SearchQuery.getCursor()` (公開 API) を使う 25 行ほどの ViewPlugin を
自前で持つ。検索状態そのもの (`search()` の StateField・`setSearchQuery`・
`findNext` / `findPrevious`) は標準のものに乗る — 折り返しも位置の付け替えも
書き直す必要がない。

`findNext` はパネルが無くても動く (`selectSearchInput` がパネル不在で
何もしないだけ)。**クエリが valid なうちは**標準パネルは開かない。

## §4 検索中はライブプレビューを畳む

ライブプレビュー (docs/70) は記法を `Decoration.replace` で隠す。隠れた範囲は
DOM に無いので、そこに当たった一致は**ハイライトが出ず、飛んでも何も無い所に
着く**。表・図・数式のブロックの中も同じ。

バーを開いている間だけ Compartment を OFF に差し替え、閉じたら利用者の設定へ
戻す。**localStorage の設定は書き換えない** — 検索を閉じたら元の見た目に戻る。

## §5 置換の安全策

スマホで押す「すべて置換」は、押し間違いの被害がいちばん大きい操作なので、
4 つ足す。

1. **件数をボタンに出す** — `すべて(12)`。押す前に規模が判る。
2. **1 手で戻せる** — 置換は 1 トランザクションにまとめるので `Ctrl+Z` /
   「元に戻す」1 回で全部戻る。置換後は「12 件置換しました｜元に戻す」を
   バーの上に数秒だけ出す (確認ダイアログより速い)。
3. **上限を超えるなら断る** — 本文には `MAX_TEXT_LENGTH` (32,000) の
   `changeFilter` が掛かっており、超える変更は**黙って捨てられる**。
   置換後の長さを先に計算し、超えるときは理由を出して実行しない。
   (`fix:` として書けば「押したのに何も起きない」で終わっていた罠)
4. **シークレット記法は書き換えない** — `![ラベル](/api/secrets/<名前>)` の
   `<名前>` が壊れると、暗号化された断片への参照が切れて**戻せない**
   (docs/51)。全置換はこの記法に重なる一致を飛ばし、飛ばした件数を出す。

置換 (1 件) は「いまの一致を置き換えて次へ進む」。一致の上にいなければ、
置き換えずに次へ進むだけ。

## §6 キーボードに隠れない

一致へ飛ぶとき `EditorView.scrollMargins` に下余白を積む。ソフトキーボードは
iOS では**レイアウトの高さを変えない**ので、素直に scrollIntoView すると
一致がキーボードの裏に着地する。余白は `visualViewport` から毎回計算する
(`scrollMargins` は関数を受け取り、スクロールのたびに呼ばれる — 拡張を
組み直さずに値を変えられる)。

## §7 やらないこと

- **正規表現** … `.*` のトグルは入れない。全置換といちばん相性の悪い機能で、
  無効なパターンの表示・後方参照の説明までを狭い帯に載せる釣り合いが取れない。
  必要になったら足す。
- **選択範囲だけを置換** … スマホでの範囲選択そのものが難しい。
- **閲覧画面の自前検索** … §1。やるなら `<mark>` の差し込みではなく
  CSS Custom Highlight API (DOM を触らない)。
