# 解答履歴計画

quiz フェンス ([docs/58-CBT問題集計画.md](./58-CBT問題集計画.md)) に
「解いた記録」を残せるようにする。紙の問題集の**余白に日付と○×を書く**
習慣に当たるもの。

いまのチェック 2 つ (docs/60 §1) が持つのは**現在の状態**だけで、
「3 回解いて 2 回間違えた問題」と「1 回で通った問題」の区別が付かない。
数か月単位で回す資格試験では、この履歴が復習の優先順位そのものになる。

docs/58 §6 は解答履歴を「保存するなら正本 (本文) に刻む方式になる」と
見送っていた。本計画はその方式をそのまま採る。

## 1. 記録は本文の行 — テーブルも列も作らない

解答後に「記録する」を押すと、**その quiz フェンスの直下**に 1 行足す。

````text
```quiz
問: …
正解: 2
```

- 2026-08-13 ×
- 2026-08-20 ○
````

- 正本はメモ本文 ([docs/55](./55-チェックボックス操作計画.md) のチェックと
  同じ考え方)。専用テーブルを作らないので、git 履歴 (docs/57)・
  エクスポート・オフライン同期・公開ビューのどれにも手が入らない。
- ただの markdown のリスト行なので、**編集タブで自由に消せる・直せる**。
  特別な記法を覚える必要もない。
- 記号は 3 つ。○ = 正解、× = 不正解、△ = 降参して解説を見た
  (docs/60 §3 の `revealed`)。どれになるかは押した時点の解答状態から
  決まり、利用者は選ばない (ボタンは 1 つ)。

### 末尾追記ではなくフェンス直下に置く理由

ノート末尾に追記する案は採らない。B 問題 (docs/58 §5) は 1 ノートに
quiz フェンスが (a)(b) の 2 つ並ぶが、**フェンスにはカードを識別する
id が無い** ([QuizFence.tsx](../src/components/quiz/QuizFence.tsx) に
渡るのはフェンス本文だけ)。末尾に集めると a と b の記録が混ざる。
フェンス直下なら**位置が所属を表す**ので、id を導入せずに済む。
読むときも問題のすぐ下に履歴があるほうが自然。

## 2. どのフェンスかは行番号で指す (チェックボックスと同じ作法)

カード id を作らない代わりに、チェックボックス (docs/55 §2) と同じく
**本文上の行番号**で指す。

- mdast の `code` ノードは `position` を持つ。quiz の描画分岐
  ([MarkdownView.tsx](../src/components/MarkdownView.tsx) の
  `preOrDiagram`) からフェンス終端行を `QuizFence` へ渡す。
  sanitize 後に position が残らない描画経路だった場合は、
  [rehypeTaskLines.ts](../src/components/rehypeTaskLines.ts) と同じ
  「行番号を data 属性に写すプラグイン」の作法へ切り替える。
- **ページ分割のオフセットを忘れない。** [NoteBody.tsx](../src/components/NoteBody.tsx)
  はページごとに本文を切って描き、チェックには `lineOffset` を足している
  (docs/74)。quiz の行番号も同じ規約を通す。ここを漏らすと 2 ページ目
  以降の記録が 1 ページ目の行に刺さる。

## 3. 書き換えは「パーサに聞いてから行挿入」

`src/lib/quizRecord.ts` に純関数を置く。

```ts
appendQuizRecord(memo, fenceEndLine, date, mark): string | null
```

1. `MEMO_PARSER` で本文を解析し、`lang === 'quiz'` の `code` ノードで
   `position.end.line === fenceEndLine` のものが**本当にある**ことを
   確かめる。無ければ null (別タブで本文が変わった) —
   [toggleTaskLine](../src/lib/taskCheckbox.ts) と同じ二段構え。
2. 挿入位置は、フェンス終端の直後から**既存の記録行の連なり**
   (`- YYYY-MM-DD ○|×|△` に一致する行と間の空行) を読み飛ばした先。
   古い記録が上、新しい記録が下 (時系列で読み下せる)。
3. 最初の 1 件はフェンスとの間に空行を 1 つ入れてから足す
   (フェンス直後の行はリストとして解釈されるが、詰めて書くと
   編集画面で読みにくい)。
4. **同じ日付・同じ記号が既に最後の記録なら書かずに null を返す**
   (連打・同日の解き直しで同じ行が並ばない。冪等)。日付が同じでも
   記号が変われば足す — ×→○ の同日挽回は残す価値がある。
5. 改行コードは [memoLines.ts](../src/lib/memoLines.ts) の
   `splitLines` / `joinLines` / `newlineOf` で保つ (CRLF メモを壊さない)。

## 4. 保存は Server Action

`recordQuizAction(itemNo, fenceEndLine, mark, date)`。

- `requireUser()` 必須 (画面を通さず叩ける POST の口)。公開ビュー・
  印刷・`/docs/*` にはボタン自体を出さない (docs/55 §5 と同じ線引き)。
- **シークレット断片の中の quiz にも出さない。** 断片は独立した
  MarkdownView で描かれ、行番号が本文と一致しない (docs/55 §5 と
  同じ理由)。
- `date` はクライアントの端末日付 (`YYYY-MM-DD`) を受ける。サーバは
  UTC で動いており日付境界がずれるため、サーバ時刻では作らない。
  境界の入力検証として形式 (`/^\d{4}-\d{2}-\d{2}$/` + 実在日) を検め、
  外れたら弾く。
- `appendQuizRecord` が null なら書かない。本文が変わっていた場合は
  「本文が変わっています」をクライアントへ返す (握り潰さない)。
- 保存は `upsertMemo` (派生列も再計算される)。その後
  `revalidatePath('/item/…')` と `revalidatePath('/')` —
  [toggleMemoTaskAction](../src/app/actions.ts) と同じ並び。

配線も docs/55 §5 の型をなぞる: `MarkdownView` に
`onRecordQuiz?: (fenceEndLine, mark) => Promise<void>` を足し、
[ItemView.tsx](../src/components/ItemView.tsx) だけが
`recordQuizAction.bind(null, itemNo)` を渡す。描画部品にノート番号を
持ち込まない。

## 5. ボタンの見た目と状態

- 「やり直す」の並びに「記録する」を置く。**解答後にだけ**出す
  (unanswered では出さない — 解いていないものを記録させない)。
- 押すと `useTransition` で送信し、成功したら「記録した ○」の表示で
  押せなくする。楽観更新はしない — 見た目に出るのは追記された行で、
  それは revalidate の再描画が運んでくる。
- 失敗は文言で出す (チェックボックスと同じ。黙って戻さない)。
- 記録される記号は状態から導く純関数 `recordMarkOf(state, answer)`:
  `answered` で `choice === answer` → ○、外れ → ×、`revealed` → △。

## 6. 検索との関係 — 履歴は「開いて読む」もの

記録行を全文検索で拾うことは当てにしない。PGroonga のトークン化は
記号を落とすことがあり (docs/56 §1 で `- [ ]` を直接探す案を捨てたのと
同じ理由)、`×` 単体の検索は保証できない。

- **横断の絞り込みは今までどおりチェック 2 つの仕事** (`is:todo` ほか)。
  履歴はノートを開いたときに「この問題は 2 回続けて×だ」と読むための
  もの — 役割を分ける。
- 「×が多い問題を並べる」が本当に欲しくなったら、`task_todo` と同じ
  派生キャッシュ列 (docs/56 §1 の型) を足す計画を別に切る。今は YAGNI。

## 7. 実装ステップ (TDD)

1. `src/lib/quizRecord.ts` — 純関数。最初の 1 件 (空行込み)・
   追記 (連なりの末尾)・同日同記号の冪等・同日別記号は足す・
   フェンス不一致で null・quiz 以外のフェンス行で null・CRLF 維持・
   ノート末尾がフェンスで終わる場合、をテスト。
2. `recordMarkOf` — 3 状態 × 正誤の表をテスト。
3. `recordQuizAction` — 認証・不正な itemNo・日付形式・本文が変わって
   いた場合の文言。
4. `QuizFence` / `QuizCard` に行番号と callback を通す。カードのテストは
   `renderToStaticMarkup` の作法で届く範囲 — 「未解答では記録ボタンが
   出ない」に絞る (押した後は実機。docs/58 の「テストの届く範囲」)。
5. `MarkdownView` の配線 (`onRecordQuiz` を渡したときだけ有効) と
   `NoteBody` の `lineOffset`。
6. [メモ記法.md](./メモ記法.md) の quiz 節に記録行の形式を追記。
   iPhone 実機で確認 (1 カードのノートと B 問題 2 カードのノート、
   2 ページ目のフェンス)。

## 8. やらないこと

- **解答のたびに自動で記録** — 気軽に押し直すたび本文が書き換わり、
  git 履歴 (docs/57) がノイズで埋まる。記録は意図して押す 1 手にする。
- **正答率の集計・×が多い順の並べ替え** — §6 のとおり。派生列が要る
  ので別計画。
- **経過時間・スコアの記録** — docs/58 §6 のタイマー見送りと同じ理由。
- **記録行の専用レンダリング (チップ化・折り畳み)** — ただのリストで
  始める。行数が邪魔になってから考える。
- **間隔反復 (次回出題日の計算)** — 記録は材料としては揃うが、
  出題スケジューラは別の道具。まず履歴を読む運用で回す。

## 9. 承知しておく制約

- 記録は `upsertMemo` を通るので `updated_at` が動き、**更新順の一覧では
  ノートが先頭へ移る** (docs/60 §4 の既知の性質)。問題集は番号順
  (`sort=itemNo`) で回す前提なのでそこでは影響しない。
- revalidate の再描画で `ItemView` 全体が描き直される (docs/55 §7 と
  同じコスト)。カードの解答状態 (client state) は React が同じ位置の
  部品として保てば残るが、保証はしない — 記録済みのボタン表示が
  未解答に戻っても、本文の記録行は残っているので実害はない。
- 編集タブに未保存の変更があるとき記録すると、その後の保存で記録が
  巻き戻る (docs/55 §7 と同じ既存の性質)。
- 記録行は手で消せる・書き換えられる。それは仕様 (正本は本文) だが、
  形式を崩すと §3 の「連なり」判定から外れ、次の記録がその手前に
  挿し込まれることがある。壊れ方は穏やかで、並び順が乱れるだけ。
