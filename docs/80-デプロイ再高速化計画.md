# デプロイ再高速化計画

`docs/41-デプロイ高速化.md` でレジストリ差分転送に切り替えた後の、2 回目の高速化。
前回は「転送量」だけを見たが、今回は**デプロイ 1 回の全区間を実測**して配分を出した。

結論を先に書くと、1 回 **約 110 秒**のうち **60 秒以上が捨てられる**。
内訳は「毎回やり直している `npm ci` (20.7s)」「変わっていないのに送り直している
108MB (約 9s)」「直列に並べているだけの lint + test (30s)」の 3 つ。

## 1. 実測 (v0.22.50 のデプロイ, 2026-08-13)

実際に流れた本番デプロイを、後から残っている痕跡だけで再構成した。

- 起点: リリースコミット `chore: release v0.22.50` の author 時刻 `20:17:13`
  (手順 2/8 の `doVersion.sh` が打つ)
- push の区間: vps2 のレジストリ volume に書かれた blob の mtime
- 終点側: vps2 の app コンテナの `.State.StartedAt` = `20:18:55`

```text
20:17:13  2/8 doVersion.sh (リリースコミット)
          3/8 lint + test
          4/8 npm ci + next build + export        ← 78.8 秒
20:18:31  4/8 push 開始 (最初の blob が着地)
20:18:42  4/8 push 完了 (manifest)               ← 10.7 秒 / 122.8MB
          5/8 pull + retag
          6/8 migrate + backfill ×2
20:18:55  7/8 app 再作成                          ← 12.3 秒
          8/8 ヘルスチェック (未計測)
```

78.8 秒の中身は、同じ入力を手元で個別に計った値の合計とほぼ一致する。

| 区間 | 実測 | 備考 |
| ---- | ---- | ---- |
| `npm run lint` | 6.65s | warning 1 件 |
| `npm test` | 23.45s | 237 ファイル / 3056 テスト |
| `npm ci --ignore-scripts` | 20.7s | **毎デプロイ動いている** (後述) |
| `npm run build` (Turbopack) | 14.9s | 依存キャッシュありの場合 |
| export (`rewrite-timestamp`) | 4.9s | 全層の mtime 書き換え |
| 小計 | 70.6s | + doVersion / git / コンテキスト転送 ≒ 78.8s |

push の実効速度は **122.8MB / 10.7s = 11.5MB/s (約 92Mbps)**。
**回線は詰まっていない** — 送る量そのものが多い。

## 2. 何が無駄か

### 2-1. `npm ci` が毎デプロイやり直しになっている (20.7 秒)

`doVersion.sh` はビルドの**前**に `package.json` と `package-lock.json` の
`version` を書き換える。Dockerfile の依存レイヤーは

```dockerfile
COPY package.json package-lock.json prisma.config.ts ./
RUN npm ci --ignore-scripts
```

なので、版が 1 つ上がるだけで COPY 層のダイジェストが変わり、**依存が 1 つも
変わっていなくても `npm ci` が走り直す**。実測 20.7 秒。

手元で確かめた: `package.json` を触らずにビルドすると `npm ci` は `CACHED` になり、
ビルド全体が 17 秒で終わる。触ると 20.7 秒が上乗せされる。

### 2-2. 変わらない 180MB を毎回送っている

push されるイメージの層を実測した (`296.4MB` 圧縮)。

| 層 | 圧縮サイズ | 中身 | 毎回変わるか |
| ---- | ---- | ---- | ---- |
| 0–5 | 76.7MB | `node:24-slim` ベース | いいえ |
| 6 | 31.0MB | `apt-get install git` | いいえ |
| 7 | **92.1MB** | `COPY .next/standalone` | **はい** |
| 8 | **25.0MB** | `COPY .next/static` | **はい** |
| 9 | 59.0MB | `COPY public` | いいえ |
| 10 | 12.6MB | onnxruntime の `.so` | いいえ |

毎回送っているのは層 7 + 層 8 = **122.8MB**。vps2 のレジストリに実際に着地した
blob サイズ (96,532,227 + 26,240,612 = 122,772,839 バイト) と一致する。

問題はその中身。層 7 の tar を展開して数えた。

```text
178.9 MB  app/public        ← モデル群。中身は変わらない
 74.2 MB  app/node_modules  ← トレースされた依存。src だけ直した日は変わらない
 14.0 MB  app/.next         ← ここだけが本当に毎回変わる
  3.9 MB  app/src
  1.1 MB  app/docs
```

`public/` が standalone の中に入っている。Next の公式ドキュメント
(`node_modules/next/dist/docs/.../output.md`) は「standalone は `public` を
**コピーしない**」と書いているが、実際には file tracing が `public/` を辿って
**369 ファイル**を取り込んでいる。辿っている入口は埋め込み用の wasm で、
`.next/server/app/(search)/page.js.nft.json` などに

```text
../../../../public/embedding-onnx/ort-wasm-simd-threaded.asyncify.mjs
```

として入っている。

結果として **同じ 180MB が層 7 と層 9 に二重に入り**、しかも層 7 は毎ビルド
変わるので、**不変のモデル群を毎回 push している**。

層 8 も同じ構図。`.next/static/media` はフォント 60 個で 61MB (gzip 19.2MB)、
ファイル名は内容ハッシュなので**不変**なのに、毎回変わる `chunks` と同じ層にいる。

```text
61M  .next/static/media    ← woff2/woff/ttf 各 20。不変
30M  .next/static/chunks   ← 毎回変わる
```

### 2-3. lint → test → build が直列

3 つとも独立なのに順番に流している (合計 45 秒)。手元は 24 コア / 47GB で、
並列にする余力は十分ある。

### 2-4. その他

- buildx のキャッシュが **98GB** 溜まっている (`docker buildx du` の Reclaimable)。
- `tsconfig.tsbuildinfo` (560KB) が `.dockerignore` に無いため、手元で型検査を
  走らせるたびにビルドコンテキストが変わり、イメージにも入っている。
- 同様に `vitest.config.ts` / `eslint.config.mjs` / `do*.sh` / `src/` が
  本番イメージに入っている (実害は小さいが、standalone 層の贅肉)。

## 3. 施策

効果の大きい順。上 3 つで **約 60 秒**削れる。

### S1. `npm ci` をキャッシュに戻す (−20.7 秒)

依存レイヤーが版番号を見ないようにする。**推奨は (c)** — アプリのコードを
触らずに全額回収できる。

- (a) 版をビルド引数にする。`doVersion.sh` を「次の版を計算するだけ」と
  「成功後に commit + tag する」に割り、`--build-arg` で渡して
  `layout.tsx` は `process.env.NEXT_PUBLIC_APP_VERSION` を読む。
  一番きれいだが、フッター表示の経路を変えるので取り違えると版が嘘をつく。
- (c) **依存レイヤー専用の、版を潰した写しを配る。** `doDeploy.sh` が
  `.deps/package.json` と `.deps/package-lock.json` を `version: 0.0.0` で
  書き出し、Dockerfile はそちらで `npm ci` する。実体は続く `COPY . .` が
  上書きするのでイメージの中身は変わらない。`.deps/` は `.gitignore` に足す。

```dockerfile
# 依存レイヤーは版を見ない写しで固定する (版が上がっても npm ci を走らせない)
COPY .deps/package.json .deps/package-lock.json ./
COPY prisma.config.ts ./
COPY prisma ./prisma
RUN npm ci --ignore-scripts
COPY . .
```

補助として `RUN --mount=type=cache,target=/root/.npm npm ci --ignore-scripts` も
足しておくと、依存を実際に変えた日の再インストールも速くなる。

### S2. `public/` を standalone 層から外す (−59MB / 約 −5 秒)

builder の最後で消すだけでよい。`public/` は後段の
`COPY --from=builder /app/public ./public` が別層で入れているので、
**最終イメージの中身は 1 バイトも変わらない**。層の割り当てが変わるだけ。

```dockerfile
RUN npm run build \
 && rm -rf .next/standalone/public
```

効果は二重で、(1) 毎回の push が 59MB 減り、(2) イメージ自体も 59MB 縮む
(二重同梱の解消)。

### S3. `.next/static/media` を別層にする (−19MB / 約 −1.7 秒)

不変のフォントを、毎回変わる chunks から切り離す。

```dockerfile
COPY --from=builder /app/.next/static/media ./.next/static/media
COPY --from=builder /app/.next/static ./.next/static
```

内容ハッシュ名なので、フォントを足さない限り層 8 は「既に存在」で飛ぶ。

### S3b. `standalone/node_modules` も別層にする (−27MB)

実装中に判明した分。S2 で `public` を追い出した後の standalone 層はまだ 32.9MB
あり、その中身はトレースされた依存 (74MB / gzip 27.5MB) だった。**依存を変えない
限り不変**なのに、毎ビルド変わる `.next/server` と同居している。同じ手で分ける。

最終的な置き場は `/app/node_modules` のままなので `server.js` の解決は変わらない。

S2 + S3 + S3b の後、毎デプロイの転送は **122.8MB → 約 15MB** になる見込み
(残るのは `.next` の server 出力と chunks)。push は 10.7s → 約 1.5s。
vps2 側の pull と展開 (3 コア / RAM 2GB) も同じ比率で軽くなる。
レジストリの消費も 1 版あたり 123MB → 15MB になり、`registryGc.sh` の出番が減る。

### S4. lint / test / build を並列にする (−約 25 秒)

ビルドは lint / test の結果に依存しない。3 つを同時に走らせ、**全部通ってから**
push する。push 用の 2 回目の `buildx build` は全層キャッシュ済みなので
export + push だけで済む (約 5 秒の重複)。

```bash
# 1) ビルドは push せず走らせる (lint/test と並列)
docker buildx build --builder "$BUILDER" --output type=cacheonly . &
BUILD_PID=$!
npm run lint > "$LINT_LOG" 2>&1 & LINT_PID=$!
npm test    > "$TEST_LOG" 2>&1 & TEST_PID=$!

# 2) 1 つでも落ちたら中止する (ログを出してから die)
wait "$LINT_PID" || { cat "$LINT_LOG"; die "lint 失敗"; }
wait "$TEST_PID" || { cat "$TEST_LOG"; die "test 失敗"; }
wait "$BUILD_PID" || die "ビルド失敗"

# 3) ここで push (全層キャッシュ済み → export + push のみ)
docker buildx build --builder "$BUILDER" --output "type=image,...,push=true" .
```

注意点。

- `set -e` はバックグラウンドジョブの失敗を拾わない。**`wait` の戻り値を
  必ず見る**こと。
- 出力が混ざると読めないので、lint / test はログファイルに落として
  失敗時だけ吐く。
- **push を「全部通った後」に置くのが肝**。並列にしたまま push まで走らせると、
  テストが落ちた版のイメージがレジストリに残り、`--no-version-up` の再利用
  経路がそれを拾ってしまう。

### S5. マイグレーションをビルドと重ねる (−5 秒程度, 任意)

手順 6/8 の `prisma migrate deploy` と backfill ×2 はイメージに依存しない。
S4 の並列群に混ぜられる。ただし失敗時の後始末が絡む区間なので、**S1〜S4 が
落ち着いてから**にする。

### S6. 細かい掃除

- `.dockerignore` に `tsconfig.tsbuildinfo` / `.playwright-mcp` / `samples` /
  `_del` を足す。手元の型検査でコンテキストが変わるのを止める。
- `docker buildx du` の 98GB を `docker buildx prune --keep-storage 20GB` などで
  刈る。直後の 1 回だけビルドが遅くなる。

## 4. 実装順

1. **S2 + S3** (Dockerfile だけ。アプリの挙動に触れない。効果が大きい)
2. **S1(c)** (`doDeploy.sh` + Dockerfile + `.gitignore`)
3. **S4** (`doDeploy.sh` の 3/8・4/8 を組み替え)
4. S6 の掃除
5. 必要なら S5

各段で `./doDeploy.sh --demo` を先に通し、デモで健全性を見てから本番に配る。

## 6. 実装結果 (2026-08-13, 実測)

S1〜S4 + S6 を実装した。ローカルの `registry:2` へ 2 回 push し、
**ソースを 1 行変えたときに何バイト再送されるか**を manifest の層ダイジェスト
比較で実測した。

| 層 | サイズ | 2 回目 |
| ---- | ---- | ---- |
| ベース (`node:24-slim`) | 76.7MB | 再利用 |
| `apt-get install git` | 31.0MB | 再利用 |
| `standalone/node_modules` | 27.5MB | 再利用 |
| `.next/static/media` (フォント) | 15.9MB | 再利用 |
| `public` (モデル群) | 59.0MB | 再利用 |
| `.next/static` (chunks) | 9.1MB | **再送** |
| `standalone` (server 出力) | 5.4MB | **再送** |
| onnxruntime `.so` | 12.6MB | 再利用 |

- 毎デプロイの転送: **122.8MB → 14.5MB** (約 1/8)
- イメージ全体: **296.4MB → 237.2MB** (`public` の二重同梱を解消した分)
- `npm ci`: 版を上げても `CACHED` になることを確認 (`.deps/` が版に依らず
  バイト単位で同じことも検査済み)

動作確認として、組み上げたイメージを実際に起動して確かめた。

- コンテナが起動し `✓ Ready`、`/` が 307 (ログインへの誘導) を返す
- 層を移した `/_next/static/media/KaTeX_AMS-Regular.*.woff` が 200 で配れる
- `/_next/static/chunks/*.js` が 200 で配れる
- `public/` が二重になっていない (180MB のまま) / `libonnxruntime.so.1` が居る

## 7. 検証方法

推測でなく毎回の実測が残るように、`doDeploy.sh` に区間計時を入れる。

```bash
STEP_T0=$(date +%s)
step_done() {
  echo "    [${1}] $(( $(date +%s) - STEP_T0 ))s"
  STEP_T0=$(date +%s)
}
```

各手順の終わりで `step_done "4/8 build+push"` のように呼び、最後に合計を出す。
これがあれば、次に「遅い」と感じたときに**どこが遅いかを推測しないで済む**。

今回の再構成に使った痕跡は、計時を入れるまでの代用として覚えておくとよい。

- リリースコミットの時刻 = 手順 2/8 の終わり
- vps2 の `registry_registry-data` volume 内 blob の mtime = push の区間
- `docker inspect <app> --format '{{.State.StartedAt}}'` = 手順 7/8

## 8. 後から埋めた穴 (2026-08-14)

§3 を実装した後で読み直して、**取り切れていなかった無駄**と**黙って間違ったものが
出る経路**が 4 つ見つかった。速さの話は 8-1 だけで、残りは「速くした副作用で
おかしなイメージが警告なしに出来る」ほうの問題。

### 8-1. 依存レイヤーが prisma/ を読んでいた (§S1 の穴)

§S1 の例示どおり、依存レイヤーは長らくこうなっていた。

```dockerfile
COPY .deps/package.json .deps/package-lock.json ./
COPY prisma.config.ts ./
COPY prisma ./prisma
RUN npm ci --ignore-scripts
```

版番号は潰したのに **prisma/ を触れば npm ci は走り直す**。マイグレーションを
1 本足すデプロイや `schema.prisma` を直すデプロイでは、§S1 で削った 20.7 秒が
そのまま戻っていた。しかも `--ignore-scripts` で postinstall (prisma generate) を
止めている以上、**この層が prisma を読む場面は一度もない** — 初期実装
(`b4cbfc2`) からの居残りで、キャッシュを壊す以外の働きがなかった。
prisma generate は `npm run build` の中で走り、`prisma/` と `prisma.config.ts` は
続く `COPY . .` が運ぶ (どちらも `.dockerignore` に無い)。

2 行を削って実測した。作業ツリーを汚さないようビルドコンテキストを複製し、
`prisma/migrations/` に空のマイグレーションを 1 本足してから建て直した結果:

| Dockerfile | 追加後の `RUN npm ci --ignore-scripts` |
| ---- | ---- |
| 修正前 (2 行あり) | `DONE 18.6s` (走り直し) |
| 修正後 (2 行なし) | `CACHED` |

「この層に他のファイルを足さない」ことが §S1 の効果の前提なので、Dockerfile 側にも
理由を書き残した。

### 8-2. `.deps/` が古いままでも黙って通っていた

`.deps/` は git 管理外の生成物で、作り直すのは `doDeploy.sh` と `doStart.sh` だけ。
Dockerfile のコメントは「手で `docker compose build` するなら先に
`node scripts/writeDepsManifest.mjs`」と**書いてあるだけ**で、誰も検査していなかった。

忘れたときの筋書きが悪い。npm ci は古い写しで**古い依存**を入れ、続く `COPY . .` が
新しい `package.json` で上書きし、依存自体は解決できるので `next build` は通る。
つまり **古い依存を積んだイメージが、どこにも警告を出さずに出来上がる**。
「上げたのに直らない / 下げたのに再現しない」という形でしか表に出ない。

`COPY . .` の直後に照合を足した。生成器をもう一度走らせ、写しと 1 バイトでも
違えば落とす (正規化の規則を Dockerfile に書き写すと二重管理になり、片方だけ
直したときに嘘の合格を出すため、**規則は生成器 1 箇所に置いたまま**使う)。
揃っていれば書き出す内容は元と同一なので、イメージには何も足さない。実測 0.2 秒。

### 8-3. push が「検査していない木」から作り直されうる (§S4 の穴)

§S4 で lint / test / ビルドを並列にし、通ってから push するようにした。
ところが push は**別の `docker buildx build .`** で、これは
**作業ツリーをもう一度読む**。並列の約 30 秒のあいだにエディタが保存すれば、
push 用のビルドだけが新しい `COPY . .` を拾って作り直し、
**lint / test が一度も見ていない変更を焼いたイメージ**が本番に出る。
版もログも「全部通った」ように見えるので、後から気づく手掛かりが残らない。

手順 3/8 の入口と 4/8 の直前で作業ツリーの指紋を採り、ずれていたら
配らずに落とすようにした (`context_fingerprint`)。見るのは HEAD +
`git status --porcelain` + 変更・未追跡ファイルの中身のハッシュで、実測 11ms。
gitignore された生成物 (`.deps/` や `copy:assets` が作る `public/` の wasm・
モデル群) は見ていない — あれらはスクリプト自身が作るもので、デプロイ中に人が
書き換える類ではないし、そこまで見ると 188MB を毎回ハッシュする羽目になる。

「ビルドを 1 回にして結果を使い回す」ほうが筋は良いが、docker-container
ドライバのビルダーはイメージを後で push できる形で残さず、`docker save` →
`docker load` → `docker push` に回すと**デーモンが層を再圧縮してダイジェストが
変わる** = §S2/§S3 で稼いだ差分転送が丸ごと無効になる。指紋照合はその代わりに
「ずれたら配らない」だけを保証する。

### 8-4. `mv .next/static/media` が無条件だった (§S3 の穴)

§S3 でフォントを別層へ切り出すために `mv .next/static/media /static-media/media`
を `&&` 連鎖に入れたが、**Next が `media/` を出さなかった日にデプロイ全体が
止まる**。今そこに居るのは KaTeX の webfont・app icon (`src/app/icon.svg`,
`apple-icon.png`)・Worker のチャンクで、いずれも「CSS や import から辿られたから
たまたま media/ に出た」もの (`next/font` は 1 箇所も使っていない)。
再現も実測した。

```text
mv: cannot stat '.next/static/media': No such file or directory
```

層を分けるための都合で本筋と関係ないのに、原因の見当も付かない止まり方をする。
存在検査を挟み、無ければ空のまま進めるようにした (runner 側の
`COPY --from=builder /static-media/media` は空ディレクトリでも通ることを確認済み)。
`mv` そのものは残してあるので、**本当に失敗したときは今までどおり落ちる**。

### 9-1. push を並列の窓に畳む (−7 秒)

手順 4/8 の 7 秒は「検査が通った後に、もう一度ビルドして export + 転送する」ぶん
だった。ビルドを 1 回にして**その場で `staging` タグへ push**し、4 本とも通ったら
`staging` の manifest を `v$VERSION` にも張る (`promote_tag`)。

レジストリはタグを manifest への別名として持つだけなので、昇格は manifest 1 枚の
PUT で済む。**層は 1 バイトも動かない** (実測 0.03 秒)。

- GET した本文を**そのまま** PUT する。整形し直すとダイジェストが変わり、同じ
  イメージなのに層が再アップロードになる。
- `Content-Type` は GET の応答ヘッダのものをそのまま使う (registry は manifest の
  `mediaType` と突き合わせる)。
- 昇格後に両タグの `Docker-Content-Digest` を比べる。ここが食い違うと**配るものが
  変わる**のに、後段の pull は成功してしまう (別のイメージが取れるだけなので)。
- staging タグを版形式 (`v0.0.0`) にしないこと。`--no-version-up` の再利用経路も
  `registryGc.sh` も `^v[0-9]` で版を拾うため、検査に落ちたイメージが「配れる版」に
  見えてしまう。

代償が 1 つある。**検査に落ちた回のイメージも層はレジストリに着地する**
(約 14.5MB)。次のデプロイで `staging` を上書きすると、その manifest は
タグから外れるが、`registryGc.sh` が消すのは `^v[0-9]` のタグだけで、
末尾の `registry garbage-collect` も `--delete-untagged` を渡していないため
回収されない。溜まるのが気になったらそのフラグを足す。

副産物として **§8-3 の穴が構造的に消えた**。push 用の 2 回目のビルドが無くなり、
公開されるのは検査と同じ 1 回のビルドの成果物になる。`context_fingerprint` の照合は
残す — lint と test は 10 秒かけて木を読み続けるので、「イメージに焼かれた内容」と
「検査が見た内容」が食い違う筋自体はまだあるため。

### 9-2. 型検査を `next build` から出す (ビルドレーン −4.7 秒)

`next build` の中の型検査は単スレッドで 4.7 秒、Turbopack のコンパイル (多コアで
4.9 秒) の後に直列で積まれていた。`next.config.ts` の
`typescript.ignoreBuildErrors` で外し、4 本目のレーンに移した。

```json
"typecheck": "next typegen && tsc --noEmit"
```

**`next typegen` を省かないこと。** `.next/types/validator.ts` は
「ページ・レイアウト・route handler の署名が経路と合っているか」を検査する生成物で、
これが古いと**経路を足した日に古い一覧のまま検査が通る**。typegen は 0.35 秒、
`tsc --noEmit` は 1.8 秒。

代償: `npm run build` 単体 (`./doStart.sh` 経由を含む) は型エラーで落ちなくなる。

### 9-3. 10 秒級のテストを別ファイルへ (test レーン 24.3s → 10.5s)

vitest は forks プールで**ファイル単位に**並列化する。1 ファイルの中は直列なので、
重いテストが同居しているとそこがテスト全体の所要になる。

- `circuitikz.test.ts` → 純粋関数 / `render` / `timeout` / `injection` の 4 つに分割。
  `renderCircuit` は node-tikzjax のモジュール状態のせいで**同一プロセス内では
  必ず直列化される** (`enqueue`) が、ファイルを分ければプロセスが分かれて同時に走る。
- `readZip.test.ts` → 1GB を deflate する 2 本 (`totalLimit` と
  `totalLimit.skipped`) を別ファイルへ。ゼロ埋めを圧縮率で誤魔化すことはできない
  — 実測では level 1 でも 6 と変わらず、level 0 は 1GB の ZIP がメモリに載る。

残る floor は暴走 TeX の 10 秒 (`CIRCUIT_TIMEOUT_MS` を待つのが検査したい性質
そのもの)。テストは全 3128 本が通ったまま、24.3 秒 → 10.5 秒になった。
