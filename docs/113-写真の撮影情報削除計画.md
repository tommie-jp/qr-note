# 写真の撮影情報 (EXIF) 削除計画

状態: **写真・動画とも実装済み (2026-09-19)・v0.23.47 で本番配布済み・本番のバックフィル済み
(2026-10-18、§8-4)・端末の写しの掃除は v0.23.48 (§8-5)。** 本番で GPS 入り写真を保存し、
ブラウザで落として GPS が無いことを確認済み (§8-6)。iPhone 実機も確認済み (2026-10-18)。動画は §10

添付した写真に残る撮影情報 (位置・日時・機種など) を、保存するときに
**既定で削除する**。残したい人はハンバーガーメニューの
「写真の撮影情報 (EXIF)」で「残す」を選べる。

きっかけと方針決定の経緯は 41-QR-search/docs/22-先行事例qrnote調査メモ.md §8-1。

## 1. 何が問題か

### 1-1. 写真は受け取ったまま保存し、そのまま配る

JPEG・PNG・GIF・WebP・AVIF は `images/normalizeImage.ts` の passthrough で
受け取ったバイト列のまま保存され、`/api/images/[name]` は原寸をそのまま返す。
公開ノート (docs/22) の画像は未ログインでも取れるので、写真に入っている
撮影情報は誰でも読める。

撮影情報が落ちる経路は今のところ 3 つしかない。

| 経路 | 落ちる理由 |
| --- | --- |
| HEIC / TIFF | sharp で WebP へ変換する。sharp は既定でメタデータを書かない |
| シークレットの画像・上限超えのクリップボード画像 | クライアントの canvas で描き直す (`images/imageCanvas.ts`) |
| 回転 (docs/49) | sharp で符号化し直す (`images/rotateImage.ts`) |

つまり**ファイル選択・ドラッグ&ドロップ・ZIP 取り込み・ENEX 取り込み**で
入った JPEG / PNG はすべて撮影情報を持ったまま残る。

### 1-2. 漏れるのは位置だけではない

| 情報 | 入っている場所 | 何が分かるか |
| --- | --- | --- |
| GPS | EXIF の GPS IFD | 撮影した場所 (自宅・職場) |
| 撮影日時 | EXIF DateTimeOriginal | いつ居たか |
| 機種・レンズ・シリアル | EXIF Make / Model / BodySerialNumber | 同じ人の写真を突き合わせる鍵 |
| 所有者名・著作権 | EXIF Artist / Copyright、IPTC、XMP | 実名 |
| 縮小版 | EXIF IFD1 のサムネ | 編集前の写り (トリミングで消したはずの物) |
| 埋め込み動画 | JPEG の EOI 以降 (Samsung の Motion Photo) | 撮影前後 3 秒の映像と音声 |

ローカル DB (2026-08-10 までの写し) では JPEG 123 件のうち撮影日時 111・
機種名 40・GPS 0 だった。GPS は無かったが、日時と機種は大半に残っている。
本番と、iPhone から今上げた写真に GPS が届くかは未確認 (§7 Phase 0 で数える)。

## 2. 決めたこと

### 2-1. 既定は削除。メニューで「残す」を選べる

- 保存時に落とす。配信時に落とす案は、配信の口 (原寸・エクスポート ZIP・
  将来の口) が増えるたびに漏れが出るので採らない
- 「残す」は利用者ごとの設定 (user_settings)。端末ごとではない —
  落とすかどうかを決めるのはアップロードを受けたサーバなので、
  PC と iPhone で食い違う余地を作らない
- アップロードのたびに選ばせない。写真を貼るたびに 1 手増える
- 切り替えが効くのは**これから上げる写真だけ**。消した情報は戻らない

### 2-2. 残すのは「向き」と「色」だけ

残すもの:

- **EXIF Orientation**: 本文の原寸表示はブラウザが EXIF の向きで起こしている。
  消すと縦の写真が横倒しになる (`images/rotateImage.ts` の注意書きと同じ罠)
- **ICC プロファイル** (JPEG APP2 `ICC_PROFILE`、PNG `iCCP`、WebP `ICCP`):
  消すと Display P3 の写真の色が変わる
- **JPEG の APP0 JFIF・APP14 Adobe**: 復号に要る。個人情報を含まない
- **PNG の `sRGB` `gAMA` `cHRM` `pHYs`、APNG の `acTL` `fcTL` `fdAT`**:
  表示に要る。個人情報を含まない

アプリは EXIF を向き以外に使っていない (サムネの `.rotate()` も向きだけ)。
機能は何も失わない。

### 2-3. 再エンコードしない。区画だけ抜く

passthrough は画質を保つための選択で、sharp で符号化し直すと画質と
サイズが変わり、12MP の写真では vps2 のメモリも食う。
JPEG・PNG・WebP はいずれも「区画 (セグメント / チャンク) の並び」なので、
該当する区画を落として繋ぎ直すだけで済む。画素のバイト列には触らない。

Orientation は、元の EXIF から値だけ読み取り、**それ 1 つだけを持つ最小の
EXIF** を書き戻す。値が 1 (正位置) か無ければ EXIF そのものを書かない。

**抜けないときは sharp で作り直す (fail-closed)。** 形式判定は通ったが
区画の並びが壊れている入力は、パースを諦めて `sharp(bytes).rotate()` で
符号化し直す。画質は落ちるが撮影情報は確実に落ちる。黙って素通しはしない。

### 2-4. 呼ぶ側が必ず決める

`storeAttachment()` / `restoreAttachment()` のオプションに
`photoMeta: 'strip' | 'keep'` を**必須**で足す。省略できる形にすると、
新しい取り込み口を足した人が忘れて素通しになる。型で止める。

`storeAttachment()` には値の代わりに**値を引く関数**も渡せる
(`attachments/photoMeta.ts` の `PhotoMetaSource`)。`api/images` は関数で渡し、
画像を保存すると決まってから設定を引く。中身を見て断る経路 (画像でない・偽装) で
DB を引かないためで、このルートのテストは「DB に触れる前に弾く」を契約にしている。

| 呼ぶ側 | 渡す値 |
| --- | --- |
| `api/images/route.ts` (通常のアップロード) | セッションの利用者の設定 |
| `zip/importZip.ts` (ZIP 取り込み) | 同上 |
| `enex/importEnex.ts` (Web からの取り込み) | 同上 |
| `enex/importEnex.ts` (CLI の一括取り込み) | 既定 `strip`。`--keep-photo-meta` で `keep` |
| デモ | 常に `strip` (§2-5) |

### 2-5. デモは常に削除

デモは共有アカウントなので設定を持たせない。メニューにも項目を出さない
(選択色と同じ。`AppHeaderMenu` の `!isDemo` の内側)。設定を読む関数が
`isDemoMode()` のとき常に `strip` を返す形にし、呼ぶ側に分岐を持たせない。

### 2-6. 既存の画像はバックフィルで落とす

画像名はランダムな UUID で中身に依存しないので、名前を変えずに `data` だけ
差し替えられる。`scripts/backfillPhotoMeta.ts` を書き、`doBackfill.sh` に
`photometa` タスクを足す。サムネ・埋め込みは画素から作る派生物なので
作り直さなくてよい。

バックフィルは持ち主が明示的に流す操作なので、「残す」設定とは独立に動く。
残したい人は流さなければよい。

## 3. 形式ごとの抜き方

### 3-1. JPEG (Phase 1)

- 抜く: APP1 (Exif・XMP・Extended XMP)、APP13 (IPTC / Photoshop)、
  APP2 `MPF`、COM、**EOI 以降の全部**
- 残す: APP0、APP2 `ICC_PROFILE`、APP14、DQT / SOF / DHT / SOS など

### 3-2. PNG (Phase 1)

- 抜く: `eXIf` `tEXt` `zTXt` `iTXt` `tIME`
- 残す: それ以外すべて

### 3-3. WebP (Phase 1)

- 抜く: `EXIF` と XMP のチャンク (XMP の FourCC は末尾が空白)。
  `VP8X` のフラグ (bit 3 EXIF / bit 2 XMP) を落とし、RIFF サイズを更新する
- 残す: `ICCP` `ANIM` `ANMF` `VP8` `VP8L` `ALPH`

### 3-4. GIF (Phase 3)

- 抜く: Comment Extension (`21 FE`)、`XMP DataXMP` の Application Extension
- 残す: `NETSCAPE2.0` (ループ回数)

### 3-5. AVIF (Phase 3)

- `Exif` / `mime` (XMP) アイテムの中身をゼロで埋める。箱の構造は変えない
- 向きは `irot` / `imir` で持つので EXIF に依らない

### 3-6. HEIC / TIFF

- 不要。WebP へ変換済みで sharp が落とす。テストで確かめるだけ

### 3-7. JPEG の補足

- JPEG の EOI (`FF D9`) 以降を切るのは Samsung Motion Photo の動画と Apple の
  MPF 副画像 (HDR ゲインマップ) を落とすため。ゲインマップが消えると HDR
  表示が SDR になるが、ノートの用途では困らない。エントロピー符号化データの
  中では `FF` の後に必ず `00` か `D0`〜`D7` が来るので、SOS 以降を素直に
  走査して最初の `FF D9` を探せばよい
- 最小 EXIF は 34 バイト固定。並びは `FF E1`、長さ、`Exif\0\0`、TIFF ヘッダ
  (`II*\0` と IFD0 オフセット 8)、エントリ数 1、Orientation のエントリ
  (0x0112, SHORT, 1, 値)、次 IFD 0。APP0 の直後に置く
- Orientation の読み取りは TIFF の IFD0 を歩くだけ (両エンディアン対応)。
  読めなければ「無し」扱いで EXIF を書かない。**ブラウザが最小 EXIF の
  向きを起こすこと**は Phase 1 のテストで sharp の `metadata().orientation`、
  Phase 4 で実機の表示で確かめる

PNG / WebP の Orientation ≠ 1 は稀 (スマホの写真は JPEG / HEIC)。
同じ最小 EXIF を `eXIf` / `EXIF` チャンクとして書き戻す。ブラウザが PNG の
`eXIf` で向きを起こすかは Phase 4 の確認項目に入れる。

## 7. 進め方

### Phase 0. 実態を数える

`scripts/backfillPhotoMeta.ts --dry-run` を先に書き、ローカルと本番で
「GPS あり / 日時あり / 機種あり / EOI 以降にデータあり」の件数を出す。
座標の値は出さない。本番に GPS があれば、デプロイ直後にバックフィルを流す
理由になる。

### Phase 1. 抜く関数 (TDD)

テストの素材は sharp で作る (`normalizeImage.test.ts` と同じ流儀)。
`sharp(...).withExif({ IFD0: { Make, DateTime }, IFD3: { GPSLatitude, ... } })`
と `.withMetadata({ orientation: 6 })` で GPS と向き付きの JPEG / PNG / WebP を
用意し、ICC 付きは `.withIccProfile('p3')`。sharp が書けない区画 (JPEG の
APP13・COM・EOI 以降の付け足し、PNG の `tEXt`) はテスト内でバイト列を
手で足す。

確かめること (各形式):

- GPS・DateTime・Make が無い (出力の EXIF を `orientation.ts` の
  IFD 歩きで読み、GPS IFD ポインタ (0x8825) が無いこと)
- Orientation 6 が残り、`sharp(out).metadata().orientation === 6`
- ICC が残る (`metadata().icc` が入力と同じ長さ)
- 画素が同じ (`sharp(x).raw().toBuffer()` を入出力で比較)
- 2 回掛けても同じ (冪等)
- Orientation が 1 か無い入力は EXIF 区画そのものが無い
- EOI 以降に足したバイト列が消える (JPEG)
- `VP8X` のフラグが落ち、RIFF サイズが合う (WebP)。アニメ WebP のコマ数が変わらない
- 区画が壊れた入力は sharp の作り直しに落ち、EXIF が無い

### Phase 2. 経路と設定に組み込む

- `storeImage` / `restore` に差し込み、`photoMeta: 'keep'` では素通しすることを
  テスト。HEIC → WebP の出力に EXIF が無いことも既存テストに 1 本足す
- `api/settings/photo-meta` の route test (row-tint の写し)
- `api/images` の route test に「設定が strip の利用者が上げた JPEG に GPS が無い」を 1 本
- メニュー項目・layout の配線。`AppHeaderMenu` の並びは §4

### Phase 3. 残りの形式とバックフィル

- GIF / AVIF (§3)。どちらも稀なので、Phase 2 まで先に出してよい
- `scripts/backfillPhotoMeta.ts` 本体: `image` を名前だけ引いて 1 枚ずつ読み
  (`backfillThumbs.ts` と同じ)、変わったときだけ `data` を更新。件数を出す
- `doBackfill.sh` に `photometa` を足す

### Phase 4. 確認と配布

1. ローカルの実アプリで、GPS 付き JPEG をファイル選択で上げ、`/api/images/<名前>`
   を取って GPS が無く向きが正しいことを見る。「残す」に切り替えて同じ写真を上げ、
   GPS が残ることも見る
2. iPhone 実機: 位置情報オンで撮った写真をフォトライブラリから貼り、
   同じ確認。縦写真の向きが崩れないこと
3. ZIP エクスポート → 中の画像に GPS が無いこと。ZIP 取り込み → 同じ
4. 配布は頼まれたときに。配布後に `./doBackfill.sh photometa` を流し、
   件数を 41-QR-search/docs/22 §8-1 に追記する

## 8. 実装の記録 (2026-09-19)

### 8-1. 計画から変えたこと

- **設定を関数でも渡せるようにした** (§2-4 に追記)
- **保存の失敗時にメニューの選択を戻す。** 選択色は押した色を当てたまま文言で
  知らせるが、こちらはサーバが古い値のまま写真を扱うので、画面だけ「残す」を
  指していると次の写真で裏切られる
- **PNG の向きは IHDR の直後に書き戻す** (実装の初版は最初の IDAT の直前だった。
  下のレビューの項)
- **JPEG の APP0 は JFIF だけ残す。** JFXX (サムネ専用の拡張) や知らない APP0 は
  落とす。APP11 (JPEG XT / C2PA) なども「その他」として落とす
- **PNG は `dSIG` と `caBX` (C2PA) も落とす。** ImageMagick が EXIF や IPTC を
  「Raw profile type …」の文字の区画で持つ形も拾う
- **GIF は残すアプリ拡張を白名簿にした。** ループ指定 (NETSCAPE2.0 / ANIMEXTS1.0) と
  色 (ICCRGBG1012) 以外は落とす
- **読めない区画は例外の種類に関わらず作り直す。** 読み取りの穴で RangeError が
  出ても素通しにしない
- バックフィルの下見を `./doBackfill.sh photometa-check` として足した
- **細工ファイルへの上限を 2 つ入れた** (セキュリティレビューの指摘)
  - AVIF の位置表 (iloc) は値の長さを 0 バイトにでき、1 区間あたり何も読まずに
    回る。数 KB で件数 × 区間数 (最大 65535) の周回を強いられ、6KB で 1.3 秒・
    92MB を確認した。区間の総数を 65536 までにし、消す対象の位置だけを控える
  - 動画の箱の入れ子を数千段重ねるとスタックが溢れる。深さを 16 段までにした。
    実物は moov > trak > mdia > minf の 4 段
- **正しさのレビューで直したこと**
  - メニューは閉じると行ごと捨てられ、開き直すと layout がページ読み込み時に
    読んだ値から描き直す。「残す」を保存して開き直すと「消す」と出ていたので、
    保存できた値をタブの中で控えて優先する
  - PNG の向きの `eXIf` を IDAT の直前に書き戻すと、Apple の `iDOT` (IDAT の位置を
    自分からの距離で持つ) との間に挟まって距離がずれる。書き戻しは IHDR の直後に
    し、`iDOT` と IDAT の間の区画を落としたときは `iDOT` も落とす。手元の DB の
    PNG のうち 7 枚が `iDOT` を持ち、7 枚とも残った
  - バックフィルは「抜いた 0 件」でも失敗扱いにしていた。2 回目以降は 0 件が
    正常なので、全件失敗のときだけ exit 1 にした。作り直しの数え方も下見と
    本番でそろえた
  - 動画を断るときの「残す」への案内は、画面から上げたとき (非デモ) だけ
    `api/images` が添える。CLI とデモでは選べないため

### 8-2. 確かめたこと

- 単体テスト: 抜き方 5 形式・振り分け・設定・API・保存と復元・取り込み・メニュー
- 結合テスト (`RUN_DB_TESTS=1`): 設定が「消す」なら `/api/images` で上げた写真から
  撮影情報が消え、向きは残る。「残す」なら残る
- 手元の DB の写真 164 枚で下見。135 枚に撮影情報があった

| 残っていた情報 | 枚数 |
| --- | --- |

### 8-5. 端末に残る写しの掃除 (2026-10-18)

§8-3 の 3 (原寸は 1 年 immutable なので、バックフィル前の写しが端末に残る) への対処。
Clear-Site-Data は Chrome が部分実装で固まる既知の不具合があり (Firefox も一時期未対応)、
URL の版上げは URL を組む場所が 20 か所を超えるので、どちらも採らなかった。
Service Worker の範囲で直す:

- 棚を `qr-media-v1` / `qr-pin-v1` から `v2` に改名。activate で現行以外の `qr-*` を捨てる
  ことで、撮影情報の残る旧い写しが消える
- **旧い持ち出しの棚 (v1) だけは activate で捨てない。** 上限も期限も無い棚で、v2 が揃う前に
  消すと更新直後に圏外へ出た人の添付が消える。圏外で v2 に無いときだけ読み
  (`pinnedFirst`)、持ち出しの同期が取りこぼし 0 で終わったら `pinCache.ts` が捨てる
- 棚に無いときの原寸の取り直しは `cache: 'reload'` で HTTP キャッシュを飛ばす
  (sw.js の添付の分岐と `pinCache.ts`)。棚だけ空にしても、HTTP キャッシュの古い写しが
  棚に戻ってくるため。サムネ (`?thumb=`) は撮影情報が無いので従来どおり
- 上限 600 件で押し出された原寸の再表示も毎回ネットから取る。頻度が低いので許容

届かないもの: Service Worker の無い環境 (Firefox のプライベートウィンドウなど)、
アプリの外に出た写し (保存・スクリーンショット・転送・バックアップ)。
テスト: `src/lib/offline/sw.test.ts` (sw.js を偽の self / caches で読み込んで確かめる)。

### 8-6. 本番での確認 (2026-10-18, v0.23.48)

公開サンプル (ianare/exif-samples の DSCN0010.jpg) の GPS・機種 (NIKON COOLPIX P6000)・撮影日時を、
向き 6 (縦写真) の portrait_6.jpg に exiftool で書き込んだ画像を作り、QR-Note に保存した。
ブラウザでダウンロードして見たところ、**GPS 情報は消えていた** (ユーザー確認)。
配信された画像 (`/api/images/bc65790d-….jpg`) に次を掛けた。

```bash
exiftool -a -G1 -s -GPSLatitude -GPSLongitude -Make -Model \
  -DateTimeOriginal -Orientation <ファイル>
```

出たのは `Orientation : Rotate 90 CW` の 1 行だけ。GPS・機種・日時は無く、
縦向きは保たれている。
メニューの「写真の撮影情報 (EXIF)」を **「残す」** にして保存した場合は、ダウンロードした画像に
GPS (北緯 43°28′・東経 11°53′)・NIKON COOLPIX P6000・撮影日時 2008-10-22 がそのまま残った
(DSCN0010.jpg を保存。向きは Horizontal)。既定「消す」と「残す」の両方が本番で意図どおり動く。
同じ日に Chrome の Cache Storage で `qr-media-v2` / `qr-pin-v2` / `qr-secret-v1` /
`qr-shell-0.23.48` だけが残り、旧 v1 が消えていることも確認した。

iPhone 実機でも確認済み (2026-10-18、ユーザー確認)。この計画の確認事項はすべて済み。

## 9. やらないこと

- 公開トグルを押したときだけ消す (§2-1)
- アップロードごとの選択 (§2-1)
- クライアント側で消す。サーバの 1 か所で済ませる (取り込みも同じ口を通る)
- 消した撮影日時をノートに転記する。需要が出たら、消す前に読んで本文へ
  入れる形で足せる
- 既存画像の自動バックフィル。持ち主が流す (§2-6)
- 動画の時刻付きメタデータのトラック (ドローンの飛行記録など)。値が mdat の
  標本に入っていて、消すにはトラックごと落とすことになる (§10)
- WebM の撮影情報。ブラウザの録画が出す形で、カメラは書かない (§10)

## 10. 動画 (2026-09-19 追加)

写真を仕上げた後、同じ設定で動画 (MP4 / MOV) の撮影情報も消すことにした。
メニューの項目名は利用者が決めた「写真の撮影情報 (EXIF)」のまま、説明の行を
「写真と動画の位置・日時・機種など」に広げた。

### 10-1. どこに入っているか

| 場所 | 中身 | 主な書き手 |
| --- | --- | --- |
| `moov/udta` | `©xyz` (位置)・`©mak` / `©mod` (機種)・`©day` (日時) | Android・ffmpeg |
| `moov/meta` | `keys` + `ilst`。位置 (location.ISO6709)・機種・日時 | iPhone |
| `trak/udta`・`trak/meta` | トラック単位の同じもの | さまざま |
| `uuid` (XMP) | XMP の文書 | Adobe 系 |
| `mvhd`・`tkhd`・`mdhd` | 作成・更新の日時 (1904 年起点の秒) | すべて |

### 10-2. 消し方

**箱の長さを変えず、型を `free` に替えて中身を 0 で埋める。** 日時の欄は 0 を
書く。画素と音 (mdat) の位置は `stco` / `co64` にファイル先頭からの絶対位置で
書かれているので、箱を抜いて詰めると位置表を全部直すことになる。`free` なら
再生側が読み飛ばし、位置表は 1 つもずれない。moov の詰め替え
(`video/mp4Faststart.ts`) の後に掛ける。

- 実装: `src/lib/video/videoMeta.ts` (`stripVideoMeta`)
- 保存: `attachments/storeVideo.ts`。WebM は触らず、設定も引かない
- 復元: `attachments/restore.ts` の動画分岐
- バックフィル: `scripts/backfillPhotoMeta.ts` が MP4 / MOV も扱う

**箱の並びが読めない動画は断る。** 写真と違い、本番には作り直す手段 (ffmpeg) が
無い。撮影情報を残したまま保存するくらいなら断り、「残す」にすれば保存できると
理由の文言で伝える。バックフィルでは手を付けずに失敗として数える。

### 10-3. 確かめたこと

ffmpeg で位置・機種・日時を入れた MP4 (Android 形) と MOV (iPhone 形の鍵と値) を
作り、手元の DB の実物の MP4 1 本と合わせて 3 本で確かめた。

- ffprobe で見て、位置・機種・日時のタグがすべて消えた
- `ffmpeg -f null` で最後まで復号でき、映像と音の `framemd5` が抜く前と一致した
- ファイルの長さは 3 本とも変わらない
