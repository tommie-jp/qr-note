# 回路解析の派生列化と同期圧縮の計画

QR-Note ベンチマーク (docs/121) の本番初回で、回路フェンスの解析 (remark) が
手元の 5 倍遅く (見本 79ms)、同期の gzip が 292ms サーバを塞いでいることが
分かった。本番の cpuprofile を手元のビルドと突き合わせると、解析の内訳は表の
拡張 16%・字句解析の本体 約 50%・木の組み立て 10% だった (docs/121 §11)。

ここでは次の 5 つをまとめて進める。

| # | 手 | 効き目 | 大きさ |
| --- | --- | --- | --- |
| 1 | 回路フェンスを**書き込み時に派生列へ**保存し、一覧・同期は列を読む | 一覧・同期・配布直後から解析が消える | 中 (列・移行・バックフィル) |
| 2 | 抽出だけは **remark-gfm を外した parser** で読む | 書き込み時・描画時・バックフィルの解析が表の多いノートで約 16% 縮む | 小 |
| 3 | 同期の gzip を**非同期・弱め**にする | 同期中にほかの要求が待たなくなる。CPU も半分以下 | 小 |
| 4 | cpuprofile に**モジュール名を残す** (source map で引き直す) | 次の調査で手作業の突き合わせが要らない | 小〜中 (イメージの大きさ次第) |
| 5 | サーバ側ベンチに**検索ページ全体の組み立て**を足す | 応答開始 300〜500ms の内訳が本番で見える | 小 |

決めたこと (2026-10-29):

- 1 が本命。2 は 1 の後では書き込み時にしか効かないが、描画 (planCircuits)
  とバックフィルには効くので入れる。ただし**抽出の結果が描画の parser と全ノート
  で一致する**ことを確かめてから
- 4 は、source map をイメージに同梱すると転送量が増える。先に大きさを測り、
  数 MB 以内なら同梱して保存時に引き直す。大きければ手元で引き直す形にする
- どれも docs/121 のベンチで前後を測る (本番の「サーバを計測」+ iPhone の
  「この端末を計測」)

## 1. 回路フェンスの派生列

### 1-1. 列

`items.circuit_fences JSONB NOT NULL DEFAULT '[]'`。中身は
`CircuitFence[]` (`[{ lang, source }]`、本文に出てくる順・重複なし =
`extractCircuitFences` の戻り値そのまま)。索引は張らない。

- 正本は memo。`derivedFromMemo` (`items/write.ts`) に `circuitFences` を
  足し、保存のたびに作り直す。本文を書く経路はすべて `upsertMemo` /
  `derivedFromMemo` を通っている (取り込み ZIP・ENEX・履歴の復元・
  `backfillCircuitAddresses.ts`) ので、足すのは 1 か所
- 移行 `prisma/migrations/<日時>_add_item_circuit_fences`。既存行は `'[]'`
  のまま置き、バックフィル (§1-3) で埋める。**適用後に `\di` で PGroonga の
  索引が残っているか見る** (prisma migrate が落とすことがある)
- `hasNoCircuitFence(memo)` の足切りは残す。列が `[]` のとき、本文に
  `circuit` の文字が無ければバックフィル前でも「無い」と言い切れる。
  文字があって列が `[]` なら**バックフィル前**なので解析に落ちる (§1-2)

### 1-2. 読む側

| 場所 | 今 | 後 |
| --- | --- | --- |
| 一覧の回路サムネ (`circuit/thumbs.ts`) | `circuitFencesOf(item.memo)` | `item.circuitFences`。`ThumbSource` に列を足し、`ITEM_COLUMNS` (`items/where.ts`) と `trash/page.tsx` の select に `circuit_fences AS "circuitFences"` を足す |
| 同期 (`offline/syncItems.ts`) | 同上 + 50 件ごとに譲る | `select` に `circuitFences` を足して列を読む。譲りは要らなくなる (JSON の読みだけ) |
| 描画 (`circuit/cache.ts` の `planCircuits`) | `extractCircuitFences(markdown)` | 変えない (1 件・本文を持っている・編集中の未保存本文も通る) |

- 列が `[]` で `hasNoCircuitFence` が偽 (= バックフィル前) のときだけ、
  今までどおり `circuitFencesOf(memo)` に落ちる。`circuit/fenceSource.ts`
  (新規) の `fencesOfItem({ memo, circuitFences })` に集め、2 か所から呼ぶ
- `fenceMemo.ts` (記憶) はこの落ち道のためだけに残す。バックフィル後は
  使われないので、次の整理で消す候補 (docs/118 §1-2 の記憶の共有も不要になる)
- 一覧の RSC に列が乗るか: `ITEM_COLUMNS` はサーバで読むだけで、行の
  コンポーネントには渡さない (サムネの hash を作ったら捨てる)。転送量は変わらない

### 1-3. バックフィル

`scripts/backfillCircuitFences.ts` + `doBackfill.sh circuit-fences`。
`backfillTaskCounts.ts` と同じ形: 全件 (ゴミ箱も) を読み、`extractCircuitFences`
の結果が列と違う行だけ生 SQL で `UPDATE items SET circuit_fences = $1::jsonb`
(`@updatedAt` を動かさない)。冪等。50 件ごとに進みを出す。

配布の順: 配布 (移行で列が足される。読む側はバックフィル前の落ち道で動く) →
`./doBackfill.sh circuit-fences` → 「サーバを計測」で `parse:cold` が消え、
同期の `db=` が縮むことを見る。デモは `--demo`。

### 1-4. ベンチへの影響

`parse:cold` (実ノート 20 件の冷え解析) は、本番の経路からは消える。ベンチの
項目としては残す — 移行先の CPU を測る物差しとして要る (見本と並べて)。
ラベルを「回路の解析 (実ノート 20 件・記憶なし)」から「(実ノート 20 件・
書き込み時の処理)」に改める。`sync:payload` の `db=` が縮む。

## 2. 抽出だけ remark-gfm を外す

`markdown/parser.ts` に `createFenceParser()` を足す。`NOTE_REMARK_PLUGINS`
から `remarkGfm` だけを除いた列 (`remarkDetailsSyntax`・`remarkDetails`・
`remarkBreaks`・`remarkMath`・`remarkAlerts` は残す)。`markdown/extractFences.ts`
の `NOTE_PARSER` をこれに替える (回路・matrix・health の抽出が全部この道)。

フェンスの見つけ方が変わらない理由:

- GFM の拡張は、表以外はインライン (autolink・打ち消し・脚注の参照) か
  リストの子 (タスク) で、フェンスは行頭のブロック構文なので影響しない
- 表は「空行か、別のブロック構文の始まりで終わる」ので、表の直後の ``` は
  表を閉じてフェンスになる。表のセルの中の ``` はインラインのコード
- 脚注の定義 (`[^1]:` の続き) の中のフェンスは、拡張があれば定義の中の
  フェンス、無ければ段落を割り込むフェンスで、どちらもフェンスとして出る
- **math (`$$`) と details (`:::`) は外さない**。`$$` の中の ``` は数式の中身
  で、外すとフェンスに化ける。`:::` の中身は flow として解析されるので同じ

確かめ方 (入れる前に):

1. 単体テスト: 表のセルの中のフェンス記号・表の直後のフェンス記号 (空行なし)・脚注の中・
   `:::details` の中・`$$` の中・リストの中、の 6 つで新旧の parser の抽出が
   一致する
2. `scripts/checkFenceParsers.ts` (新規・読むだけ) で、手元の全ノート (1148 件)
   と本番のダンプを戻した DB で、新旧の抽出が全件一致することを見る。1 件でも
   違えば入れない

効き目は見本で測る (`parse:fixture` に表が 1 つ入っている)。

## 3. 同期の gzip

`route/compress.ts` の `apiOkGzip` を**非同期** (`node:zlib` の `gzip` を
promisify) にし、**level を下げる**。

- 非同期にする意味: zlib は libuv のスレッドプールで走るので、圧縮の間
  Node のイベントループが空く。3 コアの本番で「同期と重なった検索が待つ」
  が消える。CPU の総量は変わらない
- level: 既定 6 → **4 を第一候補**。手元で 11MB の JSON を 1・3・4・6 で測り、
  大きさ (gzip 後 MB) と時間を並べて決める (ベンチの `sync:payload` の
  `gzip=` と `規模` にそのまま出る)。キャリア (下り 51Mbps) で 0.5MB 増は
  約 80ms。gzip の 200ms 減と釣り合う所を取る
- 呼ぶ側 (`api/sync/items/route.ts`) は `await` に替え、計測の段階は
  `timeSync('json')` → `time('json')`。ベンチの `sync:payload` も同じ level
  で測るよう、level は `compress.ts` の定数 `SYNC_GZIP_LEVEL` にして
  `serverBench.ts` から import する

## 4. cpuprofile にモジュール名を残す

束ねたファイルにはモジュール名が残らない (Turbopack は数字の id)。
`experimental.serverSourceMaps: true` で `.next/server/chunks/**/*.js.map` が
出るので、**保存するときに source map で引き直す**。

- Node 標準の `node:module` の `SourceMap` (`new SourceMap(payload)`、
  `findEntry(line, column)`) を使う。依存は増やさない
- `lib/diag/benchProfile.ts` に `remapProfile(profile)` を足す。各 `callFrame`
  の `url` が `.next/server/chunks/` 配下なら、隣の `.map` を読み (chunk ごとに
  1 度だけ・Map に控える)、`originalSource`・`originalLine`・`name` で
  `url`・`lineNumber`・(空なら) `functionName` を置き換える。`.map` が無ければ
  そのまま (落とさない)。元の値は `callFrame.url` を `bundleUrl` に残す
- `scripts/profileParse.ts` の集計 (今は手元の `summarize.mjs` 相当) を
  `scripts/summarizeProfile.mjs` としてリポジトリに入れる: モジュール
  (`node_modules/<pkg>` か `src/<dir>`) ごとの自己時間の表
- **先にイメージの大きさを測る**: `serverSourceMaps` を付けてビルドし、
  `.next/standalone/.next/server` の `.map` の合計を見る。数 MB なら同梱
  (転送は差分なので 1 度だけ増える)。数十 MB なら同梱せず、`.map` は
  `builder` 段に置いたまま `runner` へ写さない (`Dockerfile` で
  `find -name '*.map' -delete`) — その場合は手元で同じ版をビルドして
  `scripts/remapProfile.ts <profile> <.next/server>` で引き直す形にする
- 縮小 (`serverMinification`) は切らない。関数名は source map の `name` で戻る

## 5. 検索ページ全体の組み立てをベンチに足す

本番の iPhone (Wi-Fi) は RTT 18ms で応答開始が 300〜500ms。DB は 7ms なので、
残りはサーバのページ組み立て (RSC) だが、今のベンチには項目が無い。

- `serverBench.ts` に `page:search` を足す: 自分自身 (`http://127.0.0.1:3000/`)
  に `RSC: 1` と**自分のセッション cookie**で GET し、応答開始 (`responseStart`
  相当 = ヘッダが届くまで) と全体を測る。検索語は `?q=抵抗`。3 ペインの
  cookie (`panes=3`) も付けて、本番の PC と同じ形にする
- cookie は Server Action の `cookies()` から写す (管理者が押した要求の物)。
  ベンチの中から外へは出ない (同じプロセスへのループバック)
- 段階は `応答開始` / `全体` の 2 つ。`規模` は本文のバイト数。これで
  「DB 7ms なのに応答開始 400ms」の差が、本番の 1 回の計測で見える
- 自分自身への要求が失敗する環境 (ポートが違う・Basic 認証の proxy) では
  項目ごと `failed` に落とす (ほかの項目は出す)。待ち受けのポートは
  `process.env.PORT ?? 3000`

そこだけ別の配布にする。

## 9. 実装 (2026-10-29)

5 つとも入れた。計画から変えた点:

- **§1 は items の列ではなく別の表にした。** 一覧の `ItemList` は client
  コンポーネントで `Item` を丸ごと受け取るので、`items` に列を足すと回路の中身
  (本文の写し) が一覧の RSC にもう一度乗る。本文の sha1 を鍵にした
  `memo_circuit_fences (memo_hash, fences)` に控え、`circuit/fenceStore.ts` の
  `circuitFencesOfMany` が一覧・同期から 1 クエリで引く。控えに無い本文だけを
  解析して書き足す (50 件ごとに順番を譲る)。鍵が中身なので本文を書く経路は
  触らない。`Item` の型も変わらない。移行は手書き (PGroonga の索引を落とさない)
- **§2 は脚注を残した。** remark-gfm を丸ごと外すと、脚注の定義の続き (字下げ 4 つ)
  のフェンスが字下げのコードになる (既存のテストが拾った)。`remarkFootnotes`
  で脚注の部品 (mdast-util-gfm-footnote・micromark-extension-gfm-footnote、
  remark-gfm と同じ版を直接の依存に足した) だけを読む。全ノートの一致は手元
  1,169 件・本番 (10/25 のダンプ) 1,488 件とも不一致 0。解析は全件で約 44% 縮んだ
- **§3 は level 4。** 本番ダンプの同期 (JSON 8.8MB) で level 1: 2.76MB 65ms・
  4: 2.36MB 78ms・6: 2.24MB 121ms
- **§4 は source map を絞って同梱した。** 全部だと 56MB。ベンチマークの画面の
  入口が読む束ねのうち、解析の道を含む物だけを、元のソース全文
  (`sourcesContent`) を落として写す (10 個・0.5MB、`scripts/copyProfileMaps.mjs`)。
  保存の前に `lib/diag/profileRemap.ts` が引き直し、画面にモジュール別の自己時間の
  表を出す。`scripts/summarizeProfile.mjs` は作らなかった (画面の表で足りる)
- **§5 は `_rsc` と待ち受けのアドレスが要った。** Next 16 は RSC の要求に `_rsc`
  の引数が無いと 307 で転送する。standalone は `HOSTNAME` (docker ではコンテナ名)
  で待ち受けるので、`127.0.0.1` では届かない

手元 (Core Ultra 9 285K) の前後:

| 項目 | 前 (v0.23.83) | 後 |
| --- | --- | --- |
| 回路の解析 (見本 5KB × 10) | 15.8ms | 11.4ms |
| 回路の解析 (実ノート 20 件) | 40.6ms | 27.1ms |
| 同期の組み立て (gzip) | 217ms (107ms) | 159ms (65ms) |
| 検索ページの組み立て「抵抗」 | — | 43ms (応答開始 7.8ms) |

一覧の回路サムネは、控えが埋まった後は解析せずに 1 クエリで引く。手元の検索
「抵抗」は、起動直後の 1 回目 (控えなし・JIT も冷えている) が 303ms、2 回目が 23ms。
1 回目には起動直後の分も混ざるので、控えだけの効き目ではない。
