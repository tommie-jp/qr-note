# ノートのエクスポート・インポート計画 (Ver2.x)

ノートをクライアント (スマホ / PC) からダウンロードして手元に保全し、
同じファイルを戻せる (インポート) ようにする。対象は**全ノート一括**と、
選択モードで選んだ**サブセット**の 2 通り (§7)。ここでは**ファイル形式と
導線の設計判断**を残す。エクスポート・ZIP インポート・ENEX インポートとも
実装済み (§8 のタスク一覧が現状)。

完全バックアップは既に pg_dump が担っている (画像を DB に置いた設計理由が
まさにそれ。schema.prisma の Image コメント参照)。この機能の目的は
バックアップではなく**ユーザー自身による持ち出し・可搬性**。人間がそのまま
読める形式であることを最優先にする。

## 1. 形式 — ZIP 1 ファイル (Markdown + frontmatter + images/)

```text
qr-search-export-2026-07-18.zip
├── export.json        ← 書き出しの覚え書き (版・時刻・件数)
├── notes/
│   ├── 1000.md        ← itemNo をファイル名に
│   ├── 1001.md
│   └── ...
└── images/
    └── <uuid>.jpg     ← Image.data をそのままファイル化
```

各 `.md` は YAML frontmatter にメタデータ、本文は memo をそのまま:

```markdown
---
itemNo: "1042"
mode: memo
url: ""
created: 2025-11-02T01:30:00.000Z
updated: 2026-07-01T08:12:00.000Z
public: false
---
hFE=208
2SC1815 のストック #トランジスタ
![](../images/abc-123.jpg)
```

選定理由:

- memo はもともと Markdown 系の記法 ([メモ記法.md](./メモ記法.md)) なので
  変換コストゼロ・ロスレス。circuitikz フェンスもソースのまま残る
- 人間がそのまま読める。テキストエディタや Obsidian でそのまま開ける
  (frontmatter + 相対パス画像は Obsidian 互換で、vault に置くだけで
  閲覧できる)
- frontmatter が構造化メタデータを持つので機械的な再インポートにも耐える
- 画像は base64 化せず生ファイルで同梱。サイズ膨張 (base64 は約 +33%) が
  なく、画像単体でも取り出せる。本文中の `/api/images/<name>` リンクは
  `../images/<name>` に書き換えるだけ
- ZIP はサーバでストリーミング生成して 1 リクエストで返せる。iOS の
  「ファイル」アプリも Android も標準で展開でき、スマホで「ファイルが
  数百個バラバラに降ってくる」事態を避けられる

### export.json — 書き出しの覚え書き

直下に 1 枚だけ置く (lib/zip/exportMeta.ts)。

```json
{
  "format": "qr-search-export",
  "formatVersion": 1,
  "appVersion": "0.20.20",
  "exportedAt": "2026-08-07T05:57:05.708Z",
  "noteCount": 1
}
```

狙いは 3 つ:

1. **不具合の調査** … 手元に残った ZIP だけを見て、どの版がいつ書き出した
   ものか判る。「取り込めない」と言われたときに版を尋ねずに済む
2. **将来フォーマットを変えたとき**の判断材料 (`formatVersion`)
3. **このアプリの ZIP だという印** … 別物の ZIP を選んだときに取り込み側が
   言い切れる (§3 の「別物の ZIP」)。0 件の書き出しはこれ 1 枚だけになるので、
   「空の書き出し」と「選び間違い」もこれで区別できる

**取り込みはこれを要求しない**。この覚え書きが入る前に書き出した ZIP も、
手で組んだ vault (notes/ と images/ を並べただけ) も、これまでどおり
取り込めなければならない。あれば読む、無ければ無いで読む。

`exportedAt` を入れると同じ内容でも書き出すたびに ZIP のバイト列が変わり、
バックアップの差分・重複排除とは相性が悪い。それでも入れてあるのは、個人の
道具としては「いつ書き出したか」が判るほうが実際に助かるため
(再現性より調査のしやすさを採る)。

エクスポートに**含めない**もの — memo から再生成できる派生キャッシュ:
`tags` / `props` / `Image.thumb` / `Image.embedding` / `CircuitSvg`。

選択エクスポート (§7) も**同じ形式のサブセット**にする。`notes/` が
選んだノートだけ、`images/` がそれらの参照する添付だけになる以外は
全件と同一で、形式を 2 つ持たない。インポート側 (§3) は中身が全件か
一部かを気にしなくて済む。

## 2. 却下した形式

- **JSON / JSONL 単一ファイル** … 機械復元には最適だが、画像を base64 で
  抱えてサイズが膨れ、人間が読めない。「完全バックアップ」用途は pg_dump が
  担うので、ユーザー向けでこれを選ぶ動機は薄い。復元保証を強めたければ
  ZIP に `meta.json` (全ノートのメタデータ一覧) を 1 枚同梱する折衷で足りる
- **PDF / HTML** … 見た目は保てるが編集・再利用できず、エクスポートと
  いうより「印刷」。用途が違う
- **CSV** … 複数行 Markdown + 画像に根本的に不向き

## 3. インポート — 同じ ZIP をそのままアップロード

エクスポートと同一形式をラウンドトリップさせる。専用フォーマットを
別に作らない (KISS)。

- 入口はメニュー → インポート (`/settings/import`) の既存
  `<input type="file">`。accept に `.zip` を足し、拡張子で振り分ける
  (`.enex` → §4)。選択エクスポートで書き出した部分 ZIP も同じ経路で、
  含まれているノートだけが upsert される
- **上限は 500MB** (`MAX_ZIP_BYTES`)。全ノートを丸ごと戻せる大きさにしてある。
  受けられるのは本文を溜めずに流して展開するから — 詳細は下の実装結果
- スマホからは `<input type="file" accept=".zip">` で「ファイル」アプリ /
  Files から選ぶだけ。iOS・Android とも ZIP のまま選択できるので、
  端末側で展開させる必要はない
- サーバ側で展開し、`notes/*.md` の frontmatter + 本文を upsert、
  `images/*` を `Image.name` (UUID.拡張子) で upsert。本文中の
  `../images/<name>` は `/api/images/<name>` に書き戻す
- 派生キャッシュ (tags / props / thumb / embedding / CircuitSvg) は
  既存の保存経路を通して再生成する。エクスポートに含めない (§1) のと
  対になる設計
- 手書きの Markdown (エクスポート由来でないファイル) も、frontmatter の
  必須項目さえ満たせば取り込める副産物がある

### 検証 (インポートは書き込み境界なので必須)

- frontmatter の必須項目・型 (itemNo の形式、mode の enum) を検証し、
  不正なファイルは**そのファイルだけスキップして結果レポートに載せる**
  (全体を止めない)
- ZIP 爆弾対策: 展開後サイズ・ファイル数・1 ファイルの上限を設ける
- 画像は mime と拡張子の整合を確認。パス名は `notes/` `images/` 直下のみ
  許可 (パストラバーサル対策)
- 要ログイン。公開側 (publicPaths) には一切出さない

### 実装結果 — ZIP インポート (Ver2.x)

構成:

| ファイル | 役割 |
| ---------- | ------ |
| `lib/zip/readZip.ts` | ZIP を開く。爆弾・項目数・署名の門番もここ |
| `lib/zip/importZip.ts` | 繋ぎ役。振り分け → 添付 → ノート → レポート |
| `lib/attachmentStore.ts` | 復元時の形式判定 (`restoreAttachment`) |
| `lib/imageStore.ts` | 元の名前のまま行を作る (`restoreAttachmentRow`) |
| `lib/importReport.ts` | ZIP と ENEX で共通のレポートの形 |
| `lib/zip/conflictPolicy.ts` | 衝突時の 3 択 (§5)。画面とサーバで共有 |
| `lib/importDuplicate.ts` | 取り込み済みの判定。ENEX と ZIP で共有 (§4/§5) |
| `lib/zip/exportMeta.ts` | export.json の組み立て (§1) |

決めたこと:

- **添付は元の保存名 (UUID) のまま戻す**。新しい名前を振ると本文の
  `/api/images/<名前>` と食い違い、戻したノートの画像が割れる。名前は
  この DB がかつて発番したものなので、保存名の規則 (isValidAttachmentName)
  はそのまま満たしている。同じ名前の行が既にあれば何もしない = 同じ ZIP を
  二度取り込んでも増えない
- **復元は「拡張子が名乗る形式を中身が裏付けるか」で見る**。新規保存
  (storeAttachment) は名前が利用者由来なので中身だけで決めるが、復元では
  名前がこちらの発番なので逆向きに問える。判定順の綾 (UTF-16 の BOM を MP3 と
  読む等) が出ないぶん素直になる。食い違うものは断る — 配信側は DB の mime を
  そのまま Content-Type にするので、「.png という名前の HTML」を通さない
- **サムネを作るのは行を作ると決めた後**。sharp は 1 枚あたり数十 ms と
  数十 MB を使うので、「既にあるので入れない」と分かる前に走らせない。
  「書き出して手元で直して戻す」使い方ではほとんどの添付がこの経路を通る
- **動画の poster は戻せない**。派生キャッシュなので書き出しに含めておらず、
  サーバに ffmpeg も無い。一覧で絵の無い行になるだけで再生には影響しない
- **添付を先に、ノートを後に入れる**。逆にすると、取り込んだ直後の一覧で
  画像が割れて見える瞬間ができる
- **形式の振り分けは中身の先頭バイトで行う** (拡張子ではない)。判定は展開
  する側と同じ関数 (`isZipBytes`) を使う — 振り分けと展開が「ZIP とは何か」で
  食い違うと、振り分けだけ通って展開で落ちる組み合わせができる
- **ZIP 爆弾の門は 2 段で、1 段目が本命**。ヘッダが展開後の大きさを名乗って
  いれば展開する前に断てる。このアプリの書き出しはヘッダにサイズを書く
  (§7 実装結果) ので 1 段目で受かる。名乗らない他所の ZIP は出てきたバイト数を
  数えて断つが、**fflate は 1 項目を 1 回でまとめて渡してくる**ので、2 段目が
  火を噴く時点でその 1 項目ぶんの確保は済んでいる (実測: 80MB の項目は 80MB の
  チャンク 1 つで届き、入力を細切れに push しても変わらない)。つまり 2 段目が
  守るのは「積み上がり」であって「1 項目の山」ではない。**守れている範囲を
  過大に書かない** — 実害が小さいのは、この口がログイン必須で、1 項目の上限が
  50MB と小さく、確保に失敗しても 400 に写して応答を返せるから
- **本文が指しているのに ZIP にも DB にも無い添付は報告する**。ノートは
  失敗させない (本文は正しく入っている) が、黙っていると画像切れのノートが
  「取り込めた」ことになる
- 取り込みをやめたノートの添付は消さない (ENEX と違う点)。同じ添付を既存の
  ノートが参照していることがあるため。参照されない行は画像 GC の担当
  (docs/20-画像GC計画.md)

#### 別物の ZIP を選んだとき (2026-08 に追加)

アプリの配布物 (`guruguru-avatar-win-v1.9.1.zip`) を取り込ませてみて、
2 つ落ちていることが判った。**どちらも「利用者の選び間違い」を、こちらの
都合でしかない言葉で返していた**。

**1. 中の大きなファイルで全体を断っていた。** ZIP の中に 98MB の exe が
あり、1 項目 50MB の門に掛かって「ZIP の中のファイルが大きすぎます
(guruguru-relay.exe / 上限 50MB)」で 400。しかし**その exe は取り込む対象
ではない** — 取り込まないファイルの大きさは、こちらの器の都合とは関係がない。

読む項目を呼び出し側が選べるようにした (`ZipReadOptions.accept`)。
`classifyEntry` が reject と判じた項目は展開して**捨てるだけ**にし、
1 項目の大きさの門にも掛けない。ZIP 爆弾よけの合計 (`MAX_ZIP_TOTAL_BYTES`)
だけは捨てる項目も数える — 捨てるにせよ展開はしているので、際限なく
付き合わないための歯止めは要る。

**捨てる項目でも `file.start()` は呼ぶこと。** fflate は start() されていない
項目のバイト列を「後で読むかもしれない」と抱え込む (`Unzip.push` の `this.k`)
ので、呼ばずに放置すると読み飛ばしたはずの中身がメモリに積み上がる。
展開して捨てるほうが安い。

**2. 中身が別物でも「0 件取り込めました」に見えていた。** notes/ も images/ も
無い ZIP は、257 件の「想定していないフォルダです」が並ぶだけの結果になる。
壊れているのか選び間違えたのかを判断できないので、**1 行で断る**ことにした:

```text
このアプリが書き出した ZIP ではないようです (notes/ の Markdown も
images/ の添付も入っていません)。エクスポートで書き出した .zip を選んで下さい
```

断らない例外が 2 つある。**項目が 1 つも無い ZIP** (空を取り込んで「0 件でした」
と言うのは正しい) と、**export.json があるもの** (0 件のときの書き出しがこの形
なので、中身が空なのと選び間違えたのとは別の話)。ノートが 1 件でもあれば
今までどおり個別のレポートを返す — vault に .DS_Store が混ざる使い方を壊さない。

#### エラー応答の前に本文を読み捨てる (2026-08 に追加)

上の 1. で 400 になるとき、画面は「取り込み中…」のまま**止まって見えた**。
サーバのログには 400 が残っているのに、ブラウザには何も出ない。

原因は**本文を読み終える前に応答を返していた**こと。直結 (curl・localhost)
なら早い応答としてそのまま届くが、間に中継が挟まると話が変わる。本番の
nginx は `/api/import` だけ `proxy_request_buffering off` で中継しており、
WSL のポート転送や社内 proxy も同じ位置に立つ。中継はクライアントの送信を
先に捌こうとするため、応答が中継されないまま送信だけが続く。

エラー応答を返す前に、届いていない本文を読み捨てるようにした
(`drainRequest`)。読み捨てたぶんも進捗に数えるので、バーは最後まで進み、
送り終わったところで理由が出る (止まったようには見せない)。

- **読み捨ての上限は「まだ受け取ってよい残り」まで** (500MB − 受信済み)。
  413 (大きすぎる) で抜けたときは予算が尽きているので 1 バイトも読まない —
  断った相手に付き合って 500MB を読むのでは、上限を設けた意味がなくなる
- **本文を読む前に断つ経路 (401 / 403 / 409 / Content-Length 413) は
  読み捨てない**。未認証の相手の 500MB に付き合う理由はない
- 接続を切る (`body.cancel()`) 案は採らない。ブラウザ側が TypeError になり、
  本当の理由 (「〜が大きすぎます」) が「送信が途中で切れました」に化ける

#### 500MB を受けるためにしたこと

当初の上限は ENEX と同じ 10MB だった。**全ノートを戻すには小さすぎる**ので
500MB へ上げたが、そのために変えたのは定数ではなく受け方である。

- **本文は multipart で包まず、ファイルそのものを POST の本文にする**。
  `request.formData()` は本文全体をメモリに載せ、`arrayBuffer()` がさらに
  複製を作る — 500MB なら入口だけで 1GB を超える。生のボディなら
  `request.body` をそのまま展開器へ流せる。同時に送りたい設定 (上書きするか)
  はクエリへ移した
- **fflate へは 64KB ずつ push する**。1 回で押し込むと項目ごとの再帰で
  3500 件から `RangeError` になるが、細切れなら 30000 件でも通る (実測)。
  かつて項目数の上限を 2000 に置いていたのはこの制約のためで、**実装の都合が
  仕様の上限を決めていた**。細切れ push でそれが外れたので、上限は
  「個人のノート数として現実的な数」(20000) に置き直した
- **添付は届いたそばから DB へ書いて捨て、ノート本文だけ溜める**。順序の
  要件は「添付 → ノート」だが、書き出した ZIP はノートが先に並んでいる。
  全部読んでから処理すると 500MB が丸ごと載るので、**小さいほう
  (ノート本文) だけを待たせる**ことで両立させた。溜まる量にも上限を置く
  (`MAX_ZIP_NOTE_BYTES` = 64MB)
- **エッジは `/api/import` だけ開ける** (nginx の `location = /api/import` に
  `client_max_body_size 512M` + `proxy_request_buffering off`)。server 既定の
  35M は据え置き — 500MB を全パスに開くと、どの口へでも巨大なボディを
  投げ込めることになる。`proxy_request_buffering off` が無いと nginx が
  ボディを溜めきってから渡すので、流して展開する設計が効かない
- **`/api/import` は proxy (src/proxy.ts) の matcher からも外す**。Next.js は
  proxy を通るルートの本文を「proxy と route の両方で読めるように」**メモリへ
  丸ごと複製し、その上限が既定 10MB**
  (`experimental.proxyClientMaxBodySize`)。本番で実際に踏んだ — 87MB の取り
  込みが 10MB で千切れ、「ZIP を展開できませんでした」に見えた (サーバログに
  `Request body exceeded 10MB` が出る)。上限を 512MB に上げる選択肢は罠で、
  今度は 500MB がメモリに載って RAM 2GB の本番が落ちる。matcher から外せば
  複製ごと消える。認証は route 側の denyUnlessLoggedIn が正で、proxy は
  もともと楽観的検査 (docs/18 §4) なので、外しても砦は減らない
- **復元の 1 件上限は「DB に入りうる最大」(50MB = CLI 取り込みの添付上限)**。
  当初は Web アップロードの上限 (画像 10MB / 動画 30MB) を流用していたが、
  CLI から入った 11〜12MB の iPhone 写真が復元で弾かれた —
  「書き出せるのに戻せない」は往復の要件違反。上限は入口 (HTTP) の都合では
  なく器 (DB) に合わせる (`MAX_ZIP_FILE_BYTES`)

実測 (手元、`--expose-gc` で基準 RSS を取ってから):

| 入力 ZIP | 取り込み中の RSS 増分 |
| ---------- | ------------------------ |
| 200MB | +104MB |
| 400MB | +115MB |

**入力を倍にしても増分はほぼ変わらない** = 載っているのは「いま保存している
添付 1 件」ぶんで、入力の大きさには連れない。あわせて、Next.js が本文を
先読みして溜め込まないことも確かめた (300MB を POST しても、門番が 401 を
返すまでサーバの RSS は 197MB から動かない)。

最後に、テスト用の資格情報で本物のログインを通し、HTTP 経由の端から端
(エクスポート 175MB → インポート 200・見送り 0 件・切り詰め警告なし) まで
確認した。層ごとの検証だけでは proxy の本文複製 (上記) を見逃した — HTTP を
挟まない検証は、HTTP にしか無い層のバグを構造的に検出できない。

## 4. ENEX (Evernote) インポート

Evernote からの乗り換え取り込みもやりたい。ENEX は XML で、
1 ファイルに複数ノートが入る:

- `<content>` … ENML (XHTML 系) の CDATA。Markdown ではない
- `<resource>` … 添付 (画像など) の base64 + mime。本文からは
  `<en-media hash="MD5">` で参照される
- `<title>` `<created>` `<updated>` `<tag>` … メタデータ

方針: **ENEX を §1 の内部形式に変換する前段コンバータ**として作り、
upsert・検証・派生キャッシュ再生成は §3 の経路をそのまま通す。
インポート経路を 2 本持たない。

変換の対応表:

| ENEX | 本アプリ |
| ------ | --------- |
| `<title>` | memo の 1 行目 (title 列は無い) |
| `<content>` (ENML) | Markdown へ変換 (turndown 系。ENML 固有タグは前処理で除去) |
| `<tag>` | memo の 2 ブロック目に `#タグ` 行 (tags は memo からの派生のため) |
| `<resource>` | base64 を decode して Image 行に。name は新規 UUID を発番 |
| `<en-media hash>` | resource の MD5 と突き合わせて `![](/api/images/<name>)` に置換 |
| `<created>` `<updated>` | createdAt / updatedAt に反映 |
| itemNo | 無いので `nextItemNo()` で採番 (衝突なし = §5 のポリシー対象外) |

- ENML → Markdown はロスが出る前提 (表・整形・チェックボックスなど)。
  変換できない断片は素の HTML のまま残すか落とすかを実装時に決める
- 既存 OSS (evernote2md など、ENEX → Markdown 変換器) の変換ルールを
  参考にする。丸ごと採用できれば前段はそれで済む可能性もある
- ENEX も ZIP と同じ `<input type="file">` から拡張子で振り分ける
  (`.zip` → §3、`.enex` → 本節)

### 実装結果 (Ver2.x)

ENEX の取り込みはエクスポートより先に実装した (この節は当時の記録)。
入口は `/settings/import` のファイル選択で、
**変換はすべてサーバ側** (`POST /api/import`)。クライアントは端末の
ファイルを選んで送るだけで、認証・CSRF・大きさの作法は `/api/images` に揃えた。

構成 (純関数を分けてテストできるようにする):

| ファイル | 役割 |
| ---------- | ------ |
| `lib/enex/parseEnex.ts` | ENEX (XML) → ノート配列。fast-xml-parser (既存依存) |
| `lib/enex/enmlToMarkdown.ts` | ENML → Markdown。turndown + gfm プラグイン |
| `lib/enex/buildMemo.ts` | 題名・タグ行・本文を memo 1 枚に組む |
| `lib/enex/importEnex.ts` | 繋ぎ役。保存は既存の `upsertItem` を通す |
| `lib/attachmentStore.ts` | 添付の形式判定と保存。`/api/images` と共有 |

決めたこと:

- **変換ライブラリは turndown + turndown-plugin-gfm**。HTML → Markdown の
  実質の標準で、Evernote 移行ツール (yarle) も内部で使っている = ENEX が吐く
  実際の HTML に対する実績がある。yarle / evernote2md を丸ごと使う案は
  不採用 — どちらも「ファイルシステムに .md を書き出す CLI」設計で、
  添付を DB に置く本アプリには嵌まらない
- **フォント・文字サイズは捨てる**。memo は Markdown なので持てない。
  turndown が span/font の殻を落とす既定の挙動がそのまま要件に一致する
- **リンクは残す**。`evernote:///` の内部リンクはそのまま (解決には
  ノート間の GUID 対応表が要る。複数ファイル対応時の課題)
- **`<div>` は段落ではなく改行**にする。Evernote は 1 行を 1 つの div で
  包むため、turndown の既定 (未知のブロック要素 = 前後に空行) だと行間が
  倍に開く。このアプリの表示は remark-breaks なので改行 1 つで元の形になる
- **ENML の空要素は img / input へ寄せてから** turndown に渡す。ENML は
  XHTML で `<en-media/>` と自分で閉じるが、turndown の HTML パーサ (domino)
  は HTML の規則で読むため未知のタグが「開いたまま」になり、後続の本文を
  丸ごと飲み込む (実測: チェックボックス直後の文字が消えた)
- **表は 1 行目を `<th>` に仕立ててから**変換する。turndown-plugin-gfm は
  見出し行の無い表を `keep` して**生 HTML のまま**残すが、このアプリの表示は
  生 HTML 無効なので**表がまるごと消える**。しかも Evernote の表は `<td>` しか
  使わないため、実物の ENEX はまるごとこの穴に落ちる。表の中の `<en-media>` も
  変換されず、保存した添付が参照されないまま残る二次被害もあった。
  自前で表を組むより入力を寄せて既存の実装に乗せるほうが安全
- **表のセルの中では div を改行にしない**。Evernote はセルの中身も div で
  包むが、GFM の表は 1 行 1 レコードなので改行を入れると崩れる
  (実測: `| 型番 |` が 3 行に割れた)
- **変換にかける前に大きさと入れ子の深さで断る**。turndown も domino も木を
  再帰で歩くため、`<div>` を延々と入れ子にした ENML は失敗するまでに数十秒の
  同期処理を回す (実測: 660KB / 6 万段で 23.5 秒)。Node は 1 本の
  イベントループなのでその間アプリ全体が止まる。上限は 512KB / 200 段で、
  門番を通せば同じ入力が 1ms で片付く
- **添付のファイル名は Markdown の記号を殺してからリンクの表示文字にする**。
  ファイル名は ENEX の書き手が自由に書けるので、`資料.pdf](https://evil…)[`
  のような名前で意図したリンクを閉じて偽装リンクを差し込める
  (rehype-sanitize は `javascript:` は消すが http(s) の偽装先は止めない)
- **タグ行は本文より前**に置く。後ろに置くと、コードフェンスで終わる本文の
  ときにフェンスの内側へ落ちて `extractTags` に拾われない
- Evernote のタグは空白・記号を含められるので `-` に寄せる
  (「電子 工作」→ `#電子-工作`)。潰して「電子工作」にすると別タグと衝突する
- **申告 MIME は信用しない**。`<resource><mime>` は書き出し元の申告でしかなく、
  形式は既存の先頭バイト判定 (`uploads.ts`) で決め直す
- 添付は既存の保存経路を通すので、**サムネイル・画像検索の埋め込みも自動で付く**
- 本文が `MAX_TEXT_LENGTH` (10000 字) を超えるノートは切り詰めずに飛ばし、
  **保存済みの添付も消す** (本文が入らない以上どこからも参照されないため)
- 1 回の取り込みは 500 ノートまで (採番を延々と回されないための安全弁)

#### 取り込み口は 2 つある (Web と CLI)

実データの書き出しが **40.2MB** あり、これを Web の口へ投げると本番 VPS
(RAM 2GB / swap 常用。docs/09) には重い。そこで**大きいものはローカル (WSL) で
変換する**。イメージをローカルでビルドして送る `doDeploy.sh` と同じ考え方で、
「重い処理は手元、成果物だけ本番へ」に揃える。

| 口 | 使いどころ | ファイル上限 | 添付 1 件の上限 |
| ---- | ------------ | ------ | ------ |
| `/settings/import` (Web) | スマホから小さい .enex を入れる | 10MB | 10MB |
| `./doImportEnex.sh` (CLI) | 本命。40MB 級をローカルで変換して本番 DB へ | 実質なし | 50MB |

**添付 1 件の上限を CLI で分けている**のが要点。10MB (`MAX_IMAGE_BYTES`) は
エッジのボディ上限 12MB に収まる大きさとして決めた **HTTP アップロードの
都合**であって、DB に置ける大きさの上限ではない。iPhone の写真は普通に超える
(手元の書き出しでは添付 10 枚のうち 3 枚が 11〜12MB) ので、そのまま CLI に
持ち込むと移行のたびに写真が虫食いになる。実際 1 枚目の取り込みで
12.1MB の写真が落ちた。

縮小はしない。移行は一方通行なので、元の解像度を黙って落とすより、そのまま
入れて必要になってから間引くほうが取り返しがつく。

判定は**変換前のバイト列**に対して行う点に注意 (HEIC は保存時に WebP へ縮むが、
その前に大きさで弾かれる)。

**中身は同じ `importEnex()` を呼ぶ**。変換規則・レポート・巻き戻しを 2 か所に
持たない (§4 の「インポート経路を 2 本持たない」はここにも効く)。

CLI は `doDeploy.sh` の「6/8 マイグレーション」と同じく SSH トンネル
(`localhost:15433` → vps2 の `127.0.0.1:5432`) 越しに書く。vps2 の Postgres を
外へ公開する必要はない。**採番が本番に対して行われる**のがこの形の勘所で、
ローカル DB に取り込んでから行を移す案だと itemNo が本番と衝突する。

ローカルは潤沢なので CLI は既定で**画像検索の索引まで作る** (`embedImages`)。
Web の口は逆に作らない (下の表のとおりモデル読み込みだけで +475MB)。

Web の上限を 10MB に抑えているのは、エッジ (Caddyfile / deploy/nginx) の
ボディ上限 12MB をそのまま使うため。**片方だけ上げると事故る** — エッジが
低いとアプリに届く前に 413 でボディを読み捨てられ、ブラウザには
「Load failed」としか出ない (サーバの JSON エラーは届かない)。
上限超過はクライアント側でも送信前に検査し、CLI へ誘導する。

手順の推奨:

1. `./doCopyDBfromVPS2.sh` — 本番のコピーをローカルに作る (採番も本番と同じ)
2. `./doImportEnex.sh f.enex --local` — 下見。レポートと画面を確認する
3. `./doImportEnex.sh f.enex` — 本番へ。**実行中はアプリを触らない**
   (`nextItemNo()` は空き番号の最小値を返すだけで予約しない)

本番へ書く前に DB のバックアップを取る (`doImportEnex.sh` が自動で取る)。
数百行を本番へ書く操作で、取り消す手段はそのダンプしかない。

#### 複数ノート・複数ファイル・重複 (Evernote の実運用)

Evernote で複数ノートを選択して書き出すと、**1 ファイルに複数ノート**が入る。
パーサもインポータも最初からノート配列で扱うので、これはそのまま取り込める
(そこは変更不要)。実運用で足したのは次の 4 点:

- **重複はスキップ (既定)**。手で選択してバッチを作ると、選択の重なりや
  同じファイルの再実行で二重取り込みが現実に起きる。「同じ created_at
  (ENEX 由来・秒精度) + 同じ題名 (memo 1 行目)」で既存を照合し、あれば
  入れない。この組はほぼ一意で、同時刻・同題名の別内容ノートは実用上ない。
  **日時の無いノートは判定対象外** (題名だけでは同名の別ノートを取り違える)。
  `--force` で入れ直せる。判定は添付を保存する前に撃つのでゴミが残らない。
  これにより「途中で失敗 → 同じファイルを流し直す」が安全になった
  (再実行しても増えない)
- **500 ノート上限は CLI では撤廃**。`MAX_NOTES_PER_IMPORT` は Web の口の
  安全弁 (細工ファイルで採番を回されない) で、自分のファイルを渡す CLI には
  不要。撤廃しないと 500 超のバッチで再実行時に先頭 500 件が二重になる
- **`#evernote` を全ノートに必ず付ける**。由来の印で、移行に不満が出たとき
  「#evernote で全選択 → ゴミ箱」でやり直せる。要らなくなれば一括タグ削除で
  外せる (付けて後悔は消せるが、付けずに後悔は手遅れ、の非対称性)。
  `--tag レシピ` でノートブック名の代わりの分類タグを足せる (役割が違う:
  #evernote は由来、--tag は分類)
- **複数ファイルを一度に渡せる**。`./doImportEnex.sh a.enex b.enex`。
  本番へのバックアップは最初に 1 回、SSH トンネルも張りっぱなしで使い回す
  (ファイルごとに 4GB 級のダンプを繰り返さない)

大きすぎるファイルは読む前に断る。Node は 1 つの文字列を 512MB
(`buffer.constants.MAX_STRING_LENGTH`) までしか持てず、`readFileSync` は
ファイル全体を 1 文字列にするため、超えると意味不明な `ERR_STRING_TOO_LONG`
で落ちる。余白を取った 400MB (`MAX_CLI_ENEX_BYTES`) で断り、
「選択を分けて書き出し直す」よう案内する (docs/13-EVERNOTE全ノート移行メモ.md)。

本番 VPS は RAM 2GB で swap を常用している (docs/09)。50MB の ENEX
(4000x3000 の写真 4 枚) を素直に実装したときの実測は **RSS +2610MB** で、
そのままでは確実に落ちる。内訳を測って 3 つ直し、**+288MB** まで下げた:

| 原因 | 実測 |
| ------ | ------ |
| 巨大な base64 を XML パーサへ渡していた | 48MB で **+1219MB** / 2.2 秒 |
| 復号したバイト列を全件ぶん抱えていた | 30MB 前後が生き続ける |
| 画像検索の埋め込みを画像の数だけ撃っていた | モデル読み込みで **+475MB** |

対処:

- 解析の前に `<data>` の中身を抜いて目印に差し替える
  (`liftDataPayloads`)。抜いた中身は V8 の部分文字列なので複製は起きない
- `base64` のまま持ち、保存の直前に 1 件ずつ復号する
  (`decodeResourceData`)。md5 のために 2 回復号することになるが、
  CPU を少し払ってピークを下げる取引
- 一括取り込みでは埋め込みを作らない (`deferEmbedding`)。派生キャッシュなので
  `npm run backfill:embeddings` が後から埋める。後回しにしたことは画面で知らせる

参考: サムネイル生成 (sharp) は +2MB で無視してよい。`XMLValidator.validate`
も 86ms / +7MB と安い (壊れたファイルを弾く価値のほうが大きい)。

測り直すときは、検証スクリプト自身の画像生成分を基準から外すこと
(`--expose-gc` で GC してから基準 RSS を取る)。取らないと 2 倍近く多く見える。

ロスが出るもの (レポートに載せる): 対応外形式の添付、base64 として読めない
添付、参照先の見つからない `<en-media>`、タグに書けない文字だけのタグ、
長すぎる本文、大きすぎる/深すぎる本文、`<en-crypt>` (端末の鍵でしか開けない)。

**「入らなかったもの」は必ずレポートに出す**のがこの実装の背骨。本文に跡を
残すだけだと、利用者は全ノートを目視するまで欠落に気づけない。逆に、行が
できた後で転んだノートは「取り込み済み」として報告する — 入っているのに
「入らなかった」と伝えると、取り込み直して二重に作ってしまう。

## 5. 衝突ポリシー (決定済み)

itemNo が既存ノートと衝突したときの扱い。**既定はスキップ + レポート、
上書きは取り込み画面のチェックボックスで明示的に選んだときだけ**にした
(検討していた案 2 + 案 1 のオプション)。

- 戻す操作で手元の編集を黙って潰すほうが取り返しがつかない。既定は安全側へ
- 送られてこなければ上書きしない形にしてある (旗の欠落が無防備へ倒れない)
- スキップした件数は「失敗して入らなかった」ではなく**あえて入れなかった**
  ものとして、赤い「取り込めなかったもの」とは分けて画面に出す
- **ゴミ箱の行も「使用中の番号」として数える**。番号はゴミ箱にある間じゅう
  予約されている (docs/12-ゴミ箱計画.md §4) ので、上書きの可否も同じ扱いに
  しないと、復元したときに中身が入れ替わっている事故になる

updated の新旧比較で自動判定する案は見送ったまま (時計依存の複雑さが増す)。

選択エクスポート (§7) が入ったことで「書き出して手元で直して戻す」運用では
衝突がむしろ通常ケースになる。そのぶん、上書きを 1 クリックで選べる位置に
置いてある。

### 新しい番号で取り込む (実装済み)

衝突時の第 3 の選択肢。**既存のノートはそのまま残し、ZIP 側のノートに
空き番号を振って取り込む**。用途は「別のインスタンス (デモ・他人の書き出し)
のノートを、手元を壊さず取り込む」「ノートの複製」— スキップ (どちらか
片方) とも上書き (置き換え) とも違う「両方残す」が欲しい場面。

#### UI — チェックボックスをラジオ 3 択へ

同じ番号のノートが既にあるとき:

- **そのまま残す** (既定) … ZIP 側は見送り、件数を報告 (現行の既定)
- **上書きする** … ZIP の内容で置き換える (現行のチェックボックス)
- **新しい番号で取り込む** … 既存はそのまま、ZIP のノートへ空き番号を振る

3 つ目には注意書きを添える: **新しい番号を振ったノートは、印刷済みの
QR シールとは対応しなくなる**。itemNo は印刷した QR の URL そのもの
(§1 の設計前提) なので、これはオプションの本質的な代償で、選ぶ人にだけ
見えればよい。

#### API と番号の振り方

- クエリを `?overwrite=1` から **`?conflict=skip|overwrite|renumber`** へ
  置き換える (既定 skip)。省略は skip に倒すが、**未知の値は 400 で断る** —
  タイポで renumber のつもりが skip で走り「取り込めたのに増えていない」に
  見えるのを防ぐ (export の scope と同じ主義)。`ZipImportOptions` も
  `overwrite?: boolean` を `conflict` の 3 値に置き換える
- 衝突していないノートは**元の番号のまま**入れる。採番するのは衝突した
  ものだけ (全部を振り直すと、衝突していないノートまで QR シールと
  切れてしまう)
- 採番は ENEX と同じ `nextItemNo()` (空き番号の最小値)。ノートのループは
  直列なので採番の競合はない
- **採番は ZIP 側の番号も避ける** (実装で判明)。`nextItemNo(alsoUsed)` に
  同じ ZIP の全ノートの番号を渡す。空き番号がたまたま ZIP の別ノートの番号
  だと、それを横取りして「衝突していないノートは元の番号のまま」という上の
  約束が崩れる (手元が 1〜50、ZIP が 3 と 51 のときに実際に起きる)
- 添付は何も変えない。保存名 (UUID) は内容と 1:1 で、同名 = 同内容として
  共有されるのが正しい (docs/20 §1)
- **本文は書き換えない**。本文中の `/item/<番号>` への URL 参照は「取り込み
  先に元からあるノート」を指す意図かもしれず、書き換えは当て推量になる。
  ENEX の `evernote:///` リンクをそのまま残すのと同じ判断

#### 再実行の安全 — 同内容なら採番しない

renumber の罠は再実行で、素朴に作ると同じ ZIP を 2 回流した時点で全ノートが
複製される (毎回衝突 → 毎回採番)。ENEX で実証済みの重複判定
(**同じ created_at (秒精度) + 同じ memo 1 行目なら既に取り込み済み**。
importEnex の isDuplicate) をここでも通す:

- 衝突したノートについて、同内容のノートが既に居れば**採番せず見送る**
  (duplicateSkipped として報告 — ENEX と同じ名前・同じ意味)
- これで「自分の書き出しを renumber で再実行」しても増えない。増えるのは
  本当に中身の違うノートだけ
- 日時の無いノート (手書き Markdown) は判定対象外 = 常に採番する
  (題名だけの照合は同名の別ノートを取り違える。ENEX と同じ理由)
- isDuplicate は importEnex.ts の私有関数なので切り出して共有する。
  **置き場所は lib/items.ts ではなく lib/importDuplicate.ts にした** —
  items.ts は検索・ゴミ箱まで抱えた大きな面で、DATABASE_URL を要求する経路も
  多く、この判定だけを差し替えて確かめられない (itemNo.ts を切り出したのと
  同じ理由)。依存を prisma 1 つに絞ってテストから通せる形にしてある

#### 報告

## 7. エクスポートの導線と API (全件・選択)

エクスポートの入口は 2 つ。どちらも同じ ZIP (§1) を返し、
メニュー → インポート (`/settings/import`) でそのまま戻せる (§3)。

### 全件 — メニューのインポートページに同居

- 既存の `/settings/import` を「インポート / エクスポート」ページに拡張し、
  「全ノートをエクスポート」ボタンを置く。メニュー項目は増やさない
  (docs/11-アプリ的UIUX計画.md §6 の「たまにしか使わないものは奥へ」)。
  書き出す場所と戻す場所が同じ画面になり、ラウンドトリップの説明も
  1 か所で済む
- ゴミ箱 (`deletedAt` 非 null) は含めない (§6 既定)

### 選択 — 検索結果の選択モードに 1 ボタン足す

- 下部バー「選択」で入る既存の選択モード (docs/31-下部操作バー計画.md
  §5-2) の BulkTagToolbar に「エクスポート」ボタンを足す。一括タグ・
  ゴミ箱行きと同じ選択集合 (`Set<itemNo>`) を使うだけで、新しい選択 UI は
  作らない
- ボタンはタグ操作と同じ行に置かず、最下段でゴミ箱行きと**両端に離す**
  (誤操作の距離を、行を増やさずに稼ぐ)。0 件選択は disabled
- 「全選択」は**表示中の検索結果**への全選択であって全ノートではない。
  裏を返すと、タグや検索で絞ってから全選択 → エクスポートが
  「タグ単位・検索結果単位の書き出し」になる。§6 で見送った形を
  検索構文の持ち込みなしで実現できる

### API — POST /api/export の 1 本

- `POST /api/export`。form body の `scope` が `all` なら全件、`selected` なら
  `itemNo` (複数値) で選んだぶんだけ。エンドポイントを 2 本にしない
- 旧タスクの GET 案から POST へ変更する。理由:
  - 選択した itemNo の列は URL 長の実用上限 (~2KB) に収まる保証がない
  - `<form method="post">` の画面遷移なら `Content-Disposition: attachment`
    をブラウザがそのままダウンロードとして受ける。fetch + blob と違い
    JS がファイル全体をメモリに抱えない (スマホ + 画像入り ZIP で効く)
- **`scope` を省略したら 400 で断る** (全件に倒さない)。選択の受け渡しが
  壊れたときに黙って全ノートを書き出すより、断って気づけるほうがよい
- 選択の番号は一括タグ・ゴミ箱行きと同じ `parseSelectedItemNos`
  (lib/itemSelection.ts) を通す。フォームの形が同じなら解釈も 1 か所に置く
- 要ログイン。デモモードでは閉じる (docs/38 §4。インポートと同じ判断で、
  デモデータの持ち出し口を開けておく理由がない)
- ZIP はストリーミング生成 (§1。画像が DB にあるため全件をメモリに載せない)
- 同梱する添付は**対象ノートの memo が参照する Image 行だけ**。画像とノートの
  関係は DB に無く、本文の `/api/images/<name>` が唯一の紐である
  (docs/20-画像GC計画.md §1)。複数ノートから参照される添付は 1 回だけ入れる
  (name は UUID なので Set で重複排除)
- 存在しない itemNo・ゴミ箱入りが混ざったら黙って除外する。選択 UI から
  ゴミ箱は選べないので実際にはほぼ来ないし、読み取りだけの操作なので
  インポートのような結果レポートまでは要らない
- シークレット (部分暗号化) のブロックは**暗号文のまま**出す。鍵は
  サーバーに無いので平文にはできず、暗号文のまま戻せばラウンドトリップは
  保たれる。「人間がそのまま読める」の例外になることは承知の上
- ファイル名は `qr-search-export-YYYY-MM-DD.zip` (全件・選択共通。中身は
  frontmatter で判別でき、名前で区別しない)

### 実装結果 — エクスポート (Ver2.x)

構成 (純関数を分けてテストできるようにする。ENEX 側と同じ流儀):

| ファイル | 役割 |
| ---------- | ------ |
| `lib/zip/layout.ts` | ZIP の中の配置。書く側のパス組み立てと、読む側の振り分け |
| `lib/zip/frontmatter.ts` | `---` で挟んだ key/value の読み書き |
| `lib/zip/noteFile.ts` | ノート ⇄ Markdown 1 枚。参照の書き換えと添付の拾い出し |
| `lib/zip/zipStream.ts` | 項目の並び → ZIP のバイト列 (背圧つき) |
| `lib/zip/exportZip.ts` | DB を引いて項目の並びを作る (非同期ジェネレータ) |
| `app/api/export/route.ts` | 門番と応答の組み立て |

決めたこと:

- **ZIP の箱は自前で書く** (書きは fflate を使わない。読みは fflate の
  `Unzip`)。当初は fflate の `Zip` で書いていたが、あれはローカルヘッダに
  サイズを書かない「データ記述子」方式で、**無圧縮の項目の終端が自己記述
  されない**。ストリーミングで読む側は本文の中から次のシグネチャを走査して
  枠を切るしかなく、添付の中身に偶然 `PK\x03\x04` が埋まっていると枠がずれて
  壊れる。**実データで踏んだ** — PNG 1 枚の 4.7MB 地点にこの 4 バイトがあり、
  書き出した ZIP を自分の取り込みが読めなかった (展開ツールは中央ディレクトリ
  から読むので開けてしまい、エクスポート直後の確認では気づけない)。
  項目の中身は書く前に丸ごと持っているので、CRC とサイズを先に計算して
  ヘッダに書ける。読み手はバイト数で枠を切るだけになり、中身に何が
  埋まっていても壊れない。ZIP64 (4GB 超) は未対応で、超える場合は黙って
  壊れたファイルを作らず失敗させる
- **背圧は自前で組む**。`ReadableStream` の `pull` が呼ばれたときにだけ
  次の項目を DB から取りに行く (pull 1 回 = 項目 1 件)。これで「読み手が
  遅いと DB を先読みして溜め込む」事故が構造的に起きない。中断 (`cancel`)
  ではジェネレータを畳んでカーソルを閉じる
- **添付は無圧縮 (stored) で入れる**。jpg/webp/mp4/pdf は圧縮済みで、
  deflate に通しても縮まないのに CPU だけ増える。縮めるのは 1 件 10KB 以下の
  Markdown だけなので、同期版の deflate (`node:zlib`) で足りる。deflate して
  逆に太る入力は素通しへ倒す (読む側はヘッダの method に従うだけ)
- **サーバーアクションの form の中から素のダウンロードへ抜けられる**。
  React は送信ボタンの `formAction` が**文字列**のとき preventDefault せず、
  ブラウザの素の送信に戻す (react-dom の FormAction 処理を実機とテストで確認)。
  hidden form を組み立てて submit する必要はなく、ボタン 1 つで済む。
  `scope` はボタン自身の `name`/`value` で送られる
- **itemNo のサニタイズは不要だった**。`isValidItemNo` が
  `[0-9A-Za-z_-]{1,20}` しか通さないので、パス区切りも `..` も先頭 `-` も
  そもそも入らない。**新たに畳む代わりに、ファイル名にする直前で検証する**
  (通っていない値が来たら投げる) 形にした
- **日時は UTC の ISO 8601 で書く** (`2026-07-01T08:12:00.000Z`)。時差つき
  表記より往復が確実で、表示に使う値ではない (画面はブラウザ側で JST に
  整形する)。ダウンロードのファイル名だけは JST の日付 — 手元に落ちたときに
  「いつ取ったか」が地元の日付で読めるほうがよい
- **添付の拾い出しは一覧サムネ (memoImages.ts) とは別の規則**にした。あちらは
  「そのノートの顔になる絵」を選ぶので Markdown の画像記法だけを見てコードの
  中を外すが、書き出しは「本文が指しているものを 1 つも落とさない」ことが
  最優先なので、記法もコードフェンスも問わず URL の形だけで拾う。リンク記法
  (`[資料](…)`) で貼る PDF・音声も同じ網に入る
- **参照の書き換えは保存名として妥当なものだけに当てる**。単純な文字列置換に
  すると、本文にたまたま書かれた `../images/…` という文字列まで配信 URL に
  化けて、往復で本文が変わる
- **本文の末尾には必ず改行を 1 つ足し、読む側が必ず 1 つ外す**。これで
  「改行で終わる memo」も「終わらない memo」も同じ形で往復する
- 参照先の添付が見つからないときは**ログに残して続ける** (1 枚欠けただけで
  全件の書き出しを失敗させない)。本文の参照はそのまま残るので、戻せば
  元の状態に戻る

## 9. 取り込みの進捗表示

500MB を受けられるようになった (§3) ことで、取り込みは**分単位で待つ操作**に
なった。いまの UI は「取り込み中…」の一言だけで、進んでいるのか固まって
いるのか見分けが付かない。% と推定残り時間 (秒) を出す。

### 進捗の正はサーバに置き、クライアントはポーリングで覗く

進捗の情報源は 2 つに割れている:

- **送る側の進み** … ブラウザが何バイト送ったか
- **受けた後の進み** … サーバがどこまで処理したか (ノートの反映は
  全添付の後 = アップロード完了後にも仕事が残る。§3 実装結果)

これを**サーバ側の 1 つの進捗状態に集約する**。本番 nginx は
`/api/import` だけ `proxy_request_buffering off` (§3) なので、サーバが
読んだバイト数 = 実際にアップロードが進んだ量であり、送る側の進みも
サーバ側で観測できる。クライアントに XHR (`upload.onprogress`) を持ち込む
必要はなく、fetch のまま**別 GET をポーリング**すれば足りる。

- `lib/zip/importProgress.ts` … モジュール変数の**単一スロット**。
  logBuffer と同じ流儀 (プロセス内メモリ)。本番は `node server.js` の
  単一プロセスなので、モジュール変数で届く。多重取り込みはこのスロットを
  取れなかった時点で **409 で断る** — importZip は同時実行を想定して
  いない (採番・衝突判定が競合する) ので、進捗以前に必要な門
- 状態: `{ startedAt, totalBytes, readBytes, phase, notesDone, notesTotal,
  finishedAt }`。phase は `receiving` (バイトを読みながら添付を保存) →
  `notes` (ノートの反映) → `done`
- 計測点は既にある: `readBytes` は route の `withLimit` (バイトを数えて
  いる唯一の場所)、`notesDone/notesTotal` は importZip のノートループに
  コールバック (`onProgress`) を 1 本足す
- `GET /api/import/progress` … 要ログイン。スナップショットを返すだけ。
  この GET は proxy を通ってよい (本文が無いので複製の問題 (§3) は無関係)

### % の定義 — 2 段階を 1 本に繋ぐ

- `receiving` 中: `readBytes / totalBytes × 90`。totalBytes は
  Content-Length (fetch + File 本文では必ず付く。付かない相手には % を
  出さずスピナーに倒す)
- `notes` 中: `90 + notesDone / notesTotal × 10`
- 90/10 の配分は実測から: 175MB の取り込みでバイト受信 + 添付保存が
  支配的で、ノート反映は数秒。**配分が実態とずれても進捗が後戻りしない**
  ことのほうが大事なので、段の境界で必ず 90 を跨ぐ単調な定義にする

### 残り時間 (秒) の推定

- クライアント側で計算する (サーバは生の数字だけ返す。表示の滑らかさは
  表示側の問題)
- 直近数サンプル (ポーリング間隔 500ms × 5 回程度) の移動平均で速度を
  出し、`残り = (100 - %) / 速度`。開始直後 (サンプル 2 個未満 or 2 秒
  未満) は数字を出さない — 初速で計算した「残り 4000 秒」が一瞬見える
  ほうが、数字が無いより悪い
- 表示は「約 n 秒」。90 秒を超えるときだけ「約 n 分」に畳む

### UI (NotesImporter)

- 「取り込み中…」の行をプログレスバー + `n% ・ 残り約 n 秒` に置き換える
- phase = `notes` の間は補足として「ノートを反映しています (n/m)」
- ポーリングは fetch の応答が返った時点で止める。進捗 GET の失敗は
  **表示を止めるだけ**で取り込み自体には影響させない (本体の fetch が正)

### 見送り (YAGNI)

- **SSE / WebSocket でのプッシュ** … ポーリング 500ms で十分滑らか。
  接続管理の複雑さに見合わない
- **ENEX の変換中の %** … ENEX は全文を読んでから木にする (§4) ので
  バイト % が受信で止まる。ノート反映のループにだけ同じ onProgress を
  足し、変換中はスピナーのままにする
- **複数同時取り込みの進捗** … 単一スロット + 409 で始める

- **世代 (token) を持たせた**。解放後に古い取っ手が触っても、次の取り込みの
  進捗を汚さない
- **取り残しは覗いたときに片付ける** (30 分)。応答が返る前に画面を閉じられる
  などでスロットが解放されないまま残ると、**次の取り込みが永久に始められなく
  なる**ほうが困る
- **`done` は次の取り込みを止めない**。応答が届くまでの一瞬だけ 100% を
  見せるために残してあるだけの控えなので、次を断る理由にならない
- **見送ったノートも「1 件進んだ」に数える**。分母が読んだファイル数なので、
  数えないと最後まで到達しない (`finally` で呼ぶ)
- **残り秒は移動平均を持たない**。表示は 500ms ごとに更新されるので、経過に
  対する平均速度がそのまま滑らかな見積もりになる。瞬間速度で出すと添付 1 件の
  保存のたびに数字が跳ねる
- **進捗の口は proxy を通してよい**。本文をメモリへ複製する問題 (§3) は本文を
  持つ要求の話で、GET は無関係。`/api/import` の matcher 除外は `$` で
  終端を固定してあるので、`/api/import/progress` はそのまま門番を通る
- 進捗の GET は **DB に触らない**。500ms ごとに叩かれるので、触ると
  ポーリングがそのまま負荷になる

実測 (ローカル、175MB・ノート 589 件の取り込み):

```text
receiving read=43224240 total=183446815 notes=0/0     ← 受信中 (21%)
notes     read=183446815 total=183446815 notes=0/589   ← 90%
notes     read=183446815 total=183446815 notes=556/589 ← 99%
```

ローカルは受信が一瞬で終わるためノート反映が目立つが、実際の回線では受信が
支配的になる (だから 90/10 の配分)。
