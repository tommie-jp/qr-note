# 回路図表示待ち計画

回路図 (` ```circuitikz `。[docs/07](./07-回路図計画.md)) を含むノートを
**初めて開いたときの数秒間、ノートが真っ白になる**のを直す。

## 0. 何が困っているか

利用者の報告:

> ノートを初めて表示するとき、数秒時間がかかる。その間、ノート部分が
> 真っ白なので不安になる。回路図があると最初の表示に時間がかかるようだ。

原因は 2 つあり、どちらも「待たせている」のではなく**待たせ方**の問題だった。

### 0-1. ノート全体が図 1 枚を待っていた

`ItemView` は本文を描く前に描画の完了を待っていた。

```tsx
const [circuits, ...] = await Promise.all([renderCircuits(memo), ...])
```

`circuitikz` は TeX (WASM) を子プロセスで走らせる。この await が解けるまで
**見出しもタグも問題文も 1 文字も出せない**。図と関係のない本文まで、図の
描画時間ぶん止まっていた。

計測 (ローカル・キャッシュミス。`/item/1085`):

| | 本文が出るまで | 図が出るまで |
| --- | --- | --- |
| 改善前 (await) | **+1504ms** | +1504ms |
| 改善後 (planCircuits) | **+310ms** | +1507ms |

本番 (vps2) はもっと遅い。3 コア・空きメモリ 750MB・スワップ 470MB 使用の
箱で、描画のピーク RSS は約 400MB — 報告の「数秒」はここで伸びた分。

### 0-2. 待っている間に出ていたのが「白い箱」だった

`loading.tsx` の骨組みは `SkeletonBox`、その実体は
`bg-white` + 薄いグレーの枠 + `animate-pulse`。**白い紙の上で白い箱の
不透明度が点滅している**だけなので、見た目は本当に「真っ白」になる。
報告の言葉がそのまま実装の説明になっていた。

## 1. 方針

**描画は速くしない。待たせ方と、待つ回数を変える。**

常駐ワーカー化 (`load()` の 409ms + `require` の 232ms を使い回す) や並列描画は
採らない。1 描画のピークが約 400MB で、本番の空きが 750MB しかない。
2 本走らせればスワップに落ち、速くするつもりが遅くなる。

代わりに:

1. **本文を止めない** — 図の場所だけを Suspense で待たせる (§3)
2. **待つ回数を減らす** — 保存した時点で描いておく (§4)
3. **待っていると判るようにする** — 白い箱に言葉を入れる (§5)
4. **二重に描かない** — 同時要求の相乗り (§4) と、鍵の揺れの解消 (§6)

## 2. 型: 「描画中」を持てるようにする

```ts
export type CircuitResult = { svg: string } | { error: string; texLog: string }
export type PendingCircuit = CircuitResult | Promise<CircuitResult>

export type CircuitMap = ReadonlyMap<string, CircuitResult>        // 従来
export type PendingCircuitMap = ReadonlyMap<string, PendingCircuit> // 閲覧画面
```

`CircuitMap` は `PendingCircuitMap` に代入できるので、**描き終わった結果しか
持たない画面は今までどおり** — オフライン (`OfflineNote`)・一覧サムネ
(`circuitThumbs`) は 1 行も変えていない。

## 3. 待つのは図の場所だけ (planCircuits)

`planCircuits(markdown)` … 描画を**始めるだけ**始めて、図ごとの約束を
同期に返す。`ItemView` / `PublicItemView` はこれを使う。

```tsx
const circuits = planCircuits(memo);   // await しない
```

`CircuitDiagram` が約束を受け取り、自分の中の `<Suspense>` で待つ。
`use()` を呼ぶので `"use client"` が要る (オフラインの画面は描画済みの結果を
同期で渡すため、そちらは待たずにそのまま出る)。

React は場所取りを流す前に少しだけ待つので、**キャッシュヒット (16ms) の図で
「準備中」がちらつくことはない** — 実測でも本文と図が同じ +220ms で届く。

`renderCircuits` (待つほう) は残す。待ってよい場所だけが使う:

- オフライン持ち出し … 圏外では描けないので先に済ませる
- 保存後の先読み (§4)
- `scripts/backfillCircuits.ts`

**画面を描く経路からは呼ばない。**

## 4. 待つ回数を減らす — 保存した時点で描く

`updateMemoAction` / `updateItemAction` が `after()` で
`renderCircuits(memo)` を仕込む。図を書いた本人がいちばん先にそのノートを
開くので、待ちはそこに出る。`after()` なので保存の応答は待たせない
(redirect の後でも走る)。

このとき、先読みと**その直後に開かれた閲覧画面**が同じ図を要求する。
DB キャッシュは描き終わってから書かれるので、素通しだと両方がキャッシュミスと
判断して 2 度描く (描画は直列なので待ち時間も倍)。`getOrRenderCircuit` が
進行中の描画を `hash → 約束` で覚え、後から来たほうは相乗りする。

失敗しても保存は成功のまま。図はキャッシュ (派生データ) でしかなく、TeX の
書き間違いで本文が保存できなくなるほうがずっと困る。

## 5. 「準備中」と言う

- 図の場所 … `回路図を準備中…` (破線の枠 + `min-h-28`)。
  高さを持たせるのは、潰れた枠から図に差し替わると下の行が飛ぶため
- `loading.tsx` の本文枠 … `ノートを読み込み中…`

「読み込み中」ではなく「準備中」にしたのは、待たせているのが通信ではなく
サーバー側の描画だから (電波を疑わせない)。

## 6. 鍵の揺れ — 同じ図が 2 度描かれていた

`circuit_svgs` に**同じ図が 2 行**入っていた。SVG は md5 まで一致していた。

同じソースが経路によって別の綴りで届いていた:

- 閲覧 … DB の本文そのまま。取り込んだファイルが CRLF ならそのまま残る
- 編集のライブプレビュー … CodeMirror が読み書きする時点で LF に揃う

TeX の出力は改行コードに依らないのに、鍵が分かれて**いちばん高い処理を丸ごと
二重に払っていた**。`circuitHash` が混ぜる前に `\r\n?` → `\n` に揃える。

実測: 編集画面のライブプレビュー要求が 1226ms (描画) → 12ms (キャッシュヒット)。

`RENDERER_VERSION` は上げない (出力は変わらない)。LF のノートの鍵はそのまま、
CRLF のノートだけが 1 回描き直しになる。

## 7. やらなかったこと

- **常駐ワーカー** … 2 枚目以降が 1130ms → 420ms になるが、約 430MB を
  抱えたままになる。本番の空きが 750MB では採れない (§1)
- **並列描画** … 同上。`renderCircuit` の直列キューは残す
- **1 ノートの複数枚を 1 プロセスで描く** … 固定費 (require 232ms +
  load 409ms) を 2 枚目以降で浮かせられるが、実データは 11 件中 10 件が
  1 枚。効く相手が居ない

## 8. 既存ノートの埋め方

保存時の先読み (§4) はこれから書くノートにしか効かない。**既に本番に居る
ノートは `./doBackfillCircuits.sh` で一度埋める** (冪等。描画済みは飛ばす)。
CRLF のノートは §6 で鍵が変わっているので、ここで新しい鍵の行が入る。
