# 健康管理フェンス計画

体重・体温のような**日々の数値**をノートに書き溜め、
` ```health ` フェンスでその場でグラフにする。

きっかけは iPhone アプリ「BPNote」(血圧・体重・体温・服薬を毎日入力し、
グラフ・分布図・レポートで見返す) を QRNote でやりたい、という要望。
一般化すると「専用の入力画面 → データをノートへ保存 → 表やグラフで見る」で、
Excel / Access に近い使い方になる。

## 0. 3 つのうち、新しいのは 1 つだけ

要望は 3 段に分かれるが、このアプリには既に 2 段ぶんの前例がある。

| | やること | 前例 |
| --- | --- | --- |
| 1 | 専用の入力画面 | チェックの ON/OFF (docs/55) |
| 2 | 入力をノートへ保存 | 同上 (本文の 1 行を書き換える) |
| 3 | ノートを元に表・グラフ | 進捗マトリックス (docs/77) |

**新しいのは「数値を折れ線で描く」ことだけ。**
だから設計の大半は [docs/77](./77-進捗マトリックス計画.md) の写しになり、
違いは「チェックの有無を表に畳む」が「数値を折れ線に畳む」へ変わる点に集まる。

## 1. 正本はノート本文 — 新しいテーブルを作らない

体重テーブルを足す案は採らない。docs/77 §1 と同じ理由で、
**正本はメモ本文**にする。

- 記録は本文の 1 行。手で直せる・git 履歴 (docs/57) に残る・
  検索に当たる・QR を貼れる・オフラインに持てる。
- 新しいテーブルはそのどれも持たず、代わりに移行・バックアップ・
  エクスポートの経路をもう 1 本ずつ増やす。

## 2. 1 ノート = 1 か月ぶん

1 日 1 ノートは煩わしい (要望どおり)。かといって全期間 1 枚だと、
数年後に 1000 行のノートを iPhone で編集することになる。

**1 か月 1 ノート**を既定の運用にする。1 年 1 枚 (365 行) でも動くが、
勧めない — グラフは複数ノートを横断して集めるので、
ノートを細かく割っても表示は連続する。**分けても損をしない**のが要点。

```text
# 健康管理 2026-08

#健康管理

- 2026-08-13 体重=66.8
- 2026-08-14 体重=66.4 体温=36.5
```

## 3. データ行 — 「日付で始まる行」だけを読む

````text
- 2026-08-14 体重=66.4 体温=36.5
````

- **行頭 (箇条書き記号があればその後) が ISO の日付**の行だけをデータ行と
  みなす。日付の後ろに続く `キー=値` を測定値として読む。
- 箇条書き記号 (`-` / `*` / `+`) は任意。付けたほうが本文として読みやすい。
- 値は数値 + 任意の単位 (`66.4` / `66.4kg`)。数値として読めない値は
  **その項目だけ**捨てる (同じ行の他の項目は生きる)。

### `キー=値` にする理由

プロパティ (`hFE=195`。[docs/08](./08-プロパティ計画.md)) と
` ```matrix ` の設定行に続く 3 つ目の `キー=値` になる。同じアプリの中で
3 通りの書き方を覚えさせない。引用符を使わないのも docs/77 §3 と同じ
(iPhone で打つ記法に `"` を混ぜない)。

**項目名は日本語のまま**にする。プロパティのキーは「英字始まり」という
規則があり (props.ts の `KEY_PATTERN`)、`体重` はそこに当たらない。
つまり日本語の項目名を使うかぎり、日々の記録がプロパティの列として
特性表に流れ込むことはない。**衝突を避けるための規則ではなく、
既にある規則の副産物**として住み分けが成立している。

なお `- 2026-08-14 体重=66.4` は日付トークンが `キー=値` ではないため、
そもそも「行全体が `キー=値`」というプロパティ行の条件を満たさない。
英語の項目名 (`weight=66.4`) を書いても props には落ちない。

### 日付は ISO 固定

`8/14` や `2026年8月14日` は受けない。

- 年をまたいだ並べ替え・重複判定・期間の切り出しが、文字列比較のままで済む。
- 表示のときだけ `8/14` に畳めばよい (逆は情報が足りず復元できない)。
- タイムスタンプの表示が既に JST 固定の `YYYY-MM-DD` (datetime.ts) で、
  同じ形をもう 1 つ増やさない。

### 同じ日付が 2 回出てきたら

**後に読んだほうを採る。** 読む順は「検索結果の並び → 本文の行順」で
決まるので結果は毎回同じになる。エラーにはしない —
書き直しの途中で一時的に 2 行になるのは普通のことで、
そのたびにグラフがエラーカードに化けるほうが困る。

**書く側も同じ「後勝ち」に揃える。** 記録欄が 1 行の中の同じ項目を
差し替えるとき、前のほうを直すと、保存は成功しているのにグラフの値が
動かない (何度押しても直らない) 形になる。

残る食い違いが 1 つある。**同じ日付を 2 つのノートに書いた**とき、
グラフは番号の大きいノートの値を出すが、記録欄が書き換えるのは
フェンスのあるノートのほう。月替わりで両方のノートに同じ日を書くと起きる。
記録欄が別のノートへ書きに行く作りにはしない — 「どこに書かれるか」が
画面を見れば判る、という §7 の約束のほうを優先する。

### コードの中かどうかはパーサに聞く

記号を自分で数える走査は、番号付きリストの中のフェンス (CommonMark では
4 字下げが正しい書き方) を見落とす。見落とすと**記法の説明を書いたノートの
用例が記録として読まれ**、しかも記録欄がその説明文の数字を書き換えてしまう
(書く側も同じ関数で行を探すため)。`taskCheckbox.ts` が「パーサに聞いてから
正規表現で置換する」のと同じ作法にする。

## 4. フェンス — 1 行目は検索式、以降は `キー=値`

````text
```health
#健康管理
```
````

docs/77 §3 と**同じ文法**。1 行目は検索式 (検索窓にそのまま貼れる形)、
2 行目以降が設定。設定はどれも省ける。

````text
```health
#健康管理
y=体重
days=90
```
````

| キー | 意味 | 既定 |
| --- | --- | --- |
| `y` | 縦軸にする項目 | 記録がいちばん多い項目 |
| `days` | 何日ぶん遡るか (1〜400) | 30 |

### なぜ `項目=` `期間=` ではないか

日本語のキーを最初に検討したが、`matrix` の `col=学習済み` が既に
**英語のキー + 日本語の値**という形をしている。同じ見た目の記法で
キーの言語だけ違うと、どちらだったか毎回思い出すことになる。

`y=` にしたのは「縦軸」そのものだから。横軸は日付で固定なので `x=` は要らず、
`col=` (列) はグラフには合わない言葉になる。

### なぜ `1ヶ月` ではなく `days=30` か

`1ヶ月` / `3ヶ月` / `1年` という語彙を作ると、「`半年` は?」「`2週間` は?」と
必ず増える。日数なら語彙が要らず、`days=90` も `days=400` も同じ規則で書ける。
`ヶ` は iPhone で打ちにくい文字でもある。

### 期間の起点は「いちばん新しい記録」

「今日から遡って 30 日」にはしない。**最新の記録日から遡る**。

- サーバの時刻・タイムゾーンに依存しない (集計が純関数のままでいられ、
  テストに「今日」が現れない)。
- 記録を 1 週間さぼってもグラフが痩せていかない。
  毎日書いている人にとっては「今日から」と同じ意味になる。

## 5. 実装 — matrix の双子

| | matrix | health |
| --- | --- | --- |
| フェンスの取り出し | `matrixData.ts` の中 | `healthFences.ts` |
| フェンスの解析 | `matrixFence.ts` | `healthFence.ts` |
| 本文 → 記録 (純関数) | `taskCheckbox.ts` | `healthRecords.ts` |
| 記録 → 描くもの (純関数) | `matrixTable.ts` | `healthSeries.ts` |
| DB から集める | `searchItemChecks` | `searchItemHealth` |
| 事前計算 (要ログイン) | `matrixData.ts` | `healthData.ts` |
| 描画 | `matrix/MatrixTable.tsx` | `health/HealthChart.tsx` |
| 本文への書き込み | `taskCheckbox.ts` | `healthEdit.ts` |

フェンスの取り出しだけ matrix と置き場が違う。あちらは集計 (DB を持つ側) と
同じファイルにあるが、**取り出した文字列がそのまま集計結果の鍵**になり、
描く側は `readFence` が読んだ中身で引く — その一致が壊れるとグラフは静かに
コードブロックへ落ちる。試したいのはそこであって DB ではないので、
`circuitFences.ts` と同じく DB を持たない葉モジュールに置く。

`ItemView` が `Promise.all` の中で `buildHealthCharts(memo)` を呼び、
`MarkdownView` の `preOrDiagram` が言語で振り分ける。
どちらも既にある口に 1 行ずつ足すだけで済む。

上限も揃える。

- 1 ノートに置けるグラフ … 4 枚 (`MAX_HEALTH_CHARTS_PER_MEMO`)。
  **接続プールは進捗の表と分け合う** — `ItemView` は同じ `Promise.all` で
  両方を集計するので、表の枚数と足した数が同時に飛びうるクエリ数になる
- 集める対象ノート … 200 件 (`HEALTH_ROW_LIMIT`)。溢れたら件数を出す
- `days` … 400 日。1 日 1 点なので、点の数も自然に 400 で頭打ちになる

### 絞り込みは「チェックを持つ」に当たるものを持たない

matrix は SQL 側で `HAS_TASKS` を掛けられた (チェックの数が列にある)。
健康の記録にはそういう派生列が無いので、**検索式で絞るしかない**。
既定の検索式が空だと全ノートの本文を舐めることになるため、
`#健康管理` のようなタグを書くのが実質必須になる。
0 件のときは「その検索に当たる記録がありません」と検索式を添えて言う
(docs/77 の空表示と同じ作法)。

## 6. グラフはライブラリを足さず SVG で描く

recharts / chart.js は入れない。

- 依存が 1 つ増えるコストに対して、要るのは**折れ線 1 本と軸**だけ。
- 体重のグラフは**縦軸を 0 から始めてはいけない** (66kg と 65kg の差が
  見えなくなる)。既製品の既定と戦うより、範囲を自分で決めるほうが短い。
- サーバで描ける (状態を持たない) ので、`MatrixTable` と同じく
  `"use client"` が要らず、オフラインの閲覧からも同じ形で出せる。

決めごと。

- 縦軸はデータの範囲 + 上下 5% の余白。目盛りは 1 / 2 / 2.5 / 5 × 10ⁿ から
  選んで 3〜5 本。
- 横軸のラベルは `M/D` を数個 (両端と中間)。
- **7 日以上空いた区間は線を切る**。点だけ残す。2 週間の空白を直線で
  結ぶと、測っていない期間を測ったように見せてしまう。
- 単位は最初に見つかった非空のものを軸に添える (`66.4kg` の `kg`)。

## 7. 入力欄はフェンスの中に置く

BPNote の入力画面に当たるものを、**グラフの上**に置く。

`/health` のような専用ページは作らない (docs/77 §2 と同じ理由。
専用ページはタイトルも `#タグ` も持てず、URL を書き留める先が結局ノートになる)。

### 書き込み先は「そのフェンスがあるノート」

当月ノートを探して無ければ作る、という仕掛けは持たない。
**フェンスを書いたノートの本文に追記する。**

- 月が替わったら新しいノートを作ってフェンスを貼る。フェンスの検索式は
  `#健康管理` なので、**グラフは過去の月のノートも一緒に集める** —
  入力先が今月のノートだけでも、線は途切れずに続く。
- 「どこに書かれるか」が画面を見れば判る。自動で別のノートへ書く仕掛けは、
  書かれた先を開くまで結果が確かめられない。

### 同じ日の行を壊さない

保存は純関数 `recordMeasurement(memo, date, item, value)` が本文を返す。

1. その日付のデータ行があれば、**その項目のトークンだけ**を差し替える。
   無ければ行末にトークンを足す。
   `- 2026-08-14 体重=66.4 体温=36.5` の体温を直しても体重は残る。
2. その日付の行が無ければ、**最後のデータ行の直後**に 1 行入れる。
   データ行が 1 つも無ければ本文の末尾。

Server Action は `toggleMemoTaskAction` と同じ作法にする —
`itemNo` を bind した関数を `ItemView` から渡し (`MarkdownView` に
「どのノートか」を持ち込まない)、`requireUser()` を通し、
保存後に `revalidatePath` する。

### 日付の既定は JST の「今日」

`<input type="date">` の既定値は、**サーバが JST で数えた今日**をそのまま
props で渡す (`formatJstDate`)。日付はいつでも手で直せる。

当初はクライアントの現在日を使う設計にしたが、記録欄の中で現在時刻を読むと
サーバが描いた HTML と食い違い、hydration が壊れる。effect で入れ直す手は
React コンパイラの規則 (`react-hooks/set-state-in-effect`) に当たる。
タイムスタンプの表示が既に JST 固定 ([datetime.ts](../src/lib/datetime.ts))
なので、揃えたほうが説明も短い — サーバの TZ 設定にも依らない。

## 8. 見せない場所

- **公開ビュー (`PublicItemView`) には渡さない。** 健康の数値はノート 1 枚の
  外から集まるので、docs/77 §6 と同じ危険がある。渡し忘れても漏れないよう、
  `buildHealthCharts` 自身が `requireUser()` を通す。
- **ライブプレビュー (CodeMirror) では描かない。** docs/77 §13 と同じ判断で、
  集計のための口をエディタ側に開けない。

## 9. 複合値 (血圧) — 1 つの項目が複数の線になる

Phase 3。BPNote の主役は血圧で、これは `118/76` と**対で書く値**。
Phase 1 では「数値 1 つに畳めない値」として捨てていた。

````text
- 2026-08-14 血圧=118/76mmHg 脈拍=62
````

### `/` 区切りを 1 つの項目として読む

`血圧` を `収縮期` と `拡張期` の 2 項目に分けて書かせる案は採らない。
測るのは 1 回で、手で書くのも読むのも 1 つの値だからで、
これは BPNote の入力欄が 1 行に `／` で並べているのと同じ形。

- 値は `/` で区切った**数値の並び** (3 つまで)。単位は末尾に 1 つ
  (`118/76mmHg`)。
- 区切りの数がその項目の**線の数**になる。日によって書き方が違えば
  (ある日は `118/76`、別の日は `118` だけ)、足りない線はそこで切れる。
- 全角の `／` も NFKC で `/` に畳んで受ける。

### 線の呼び名は持たない

`収縮期` / `拡張期` のような名前をアプリが持つと、血圧だけを知っている
アプリになる。**呼び名は付けず、色と並び順で見分ける** — 上の線が 1 つ目
(血圧なら上の値) というのは書いた順そのままで、説明が要らない。
見出しには `最新 118/76mmHg` と**書いたままの形**で出す。

読み上げには順番を入れる (「1 本目 最小 …、2 本目 最小 …」)。
グラフは目で見る物なので、色と並びは音にならない。

### 真偽値 (服薬) は数値で書く

`服薬=1` / `服薬=0` と書けば、そのまま 0 と 1 の線になる。
専用の記法もトグルも作らない — 記録欄は数値を受けるので、`1` と打てば済む。
チェックとして扱いたいなら本文のタスクリスト (docs/55) が既にある。

### 分布図・レポートは作らない

BPNote の下段タブ (分布図・レポート) に当たるものは持たない。
散布図は「2 つの項目の関係」を見る道具で、**軸が日付でなくなる** —
同じフェンスの上には乗らない。要るようになったら別の記法として設計する。

## 10. 段取り

1. **Phase 1 (読み取り)** … 記法・パーサ・グラフ。入力は普通の編集画面で手打ち。
   書き込む経路が無いので危険が小さく、記法の使い勝手を実データで確かめられる。
2. **Phase 2 (入力)** … フェンス内の記録欄と Server Action。
3. **Phase 3 (複合値)** … §9。血圧のような対の値を複数の線として描き、
   記録欄も `/` で区切って入れられるようにする。

## 11. やらないこと

- 専用ページ `/health` (docs/77 §13 の `/progress` と同じ理由)
- 集計結果やグラフの画像を本文へ焼き込むこと (正本が 2 つになる)
- ライブプレビューでのグラフ描画
- 汎用の「なんでも入力フォーム + なんでもグラフ」フェンス。
  Excel 化は魅力的に見えるが、matrix (学習) → health (健康) のように
  **用途ごとに小さいフェンスを足す**ほうが、記法も安全規則も短く保てる
