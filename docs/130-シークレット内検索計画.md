# 130. シークレット内検索計画

<!-- markdownlint-disable MD013 -->

シークレット断片 (docs/51) の中身も検索できるようにする。検索欄にトグルを足し、ON の間だけ
断片の中身を対象に含める。鍵はサーバに渡さず、**解錠した端末の中で復号して探す**。
docs/51 §14 が「別計画」として残していた「クライアント復号総なめ」にあたる。

## 0. 現状 (2026-11-20)

未着手。この文書は計画だけ。

- 断片の中身は全文検索に掛からない。掛かるのは本文に残るラベルだけ (docs/51 §3)
- サーバが持つのは暗号文だけ。マスターキー (MK) はパスキーの PRF か復旧キーからしか得られず、
  解錠中もタブのメモリにしか無い (`src/lib/secret/session.ts`)
- 解錠は無操作 5 分・タブを隠して 1 分・頁を離れたときに自動で外れる (同上、監査 M-7)
- `Secret` の行は `name`・`mime`・`data`・`createdAt` だけ。**どのノートの断片かを持たない**。
  対応は本文の `![ラベル](/api/secrets/<UUID>)` からしか分からない (`allSecretNames()`)
- 更新日時も持たない。編集は同じ名前への上書き (`PUT /api/secrets/[name]`)
- 本番の断片の件数と合計の大きさは未計測 (§9 の最初の作業)

関連: [51-部分暗号化計画.md](./51-部分暗号化計画.md)・
[65-オフライン対応計画.md](./65-オフライン対応計画.md)・
[129-検索一覧の枠先出しと控え計画.md](./129-検索一覧の枠先出しと控え計画.md)

## 1. 目的と守る線

**やりたいこと**: 「あの口座番号はどのノートだったか」を、ラベルを覚えていなくても探せるようにする。

**守る線** (docs/51 §1 の脅威モデルを 1 歩も下げない):

| 守ること | この計画での扱い |
| --- | --- |
| サーバは断片の平文を知らない | 復号も照合も端末の中だけ。サーバには鍵も平文も索引も渡さない |
| 解錠しなければ読めない | トグル ON = 既存の解錠。鍵が無ければ原理的に探せない |
| 平文を端末に残さない | 復号した文字列はタブのメモリだけ。施錠で捨てる |
| 派生物をサーバに置かない (docs/51 §5) | 語の索引・一致の抜粋・一致した断片の名前を送らない |

「パスコードを検証して検索を許可する」形にはしない。サーバが許可を判定する方式は、
サーバが平文か鍵を持つことを前提にするため。ここでは許可の判定そのものが要らない。

## 2. 方式の比較

| 案 | 中身 | 判断 |
| --- | --- | --- |
| A. 端末で総なめ | 暗号文をまとめて取り、端末で復号して部分一致 | **採る** |
| B. ブラインド索引 | 語や n-gram の HMAC をサーバに置いて照合 | 採らない。出現頻度と共起が漏れる。日本語の n-gram で索引が膨らむ。断片の編集のたびに作り直し |
| C. サーバで復号 | 解錠した鍵をサーバへ送って検索 | 採らない。§1 の線を破る |

A で足りる根拠は速度。AES-GCM の復号は 7KB で 0.09ms・1MB で 0.6ms
(41-QR-search/docs/25 の実測)。テキスト断片が 1000 件あっても復号は 0.1 秒台で終わる。
効いてくるのは通信なので、暗号文を端末に控えて差分だけ取る (§5)。

## 3. 画面

### 3-1. トグル

| 項目 | 決めたこと |
| --- | --- |
| 置き場 | 検索欄の道具の並び (`SearchTools.tsx`)。🔒 の釦 |
| 出す条件 | 鍵束を設定済みのときだけ。デモでは出さない (docs/51 §10) |
| ON にする | 未解錠なら既存の解錠 (`unlockWithPasskey`) を走らせる。失敗・取り消しなら OFF のまま |
| OFF にする | 復号済みの文字列を捨てる。施錠はしない (開いているノートの断片を閉じないため) |
| 自動施錠 | 施錠の通知 (`subscribeSecretLock`) で OFF に戻し、復号済みの文字列と一致の節を消す |
| 状態の保存 | **しない**。再読み込みの後は OFF。勝手に Face ID を出さない |

### 3-2. 結果の出し方

通常の結果には混ぜず、一覧の先頭に別の節として出す。

```text
🔒 シークレット内の一致 3 件
  ├ ノートの題名 A   (ラベル: 〇〇銀行)
  ├ ノートの題名 B   (ラベル: シークレット)
  └ ノートの題名 C   (ラベル: Wi-Fi)
── 通常の検索結果 ──
  …
```

- 混ぜない理由: 通常の結果は並び順・件数・無限スクロールがサーバ側にある (docs/129)。
  混ぜると枠の先出し・前後ナビ・一括選択・画像ビューアを全部直すことになる
- 行に出すのは題名とラベルだけ。**一致箇所の抜粋は出さない** (肩越しに読まれる。
  中身は行を押してノートを開き、断片を開いて読む)
- 行を押したらノートを開く。断片は自動では開かない (v1)
- 同じノートが通常の結果にも出ることがある。重複は消さない (節が違うので迷わない)

## 4. 照合の決まり

| 項目 | 決めたこと |
| --- | --- |
| 対象 | `mime` が `text/markdown` の断片だけ。画像・録音・録画は対象外 |
| 入れ子 | 断片内の画像 (別の Secret 行) は対象外。断片本文に書かれた alt は本文として掛かる |
| 語の扱い | 空白区切りの語をすべて含む (AND)。大文字小文字と全角半角は `src/lib/offline/filter.ts` の正規化に揃える |
| AND の範囲 | **1 つの断片の中**で全語が揃うこと。「語 A は平文・語 B は断片の中」は v1 では一致にしない |
| 演算子 | `tag:`・`is:`・フォルダーなどは断片の照合では無視し、素の語だけを見る。絞りとの組み合わせは v2 (§10) |
| 孤児 | どのノートからも参照されていない断片 (GC 待ち。docs/51 §11) は結果に出さない |

照合の関数は純関数にして `src/lib/secret/search.ts` に置く。入力は「名前 → 復号済みの文字列」と
検索語、出力は一致した名前の配列。

## 5. データの流れ

```text
トグル ON
  → 解錠 (Face ID)
  → GET /api/secrets/index        名前・mime・暗号文のハッシュ・参照元ノート (全件・検索語に無関係)
  → 端末の控えと比べ、無い分・変わった分だけ暗号文を取る
  → 復号してメモリに持つ (名前 → 文字列)
検索語を打つたび
  → メモリの文字列を照合 (通信なし)
  → 一致した名前 → 参照元ノート → 節に出す
```

### 5-1. 足す API

| 口 | 返すもの |
| --- | --- |
| `GET /api/secrets/index` | テキスト断片の一覧。`name`・`sha256(data)`・`bytes`・参照元ノートの `id` と題名 |
| `POST /api/secrets/batch` | 名前の配列を受け、暗号文をまとめて返す (1 回の上限は件数と合計バイトで切る) |

- どちらも門番は `guardSecretRequest`。`Cache-Control: no-store`
- **どちらも検索語を受け取らない**。全件の一覧と、端末に無い暗号文を返すだけなので、
  何を探しているかも、どれが一致したかもサーバには見えない
- ハッシュは Postgres の `sha256(data)` で都度計算する。封をし直すと IV が変わり暗号文が
  変わるので、更新の検知に使える。**列を足さないので migration は要らない**
  (`prisma migrate` が PGroonga 索引を落とす罠を踏まない)
- 参照元ノートは、本文から断片の名前を引いて作る (`allSecretNames()` と同じ規則)。
  件数が増えて遅くなったら、ノートの保存時に対応表を作る形へ移す (その時は migration)
- ゴミ箱のノートは参照元に含めない

### 5-2. 端末の控え

- 置くのは**暗号文だけ**。IndexedDB (`src/lib/offline/idb.ts`) に `name`・ハッシュ・暗号文
- 一覧に無くなった名前は控えから消す
- 鍵も平文も置かない。控えが漏れても、サーバの DB が漏れたのと同じ強さ
- オフラインの印 (docs/65 §10) の Cache Storage とは別に持つ (あちらは開く用で URL 単位)

### 5-3. メモリの文字列

- `src/lib/secret/searchIndex.ts` の module state に「名前 → 復号済みの文字列」を持つ
- 捨てる時: トグル OFF・施錠・pagehide
- 復号は `unlockedKey()` を通るので、無操作の数え直しが起きる。**照合では鍵に触れない**
  (検索語を打ち続けても自動施錠は延びない。5 分で施錠され、節が消える)。
  打っている最中に消えるのが不便なら、照合でも数え直す形に後から変える

## 6. 漏れる所と塞ぎ方

| 漏れる所 | 中身 | 手当て |
| --- | --- | --- |
| 検索語 | ON でも通常の検索は走るので、語は `/api/items?q=` でサーバに届く。nginx のログ・URL・検索履歴 (`SearchQuery`) に残る | ON の間は検索履歴に記録しない (`useSearchForm.ts` の記録を止める)。残りは v2 の「シークレットだけ」(§10) |
| 一致の節 | 題名とラベルが画面に出る | 抜粋を出さない (§3-2)。施錠で消す |
| 一覧の控え | docs/129 の控えは端末に残る | 一致の節は `listStore` に入れない。別の state に持ち、保存しない |
| RSC・サーバの記憶 | 一致の結果がサーバの応答に載る | 節はクライアントだけで組む。サーバへ一致の名前を送らない |
| 開いたノート | 一致の行を押すと、どのノートを開いたかはサーバに見える | 受け入れる。今もノートを開けば見える |
| 解錠の時間 | 検索のために解錠する機会が増え、XSS で鍵に届く時間が延びる (docs/51 §14) | 自動施錠はそのまま。CSP (docs/90・監査) も今のまま効く |

検索語がサーバに届く点は v1 の残りの穴になる。口座番号そのもので探すと、その番号がログに残る。
設定画面とトグルの説明に 1 行書く。

## 7. 性能の見込み

| 項目 | 見込み |
| --- | --- |
| 初回 | 一覧 1 回 + 暗号文のまとめ取り。テキスト断片は 1 件 数百 B〜数 KB の想定 |
| 2 回目以降 | 一覧 1 回 + 変わった分だけ |
| 復号 | 1 件 0.1ms 台。1000 件で 0.1〜0.3 秒 (iPhone は 2〜3 倍と見る) |
| 照合 | メモリの文字列の部分一致。打鍵ごとに走らせて問題ない大きさ |
| サーバ | `sha256(data)` と参照元の引き当てが全件に走る。件数が少ない前提。§9 の計測で確かめる |

上限を置く: テキスト断片の合計が 20MB を超えたら、超えた分は対象外にして節に「n 件は対象外」と出す
(数字は §9 の計測の後で決め直す)。

## 8. テスト

| 種類 | 見ること |
| --- | --- |
| 単体 | 照合 (AND・正規化・空の語)。控えの差分 (増えた・変わった・消えた)。施錠でメモリが空になる |
| API | 門番 (未ログイン・デモ・クロスサイト)。画像の断片が一覧に出ない。ゴミ箱と孤児が出ない。まとめ取りの上限 |
| E2E | 専用 DB と仮想認証器 (docs/96)。トグル ON → 解錠 → 断片の中の語で節に出る → 施錠で消える。再読み込みで OFF |
| 漏れの確認 | ON で検索した後、検索履歴に語が無い。`listStore` の控えに節の中身が無い。IndexedDB に平文が無い |

## 9. 作業の順

1. 本番のテキスト断片の件数と合計バイトを数える (§7 の上限と、参照元の引き当て方を決める材料)
2. 照合の純関数とテスト (`secret/search.ts`)
3. `GET /api/secrets/index`・`POST /api/secrets/batch` とテスト
4. 端末の控えと差分の取得
5. メモリの文字列と、施錠・OFF での破棄 (`secret/searchIndex.ts`)
6. トグルと一致の節。ON の間は検索履歴を止める
7. E2E と漏れの確認
8. docs/51 §14・メモ記法・設定画面の説明を直す

変更は鍵と断片の API に触れるので、コミット前に security-reviewer を通す。

## 10. v1 でやらないこと

| 項目 | 中身 |
| --- | --- |
| シークレットだけの検索 | 検索語をサーバへ送らず、断片だけを探すモード。§6 の検索語の穴を塞ぐ |
| 平文と断片をまたぐ AND | 通常の検索をノート単位で端末に持つ必要がある。オフラインの絞り込み (`offline/filter.ts`) が土台になる |
| タグ・フォルダー絞りとの組み合わせ | 参照元ノートの id をサーバへ渡して絞る。どれが一致したかがサーバに見えるので、送る前に判断が要る |
| 一致した断片を開いて強調 | ノートを開いた後、断片を自動で開き一致箇所へ送る |
| 画像の断片の OCR | 端末で OCR して照合。重いので別計画 |
| オフラインでの検索 | 控えの暗号文と鍵束の控え (`offline/keyring.ts`) で原理的には動く。一覧の控えが要る |

## 11. 決めていないこと

- トグルを ON にしたまま検索語を打ち続けたとき、自動施錠を延ばすか (§5-3)
- 上限の数字 (§7)。本番の件数を数えてから
- 一致の節を 1 ペイン・2 ペイン・3 ペイン (docs/86) のどこに出すか。v1 は一覧の器の先頭
