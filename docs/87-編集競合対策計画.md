# 編集競合対策計画

iPhone と Windows で**同じノートを同時に開いて編集**すると、後から保存した側が
相手の変更をまるごと消してしまう (lost update)。これを、複雑な同期なしで
「黙って消えない」ようにする。

> **改訂 2 (2026-08-22)** — 初版から次の 4 点を変えた。
>
> 1. 保存のたびの自動コミットをやめる。[docs/57](./57-ノートgit履歴計画.md) §8 が
>    「履歴のノイズになる」と退けていた。刻むのは**競合で上書きされる側だけ**。
> 2. 競合の知らせをリダイレクトではなく**その場** (`useActionState`) で出す。
>    本文がエディタから出ないので localStorage や 400ms の debounce に頼らない。
> 3. 基点 (版) を**本文と同じ瞬間の対**としてエディタが持つ。同じ画面の
>    チェック操作で本文が動いたとき、黙って戻さない。
> 4. 下書き (localStorage) に基点も入れる。復元した下書きが別端末の保存を
>    潰す経路を塞ぐ。
> 5. レビュー指摘を反映: 追随後の undo で基点だけ新しくなる穴 (§2-3)、
>    刻めなければ上書きしない (§4)、旧形式の下書きは必ず競合扱い (§2-6)、
>    版番号の強単調化 (§1-1)。
>
> **実装済み (2026-08-23)**。ローカルの実アプリで一通り確認した (§7 の手動項目)。
> 実装で判ったことは各節に「実装時の追記」として残す。

## 0. 何が困っているか

保存は本文まるごとの上書きで、勝敗は後勝ち。

- `/edit` の「更新」→ `updateItemAction` → `upsertItem` (memo / url / mode)
- `/item` 編集タブの「更新」→ `updateMemoAction` → `upsertMemo` (memo)

DB へは upsert 1 文なので**半端に混ざった本文はできない**。壊れ方は
「後から保存した側が、相手の保存をまるごと消す」の一種類だけ。

1. iPhone で `/edit/4518` を開く (画面の本文はこの時点のサーバ値)
2. Windows で同じノートを編集して保存
3. iPhone が保存 → 2 の内容が丸ごと消える

本当に痛いのは、**消えた版がどこにも残らない**こと。git 履歴
([docs/57](./57-ノートgit履歴計画.md)) はあるがコミットは手動なので、
上書きされた版はたいてい誰も持っていない。

同じ型の事故は 2 端末に限らない。

- **同じ画面の中**: `MemoPanel` は一度開いたタブを hidden で保持し、
  `MemoEditor` は本文を自分の state に持つ。編集タブを開いたあと markdown
  タブでチェックを押す (`toggleMemoTaskAction` → `revalidatePath`) と、
  画面は描き直されるがエディタの本文は古いまま。そこで「更新」を押すと
  チェックが黙って元に戻る。画像回転 (`router.refresh()`)・健康記録も同じ
  (`ZoomableImage.tsx` のコメントは「編集中の CodeMirror は refresh でも保持
  される」と保持を意図として書いており、古いままになる問題は未扱い)。
- **新規作成**: `/new` は `nextItemNo()` で採番して `/edit/<no>` へ飛ぶだけで
  行を予約しない。2 端末で続けて「+」を押すと同じ番号になり、後から保存した
  側が先のノートを丸ごと潰す。
- **1 行書き換え系**: `toggleMemoTaskAction` / `recordHealthAction` /
  `bulkTagAction` は「読む → 純関数 → 全文 upsert」で、読みと書きの間に
  別の書き込みが入るとそれを消す。窓は ms 単位だが同じ型。

### 0-1. ロック (悲観排他) にしない理由

デッドロックは実は起きない — 取り合う資源がノート 1 つなので循環待ちが
組めない。実際に起きるのは**自己ロックアウト**のほう。

- iPhone は編集画面のタブを OS が黙って落とす実績がある (OCR のモデル
  読み込みで WebKit がタブごと再起動する。[docs/24](./24-画像OCR計画.md) §9)。
  unlock が飛ばず、**自分のノートが自分に開けなくなる**。
- 直すには TTL + 強制解除 UI が要り、実装が楽観方式より重くなる。
- しかも TTL が切れた瞬間は無防備で、同じ lost update が起きる。
  つまり**ロックを入れても基点チェックは結局要る**。ロックは飾りになる。

単独ユーザーでほとんどの時間は競合しない。常時払うコスト (取得・解放・失効)
に見合わないので、「保存の瞬間に基点を検める」楽観方式にする。

## 1. 方針

三つの約束にまとめる。

| 約束 | 仕組み |
| --- | --- |
| 見ていない版を黙って上書きしない | 保存を「基点が同じなら書く」1 文の UPDATE にする (§2) |
| 競合しても本文は失わない | その場で知らせ、差分を見て選ばせる。エディタの中身は動かさない (§3) |
| 上書きを選んだ側の版は戻せる | 上書きの直前に、消える側を git に 1 版残す (§4) |

### 1-1. `updated_at` がそのまま版番号になっている

楽観ロックの版番号に **`updated_at` を流用**する。items テーブルの書き手を
全部洗うと、この列が動くのは本文系の書き込みだけ。

| 書き手 | updated_at |
| --- | --- |
| `upsertMemo` / `upsertItem` (prisma upsert) | 進む |
| `rewriteImageReference` (画像回転。本文の URL 書き換え) | 進む (本文が変わるので妥当) |
| `applyImportedTimestamps` (インポート。生 SQL) | ファイル由来の値を明示的に書く |
| 公開・オフライン印・アクセス日時・ゴミ箱 (生 SQL) | 触らない (コメントに明記) |
| `scripts/backfill*` (生 SQL)・`migrateFromVer1` | 派生列のみ / 一回限り |

列型は `TIMESTAMP(3)` (ミリ秒)、Prisma が書く値も JS の `Date` (ミリ秒) なので
`getTime()` の文字列で往復しても丸めは起きない。**生 SQL で
`updated_at = now()` と書く経路は作らない** — JS 側と DB 側の時計を混ぜない
(基点は JS 側で打った値と比べる)。なお `upsertMemo` / `upsertItem` は内容が
同じでも進む (二重保存・同内容の復元) — 保存側の `sameContent` が吸収する。

同一ミリ秒に 2 回書くと同じ値になりうる (ABA) ので、§2-4 の保存は
`updated_at` を**明示的に基点 + 1ms 以上**へ進める。これで版番号として
強単調になる。

`version Int` 列を足す案は採らない。migrate は PGroonga 索引を落とす
(過去に 1 度実際に失った) ので、列なしで済むなら済ませる。

### 1-2. 初版からの変更と理由

- **git へ刻むタイミング** — 初版は保存ごとに 2 本 (前・後)。改訂 2 は
  上書きを選んだときだけ 1 本。docs/57 §8 の却下事項であり、`after()` は
  redirect でも走って失敗が握られる。
- **競合の知らせ方** — 初版は `?conflict=` へ redirect + 下書き復元。改訂 2 は
  その場で戻り値。本文の置き場が localStorage だけになるのと、ItemView が
  3 箇所から描かれて配線が増えるのを避ける。
- **基点の置き場** — 初版は form の hidden (サーバ描画)。改訂 2 はエディタが
  本文と対で持つ。サーバ描画の hidden だけ新しくなると、古い本文が CAS を
  通ってしまう。
- **下書き** — 初版は本文だけ。改訂 2 は基点も入れる。タブ落ち → 他端末が
  保存 → 復元 → 更新、で潰す経路を塞ぐ。
- **toggle / health** — 初版は対象外。改訂 2 は同じ CAS + 再適用。同じ型なので
  道具が 1 つで済む。

## 2. 基点の往復と保存

### 2-1. 基点の形

純関数モジュール `src/lib/saveBase.ts` (DB 非依存、テスト容易性のため)。

```ts
export const BASE_NEW = 'new'
export type SaveBase =
  | { kind: 'new' }
  | { kind: 'at'; at: Date }
  | { kind: 'stale' } // 基点不明 (旧形式の下書き。§2-6)。必ず競合扱い
// null (行が無い) → 'new'、それ以外は String(updatedAt.getTime())
export function formatBase(updatedAt: Date | null): string
// 'new' / 'stale' / 数字列だけを受ける。欠落・空・その他は null (呼び手は投げる)。
// 数字は Number.isSafeInteger かつ 0 ≤ n ≤ 8.64e15 (Date の範囲) に限る —
// '1e400' や範囲外は Invalid Date になり、Prisma の引数検証で 500 になる
export function parseBase(raw: FormDataEntryValue | null): SaveBase | null
```

`'new'` は「まだ行が無い前提」、数字は「この `updated_at` の行が前提」。
不正は**閉じる側に倒す** (保存しない)。ISO 文字列や JST 表示は使わない —
パース差と丸めの温床。

### 2-2. 基点は本文と対でエディタが持つ

`MemoEditor` に `base: string` prop を足し、本文と同じように
`useState` で凍結して、hidden を**自分で 2 つ**描く。

```tsx
<input type="hidden" name="memo" value={value} />
<input type="hidden" name="base" value={base} />
```

form 側 (サーバ描画) の hidden に置いてはいけない。§0 の同一画面の罠で、
サーバ再描画のたびに hidden の基点だけ新しくなり、古い本文の保存が CAS を
**通ってしまう** — チェック戻しを正当化することになる。基点は本文と
同じ場所・同じ瞬間に凍結する。

### 2-3. サーバの (本文, 基点) が動いたときの追随規則

サーバ再描画で `defaultValue` / `base` が変わったとき、1 箇所で決める。

- **打っていない** (本文が最後に揃えたサーバ値のまま) → 本文・基点とも
  黙って追随する。失うものが無い。「編集タブを開いてから markdown タブで
  チェックを押す」という最頻の使い方がここに入る。
- **もう同じ** (本文が新しいサーバ値と一致。保存直後など) → 基点だけ追随。
- **打っている最中** → 本文・基点とも保持する。保存で CAS が負けて §3 の
  バナーになる。黙って戻らない。小さく「別の操作で本文が変わりました
  (保存時に確認します)」と出してもよい。

**追随・読み込みで本文を差し替えたら undo 履歴を切る。** 外から value を
差し替えると CodeMirror の履歴に 1 手として積まれる (`MemoEditor.tsx` の
CRLF の注記どおり) ので、差し替え直後に「元に戻す」(下部バーのボタンで
届く) を押すと**古い本文 + 新しい基点**の対ができ、CAS を素通りして黙って
上書きする (チェックポイントも打たれない)。`MemoEditorInner` に `key` を
付けて作り直すのが最短 (フォーカス・スクロールは飛ぶが稀な経路)。

規則 2 が効くのは toggle 等の**同一応答内の再描画**のとき。保存成功の
`redirect(savedHref)` では Next が部分木を作り直す (MemoPanel / MemoEditor は
再マウント = 現行挙動) ので、そこでは追随規則は関係ない。

下書き (`persistDraft` / `loadDraft`) の比較基準は「最後に揃えたサーバ値」に
差し替える (揃えた本文に戻せば下書きが消えるように)。
`UnsavedGuard` の基準も動くので、揃えた直後に form へ `CustomEvent`
(`qr:memo-baseline`) を投げて取り直させる (数行)。

### 2-4. 保存を条件付き UPDATE にする

`src/lib/items.ts` に保存関数を足す。読んで比べて書くのではなく、
**where に基点を入れた 1 文**にするのが要点 (検査と書き込みの間に隙間が無い)。

```ts
export type SaveOutcome =
  | { ok: true; item: Item }
  | { ok: false; reason: 'conflict' | 'exists'; current: Item }
  | { ok: false; reason: 'missing' }

export async function saveItemIfUnchanged(
  itemNo: string,
  data: { memo: string; url?: string; mode?: Mode },
  base: SaveBase,
): Promise<SaveOutcome> {
  const derived = derivedFromMemo(data.memo)
  if (base.kind === 'new') {
    await assertDemoItemQuota(itemNo) // 新規のときだけ効く門番 (今と同じ)
    try {
      const item = await prisma.item.create({
        data: { itemNo, itemNoNum: itemNoToNum(itemNo), ...data, ...derived },
      })
      return { ok: true, item }
    } catch (error) {
      if (isUniqueViolation(error)) { // P2002。secretStore.ts と同じ捕まえ方
        const current = await getItem(itemNo)
        if (current !== null) return { ok: false, reason: 'exists', current }
      }
      throw error
    }
  }
  if (base.kind === 'stale') {
    const current = await getItem(itemNo)
    return current === null
      ? { ok: false, reason: 'missing' }
      : { ok: false, reason: 'conflict', current }
  }
  const rows = await prisma.item.updateManyAndReturn({
    where: { itemNo, updatedAt: base.at },
    // 版番号を強単調に (同一 ms の ABA を断つ。@updatedAt の挙動にも頼らない)
    data: { ...data, ...derived, updatedAt: nextVersion(base.at) },
  })
  if (rows[0] !== undefined) return { ok: true, item: rows[0] }
  const current = await getItem(itemNo)
  if (current === null) return { ok: false, reason: 'missing' } // 永久削除
  if (sameContent(current, data)) return { ok: true, item: current } // 冪等
  return { ok: false, reason: 'conflict', current }
}
```

- `updateManyAndReturn` は生成済みクライアントにある (Prisma 7.9.1 /
  PostgreSQL)。`updated_at` は `@updatedAt` に任せず
  `nextVersion(prev) = new Date(Math.max(Date.now(), prev.getTime() + 1))` で
  明示的に打つ — 同一 ms に 2 回書いても版が重ならない (§1-1)。DB テストは
  「基点より進む」だけ見ればよい。
- `sameContent` は memo (と渡された url / mode) の一致。Ver1 由来の CRLF 本文は
  エディタが LF に正規化して送るので、比較は両側を `\r\n → \n` に揃える
  (「何も変えていないのに競合」を作らない)。二重送信・別タブが同じ内容を
  先に保存した場合は成功扱い (updated_at は動かさない)。
- `upsertMemo` / `upsertItem` は残す — インポート・履歴からの復元・テストが
  使う「明示的な上書き」の口。画面からの保存はもう呼ばない。

### 2-5. 1 行書き換え系も同じ道具で

チェック・健康記録・一括タグは「読む → 変換 → CAS、負けたら読み直して
再適用」にする。送ってくるのは**望む状態**なので再適用は安全
(`toggleMemoTaskAction` の約束そのもの)。

```ts
export async function modifyMemo(
  itemNo: string,
  transform: (memo: string) => string | null, // null = この本文には適用できない
  attempts = 3,
): Promise<'saved' | 'unchanged' | 'rejected' | 'missing'> {
  let first: string | null = null
  for (let i = 0; i < attempts; i++) {
    const item = await getItem(itemNo)
    if (item === null) return 'missing'
    first ??= item.memo
    // 再適用は「最初に読んだ本文との差がチェック印だけ」のときに限る。
    // 行が増減していれば行番号がずれ、別のタスク行を裏返しかねない
    if (i > 0 && !differsOnlyInTaskMarks(first, item.memo)) return 'rejected'
    const next = transform(item.memo)
    if (next === null) return 'rejected'
    if (next === item.memo) return 'unchanged'
    const rows = await prisma.item.updateManyAndReturn({
      where: { itemNo, updatedAt: item.updatedAt },
      data: {
        memo: next,
        ...derivedFromMemo(next),
        updatedAt: nextVersion(item.updatedAt),
      },
    })
    if (rows.length === 1) return 'saved'
  }
  throw new Error('本文の更新が競合しました。もう一度お試しください')
}
```

`'rejected'` は既存の「本文が変わっています。画面を更新してください」、
`'missing'` は「ノートが見つかりません」に対応させる。健康記録の長さ検査は
transform の中で投げる。`bulkTagAction` は itemNo ごとに呼び、`'missing'` は
飛ばす (今は行が無ければ作っていたが、検索結果由来なので実害なし)。
`differsOnlyInTaskMarks` はチェック印 (`[ ]` / `[x]`) を揃えたうえでの一致を
見る純関数 (`taskCheckbox.ts`)。

**実装時の追記**: この門番は `modifyMemo` に内蔵せず、`canRetry` として
**呼び手が渡す**形にした。行番号で対象を指すのはチェックの切り替えだけで、
健康記録と一括タグは本文で位置が決まる (何度当て直しても同じ場所に着く)。
内蔵すると、無関係な行が 1 行増えただけで健康記録が拒まれる。

`restoreNoteVersionAction` は `upsertMemo` のままだが、**復元の直前に §4 の
`checkpointBeforeOverwrite` を通す** — いま DB にある (未コミットかもしれない)
本文を失う操作だから。ZIP / ENEX の上書きインポートは件数が多いので刻まない
(§6)。

### 2-6. 下書きに基点も入れる

`MemoDraft` に `base?: string` を足す。`persistDraft` は本文と一緒に保存し、
`loadDraft` は `{ value, base }` を返し、`MemoEditor` は**対で**復元する。
基点を持たない旧形式の下書きは `'stale'` (§2-1) で復元する — 現在の基点を
当てると「古い本文 + 新しい基点」の対になり、塞ぎたい経路そのものになる。
`'stale'` の保存は必ず競合扱いで、バナーで差分を見てから決める (配備直後
だけの過渡)。

これをしないと、iPhone で下書き → タブが落ちる → Windows で保存 → iPhone が
再訪して下書きを復元 → 「更新」で、Windows の版を黙って潰す (復元した本文は
古いのに基点だけ新しい)。対で復元すれば CAS で止まり、§3 のバナーで
差分を見て決められる。`/item` 編集タブの `MemoEditor` にも `draftKey` を
付けてよい (基点が乗るので安全になった)。

## 3. 競合をその場で知らせる

### 3-1. form を `useActionState` で包む

Server Action の戻り値は `useActionState` で受ける (Next の forms.md
「Validation errors」の定石)。`revalidatePath` / `redirect` を**呼ばずに
値だけ返せば現在ルートは描き直されない** (server-actions.md) ので、
エディタの state は無傷のまま、バナーだけ足せる。

```tsx
'use client'
export function NoteSaveForm({ action, itemNo, className, children }: Props) {
  const [state, formAction] = useActionState(action, null)
  return (
    <SaveFormContext.Provider value={state}>
      <form action={formAction} className={className}>
        <input type="hidden" name="itemNo" value={itemNo} />
        {children}
      </form>
    </SaveFormContext.Provider>
  )
}
```

`ItemView.tsx` と `edit/[itemNo]/page.tsx` の `<form action={…}>` を
これに置き換える (children は今までの要素のまま)。Server Action は
`(prev: SaveState, formData) => Promise<SaveState>` の形になり、成功は
今までどおり `revalidatePath` + `redirect(savedHref)` (try の外で)、
競合は戻り値だけ。

```ts
export type SaveState =
  | null
  | {
      kind: 'conflict' | 'exists' | 'missing' | 'checkpointFailed'
      seq: number // Date.now()。同じ結果を 2 度処理しないための印
      server: {
        memo: string
        url: string
        mode: Mode
        updatedAt: number
        deletedAt: number | null // ゴミ箱の行と衝突したとき、バナーに添える
      } | null
    }
```

`EditToolbar` の「更新」は portal されているが `useFormStatus` は
`<form action={formAction}>` のままなら今までどおり効く。アップロード中の
submit 抑止 (preventDefault) も無変更。

初版の「redirect + 下書き復元」と比べて: 本文の置き場が React state (制御
hidden) になり、プライベートモードや容量超過で消えない・400ms の debounce で
最後の打鍵が落ちない・url / mode も残せる。さらに ItemView は `/item`・
検索 3 ペイン (`(search)/page.tsx`)・`@detail` の 3 箇所から描かれるので、
`?conflict=` を配って回らずに済む。

### 3-2. React 19 のフォーム自動リセット (必須の対処)

`<form action={fn}>` は送信時に `requestFormReset` を**アクション実行前に**
予約する (`react-dom-client` の `startHostTransition`)。fn が値を返して
終わると、非制御の入力 (`defaultValue` / `defaultChecked`) は初期値へ戻る。
`MemoEditor` の memo hidden は制御なので無事だが、`/edit` の **url textarea と
mode ラジオは競合応答の直後に巻き戻る**。

→ 小さな Client Component `EditItemFields` で url / mode を制御にする
(`useState` + `value` / `checked` + `onChange`)。jsdom が無いので自動化せず、
§7 の手動項目「url を変えた状態で競合 → url が残る」で確認する。

**実装時の追記 (実機で判明)**: 制御にしても `checked` は戻らない。
`value` (textarea・hidden) は React が復元するが、ラジオの `checked` は
リセットで既定へ落ちたまま React の state と食い違う。そのまま次の「更新」を
押すと FormData は DOM を読むので、**選んでいない種別が黙って保存される**。
`EditItemFields` は結果が返るたびに `checked` を state から当て直す。

### 3-3. バナーと 3 択

`MemoEditor` の中 (下書き復元バナーと同じ場所) に、`SaveFormContext` の
`seq` が未処理のとき出す。文言は「別の端末」と決めつけない (同じ画面の
チェック操作でも来る)。

> 別の端末 (またはこの画面の別の操作) で本文が HH:MM に更新されています。
> あなたの変更はまだ保存されていません。

1. **差分を見る** — `NoteDiffView` (既存・`@codemirror/merge`・client) に
   `oldText = server.memo` / `newText = 自分の本文` を渡して畳んで出す。
2. **サーバ版を読み込む (自分の変更を捨てる)** — 本文・基点を server の値に
   する。`/edit` では url / mode も `EditItemFields` が同じ context を見て
   取り込む。
3. **このまま上書き** — 基点を `server.updatedAt` に差し替え、hidden
   `checkpoint=1` を立てて `form.requestSubmit()` (`submitForm` と同じ辿り方)。
   hidden は state 制御なので **`flushSync` で反映してから** `requestSubmit()`
   する (同期に呼ぶと古い値で送られる)。`checkpoint` は送信直後に下ろす
   一発もの — 残ると次の普通の保存が自分の直前版を `conflict` として刻む。
   **force フラグは持たない** — 「いま見せた版に対する CAS」なので、その間に
   第 3 の書き込みがあればまた競合になる (黙って潰さない)。

バナーには url / mode の差も出す (`SaveState.server` に載っている)。
**url / mode は git 履歴に入らない** (`notesRepo` は memo だけを
`notes/<no>.md` に書く) ので、上書きで消える url / mode は戻せない — 見せて
から選ばせるしかない。

`exists` (新規のはずが行があった) は文言を「#no は別の操作で先に作成
されています」に変えて同じ 3 択。`missing` (編集中に永久削除された) は
「このノートは削除されました」+ **新規として保存** (基点を `'new'` にして
再送 → create)。

クライアント側の自動再送は持たない。同内容の二重保存はサーバの
`sameContent` (§2-4) が吸収するし、「memo が同じなら再送」は url / mode だけが
違う競合を黙って潰す。

## 4. git に刻むのは「上書きされる側」だけ

| 案 | 評価 |
| --- | --- |
| 毎保存で自動コミット | docs/57 §8 が退けた (ノイズ)。保存経路に git が挟まる (同 §1 の禁) |
| 一切刻まない | 検出で「黙って消える」は無くなる。残る喪失経路は本人が差分を見て選ぶ「上書き」だけ |
| **上書きを選んだときだけ、消える側を 1 版** | **採用**。稀・意味のある版。刻めなければ上書きしない |

```ts
// actions.ts。checkpoint=1 が立っている保存と、履歴からの復元の前に呼ぶ。
// 刻めなかったら false — 呼び手は上書きせず、その旨をバナーで返す
async function checkpointBeforeOverwrite(
  itemNo: string,
  incoming: string,
): Promise<boolean> {
  if (isDemoMode()) return true // デモは履歴ごと無効 (docs/57 §4)
  const current = await getItem(itemNo)
  if (current === null || current.memo === incoming) return true
  try {
    // HEAD と同じなら null で何も起きない
    await commitNote(itemNo, current.memo, `conflict ${itemNo}`)
    return true
  } catch (error) {
    console.error(`競合チェックポイントのコミットに失敗 (${itemNo})`, error)
    return false
  }
}
```

- **`await` で呼ぶ。`after()` は使わない** — `after()` は redirect でも
  エラーでも走るうえ、notesRepo のキューは reject を先に処理済みにするので
  失敗が見えなくなる。競合時だけの稀な経路なので応答に数十 ms 載せてよい。
- **刻めなかったら上書きしない** (fail closed)。docs/57 §1 の「保存が git の
  失敗に巻き込まれてはいけない」は普段の保存の原則で、ここは利用者が
  「消してよい」と選んだ稀な経路。`{ kind: 'checkpointFailed' }` を返し、
  バナーで「履歴に残せませんでした。差分をコピーしてから再試行して
  ください」と示す。
- `restoreNoteVersionAction` も同じ関数を通す (§2-5)。刻めなければ復元しない。
- チェックポイントと CAS の間に第 3 の書き込みが入れば CAS が負けて再び
  競合になるだけ (コミットは無駄にならない)。
- 「サーバ版を読み込む」で捨てる自分の本文は刻まない — 保存していない本文を
  コミットしない (docs/57 の原則)。差分表示で読め、必要ならコピーできる。
- `checkpoint=1` は「見せた版の上書きだ」と伝える印であって防御線ではない。
  単独ユーザーなのでそれでよい。
- 履歴画面 (`/item/<no>/history`) にそのまま出て、既存の「この版に復元」で
  取り戻せる。「N 分ごとの自動チェックポイント」は引き続き別件。

## 5. 新規ノート経路

入口は 3 つ: `/new` (`nextItemNo()` → `/edit/<no>`)、`/edit/<no>?code=`
(スキャン新規登録。[docs/10](./10-スキャン新規登録計画.md) §5)、未登録番号の
`/item/<no>` (QR シール先貼り)。どれも `item === null` → 基点 `'new'`。

- 保存は `prisma.item.create`。同じ番号を 2 端末が採番しても、後の側は
  P2002 → `exists` で止まる (今の upsert は先のノートを潰す)。
- ゴミ箱の行と衝突しても `exists` (`getItem` はゴミ箱も返す)。`TrashedBanner`
  はサーバ描画なので値だけ返す経路では出ない — バナー側で「ゴミ箱にあります」
  を添える (`server.deletedAt` で判る)。
- `assertDemoItemQuota` は create 枝だけで呼ぶ (今の `upsertMemo` と同じ効き方)。
- 任意 (後回し可): **別の番号で保存** — `allocateItemNoAction()` (requireUser +
  `nextItemNo`) を足し、itemNo hidden を差し替えて基点 `'new'` で再送。

## 6. やらないこと

- **悲観ロック・presence (在席) 表示** — §0-1。在席は心拍 + ポーリングが要り、
  タブ死で偽陽性が残る。保護にはならず注意喚起だけ。
- **自動マージ (3-way)** — 表・フェンス・`- [ ]` 行で黙って壊れるのが一番
  怖い。ただし競合ペイロード (基点本文はクライアントに、自分と相手は応答に)
  は材料を全部そろえるので、後で `git merge-file` で足せる。
- **スキーマ変更** (version 列・lock 表) — PGroonga 索引の罠を踏まない。
- **毎保存の自動コミット・N 分ごとのチェックポイント** — docs/57 §8 のまま。
- **オフライン編集の outbox** — [docs/65](./65-オフライン対応計画.md) §11。
  本計画の CAS は §11 が言う「`updatedAt` を比べて送る」の土台そのもの。
- **上書きインポート (ZIP) の保護** — 件数が多く、利用者が「上書き」を選んだ
  明示操作なので刻まない (履歴からの復元は §2-5 のとおり刻む)。
- **端末名の記録** — author 固定のまま。「別の端末」としか言わない。

    打っている最中に同じことをする → バナー。追随 (または「サーバ版を
