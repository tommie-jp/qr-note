# 編集競合対策計画

iPhone と Windows で**同じノートを同時に開いて編集**すると、後から保存した側が
相手の変更をまるごと消してしまう (lost update)。これを、複雑な同期なしで
「黙って消えない」ようにする。

## 0. 何が困っているか

保存は本文まるごとの上書きで、勝敗は後勝ち。

- `/edit` の「更新」→ `updateItemAction` → `upsertItem` (memo / url / mode)
- `/item` 編集タブの「更新」→ `updateMemoAction` → `upsertMemo` (memo)

DB へは upsert 1 文なので**半端に混ざった本文はできない**。壊れ方は
「後から保存した側が、相手の保存をまるごと消す」の一種類だけ。

1. iPhone で `/edit/4518` を開く (画面の本文はこの時点のサーバ値)
2. Windows で同じノートを編集して保存
3. iPhone が保存 → 2 の内容が丸ごと消える

そして本当に痛いのは、**消えた版がどこにも残らない**こと。git 履歴
([docs/57](./57-ノートgit履歴計画.md)) はあるがコミットは手動なので、
上書きされた版はたいてい誰も持っていない。

### 0-1. ロック (悲観排他) にしない理由

デッドロックは実は起きない — 取り合う資源がノート 1 つなので循環待ちが
組めない。実際に起きるのは**自己ロックアウト**のほう。

- iPhone は編集画面のタブを OS が黙って落とす実績がある (OCR のモデル
  読み込みで WebKit がタブごと再起動する。[docs/24](./24-画像OCR計画.md) §9)。
  unlock が飛ばず、**自分のノートが自分に開けなくなる**。
- 直すには TTL + 強制解除 UI が要り、実装が楽観方式より重くなる。
- しかも TTL が切れた瞬間は無防備で、同じ lost update が起きる。
  つまり**ロックを入れても基点チェックは結局要る**。ロックは飾りになる。

単独ユーザーでほとんどの時間は競合しない。常時払うコスト (取得・解放・失効)
に見合わないので、「保存の瞬間に基点を検める」楽観方式にする。

## 1. 方針

二段構えにする。順序が大事で、**先に「戻せる」を作る**。

| 段 | 何をする | 事故の重さがどう変わるか |
| --- | --- | --- |
| Step 0 | 保存のたびに git へ自動スナップショット | 「消えた」→「履歴から取り戻せる」 |
| Step 1 | 保存時の基点チェック (楽観ロック) | 「黙って上書き」→「気づいて選べる」 |

### 1-1. `updated_at` がそのまま版番号になっている

楽観ロックの版番号に **`updated_at` を流用**できる。公開切り替え・ゴミ箱・
オフライン印・アクセス日時は全部生 SQL で `@updatedAt` を避けている
(`src/lib/items.ts`) ので、この列は「memo / url / mode が変わったときだけ
動く」— ちょうど版番号の性質を満たしている。

`version Int` 列を足す案は採らない。migrate は PGroonga 索引を落とす
(適用前 `\di` 確認 + REINDEX が付いてくる) ので、列なしで済むなら済ませる。

Prisma の `DateTime` は `timestamp(3)` (ミリ秒精度) で、JS の
`Date.getTime()` と往復しても精度が欠けないことも効いている。

## 2. Step 0: 保存のたびに git へ自動スナップショット

対象は本文まるごとの保存経路 (`updateMemoAction` / `updateItemAction`)。
`warmCircuitsAfterResponse` と同じく `after()` で応答を返した後に打つ。

```ts
// 保存アクションの中 (概略)
const before = await getItem(itemNo) // 保存前の本文を控える
await upsertItem(itemNo, data)
after(async () => {
  try {
    // 1 本目: 保存前の本文。普段は直前の自動コミットと同じで noop。
    // チェック操作 (toggle) だけで進んでいた版が、上書きの前に 1 版残る
    if (before !== null) {
      await commitNote(itemNo, before.memo, `auto: before update ${itemNo}`)
    }
    // 2 本目: 保存後の本文
    await commitNote(itemNo, data.memo, `auto: update ${itemNo}`)
  } catch (error) {
    console.warn(`保存後の自動コミットに失敗 (${itemNo})`, error)
  }
})
```

- **必ず await する**。notesRepo のキューは reject を先に処理済みにするため、
  fire-and-forget だと失敗が unhandledRejection にすら出ない
  (`src/lib/git/notesRepo.ts` の注意書きどおり)。
- `commitNote` は内容が同じなら null を返すだけなので、**履歴は汚れない**。
  連続保存で増えるのは実際に変わった分だけ。
- デモモードは `isDemoMode()` で見送る (`assertHistoryEnabled` と同じ理由 —
  毎時再シードで履歴が嘘になる)。
- 失敗しても保存は成功のまま (履歴は派生データ。回路図と同じ扱い)。

### 2-1. 手動コミット (docs/57) はそのまま残す

自動スナップショットは「保険」、手動コミットは「節目に名前を付ける」。
役割が違うので共存でいい。`restoreNoteVersionAction` も**復元前の本文だけ**
1 本目と同じ流儀で残し、復元後は今までどおり未コミットに保つ
(「復元した」を 1 版にするかは利用者が決める、という docs/57 §4 の設計を
変えない)。

### 2-2. チェック操作・健康記録はコミットしない

`toggleMemoTaskAction` / `recordHealthAction` は対象外。単語帳の回転
([docs/56](./56-チェック検索計画.md)) は 1 日に何十回も押すので、1 押し
1 コミットは履歴を水浸しにする。押した分は次の本文保存の「1 本目」
(保存前スナップショット) が拾うので、上書きで消える前には必ず 1 版残る。

## 3. Step 1: 保存時の基点チェック (楽観ロック)

### 3-1. フォームに基点を持たせる

`/edit` と `/item` 編集タブの form に hidden を 1 つ足す。

```tsx
<input
  type="hidden"
  name="baseUpdatedAt"
  value={item ? String(item.updatedAt.getTime()) : ""}
/>
```

空文字 = 「開いたとき行が無かった」= 新規作成の意思表示。

**本文そのものを基点にしない**。DB には Ver1 由来の CRLF の本文があり、
エディタは LF に正規化する (MemoEditor の initialValue) ので、文字列比較は
「何も変えていないのに競合」という偽陽性を作る。

### 3-2. 保存を条件付き UPDATE にする

`src/lib/items.ts` に保存関数を足す。読んで比べて書くのではなく、
**where に基点を入れた 1 文**にするのが要点 (検査と書き込みの間に隙間が無い)。

```ts
export type SaveResult = 'saved' | 'created' | 'conflict'

export async function saveItemWithBase(
  itemNo: string,
  data: { memo: string; url: string; mode: Mode },
  baseUpdatedAt: Date | null, // null = 新規作成のつもり
): Promise<SaveResult> {
  const derived = derivedFromMemo(data.memo)
  if (baseUpdatedAt !== null) {
    const { count } = await prisma.item.updateMany({
      where: { itemNo, updatedAt: baseUpdatedAt },
      data: { ...data, ...derived },
    })
    if (count === 1) {
      return 'saved'
    }
    // 基点が合わない。ただし今の DB と送られた内容が同じなら成功扱い
    // (二重送信・別タブが同じ内容を先に保存した場合。updated_at は動かさない)
    const current = await getItem(itemNo)
    if (
      current !== null &&
      current.memo === data.memo &&
      current.url === data.url &&
      current.mode === data.mode
    ) {
      return 'saved'
    }
    return 'conflict'
  }
  // 新規作成。先を越されていたら P2002 = 競合として扱う
  try {
    await prisma.item.create({
      data: { itemNo, itemNoNum: itemNoToNum(itemNo), ...data, ...derived },
    })
    return 'created'
  } catch (error) {
    if (isUniqueViolation(error)) {
      return 'conflict'
    }
    throw error
  }
}
```

`upsertMemo` / `upsertItem` は残す (インポート・復元・画像回転が使う
無条件上書きの口)。画面からの保存 2 経路だけを `saveItemWithBase` に替える。

デモモード (共有アカウント) はむしろ他人と競合するので、基点チェックは
デモでも効かせる。

### 3-3. 競合したらリダイレクトで知らせる

```ts
if (result === 'conflict') {
  redirect(`/edit/${itemNo}?conflict=${Date.now()}`)
}
```

値を時刻にするのは `?saved=` と同じ理由 (連続競合でも毎回バナーを出す)。
`updateMemoAction` 側は `/item/<itemNo>?conflict=<ts>` へ。

### 3-4. `toggleMemoTaskAction` / `recordHealthAction` は今のまま

どちらも押した瞬間に DB の最新を読み、行単位で検算してから書く
(タスク行でなくなっていれば投げ返す)。読みと書きの間の窓は数 ms しかなく、
行単位の操作に本文まるごとの基点チェックを課すと、単語帳の連打が
無用に弾かれる。対象外とする。

## 4. 競合したときの画面

保存を拒否して終わりにしない。**利用者の本文を捨てさせない**のが本体。

### 4-1. 下書き復元と組み合わせる

編集中の本文は localStorage の下書き (`src/lib/memoDraft.ts`) に残っている。
競合リダイレクトで画面が**新しいサーバ値**を初期値として開き直すと、
下書き (自分の本文) は初期値と食い違うので、既存の復元促しがそのまま出る。
つまり競合画面の大半は**既にある部品でできる**。

前提が 1 つ: `/item` 編集タブの MemoEditor には draftKey が付いていない
(`ItemView.tsx`)。ここに `draftKey={itemNo}` を足す。`/edit` と同じキーを
共有するのは意図的 — 同じノートの同じ本文なので、どちらの画面で打った
下書きも、どちらの画面でも復元できるほうが正しい。

### 4-2. バナーと選択肢

`?conflict=` があるときのバナー:

> 別の端末が先に保存しています。表示は最新の保存内容に更新しました。
> あなたの編集は下書きとして復元されています。

選択肢は 3 つで、どれも既存の道具で足りる。

1. **相手の版を見る** — 履歴画面へのリンク。Step 0 のおかげで相手の保存は
   自動コミット済みなので、差分表示 ([docs/57](./57-ノートgit履歴計画.md))
   がそのまま使える。
2. **自分の版で上書き** — 復元された下書きのまま、もう一度「更新」を押す。
   リダイレクトで基点が最新に付け替わっているので、今度は通る。
   専用の force 経路は要らない。消える側も Step 0 で git に残っている。
3. **諦める** — 下書きの「破棄」ボタン (既存) で最新のサーバ値に戻る。

### 4-3. 開きっぱなしタブへの注意書き

競合が起きる典型は「iPhone で編集タブを開いたまま数日放置 → Windows で
編集 → iPhone に戻って保存」。基点チェックがあれば壊れないので、
予防 (focus 復帰時の新旧確認バナーなど) は入れない。競合表示が
実際に鬱陶しくなってから考える (YAGNI)。

## 5. やらないこと

- **悲観ロック・presence 表示** — §0-1 のとおり。
- **自動マージ (3-way merge)** — 行単位のマージは checkbox どうしなら
  嬉しいが、失敗時の説明が難しい。履歴から手で拾えれば足りる。
- **オフライン編集の outbox** — [docs/65](./65-オフライン対応計画.md) §11 の
  Level B。ただし本計画の基点チェックは §11 が言う「`updatedAt` を比べて
  送る」の土台そのものなので、やるときはそのまま乗る。
- **CRDT・リアルタイム同期** — 単独ユーザーには過剰。

## 6. テスト

- `items.test.ts` — `saveItemWithBase` の分岐 (AAA):
  - 基点一致 → saved、本文が変わる
  - 基点不一致 + 内容も違う → conflict、本文が変わらない
  - 基点不一致 + 内容が同じ → saved、`updated_at` が動かない
  - 基点 null → created / 先客あり → conflict
- `notesRepo.test.ts` — 自動コミットの noop (同内容 2 連続で履歴が増えない)
  は既存テストが担保。保存アクション経由の 2 本コミット (before / after) を
  1 本足す。
- 手動 E2E — ローカル 2 タブで「片方が保存 → もう片方が保存」を通し、
  競合バナー・下書き復元・上書きの 3 択を確認する
  (手順は既存のローカル E2E 環境で足りる)。

## 7. 段取りと規模

| 順 | 作業 | 規模 |
| --- | --- | --- |
| 1 | Step 0: 保存 2 経路の自動コミット + テスト | 半日 |
| 2 | Step 1: `saveItemWithBase` + 2 フォームの基点 + テスト | 1 日 |
| 3 | 競合バナー + ItemView への draftKey + E2E | 半日 |

1 だけ先に出しても価値がある (事故が「消えた」でなくなる)。2 と 3 は
同じリリースで出す — チェックだけ入れて受け皿の画面が無いと、
競合 = ただのエラーになってしまう。
