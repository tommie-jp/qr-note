# 通信量削減計画

C/S 化 (docs/123) の後、通信の形式を JSON からバイナリにすると速くなるかを
検討した (2026-10-30)。JSON の構造 (鍵・括弧) は圧縮後の 1% 程度で、端末の
解析も 1ms 以下なので、形式を替えても縮まない。運んでいる物の大半は文字列
(本文の Markdown と回路図の SVG) なので、**運ぶ物そのものを減らす** 4 つを
実装した。

| § | 何を | 効く所 |
| --- | --- | --- |
| 1 | 回路図サムネを一覧の応答から外し、hash で別に配る | 検索の転送 (2 回目からは図を運ばない) |
| 2 | 回路図の SVG を控える前に軽くする (svgo) | 図の転送・同期・DB |
| 3 | 圧縮を gzip から brotli へ (相手が受けるとき) | 全 JSON API と図 |
| 4 | オフライン同期を差分にする | 5 分おきの同期 |

## 0. 形式を替えない理由 (検討の記録)

検索「オペアンプ」と同じ規模 (20 件・回路図サムネ 20 枚) の試作データで測った。

| 部分 | 素のまま | gzip 後 |
| --- | --- | --- |
| JSON 全体 | 266KB | 9.0KB |
| 構造の分 (鍵・括弧) | 4.7KB | 0.4KB |
| 文字列の分 (本文・SVG) | 243KB | 8.1KB |

- MessagePack・Protobuf・CBOR が縮めるのは「構造の分」で、文字列は同じ量を運ぶ
- JSON.parse は native で、266KB を PC で 0.16ms。JS で書かれた読み手はたいてい遅い
- v0.23.88 の実機の待ちは「応答開始」(往復 + サーバ) と「描画」が大半で、
  受信は Wi-Fi で 0〜15ms・キャリアで 0〜60ms

バイナリが効くのは数値の配列が主役 (埋め込みベクトル)・小さなメッセージの
大量のやり取り (WebSocket)・圧縮が使えない場合で、このアプリはどれにも当たらない。

## 1. 回路図サムネの別配信

一覧の応答 (`/api/items`・`GET /api/trash`) の `circuitThumbs` は、ノート →
**SVG の hash** の表になった (前は SVG の文字列)。

- `GET /api/circuits/svg/<hash>` … circuit_svgs から 1 枚。hash は回路の本文と
  描画器の版から作る鍵で中身が変わらないので、`Cache-Control: private,
  max-age=31536000, immutable`。ログイン必須・クロスサイトは断る。配る前に
  毎回安全検査 (assertSafeCircuitSvg)、`X-Content-Type-Options: nosniff` と
  スクリプトを止める CSP を付ける。未描画は 404 (覚えさせない)
- 行のサムネ (小・中・大) は `<img src="/api/circuits/svg/<hash>">`。もともと
  `<img>` (data URL) だった (docs/122 §10-2) ので、URL を渡すだけ
- 画像表示のタイルは、文字をページの字体で描くために埋め込みが要る。端末の
  控え (`lib/client/circuitSvgStore.ts`) が同じ口から文字列を取り、届くまでは
  同じ大きさの灰色の枠を出す
- サーバのサムネの取得 (`circuit/thumbs.ts`) は SVG の中身を引かず、
  hash と大きさ (`octet_length`) だけを引く。埋め込みのための合計予算
  (CIRCUIT_THUMB_BUDGET) は要らなくなったので外した
- Service Worker は `/api/` を素通しするので、immutable はブラウザの HTTP
  キャッシュがそのまま効く
- セキュリティレビュー (CRITICAL・HIGH なし) を受けて 3 つ足した。CSP に
  `sandbox` と `frame-ancestors 'none'` (直に開いても別の生まれの文書になる)・
  SVG の安全検査で `@import` を字体の CSS の `url()` だけに絞る (`url()` を
  使わない `@import "…"` が素通りしていた)・ログアウトの応答に
  `Clear-Site-Data: "cache"` (共有の端末で 1 年覚えた図が残らないように)

## 2. 回路図の SVG を軽くする

node-tikzjax は描くときに svgo を通しているが、座標に浮動小数の誤差
(`-42.232000000000006`) が残っていた。`circuit/optimizeSvg.ts` が控える前に
svgo (3.3.5、node-tikzjax が既に持っていた版を直接の依存に載せた) を掛ける。

- 小数 2 桁に丸める。手元の 689 枚で、圧縮後の大きさが 12% 減 (gzip
  1164 → 1026KB・brotli 1033 → 908KB)。2 倍の解像度で描いた画素の差は 0.013%
- **形は変えない。** 後から正規表現で SVG を読む処理がある (circuit-fence の
  字体の埋め込みは `<text>` ごとの font-family を拾う・刻印は `<svg>` の
  `data-circuit-fence`)。属性をグループへ寄せる類の書き換え・`<style>` の
  書き換えは止めた。刻印か `@import` を落とした結果は使わない
- 軽くできない (例外・安全検査に落ちる) ときは元の SVG を控える
- 既に控えてある行は `scripts/optimizeCircuitSvgs.ts` が軽くする。**列は足して
  いない** — 「小数 3 桁以上の数を含む = まだ軽くしていない」を DB の正規表現で
  選ぶので冪等 (2 回目からはほぼ何もしない)。マイグレーションを避けたのは、
  prisma の差分が PGroonga の索引を落とす罠があるため。doDeploy.sh の手順 6 で
  毎回流す。手元の 689 枚で 667KB 減、2 回目は 12 枚が候補・書き込み 0
  (図の中の文字「1.234」に当たる行で、軽くしても同じ)
- hash は回路の本文から作るので、中身を書き換えても変わらない。端末が覚えた
  前の SVG のままでも見た目は同じ

## 3. brotli

`route/compress.ts` は、相手が `br` を受けるなら brotli (品質 5・文字列用の
モード)、受けなければ gzip (level 4) で返す。`q=0` は受けないと読む。1KB 未満は
圧縮しない (前と同じ)。

- 同じ試作データ 249KB で gzip 13.2KB / 0.8ms に対し brotli 品質 5 は 7.3KB /
  1.1ms (繰り返しの多い試作なので縮み方は大げさ。実データでは 15〜25% 減の見込み)
- ブラウザが `br` を送るのは HTTPS のときだけ。手元の http では gzip のまま
- ベンチマークの同期の計測 (`sync:payload`) は brotli で合計を出し、比べるために
  gzip の時間も段階に残す

## 4. オフライン同期の差分

端末は前回の同期の `cursor` (サーバが本文を読み始める前に取った時刻) を
`?since=` で送り返す。サーバ (`offline/syncItems.ts` の loadOfflineSyncDelta) は:

- `versions` … 生きている全ノートの [id, 更新時刻, 見た時刻, 印] (並びは全件と同じ)
- `items` … 起点の 10 秒前より後に書き換わったノートの本文 (時計のずれを吸う)
- `circuits` … 書き換わったノートの図と、起点の後に描けた図
- `circuitHashes` … 全件なら運ぶ図 (予算込み) の hash の全部

端末 (`offline/syncDelta.ts` の mergeSyncDelta) は前回の写しに重ね、全件と
同じ形の写しを作る。

- ゴミ箱に入れたノートは `versions` から消えるので写しからも消える
- **辻褄が合わなければ全件を取り直す** — 写しに無いノートが `versions` にある
  (ゴミ箱から戻した。更新時刻が古いまま)・本文が来ないのに版が違う
- 端末に無い図が `circuitHashes` にあれば、全件にせず「運べなかった」に数える
  (図はコードブロックとして出るだけ)
- 起点が無い (古い版の写し)・7 日より古い・hash の無い図を持つ写しは全件
- 304 (版が同じ) は前と同じで、差分より先に効く
- 計測の行に `種類=差分 / 全件` を足した

## 5. 手元の本番ビルドでの前後 (2026-10-30)

手元の開発 DB (1514 件・回路図 547 枚を同期で運ぶ) に本番ビルドを立て、curl で
測った (http でも curl は brotli を受ける)。

| 応答 | 前 (v0.23.88) | 後 |
| --- | --- | --- |
| 検索「オペアンプ」(小) | 素 500KB・gzip 103KB | 素 244KB・gzip 79KB・**br 68KB** |
| 検索「抵抗」(小) | 素 86KB・gzip 21KB | 素 60KB・gzip 18KB・**br 16KB** |
| 同期 (全件) | gzip 2,302KB | gzip 2,494KB・**br 1,889KB** |
| 同期 (差分・変化なし以外) | — (毎回全件) | **br 57KB** (版 1514 件・図の hash 547 件) |

- 検索の残りの大半はノートの本文 (回路の TeX の原文を含む)。サムネの SVG は
  別の口から 1 回だけ運び、2 回目からはブラウザのキャッシュから出る
- 同期の全件が gzip で少し増えたのは、図に hash を足したため (547 × 64 字)
- 差分は 304 (版が同じ) の次に効く。書き換えがあった同期の大半はこちらになる

## 6. 測ること (配布後)

- 本番の計測テスト (docs/120) を PC と iPhone で流し、docs/123 §11-8 と比べる
- 検索の RSC の欄 (転送 / 展開後)。オペアンプは v0.23.88 で 103KB / 500KB
- 同期の行の `転送` と `種類`。全件は 2,302KB (gzip) だった
- ベンチマークの `sync:payload` の brotli と gzip の時間

## 7. v0.23.89 の本番計測 (2026-10-29)

端末の計測は配布の直後 (21:41〜21:44)。サーバの段 (`サーバ.*`) は v0.23.84 の
ときに保存した結果がそのまま出ていたので、比べていない。

転送量 (検索の RSC は 転送 / 展開後):

| 項目 | v0.23.88 | v0.23.89 |
| --- | --- | --- |
| 検索 オペアンプ (iPhone) | 103KB / 500KB | 66KB / 239KB |
| 同期 全件 (PC) | 2,302KB | 1,846KB |

同期の差分はまだ一度も走っていない。PC は前の版の写しに cursor が無いので
全件を取り、iPhone は変化が無く 304 だった。次にノートを書き換えたあとの同期で
`種類=差分` が出るはず。

全体 (ms) を docs/123 §11-8 と比べた。iPhone は前回 2 ペイン・今回 3 ペインで
構成が違う。どれも 1 回ずつの計測。

| 項目 | iPhone Wi-Fi | iPhone キャリア | PC |
| --- | --- | --- | --- |
| 検索 抵抗 | 193 → 225 | 342 → 361 | 386 → 229 |
| 検索 コンデンサ | 120 → 131 | 399 → 358 | 148 → 205 |
| 検索 オペアンプ | 254 → 205 | 602 → 492 | 196 → 153 |
| 続き | 66 → 54 | 261 → 228 | 37 → 37 |
| ノート 1 | 144 → 343 | 241 → 342 | 55 → 58 |
| ノート 2 | 106 → 128 | 265 → 278 | 46 → 47 |

回路図の多いオペアンプは 3 端末とも速くなった。iPhone のノート 1 が遅いのは、
応答開始 (51ms) と描画 (82ms) の外に 200ms ほどある。ペイン数の違いか一過性かは、
同じ構成で測り直して確かめる。

残した課題:

1. サーバのベンチマークを流し直し、`sync:payload` の br と gzip の時間を取る
2. 同期の差分を一度走らせ、`種類=差分` の行の転送量を見る
3. 「検索 全件」の応答開始が `未了`、キャリアの描画が `-285ms` になる。計測の
   取り違えに見える。原因はまだ調べていない
