# クローラ対策計画

クローラー (検索エンジン・AI の収集・スクレイパー) に対して、
「何を読ませるか」「何を読ませないか」を一通り点検した記録。

大枠は既に出来ている — 門番 ([src/proxy.ts](../src/proxy.ts) +
[publicPaths.ts](../src/lib/publicPaths.ts)) が既定で閉じており、公開になり得る
`/item` と `/print` には noindex が付き、`/item/1, 2, …` を順に叩いても
ノートの存在は数えられない (docs/22 §4)。ログインの口は nginx で 30r/m に絞ってある。

この計画で埋めるのは、その隙間に残っていた 3 つ。

| § | 変更対象 | 埋める穴 |
| --- | --- | --- |
| §2 | `src/proxy.ts`, `api/images/` | noindex の届かない応答 |
| §3 | `src/app/robots.ts` | AI 学習収集への意思表示 |
| §4 | (変更なし) | 一般パスのレート制限を**やらない**判断 |

## 2. noindex の穴を塞ぐ

### ログイン案内 (rewrite 先)

proxy.ts は未ログインの画面 GET を `/login-required` へ **rewrite** する。
redirect ではないので、応答は「元の URL のまま 200」になる。つまり
`/`, `/settings`, `/trash` … のどれを叩いても、中身の同じ案内ページが
200 で返る。クローラーからは「同一内容のページが URL の数だけある」形に見え、
案内文が変な URL でインデックスされ得る。

**案内ページ側の metadata には書かない。** rewrite 先が 1 つである以上、
そこに `robots: { index: false }` を置くとサイトの根 (`/`) まで巻き込む。
根は SNS のカード生成クローラーが読む場所で (docs/89 §6 は
`curl -sA Twitterbot https://qr.tommie.jp/` で確かめている)、noindex を見た
クローラーはカードを出さないことがある。X は「カードなし」も 1 週間
キャッシュするため、壊すと戻すのに時間がかかる。

そこで proxy.ts 側 — **元のパスが分かる唯一の層** — で
`X-Robots-Tag: noindex` を付け、根だけ外す。根が「ログインが必要です」として
インデックスされるのは害がない (サイトの玄関そのもので、ノートは 1 件も出ない)。
`/login-required` を直接開かれた場合も同じ扱いにする。**中身を持たない殻**は
他にもあり、`/offline` (ノートを 1 件も含まず、中身は端末の IndexedDB からしか
来ない) も同じ扱いにした。載っても空の紙が並ぶだけなので。

残りの公開パス — 使い方の説明 (`/docs/*`)・PWA の manifest とアイコン・`sw.js` —
はそのまま。説明は読まれて困るものではないし、機械が取りに来るものに
インデックスの指示は要らない。

`/login` は対象外。HTML (ログインをキャンセルしたときの案内) を返すが
**401 + `Cache-Control: no-store`** なので、検索エンジンはそもそも載せない。
200 で返す形に変えるなら、ここも noindex が要る。

### 添付の配信 (画像・音声・PDF)

`/item` の noindex は**その HTML の話**であって、画像そのものには効かない。
画像は別の URL として取得され、バイト列に meta タグは書けない。
公開ノートに貼った添付は未ログインでも配る (docs/22 §6) 以上、
クローラーの手は届いている。

伝える口はレスポンスヘッダしかないので、`X-Robots-Tag: noindex` を付ける。
**経路が 2 つある**ことに注意 — 原寸/Range の `dataResponse` と、サムネの
`imageResponse`。画像検索に載るのはサムネのほうなので、片方だけでは意味がない。
206 の部分応答は基本ヘッダをスプレッドで継ぐので、基本ヘッダ側に足せば足りる。

## 3. AI 学習クローラーを断る

**noindex では止まらない。** `robots: { index: false }` は検索インデックスへの
指示であって、「読んで持ち帰る」だけの収集には効かない。断るなら robots.txt しかない。

本番の robots.txt を単一の `Allow: /` から、UA ごとの 2 グループに分ける:

- AI 学習・回答生成の UA (GPTBot / CCBot / ClaudeBot / anthropic-ai / Claude-Web /
  Google-Extended / Applebot-Extended / Bytespider / meta-externalagent /
  cohere-ai / PerplexityBot) → `Disallow: /`
- `*` → `Allow: /` (従来どおり)

**`*` を allow のまま残すのが要点。** 公開ノートを検索結果に出さない方針は
ページ側の noindex が担っており、robots.txt で crawl 自体を止めると、その
noindex を読んでもらえずかえってインデックスされる (robots.ts の元コメントの通り)。

**検索用のクローラーを混ぜないこと。** Googlebot を入れると上記のとおり逆効果になる。
`Google-Extended` / `Applebot-Extended` は「学習に使うか」だけを指す robots.txt 専用の
トークンで、検索用の Googlebot / Applebot とは別物なので入れてよい。

並び順は包括的な `*` を最後に置く (デモ側 docs/89 §5 と同じ理由。RFC 9309)。

デモ側は既に `*` を `Disallow: /` にしてあり、AI の UA もそこへ落ちるので変更なし。

従うかどうかは相手次第 — robots.txt はお願いであって鍵ではない。名乗らない
スクレイパーには効かないが、主要な事業者は公表どおり従っている。

## 4. 一般パスのレート制限はやらない

`location /` は無制限のままにする。未ログインの乱打が Next.js の
レンダリングまで届き、vps2 (RAM 2GB) には痛い場所ではあるが、
**`location /` への limit_req は通常の閲覧を壊す**ことが分かっている
(1 ページ表示で静的チャンク + 各リンクの RSC プリフェッチが一斉に飛び、
503 になる。qr-demo.tommie.jp.conf のコメントに実際に踏んだ記録がある)。
パスでは GET プリフェッチと書き込み POST を区別できないのが根本原因。

公開 URL は宣伝しておらず (sitemap も無い)、現状は乱打の実害が無い。
実際に殴られたら、閲覧を壊さない層 — nginx ログの高頻度 IP を落とす fail2ban、
または `limit_conn` — を検討する。先回りして閲覧を壊すほうが損。

## 5. 検証

デプロイ後:

```bash
curl -s https://qr.tommie.jp/robots.txt              # GPTBot 等の Disallow
curl -sI https://qr.tommie.jp/settings | grep -i x-robots-tag  # 案内の noindex
curl -sI https://qr.tommie.jp/ | grep -i x-robots-tag         # 根には**付かない**
curl -sA Twitterbot https://qr.tommie.jp/ | grep -E 'og:'     # カードの回帰確認
curl -sI 'https://qr.tommie.jp/api/images/<公開ノートの画像名>' | grep -i x-robots-tag
curl -s https://qr-demo.tommie.jp/robots.txt         # 従来どおり全 Disallow (回帰)
```

nginx は変更しないので `doDeployNginx.sh` は不要。
