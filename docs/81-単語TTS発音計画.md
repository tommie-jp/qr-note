# 単語 TTS 発音計画 (`||答え||` の中の発音ボタン)

単語帳の英単語と例文を、押すと**その場で発音する**ようにする。
きっかけは本番 #1128「英単語 10 語」で、既にこう書かれている。

```markdown
- [x] concise ||/kənˈsaɪs/ 簡潔な、要領を得た His answer was concise and clear.||
```

実際の行にはこの間に `[🔊](https://dictionary.cambridge.org/…)` も入っている。
Cambridge 辞書へ飛ぶリンクで、ネイティブ録音が聞ける代わりに
**画面がノートから離れる**。単語帳として繰り返し回すには重い。

進捗: **実装済み** (2026-08-14)。US 発音固定・オンデバイス合成。
初回リリース (v0.22.57) は iPhone だけ無音で、声の代入が例外を投げるのが
原因だった (§6-1)。

## 1. なぜ Web Speech API か

選択肢は 3 つあった。

| 手 | 発音の質 | オフライン | 実装量 |
| ---- | ---------- | ------------ | -------- |
| Web Speech API (採用) | 良 (拡張音声なら十分) | ○ | 小 |
| 辞書 API のネイティブ録音 | 最良 | ✕ | 中 |
| 音声ファイルを自分で持つ | 最良 | ○ | 大 (1900 語ぶん) |

**録音の質は要らない。** 単語カードで確かめたいのは「この綴りをどう読むか」で、
音素と強勢が正しければ足りる。iPhone の Web Speech API は
AVSpeechSynthesizer と同じ OS の合成エンジンを鳴らすので、拡張音声を
入れてあれば学習用として問題ない質になる。

決め手はオフラインで、ノートのオフライン対応 (docs/65) と揃う。
通信が要る辞書 API を混ぜると、電車の中で単語帳だけが動かない。

**ネイティブ録音の役は既にある `[🔊]` リンクが持っている。** どちらかを選ぶ
話ではなく、その場で確かめる口 (合成) と、正確に聞き比べる口 (辞書) の
2 つが並ぶ形にする。

## 2. 記法は増やさない

**既に書いてあるノートがそのまま鳴ることが要件。** 発音のための記法を
足すと、#1128 の 10 語も、これから書く 1900 語も、全部書き直しになる。

そこで目印は「答えが**発音記号で始まる**こと」だけにした。

```text
||/kənˈsaɪs/ 簡潔な、要領を得た His answer was concise and clear.||
  └ ipa ──┘ └ 訳 ────────┘ └ example ────────────────┘
```

- **ipa** … 先頭の `/…/`。これが無ければ単語帳と見なさず、**何もしない**
- **example** … 末尾の英文 (`.` `!` `?` で終わる 2 語以上)
- **見出し語** … 答えの外、`||` より前の末尾の英字 (`concise`)

迷ったらボタンを出さない側に倒す。電験ノートの `||答え||` は 1 文字も
変わらないし、単語帳でも取りこぼしは「ボタンが 1 つ出ない」だけで、
答えの文字は必ず元のまま出る (§5)。

### 2-1. 発音記号は読み上げない

Safari の Web Speech API は **SSML も IPA 指定も受け付けない**。渡せるのは
綴り・言語・速さだけなので、`/kənˈsaɪs/` を鳴らす手段は無い。
発音記号は目で読むもの、ボタンは綴り (`concise`) を読むもの、と分ける。

同綴異音語 (`read` `lead` `desert`) を正しく読ませたいときは、例文の
ボタンを使う — 文脈があれば品詞が決まる。単語のボタンだけでは直せない。

## 3. ボタンの置き場所

**答えを開いた後にだけ出す。**

```text
閉: ☐ concise 🔊 ▶
開: ☐ concise 🔊 ▼ [🔈] /kənˈsaɪs/ 簡潔な、要領を得た [🔈] His answer was concise and clear.
```

- 隠したまま音だけ聞けても単語帳にならない (先に答えが判ってしまう)
- 閉じた行は **1 行 1 語の密度** (docs/79 の本体) を守る。閉じた状態に
  ボタンを足すと、50 語を一望する画面が道具で埋まる
- ノート右上の「答えを表示」でまとめて開けば、ボタンも一斉に出る

的は 44px を取らない。行の中に混ざる小さな道具なので、答え隠しの `▶` と
同じく文字より少し広い程度にとどめる (docs/11 §1-4 の例外)。

絵は**線画のスピーカー**にした。本文には既に `[🔊]` の絵文字が並ぶので、
同じ絵文字を使うと「辞書へ飛ぶリンク」と見分けが付かない。

## 4. 層の分け方

```text
lib/vocabTts.ts          答えの分解・見出し語の切り出し (純関数)
lib/ttsSpeech.ts         声の選択と読み上げ (Web Speech API)
components/rehypeAnswerTts.ts  見出し語を span に刻む (sanitize の後)
components/answer/TtsButton.tsx   発音ボタン
components/answer/VocabAnswer.tsx 開いた答えを組み立てる
```

### 4-1. 見出し語は rehype で刻む

`concise` は答えの**外**にあるので、答えを描く部品 (AnswerSpoiler) からは
見えない。かといって「同じ行の前のほう」を DOM から探すのは脆い。

hast の同じ親の中を見れば済むので、**rehype プラグインで span に刻む**。
`rehypeTaskLines` (チェックボックスの行番号) とまったく同じ作法で、

- **sanitize の後**に走らせる。前だと属性ごと落ちる
- 値は本文から取った英字だけなので、**サニタイズのスキーマは緩めない**
- 読むのは `spanWithAnswer` で、React の props ではなく hast の node から

remark 側 (`remarkAnswerSpoiler` の隣) に置いて `hProperties` で渡す手も
あったが、それだと sanitize のスキーマに属性を 1 つ足すことになる。
**緩めずに済むほうを選んだ。**

間に挟まる `<input>` (チェックボックス) と `<a>` (🔊 リンク) は中身ごと
飛ばして前後の文字をつなぐ。1 行に答えが 2 つあるときは、直前の答えより
後ろだけを見る (前の語の見出しを引きずらない)。

### 4-2. 4 語までを見出し語にする

`give up` `look forward to` のような句も読ませたいので複数語を許す。
ただし上限を 4 語にした — 英語だけで書かれた行では、`||` の前が文に
なっていることがあり、文まるごとを「単語」として読み上げてしまう。

## 5. 文字を落とさない

分解した `head` と `example` を**つなぐと元の答えに戻る**ように切る
(空白の位置まで含めて)。テストでも #1128 の 10 語すべてで往復を確かめている。

答えは本文であって、こちらが整形してよいものではない。分解に失敗した
ときも素の文字をそのまま描く — 静かに消えるより、ボタンが出ないほうがよい。

## 6. 声を選ぶのがいちばんの罠

**`lang` も `voice` も与えずに `speak()` すると、日本語設定の iPhone では
既定の日本語の声 (Kyoko) が英語を読む。** カタカナ発音になり、学習には
使えない。「iPhone の TTS は使えない」と言われるものの大半はこれ。

そこで `pickEnglishVoice` を自前で持つ。

1. `en-US` があれば **US だけ**から選ぶ (US 発音を優先する要件)
2. 無ければ他の英語 (`en-GB` など) で代用する
3. 選ぶ順は名前の優先表 — `Ava` `Zoe` が先頭。どちらも
   「設定 > アクセシビリティ > 読み上げコンテンツ > 声」から追加で
   落とす高品質版で、一覧に居る = 利用者が入れたということ。無ければ
   iOS に必ずある `Samantha` に落ちる
4. **効果音のような声を避ける。** Apple の英語一覧には `Albert` `Bad News`
   `Bahh` のような声が混ざっていて、しかも**名前順で先頭に近い**。
   優先表に当たらなかったときに素で先頭を取ると、これを引く
5. それしか無ければ、それで鳴らす (無音にするより読み上げるほうがまし)

Android の `en_US` 表記も英語と見なす (`_` を `-` に均してから比べる)。

速さは 0.9。既定 (1.0) は単語の聞き取りには少し速い。

### 6-1. 声を指定できない端末がある (iPhone で無音になった)

初回リリース (v0.22.57) は **iPhone だけ完全に無音**だった。iPad と Windows は
鳴る。消音スイッチでもなく、Safari でも PWA でも鳴らない。

原因は**声の代入そのものが例外を投げる**こと。

```js
utterance.voice = voice   // TypeError: Failed to convert value to 'SpeechSynthesisVoice'
```

`getVoices()` から取った声でもこうなる端末がある (ローカルの実ブラウザでも
同じ形を再現できた)。素で書くと例外が押下ハンドラまで抜けるので、

- 音が出ない
- 知らせも出ない (`onerror` は飛ばない。そもそも speak まで届いていない)
- 鳴り始めの見張りも動かない (代入のほうが先に走っていた)

の三重で「**押しても何も起きない**」になる。実機に触れないと絶対に判らない
壊れ方で、原因の切り分けにいちばん時間を食う形でもある。

対策は 3 段構えにした。**どの段でも黙らない**のが要点。

1. 声の代入を try で囲み、投げたら声を諦めて `lang` だけで鳴らす
   (`speak()` 自体を投げる場合も同じく捕まえる)
2. それでも 1.2 秒鳴り始めなければ、声を外してもう 1 度 `speak()` する
   (代入は通るのに音だけ出ない声があるため。`onstart` も `onerror` も
   飛ばないので、待つ以外に気づく手が無い)
3. そこまでやって鳴らなければ、画面に「この端末では読み上げできませんでした」
   と出す

一度 1 か 2 を踏んだら**その後は最初から声を外す**。覚えないと、押すたびに
1.2 秒待たされる。

選んだ声と失敗は `/logs` に残す (docs/30)。iPhone は Mac 無しでインスペクタを
繋げないので、実機の失敗を読む口はこれしかない。

### 6-1-2. 本当の原因は着信音量だった

§6-1 の対策を入れても iPhone は鳴らなかった。実機のログで、

```text
[発音] 声=Samantha/en-US 候補=69 英語=26
[発音] 1200ms 鳴り始めない (Samantha/en-US) → 声を外して再試行
```

声は取れていて、代入も `speak()` も投げておらず、再試行の後は
「鳴らなかった」も出ない = **JS から見える範囲では正常に喋っている**。

原因は **iOS の音声合成が「メディア音量」ではなく「着信音量」で鳴る**こと。
利用者は普段から着信音を切っていたため、合成だけが無音だった。着信音量を
中まで上げたら鳴った。iPad と Windows が鳴ったのはこの経路が違うため。

**ページから出力先 (AVAudioSession のカテゴリ) は選べない。** つまり
Web Speech を使う限り、着信音を切っている端末では鳴らせない。着信音量で
鳴ることを前提に、記法ドキュメントに注意書きを置く (メモ記法.md)。

音量に依らず鳴らしたいなら、合成ではなく**実体のある音を `<audio>` で
再生する**しかない (媒体の再生はメディア音量で鳴る)。その場合の音源は
辞書のネイティブ録音か、サーバ / ブラウザ側で合成した音声ファイルになる。

### 6-1-3. 無音の媒体で音声セッションを倒す当て — **効かなかった**

着信音を切ったままで鳴らせないか、v0.22.60 で次の賭けを試した。

> 媒体の再生が始まっているとブラウザは音声セッションを「メディア再生」側に
> 置く。その最中に読み上げれば、合成もメディア音量に乗るのではないか。

無音の WAV (8bit / モノラル / 8kHz / 1 秒) を実行時に組み立て、押した操作の
中で loop 再生を始めてから `speak()` した (iOS 系だけ)。**実機の iPhone で
鳴らなかった。** 実装は v0.22.61 で取り除いた。

**同じ手を試し直さないこと。** 媒体の再生でセッションを倒しても、合成の
出力先は着信音側のまま変わらない。Web Speech を使う限り、着信音を切った
iPhone で鳴らす方法は無いと考えてよい。

残る道は 1 つだけ — **合成をやめて、実体のある音声ファイルを `<audio>` で
鳴らす**。媒体の再生は確実にメディア音量で鳴る。音源の作り方 (辞書の録音 /
サーバ側合成 / ブラウザ内合成) は §7 に整理する。

### 6-2. iOS の作法

- **最初の `speak()` はユーザー操作の中で**呼ぶ。ボタン起動なので自然に満たす
  (自動再生はしない)
- `getVoices()` は**初回に空を返す**。ボタンのマウント時に一度呼んで
  読み込みを始めておく (`primeVoices`)。それでも空なら `lang` だけで鳴らす
- `cancel()` は**鳴っているときだけ**呼ぶ。鳴っていないのに呼ぶと、直後の
  `speak()` が巻き込まれて無音になる端末がある
- 自分が鳴らしている最中に消えるとき (画面移動・答えを閉じる) だけ止める。
  無条件に止めると、別の語を鳴らしている途中で黙らせてしまう
- **消音スイッチ**はブラウザから制御できない。実機で確かめること

### 6-3. 鳴らない端末では黙らない

対応していないブラウザでも、声が使えない端末でも、押しても何も起きないので
はなく理由を出す (§6-1 の 3 段目)。押し損ねたのか壊れているのかが判らないのが
いちばん困る。

## 7. 着信音を切ったまま鳴らすなら (未着手)

§6-1-3 のとおり、Web Speech では無理。**実体のある音声ファイルを `<audio>` で
鳴らす**しかない。音源の作り方は 3 つある。

| 案 | 例文 | 通信 | 質 | 重さ |
| ---- | ------ | ------ | ---- | ------ |
| 辞書のネイティブ録音 | ✕ 単語のみ | 毎回要る | 最良 | 小 |
| サーバ側で合成して貯める | ○ | 初回だけ | 良 | 中 |
| ブラウザ内で合成 | ○ | モデル取得のみ | 良 | 大 |

**サーバ側合成が本命**と見ている。理由:

- 単語も例文も鳴る (辞書の録音は単語しか無い)
- 一度作れば貯まるので 2 回目から即時。押してから待たされない
- 端末にモデルを降らせない。iPhone のメモリ事情 (docs/30 の調査) を考えると、
  82M 級のモデルを wasm で持つのは分が悪い
- 貯めた音は既存の仕組みに乗る — 画像・音声は既に DB に置いており
  (Ver2.x で uploads volume から移した)、オフライン印 (`offline_pin`) の
  積み荷に加えれば機内でも鳴る

ブラウザ内合成 (onnxruntime / transformers.js は OCR と画像検索で既に
積んである) は、サーバに合成器を置けない場合の代案。

## 8. やらないこと

- **発音記号 (IPA) の直接読み上げ** … Safari に手段が無い (§2-1)
- **無音の媒体で音声セッションを倒す** … 試して効かなかった (§6-1-3)
- **全語の連続再生・声や速さの設定 UI** … 要ると判ってから (YAGNI)
- **新しい記法** … §2
