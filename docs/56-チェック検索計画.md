# チェック状態の検索計画 (is:todo)

タスクリストのチェック (docs/55-チェックボックス操作計画.md) を単語帳として
使えるようにする。想定の使い方:

1. 1 ノート 1 単語で作る。1 行目 `- [ ] study`、2 行目に日本語訳。
2. 覚えたら閲覧画面でチェックする (実装済み)。
3. **まだ覚えていない単語だけを検索して**覚える ← 本計画で作るのはここ。

検索窓に `is:todo` と打つと未チェックの項目を持つノートだけに絞れるようにする。
既存の文法とそのまま組み合わさる:

```text
#英単語 is:todo     ← 英単語ノートのうち未習得だけ
is:todo             ← 未習得すべて (件数表示が「残り N 語」になる)
!is:todo is:done    ← 全項目を覚えたノート
```

この検索 URL をホーム画面に追加しておけば「開く → 未習得一覧 → 覚えたら
チェック → 一覧から消える」という単語帳の回転がそのまま成立する。

## 1. 方針: チェック数を派生キャッシュ列にする

このアプリには「正本はメモ本文、検索用の列は保存のたびに再計算する派生
キャッシュ」という確立した型がある (`derivedFromMemo` → `tags` / `props`。
[items.ts](../src/lib/items.ts))。チェック状態も同じ性質なので、同じ型に乗せる。

items に列を 2 つ足す:

- `task_todo` — 未チェックのタスク項目数 (`- [ ]`)
- `task_done` — チェック済みのタスク項目数 (`- [x]`)

真偽値 1 つではなく個数で持つのは、todo / done の両方を 1 回の集計で賄え、
「1 ノートに単語リストをまとめる」使い方でも残数が意味を持つため。

全文検索で `- [ ]` を直接探す案は採らない。PGroonga のバイグラム一致は
記号+空白をトークン化で落とすので当たらないし、`position()` の原文一致なら
動くが、コードフェンス内の擬似タスクを誤検出し `* [ ]` `1. [ ]` の変種ごとに
条件が増える。派生列なら保存時にパーサが一度だけ正確に数える。

合成タグ (`#未習得` の自動付与) も採らない。タグの正本は本文なので、本文に
無いタグを tags 列へ混ぜると不変条件が壊れ、タグ補完も汚れる。

## 2. 集計: countTasks (純関数)

[taskCheckbox.ts](../src/lib/taskCheckbox.ts) に
`countTasks(memo): { todo: number; done: number }` を足す。既にある
`MEMO_PARSER` (remark-parse + remark-gfm) で本文を解析し、`listItem.checked`
が `false` / `true` の項目をそれぞれ数える。

- パーサ基準なので、コードフェンス内の `- [ ]` は数えない (toggleTaskLine と
  同じ判定に自然に揃う。二重に文法を持たない)。
- シークレット断片の中のチェックは数えられない (本文上は暗号文)。断片内の
  タスクは閲覧でも押せない (docs/55 §5) ので、押せるもの = 数えるもので一貫する。

`derivedFromMemo` の戻り値に `taskTodo` / `taskDone` を足す。これだけで
既存の保存経路すべて (編集保存・閲覧のチェック操作・一括タグ・画像回転の
本文書き換え) が自動で列を最新に保つ。

## 3. スキーマとマイグレーション

```prisma
// memo のタスク項目数の派生キャッシュ (docs/56-チェック検索計画.md §1)。
taskTodo Int @default(0) @map("task_todo")
taskDone Int @default(0) @map("task_done")
```

- NOT NULL + default 0。既存行は 0 のままマイグレーションが通り、正しい値は
  バックフィル (§4) で入れる。
- 索引は張らない。現状 587 ノート規模で、`is:todo` 単独でも seq scan で足りる。
  ゴミ箱除外 (`deleted_at IS NULL`) と同格の整数比較が 1 つ増えるだけ。
- **末尾で PGroonga 索引を張り直す** (`CREATE EXTENSION` +
  `CREATE INDEX IF NOT EXISTS`)。この索引は Prisma スキーマで表現できず drift
  扱いになるため、prisma migrate は DROP を自動生成しうる。消えても全文検索は
  seq scan で動いてしまい気づけないので、手で `\di` を確かめる運用ではなく
  毎回張り直して冪等に保つ (他のマイグレーションと同じ作法)。

## 4. バックフィル: scripts/backfillTaskCounts.ts

[backfillTags.ts](../scripts/backfillTags.ts) / [backfillProps.ts](../scripts/backfillProps.ts)
と同じ作法 (本文由来の派生列を数え直す一回もの)。全 items (ゴミ箱含む) を走査し、
`countTasks(memo)` の結果で 2 列を UPDATE する。

- 派生キャッシュなのでいつ再実行しても整合が回復する (冪等)。値が既に合っている
  行は書かないので、二度目以降はほぼ何もしない。
- **`upsertMemo` は通さない** — 本文は変えないのに `@updatedAt` が動いて
  更新順が嘘になる (trashItems が生 SQL で避けているのと同じ理由)。
  2 列だけの生 UPDATE にする。
- npm scripts には登録しない。派生列のバックフィル (backfillTags / backfillProps)
  はどれも `npx tsx` で直接呼ぶ流儀で、登録してあるのはモデル差し替えのたびに
  回す backfill:embeddings だけ。
- **Ver1 取り込み ([migrateFromVer1.ts](../scripts/migrateFromVer1.ts)) の後にも
  流す。** あれは `upsertMemo` を通さず memo を直接書くので、既存ノートを
  上書きすると派生列が 0 ではなく**ずれた値**のまま残る (tags / props も同じ)。

### 本番へは doDeploy.sh が自動で流す

**人の記憶に頼らない。** バックフィルを忘れると検索は「壊れて見える」形では
失敗しない — 既存行が 0 のままなので `is:todo` は 0 件、その裏返しの
`!is:todo` は**未チェックが残っているノートまで含む全件**を返す。後者は
一見もっともらしい結果なので気づけない。

そこで [doDeploy.sh](../doDeploy.sh) の手順 6/8 で、`prisma migrate deploy` と
同じ SSH トンネルの中から続けて流す。冪等で、値が合っている行は書かないので
毎回走らせてよい (588 件で 1 秒未満)。毎回流すことには、派生列を更新しない経路
(Ver1 取り込み) で狂っても次のデプロイで直る、という利点もある。

手で流したいとき (デモや、デプロイと切り離して直したいとき) 用に
[doBackfillTaskCounts.sh](../doBackfillTaskCounts.sh) も置く。本番の compose
ディレクトリにはソースが無くリモートで `tsx` を動かせないため、サムネの
作り直しと同じくローカルから SSH トンネル越しに叩く
([doBackfillThumbs.sh](../doBackfillThumbs.sh) と同じ仕掛け)。デモへ当てるときは
live (qr) と種 (qr_seed) の両方に流す — 毎時のリセットで巻き戻らないようにする
ため (docs/39 §6)。

PGroonga 索引はマイグレーション自身が `CREATE INDEX IF NOT EXISTS` で
張り直すので、手で `\di` を確かめる運用には頼らない (他のマイグレーションと
同じ作法)。

## 5. 検索文法: is:todo / is:done

[search.ts](../src/lib/search.ts) の `SearchTerm` に
`{ kind: 'task'; value: 'todo' | 'done' }` を足し、`tokenize` の `flush` で
タグ (`#…`) と同じ位置に判定を挟む:

- 正規化 (NFKC + 小文字化) 後に `is:todo` / `is:done` と一致したら task 語。
  `ＩＳ：ＴＯＤＯ` も NFKC で畳まれて効く (全角演算子と同じ入力ゆれ吸収)。
- **引用したらリテラル** (`"is:todo"` は文字どおりの全文検索)。`"#tag"` と
  同じ約束で、文法の逃げ道を必ず残す。
- `is:` に続く値が todo / done 以外 (`is:foo`) は**ただの語として全文検索に
  落とす**。壊れた入力は例外にせず「それらしく」解釈する流儀 (未閉じ引用と
  同じ)。誤打で 0 件になるより、本文に `is:foo` と書いたノートが出るほうが説明可能。
- `MAX_SEARCH_TERMS` の数え上げには普通の語として乗せる。

[items.ts](../src/lib/items.ts) の `termCondition` に case を足す:

```sql
is:todo → task_todo > 0
is:done → task_done > 0
```

否定は既存の `!` がそのまま効く (`!is:todo` → `NOT (task_todo > 0)`)。
NOT が三値論理で化けない条件 (NOT NULL 列) も §3 の定義で満たしている。

## 8. 承知しておく制約

- `is:todo` は「未チェック項目を **1 つ以上** 持つノート」。単語帳 (1 ノート
  1 単語) では期待どおりだが、買い物リストのような混在ノートも引っかかる。
  用途タグ (`#英単語`) との AND で絞るのが前提の道具と割り切る。
- 派生列は保存時にしか動かないので、バックフィル前の既存ノートは 0/0 のまま
  (= `is:todo` に出ない)。§4 を必ず一度流す。
- 出題順のシャッフルや「チェック済みを隠す表示」は本計画の対象外。まずは
  検索で回してみて、必要になったら足す (YAGNI)。
