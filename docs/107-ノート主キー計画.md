# ノート主キー計画 (itemNo を外して UUID v7 へ)

ノートの主キーを Ver1 由来の `itemNo` (4 桁番号) から UUID v7 の `id` に
差し替え、旧番号は本文のタグ `#1003` にする。QR シールの URL から
アプリへ飛ぶ用途は残すが、主機能ではなくなる — コードはスキャンして
**検索する**ものであり、QR も JAN も DataMatrix も、旧番号も同じ扱いにする。

決めたこと (2026-10-17):

- 主キーは **UUID v7**。PostgreSQL 18 の `uuidv7()` を列の既定値にする
- 旧番号は列として残さず、**本文タグ** `#1003` に書き出して列を落とす
- QR 印刷 (`/print`) は残す。中身は `/item/<id>` の URL
- 段 1〜3 まで全部やる (§8)

## 1. なぜ主キーを外すのか

いまの `itemNo` は 1 列で 5 つの役を兼ねている。

| 役 | 場所 |
| --- | --- |
| 主キー | `prisma/schema.prisma` の `@id`。180 ファイルが参照 |
| URL | `/item` `/edit` `/print` の `[itemNo]`、`@detail/(.)item/[itemNo]` |
| 外部キー相当 | git 履歴 `notes/<itemNo>.md`、ZIP の項目名、IndexedDB のキー |
| 採番体系 | `nextItemNo()` (1000 以上の最小空き番号。ゴミ箱の行が番号を予約) |
| 並び順 | `itemNoNum` の番号順と、同着の決着 (`lib/offline/order.ts`) |

当初は「QR シールに URL を埋め、カメラアプリから直接ノートへ飛ぶ」のが
主機能で、URL に載る短い番号が主キーであることに意味があった。いまは
スキャンしたコードを検索して開く導線 (docs/09 §3) があり、JAN や
DataMatrix は [docs/10](10-スキャン新規登録計画.md) §1 で「コードはタグ
として本文に置く。正本はメモ本文」と決めた。旧番号だけが例外で、識別子の
列に居座っている。**旧番号もコードの 1 つとして本文に置けば、例外が消える。**

残る役は主キー・URL・外部キー相当の 3 つで、これはどれも利用者に見せる
必要のない値でよい。だから UUID にする。

## 2. 方針

### 2-1. id は UUID v7

serial (整数) ではなく UUID を採るのは 2 つの理由から。

- オフラインで新規ノートを作る (docs/65 の先) にはクライアント側で id を
  振れる必要がある。serial はサーバ往復が要る
- 多人数化 (41-QR-search/docs/23)・別インスタンスの ZIP 取り込みで id が
  衝突しない

v4 ではなく **v7 (先頭 48 bit が時刻)** にするのが要点。移行時に
`item_no_num` の昇順で id を振れば **id 順 = いまの番号順**になり、
「番号順」の並び替えと同着の決着を id に置き換えても見え方が変わらない
(§4-6)。新規ノートも作った順に id が並ぶ。B-tree 索引の局所性も v4 より良い。

生成は 2 か所。

- **DB の既定値** `uuidv7()` (PostgreSQL 18 組み込み)。生 SQL の INSERT や
  スクリプトが id を忘れても行が立つ
- **アプリ側** は `uuid` パッケージの `v7()`。`/new` が `/edit/<id>` へ送る
  前に、ENEX / ZIP の取り込みが行を作る前に振る (`crypto.randomUUID()` は
  v4 なので使わない)。Prisma 側は `@default(uuid(7))` を付けておくが、
  アプリの経路はすべて自分で振るので実際には通らない

### 2-2. 旧番号は本文タグにする

unique nullable の列として残す案も検討したが採らない。残すと「結局 2 つ目の
識別子」になり、JAN と同格にならない。本文タグなら

- 検索・タグチップ・タグリンク・GIN 索引・タグ補完がそのまま効く。新しい
  部品を 1 つも足さなくてよい
- 同じ番号を 2 つのノートに付ける、`#R-07` のような手持ちの記号を使う、
  といった自由が利く
- 「同じ番号のノートが 2 つ」は JAN と同じく**検索結果が 2 件出る**だけ。
  部品箱の 1 枚のシールを複数のノートから参照できるので、むしろ自然

`100x` のような非数字の旧番号もタグ文字 (`\p{L}\p{N}\p{M}` `_` `-`) に
収まる (`ITEM_NO_PATTERN` は `[0-9A-Za-z_-]{1,20}` なので、旧番号は必ず
タグになる)。

受け入れる副作用: **一覧の全行に `#1003` のチップが付く**。JAN のタグと
同じ見え方なので一貫してはいる。うるさければ「数字だけのタグをチップから
隠す」を後から足す (§9 見送り)。

### 2-3. 旧 URL は永久に受ける

印刷済みシール (`http://qr.tommie.jp/item/1003`) と、X にカード付きで投稿
済みの公開 URL (docs/89) を壊さない。解決規則は 1 つ (§3-2)。

### 2-4. QR 印刷は残す

`/print/<id>` が `/item/<id>` の URL を QR にする。URL が約 30 文字から
約 62 文字になるので、QR の版が 2〜3 (25〜29 セル角) から 4 (33 セル角)
に上がる。部品箱の小さいシールには不利だが、シールは主機能ではないと
割り切る。小さくしたければ「タグ文字列だけを QR にする」(どのカメラ
アプリでも読め、自アプリのスキャナが `/?q=` で検索する) を後から足せる
(§9 見送り)。

QR の下の人が読むラベルは、`#1003` の代わりに**ノートの見出し** (`title`
列の派生キャッシュ) を出す。番号を付けた旧ノートは `#1003` のタグが本文に
あるので、見出しと一緒にタグ行の先頭 1 つも添える。

## 3. スキーマとルート

### 3-1. スキーマ

```prisma
model Item {
  // UUID v7。時刻順なので id 順 = 作った順。移行時は旧番号の昇順で振った
  // (docs/107 §2-1)。DB の既定値は PostgreSQL 18 の uuidv7()
  id        String   @id @default(uuid(7)) @db.Uuid
  memo      String   @default("")
  ...                // 以下いまのまま。itemNo / itemNoNum と @@index([itemNoNum]) だけ消える
}
```

列は段階ごとに変える (§8)。最終形で `item_no` `item_no_num` と
`items_item_no_num_idx` が消え、`id` が主キーになる。

### 3-2. ルートと解決規則

ディレクトリ `[itemNo]` を `[id]` に改名する (4 ルート + `print` +
`history`)。受け取った値は 1 つの関数で解決する。

```text
resolveItemKey(key)
  key が UUID (小文字に正規化)   → そのノート (無ければ 404)
  key が旧番号の形 (ITEM_NO_PATTERN)
    段 1〜2: item_no = key の行          1 件 → permanentRedirect(/item/<id>)
    段 3〜:  tags @> ARRAY[key] の行     1 件 → permanentRedirect(/item/<id>)
                                         複数 → redirect(/?q=<key>)
                                         0 件 → redirect(/?q=<key>)
  それ以外                        → 404
```

- 0 件のとき `/?q=<key>` に送ると、docs/10 §3 の「新規登録」ボタンが出る
  (検索 0 件・単一トークン・タグ文字のみ、の条件を満たす)
- `permanentRedirect` (301) にするのは、X や検索エンジンがキャッシュした
  旧 URL を新 URL に付け替えてもらうため。複数・0 件は状況で変わるので
  一時 (307)
- `@detail` の並行ルート (docs/86) でも同じ関数を呼ぶ。ペインの中で
  redirect すると全画面遷移になるので、**スキャナは push する前に**
  サーバアクション `resolveLegacyItemNoAction(code)` で id を引き、
  `/item/<id>` か `/?q=` を自分で選ぶ (docs/09 §3 の判定表はそのまま、
  行き先が 1 段増えるだけ)。ページ側の解決はカメラアプリや X からの直打ち用
- `guardItemPage` は「UUID または旧番号の形」を通し、それ以外を 404 にする。
  `isValidItemNo` は旧番号の形の検証だけに残し、`isLegacyItemNo` に改名する
- `/print/1003` `/edit/1003` も同じ規則で `/print/<id>` `/edit/<id>` へ

`/item/<uuid>` は列挙できないので、docs/90 の「連番だから 1 件でも
クロールされると辿られる」懸念は消える。noindex は変えずに残す。

## 4. 内部参照の切り替え (段 1)

### 4-1. git 履歴

`notes/<itemNo>.md` → `notes/<id>.md`。全ノートを `git mv` して 1 コミット
(`chore: ノートのファイル名を id にする`)。履歴画面
(`/item/<id>/history`) は `git.log({ file })` で引いているので、改名の前を
追うために `--follow` を足す。**simple-git で `--follow` が効くかはローカルの
リポジトリで先に確かめる** (§11)。

### 4-2. ZIP

- 項目名は `notes/<id>.md`。frontmatter に `id` を足す
- 取り込みの突合 (overwrite) は **frontmatter の `id`** を見る。無い ZIP
  (改名前に書き出したもの、`convertWorkbookToZip.mjs` が組む教科書の ZIP、
  手で組んだ vault) は項目名の旧番号を §3-2 の規則で解決し、1 件に決まれば
  上書き、それ以外は新規。新規にするときは旧番号をタグとして本文に足し、
  番号が消えないようにする
- 教科書の入れ直し (docs/104。「冊の ZIP を overwrite」) は、段 3 で全ノートに
  `#<番号>` が入れば旧番号で 1 件に決まるので、ZIP を作り直さなくてよい

### 4-3. オフライン

IndexedDB の `keyPath` を `id` にし、`DB_VERSION` を 2 → 3 に上げて
ストアを作り直す。端末ごとに再同期が 1 回走る (全件 1 クエリなので
vps2 の負荷は増えない)。`/api/sync/items` は `id` を返す。

### 4-4. そのほか id に乗せ替えるもの

| 場所 | 変更 |
| --- | --- |
| `app/new/page.tsx` | `nextItemNo()` の代わりに `v7()` で id を振って `/edit/<id>` へ |
| `app/edit/[id]` | 行が無い id = 作成中 (いまと同じ)。`?code=` の事前入力もそのまま |
| `lib/external/scanRegister.ts` | `scanRegisterHref(id, code)` |
| `lib/enex` `lib/zip/importZip.ts` | ノートごとに `v7()`。取り込み順に id が並ぶ |
| `lib/items/write.ts` `trash.ts` `actions/*` | where / upsert のキーを `id` に |
| `lib/demo/demoQuota.ts` | `where: { id }` |
| エディタの下書き `draftKey` | `id`。旧キーの下書きは孤児になるので、**下書きが無いときに配る** |
| `lib/search/url.ts` `itemNoFromPathname` | UUID を取り出す |
| `lib/search/types.ts` の itemNo 前方一致 | 消す (§4-5) |

### 4-5. 検索

`1003` と打てば本文の `#1003` に全文検索で当たり、`#1003` と打てばタグ
検索で当たる。前方一致 (`10` で 1000 番台) はタグ補完 (docs/59) が担う。
itemNo 前方一致の実装は消す。

### 4-6. 並び順

`itemNo` / `itemNoDesc` の並び替えは **`id` 順に置き換え、表示名を
「番号順」から「登録順」に変える**。§2-1 の振り方により既存ノートは
番号順のまま、以後のノートは作った順に続く。同着の決着 (`compareText(a.itemNo, b.itemNo)`)
も `id` の文字列比較でよい (v7 は辞書順 = 時刻順)。

## 5. 採番の廃止 (段 2)

- `nextItemNo()` と `allItemNos()` を消す。ゴミ箱が番号を予約する仕組み
  (docs/12 §4) も不要になる
- `item_no` を nullable にし、新規ノートには振らない
- `/print/[id]` を id に。ラベルは §2-4
- 編集・印刷ページの `edit #1003` `print #1003` の表示は見出しに変える

段 2 を段 1 と分けるのは、段 1 の「URL だけ変わる」配布で旧シール・
X リンク・オフライン再同期が無事かを iPhone で確かめてから、利用者に
見える変化 (番号が付かない) を入れるため。

## 6. 旧番号を本文へ (段 3)

### 6-1. バックフィル

`scripts/backfillItemNoTags.ts`。全行 (ゴミ箱も) について
`addTagToMemo(memo, itemNo)` を通し、通常の保存経路 (`lib/items/write.ts`)
で書く。派生キャッシュ (`tags` `title` `props` `task_*`) が揃い、git 履歴にも
載る。git は 1 ノート 1 コミットにせず、`notesRepo` の複数パス commit で
1 コミット (`chore: 旧番号をタグにする`) にまとめる。

- `addTagToMemo` は既にあれば何もしないので**何度流しても同じ結果**
- 置き場所は 2 行目のタグ行 (docs/10 §5 の事前入力と同じ形)。見出し
  (1 行目) は動かないので `title` は変わらない
- ゴミ箱の行も対象。復元したときに番号が付いているため
- 公開ノートでも `#1003` は見える。番号は URL に載っていたので、新たに
  漏れるものは無い

検算: `SELECT count(*) FROM items WHERE NOT (tags @> ARRAY[item_no])` が 0。

### 6-2. 列を落とす

バックフィルの検算が 0 になってから、`item_no` `item_no_num` と索引を
落とす migration を当てる。§3-2 の解決規則を `tags @> ARRAY[key]`
(GIN 索引で引ける) に切り替えるのも同じ配布。

**順序が要点**: バックフィルは段 2 のコードで流す (保存経路が列を知って
いる)。列を落とすコードは、全行にタグが入ったのを確かめた後で配る。

## 7. 移行 SQL (段 1)

```sql
-- 1. 列を足す (既定値は PostgreSQL 18 の uuidv7())
ALTER TABLE items ADD COLUMN id uuid NOT NULL DEFAULT uuidv7();

-- 2. 旧番号の昇順で振り直す。1 行 1 ms ずつずらして時刻順 = 番号順にする
--    (uuidv7(interval) は時刻をずらす PostgreSQL 18 の引数)。
--    非数字の旧番号は末尾 (item_no_num が null → NULLS LAST)
WITH ordered AS (
  SELECT item_no,
         row_number() OVER (ORDER BY item_no_num NULLS LAST, item_no) AS rn
  FROM items
)
UPDATE items SET id = uuidv7(make_interval(secs => ordered.rn / 1000.0))
FROM ordered WHERE items.item_no = ordered.item_no;

-- 3. 主キーを付け替える
ALTER TABLE items DROP CONSTRAINT items_pkey;
ALTER TABLE items ADD PRIMARY KEY (id);
ALTER TABLE items ADD CONSTRAINT items_item_no_key UNIQUE (item_no);
```

`prisma migrate` は PGroonga の索引を落とすことがある
(`\di` で確認してから当てる。41-QR-search の memory に記録あり)。
段 3 の migration は `ALTER TABLE items DROP COLUMN item_no, DROP COLUMN item_no_num`
だけ。

## 8. 段階と配布

| 段 | 内容 | 利用者から見える変化 | 配る前に |
| --- | --- | --- | --- |
| 1 | §3 §4 §7。`id` を足し、内部参照と URL を id に | 新規ノートの URL だけ | DB ダンプ + doDumpGit |
| 2 | §5。採番をやめ、印刷を id に | 「＋」で番号が付かなくなる | 段 1 を iPhone で確認 |
| 3 | §6。旧番号をタグへ、列を落とす | タグチップに `#1003` が出る。「番号順」が「登録順」に | バックフィル検算 0 |

各段を 1 つの配布にし、間に iPhone での確認を挟む。段 1 で確かめること:

- 印刷済みシールをカメラアプリで読んで `/item/1003` → 301 → ノートが開く
- X に投稿済みの公開 URL が開く (カードは 1 週間のキャッシュなので当日は旧表示でよい)
- アプリ内スキャナで旧シール → ペインで開く (全画面遷移しない)
- JAN のスキャン → 検索 (変わらないこと)
- オフラインの再同期が 1 回走って一覧が戻る
- ZIP の書き出し → 取り込み (id あり) と、改名前の ZIP の取り込み (id なし)
- ノートの履歴画面で改名前のコミットまで追える

### 8-1. 開発環境

- ローカル DB・E2E 用 `qr_e2e` (`scripts/e2eDb.sh`) の両方に migration を当てる
- git 履歴のリポジトリもローカルで改名を試し、`--follow` を確かめる
- PostgreSQL 18 が前提 (`uuidv7()`)。compose の image の版を確認する

## 9. 見送り

- **タグ文字列だけを QR にする印刷** (§2-4)。URL の QR で困ってから
- **数字だけのタグをチップから隠す** (§2-2)。うるさいと感じてから
- **UUID を大文字 URL にして QR を英数字モードに乗せる**。62 文字が
  版 3 に収まる計算だが、URL の見た目が悪く効果も 1 版分だけ
- **短い乱数 id (10 文字程度)**。URL は短くなるが時刻順が失われ、番号順の
  再現ができない。決定済み (UUID v7)

## 10. テスト

単体:

- `resolveItemKey`: UUID / 旧番号 1 件 / 複数 / 0 件 / 不正、段 1 (列) と段 3 (タグ) の両実装
- `addTagToMemo` をバックフィルの形で 2 度通しても同じ本文
- `order.ts`: 登録順と同着の決着が id の文字列比較になる
- ZIP: id 付き frontmatter の往復、id 無し ZIP の旧番号解決 (1 件 → 上書き、0 件 → 新規 + タグ)
- `scanRegisterHref` / `itemNoFromPathname` が UUID で動く
- `importEnex` / `importZip` が取り込み順に増える id を振る

E2E:

- `/item/1003` → 301 → `/item/<id>`
- スキャナのフェイクカメラ (docs/09 §7) で旧シール QR → ペインで開く
- `DB_VERSION` 更新後のオフライン再同期
- `/print/<id>` の QR の中身が `/item/<id>`

既存テストの書き換えが大きい順: `lib/items/items.test.ts` (131 箇所)、
`app/actions.test.ts`、`lib/offline/*.test.ts`、`components/item/*.test.tsx`、
`lib/zip/*.test.ts`。型を変えればコンパイルが導いてくれるので、追従は
機械的に進む。
