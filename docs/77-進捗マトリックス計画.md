# 進捗マトリックス計画

チェック ([docs/55](./55-チェックボックス操作計画.md)) と 2 段階の習得状態
([docs/60](./60-学習進捗計画.md) §1) を、**表で一望**できるようにする。
` ```matrix ` フェンスを書いたノートを開くと、その場で集計した最新の表が出る。

## 0. 表は 2 つある — 作るのは先に「一覧グリッド」

要望を詰めると、形の違う表が 2 つ出てくる。混ぜると設計が濁るので分ける。

| | 行 | 列 | 答える問い |
| --- | --- | --- | --- |
| **A. 一覧グリッド** | ノート (問 1〜問 9) | チェックの名前 | **どの問題**がまだか |
| B. 集計マトリックス | タグ (単元) | 3 状態の件数 | **どの単元**が弱いか |

**作るのは A。** 理由は 3 つ。

- もともとの要望が「一覧機能がない。`#bjt` の一覧 (性能表) と似たものが
  欲しい」であり、性能表は**行 = ノート、列 = プロパティ**の表そのもの。
  A はその列がチェックに変わっただけの双子で、§4 のとおり実装も双子になる。
- B の「単元どうしを見比べる」価値は単元が 10 個ある人のもの。いまは
  過渡現象 1 単元 9 問で、`#静電気` と打てば件数行の進捗バー
  (docs/60 §2) が同じ答えを返す。
- 9 行の A を見れば B は目で読める。逆は成り立たない (B からは
  「問 4 がまだ」が判らない)。

B は §12 に設計を残す。同じフェンス・同じ安全規則の上に後から足せる。

```text
#電験三種 の学習状況                      9 件 ｜ 学習済み 5 ・自信あり 3

学習済み  自信あり   ノート
  ✓        ✓       #4551 過渡現象 問1 (RC直列)
  ✓        —       #4552 過渡現象 問2 (RL時定数)
  ☐        ☐       #4553 過渡現象 問3 (定常状態)
…
```

## 1. 正本は既にある — 新しいデータを作らない

行も列も既存のものから導ける。テーブルも列も足さない。

- 行 = 検索ヒット (既存の検索文法そのまま)
- 列 = 本文のタスク項目 (`- [ ] 学習済み`)。正本はメモ本文
  ([docs/55](./55-チェックボックス操作計画.md) と同じ考え方)

## 2. 置き場所はノート — フェンスにする

専用ページ `/progress?q=…` を作る案は採らない。**ノートに置く**。

理由は「ノートの機構が全部ついてくる」こと。表にタイトルと `#タグ` が付き、
検索で見つかり、ホーム画面に貼れて、番号順の並びの中に居場所を持ち、
オフラインの印も付けられる ([docs/65](./65-オフライン対応計画.md))。
専用ページはそのどれも持てず、URL をどこかに書き留める必要があり、
その「どこか」は結局ノートになる。**器が最初からノートなら 1 段短い。**

もう 1 つ、**表の周りに文章が書ける**。「今週は静電気を潰す」「目次ノートへ」
と併せて 1 枚にできるのは、生成されたページには真似できない。
表示モード (docs/23) の 4 つ目にする案も同じ理由で採らない — あれは
「どう見たいか」の好みを cookie に持つ仕掛けで、見出しも文章も持てない。

### フェンスは「結果」ではなく「問い」を持つ

このアプリのフェンスは既にこの形をしている。` ```circuitikz ` は SVG ではなく
TikZ のソースを持ち、` ```quiz ` は点数ではなく問題を持つ
([docs/58](./58-CBT問題集計画.md) §1)。` ```matrix ` も**数字ではなく
検索式**を持ち、表は表示のたびに作る。

そのため、**集計結果を本文へ書き込む方式は採らない**
(スクリプトやボタンでノートを書き換えて表を焼く案)。

- 数字が変わるたび本文が変わり、ノートの git 履歴
  ([docs/57](./57-ノートgit履歴計画.md)) がノイズで埋まる
- 焼いた表は他のノートから導ける派生物なので、本文に置くと
  「正本が 2 つある」状態になる。しかも**古くなっても静かに古い**
- 開いたときに集計するなら、そもそも焼く必要がない。`/item` は
  `force-dynamic` でキャッシュを持たない (確認済み) ので、
  「開けば最新」は追加の仕掛けなしで成立する

## 3. 記法 — 1 行目は検索式、以降は `キー=値`

````text
```matrix
#電験三種 !#後回し
sort=itemNo
col=学習済み,自信あり
```
````

### 検索式に `tag=` のような専用キーを作らない

当初案は `tag="#電験三種"` のような全項目 `キー="値"` 形式だった。
**「どのノートか」だけは裸の 1 行**にする。

- `tag=` を作ると、`#電験三種 !#後回し` や OR・括弧
  ([docs/16](./16-検索の論理演算.md)) を表せない。表せるように育てると
  **検索文法の二つ目の書き方**になる。このアプリは検索窓・URL の `q`・
  タグリンクの全部が 1 つの文法に乗っており、そこを割りたくない。
- 裸の 1 行なら、検索窓で試した式をそのまま貼れる。

### 引用符は付けない

値は引用符で囲まない。理由は 2 つ。

- **iPhone で打つから** (docs/58 §2 が YAML/JSON を避けたのと同じ温度感)。
  `"` は日本語キーボードで面倒な文字。
- このアプリの `キー=値` の前例は**プロパティ**
  ([docs/08](./08-プロパティ計画.md)) の `hFE=195` で、引用符を使わない。
  同じ見た目の記法が 2 通りの引用規則を持つのは嘘になる。

### 1 行目とオプション行の見分け

**1 行目は必ず検索式**として読む。2 行目以降を `キー=値` として読む。

これは曖昧さ避けでもある。`hFE=195` はプロパティ検索の**正当な検索式**なので、
全行を `キー=値` として読む実装だと 1 行目の検索式が壊れる。

- 2 行目以降で**知らないキー**が来たらエラー。黙って無視しない
  (打ち間違えたオプションが黙って効かないのが一番たちが悪い)。
- 万一 `sort` という名前のプロパティを検索したくなったら、引用リテラル
  (`"sort=asc"`) で逃げられる — docs/56 §5 で約束した文法の逃げ道が
  そのまま効く。
- 検索式が空 (1 行目が空行) なら絞り込みなし。チェックを持つ全ノートが
  対象になる。

### キーと値は URL の語彙に揃える (日本語にしない)

`並び=番号順` のように画面の呼び名を使う案から変えた。
**`sort=itemNo`** と書く。値の正本は [validation.ts](../src/lib/validation.ts) の
`SORTS` (8 値) で、`?sort=` が運んでいるものと同じ。

日本語の呼び名にしない理由は、i18n より先に**今すぐ効く不具合**がある。

- **逆順が 1 語で書けない。** 並び順は種別と方向を 1 本の文字列に畳んで
  いる ([docs/64](./64-並び順逆順計画.md)、`itemNoDesc` など 8 値)。
  画面の呼び名はこれを「番号順」＋「大きい順」の 2 語で出しており
  ([sortLabels.ts](../src/lib/sortLabels.ts))、`並び=番号順・大きい順` の
  ような複合を発明しないと逆順が指せない。**方向のための第二の文法**が
  生えることになる。
- **1 行目が既に英語**である。検索式は `is:todo` / `OR` / `!` を使う
  (docs/16, docs/56)。その真下に日本語のキーが並ぶほうが不揃いで、
  `sort=` は 1 行目と同じ調子で読める。
- **URL に既に書いている。** 問題集の運用は
  `/?q=%23過渡現象+is%3Atodo&sort=itemNo` をホーム画面に置く形で、
  `sort=itemNo` は打ち慣れた綴りになっている (docs/60 §4)。
- 画面の呼び名は将来 UI の言語が変われば変わる。ノートの本文は
  600 件と git 履歴に残り、**書き換えるには全ノートに触る**ことになる
  (docs/77 §2 が本文への焼き込みを避けたのと同じ理由)。

`SORTS` に無い値はエラーにする。`parseSort` は不正な値を黙って `updated` に
畳む (URL 用の作法) ので、フェンスからは呼ばない。

既定は **`itemNo`**。docs/60 §4 が「順番に回す用途では番号順を使う」
(更新順ではチェックを押した瞬間にノートが先頭へ移り前後が狂う) と
結論しているとおり、問題集の表は番号順が本来の並び。

### 境界: 記法は英語、データは書いたまま

`col=学習済み,自信あり` の**値は日本語のまま**。あれはノート本文に
書いてある文字列そのもの (§4 で照合する) で、記法ではなくデータだから。

同じ線引きで quiz フェンス (docs/58) の `問:` `正解:` `解説:` が日本語なのも
矛盾しない。あちらのキーワードは**日本語の中身に付ける見出し**で、文章の
一部として読まれる。こちらの `sort=` は URL の `?sort=` と同じ**パラメータ**で、
文章ではない。

日本語のキー (`並び=`) を後から別名として受け付けることはできる。
逆に、一度受け付けた綴りを**やめる**ことはできない (ノートに残るため)。
狭く始めて扉を開けておく。

### キーは短く綴る (`col=`、`columns=` にしない)

英語にする以上、**綴りで詰まらない語**を選ぶ。`columns` は `colums` /
`collumn` / `columuns` と崩れやすい綴りの筆頭で、キーは表 1 つにつき
一度しか書かないぶん「たまに書いて間違える」条件が揃っている。

- `col` / `row` は表計算 (COLUMN / ROW)・HTML (`colspan` / `rowspan`)・
  SQL で通っている略で、意味を疑う余地がない。
- **左右が同じ長さになる**。`col` / `row` は 3 文字で揃うので、表の 2 軸だと
  見た目で判る。`columns` / `rows` は不揃いで、別種のものに見える。
- このアプリの記法は元から短い (`is:todo`、`#tag`、DB の列名も `props`)。
  長い綴りを選ぶ理由がない。

### 大文字小文字は畳む。綴り違いは受けずに教える

**値とキーは小文字化して比べる** — `sort=ItemNo` も `SORT=itemno` も通る。
半角に直させるだけの門番にはしない、という既存の作法 (quizParse が全角
コロンと全角数字を許しているのと同じ理由。docs/58)。iPhone の入力では
大文字の N が余分な一手になる。

一方で**綴り違い (`cols=` / `column=`) は受け付けない**。受け付けた綴りは
やめられないので、増やすほど後が固くなる。代わりに**エラーで教える**:

```text
matrix: 知らない設定「cols」です。col= のことですか？
```

判定は [fenceLanguages.ts](../src/lib/fenceLanguages.ts) の `editDistance`
(Damerau、上限付き) をそのまま使う。フェンス名の打ち間違いを linter が
拾う仕掛け (`suggestFenceLang`) と同じ道具で、書き足すのは候補の表だけ。

### `col=` が無いときは「状態」1 列

`col=` を省くと、チェックの名前ではなく**3 状態**
(未着手 / 学習中 / 習得。docs/60 §1) の 1 列を出す。

これは手抜きではなく**費用の階段**になっている (§4)。3 状態は
`task_todo` / `task_done` から判るので本文を読まずに済む。
名前の付いた列が欲しいときだけ本文を読む。

`col=` の値はカンマ区切り。**ラベルにカンマは使えない** (使いたく
なったら `col=` を複数行に分ける形へ広げる余地は残す)。列は 4 つまで。

### fenceLanguages への登録

[fenceLanguages.ts](../src/lib/fenceLanguages.ts) の `MATRIX_LANG` を
`RENDERED_LANGS` と `FENCE_LANGUAGES` に足す。打ち間違い (`matirx`) を
エディタの linter が警告する。**`RENDERED_LANGS` に入れると一覧の
プレビューと要約も自動で正しくなる** —
[NotePreviewThumb](../src/components/NotePreviewThumb.tsx) は描画対象
フェンスを枠に置き換え、[memoSummary.ts](../src/lib/memoSummary.ts) は
フェンス本文を要約から除くので、カードに `#電験三種` の生テキストが漏れない。

### フェンスの中のタグはノートのタグにならない

`extractTags` は `stripCode` を通す ([tags.ts](../src/lib/tags.ts)) ので、
フェンスに書いた `#電験三種` は**そのノートのタグにはならない**。
表のノートを `#電験三種` で見つけたいなら、いつものタグ行に自分で書く。

副作用として都合がよい面もある: フェンスを書いただけでは自分のタグが
増えないので、タグ補完も `listTags()` も汚れない。

## 4. 実装は特性表 (`#bjt` の性能表) の双子

[searchItemProps](../src/lib/items.ts) が既にやっていることと、この表が
やることは同じ形をしている。**新しい型を持ち込まず、あれをなぞる。**

| | 特性表 (既存) | 一覧グリッド (本計画) |
| --- | --- | --- |
| 行 | 検索ヒットのうち props を持つノート | 検索ヒットのうちチェックを持つノート |
| 絞り | `HAS_PROPS` | `HAS_TASKS` (`task_todo > 0 OR task_done > 0`) |
| 取る列 | `item_no, memo, props` | `item_no, memo, task_todo, task_done` |
| 行の見出し | `memoSummary(memo)` | 同じ |
| 上限 | `PROPS_TABLE_LIMIT` (200) + 1 件多く取る | `MATRIX_ROW_LIMIT` (200) |
| 溢れ | `omitted` を返して画面が断る | 同じ |
| 並び | `buildOrderBy(sort)` | 同じ |

**memo を全行ぶん取ることも含めて前例どおり。** 特性表は既にそうしていて
(`要約はここで作り、memo 全文をクライアントへ送らない`)、200 件の上限が
その歯止めになっている。表として読める大きさと、取ってよい大きさが
同じところにあるのは偶然ではない。

### 列の中身: `checkStates` (純関数)

`col=` があるときだけ本文を読む。
[taskCheckbox.ts](../src/lib/taskCheckbox.ts) の `countTasks` の隣に置く。

```ts
checkStates(memo): { label: string; checked: boolean }[]
```

`countTasks` と同じ `MEMO_PARSER` + `visit(tree, 'listItem')` で、
`node.checked` が非 null の項目の**表示テキスト**を拾うだけ。
物差しが同じなので、コードフェンスの中の擬似タスクを数えないことも、
シークレット断片の中を見ないことも自動で揃う (docs/56 §2 と同じ理由)。

- ラベルの照合は **trim + NFKC 正規化して完全一致**
  (`normalizeTag` と同じ流儀)。前方一致にはしない —
  `学習済み` が `学習済みだが自信なし` に黙って当たるほうが怖い。
- 同じラベルが 1 ノートに 2 つあれば**最初の 1 つ**を使う。

### セルは 3 状態 — 「その項目が無い」を潰さない

| 見た目 | 意味 |
| --- | --- |
| ✓ | チェック済み |
| ☐ | 未チェック |
| — | **そのノートにその名前の項目が無い** |

3 つ目が要点。`- [ ] 自信あり` を書き忘れた問題ノートは、`—` で
はっきり出る。ここを `☐` に丸めると「まだやっていない」と見分けが付かず、
**書き忘れが永久に埋もれる**。表が自分のノートの点検にもなる。

## 5. 配線は circuitikz と同じ「事前計算を渡す」

フェンスの描画に本文以外のものが要る前例は回路図で、その型をなぞる。

- 鍵は**フェンス本文 (trim 済み)**。
  [circuitFences.ts](../src/lib/circuitFences.ts) と同じで、同じ内容の
  フェンスが 2 つあれば 1 回の集計を共有する。行番号や id は要らない
  (docs/78 が行番号を要するのと対照的に、こちらは位置に依存しない)。
- `ItemView` が `Promise.all` の中で `buildMatrices(memo)` を待ち、
  `NoteBody` → `MarkdownView` の新しい任意 prop
  (`matrices?: ReadonlyMap<string, MatrixResult>`) として渡す。
  `circuits` / `blobKinds` と同じ既存の作法。
- `MarkdownView` の `preOrDiagram` に分岐を 1 つ足す。**map に無ければ
  コードブロックに落ちる** — これが安全側の既定になる (§6)。
- 1 ノートの表は `MAX_MATRICES_PER_MEMO` (4) まで。超えた分はエラー項目に
  する (`MAX_CIRCUITS_PER_MEMO = 8` と同じ扱い)。1 フェンス = 1 クエリなので、
  上限が無いと 1 ノートで DB を殴れる。
- 形式エラー (知らないキー・`SORTS` に無い並び順・列が 5 つ以上) は
  「何が悪いか + 元ソース」を出す
  ([CircuitDiagram.tsx](../src/components/CircuitDiagram.tsx)、docs/58 §2)。

## 6. 公開ノートでは表を出さない (ここが一番危ない)

**公開ノート ([docs/22](./22-ノート公開計画.md)) にこのフェンスが
あっても、匿名の閲覧者には表を出さない。**

これは「書き込みを伴うから外す」ではなく**情報漏れだから外す**。
表の中身は**そのノート 1 枚の外**から作られる — 非公開ノートの番号・
タイトル・学習状況が行として並ぶ。これまでフェンスは自分の本文しか
映さなかったので、「公開したノートに書いてあることだけが公開される」という
不変条件があった。DB を引くフェンスはそれを破る初めての描画物になる。

前例は同じ形で断っているシークレット断片:
`/api/secrets/[name]` はログイン必須で、**公開ノートが断片を参照していても
暗号文は渡さない** ([docs/51](./51-部分暗号化計画.md) §10)。

### 落とし穴: 公開ビューは `renderCircuits` を呼んでいる

回路図の型をそのまま真似すると事故る。
[PublicItemView.tsx](../src/components/PublicItemView.tsx) は匿名の
閲覧者に対しても `await renderCircuits(memo)` を実行しており
(回路図はフェンス自身の中身だけから作れるので正しい)、**同じ場所に
`buildMatrices(memo)` を並べたら漏れる**。

したがって「公開ビューには渡さない」を実装時の判断に頼らない:

- `buildMatrices` は `requireUser()` を内部で呼ぶ。公開ビューから
  呼ばれたら例外になり、静かに漏れるのではなく落ちる。
- 渡さなければフェンスはコードブロックとして出る (§5)。フェンス本文
  (検索式) は本文そのものなので、公開ノートでは元から見えている —
  **コードブロックに落ちても新たに漏れるものはない**。
- テストで固定する: 公開ビューの描画に表が出ないこと。

`/docs/*` のページ (公開) は元から `circuits` を渡していないので、
同じ理由で何もしなくてよい。

## 7. 行から開くと前後ナビが効く

行の見出し (番号 + タイトル) のリンクは
`buildItemUrl(itemNo, 検索式, 並び)` で組む。

`q` を載せると、開いた先のノートに**「← 前 / 一覧へ / 次 →」**が出る
(docs/60 §4)。つまり**表から 1 問目を開けば、そのまま 9 問を順に
回して戻ってこられる**。表は入口であって行き止まりではない。

セル (✓ / ☐) はリンクにしない。§9 のとおり押して切り替えることもしない。

## 8. オフラインでは端末側で組む

圏外でもこの表は出せる。回路図は「サーバで描いて同期の応答に焼き付ける」
必要があったが ([docs/65](./65-オフライン対応計画.md) §8)、こちらは
**材料が既に端末にある**。

- `OfflineApp` はスナップショット全件を持ち、検索式の評価器
  ([offline/filter.ts](../src/lib/offline/filter.ts)) で絞れる。
  行の組み立て (`checkStates` を含む) は純関数なので、同じ関数がそのまま動く。
- 同期の応答に足すものは無い (`circuitsOmitted` のような予算の話も無い)。
- ただし**行のリンク先はオンラインの `/item`** なので、圏外では
  オフライン閲覧の URL へ向ける必要がある。初版はここを割り切って
  **オフラインでは表を出すがリンクにしない**でよい。

初版で §8 まで作らない判断もできる (フェンスが未計算ならコードブロックに
落ちるだけ。docs/65 §8-2 と同じ degradation)。ただし**同じ純関数が動く**
形にしておくことは初版から守る。

## 9. 表からチェックは押せない (初版)

「表のセルを押してチェックできれば速い」は成り立つ。`toggleMemoTaskAction`
は既に `itemNo` を引数に取るので、技術的にも届く。それでも初版では出さない。

- 表のセルには**問題文が見えていない**。ノートを開いて押すのは
  「解いた・理解した」の確認を伴うが、表の上の連打はただの塗り絵になる。
- docs/55 §7 の「行番号が古い」問題が**他のノートに対して**起きる。
  自分が見ている本文ではないので、ずれても気づけない。
- 表のノートを再描画するために、押すたび全行を集計し直すことになる。

行から開けば 1 タップで本文に着き、そこで押せる (§7)。まず読むための表
として使ってみてから考える。

## 10. 見た目

- 1 行目: 件数と、名前付きの列ごとの済み数
  (`9 件 ｜ 学習済み 5 ・自信あり 3`)。率のバーは docs/60 §2 の
  [TaskProgress](../src/components/TaskProgress.tsx) と同じ描き方
  (率は床関数、バーは `aria-hidden`、色だけに頼らず数字を併記)。
- ✓ / ☐ / — は記号で伝える。色だけに頼らない (docs/58 §3 と同じ理由)。
- iPhone 幅では表を `overflow-x: auto` の帯に入れる。**帯は縦のはみ出しも
  切る** (`overflow-x` を指定すると `overflow-y` も `auto` に計算される。
  [docs/11](./11-アプリ的UIUX計画.md)) ので、ポップアップを持つ物は帯に入れない。
- **帯を敷くだけでは足りなかった。** 初版はノート列に `max-w-56` (224px) を
  固定で掛けており、iPhone (幅 390px) で最後の列が 85px はみ出して横スクロール
  しないと見えなかった (実測: 帯 330px に対して表 416px)。一覧して比べるための
  表なので、**1 画面に収まることを列の幅より優先する**:
  - チェックの列は `w-px` + `whitespace-nowrap` で**自分の文字ぶんだけ**に縮む
  - ノート列は `w-full max-w-0` + `truncate` で**残り全部**を取って中身を切る
    (表組みで 1 列だけ省略記号にするときの定石)
- **チェックの列を先に置く** (ノートの名前より左)。表を開く目的は「どれがまだか」を
  一目で見ることで、名前はその次 — 左端に揃っていれば横に目を振らずに縦へ読める。
  名前を先にすると、狭い画面で真っ先に潰れるはずの名前が場所を先取りしてしまう。
  実測 (390px): チェック 2 列が 30〜174px、ノートが 174〜360px

  これで列がいくつでも自動で釣り合う。320px でも溢れず、先に潰れるのは
  タイトルで番号とチェックは残る — 番号があれば押して開けるので、
  潰れる順序としてこれが正しい。文字サイズ (docs/61) を上げて溢れたときは
  帯のスクロールが受け止める。
- 行が上限 (200) を超えたら「他 N 件」と明示する。黙って切らない。

## 12. 後段: 集計マトリックス (タグ × 3 状態)

§0 の B。単元が増えて 9 行の表では見比べられなくなったら足す。
**同じフェンスに `group=tag` を足す**形にすれば、記法も安全規則
(§5〜§8) もそのまま使える。

```text
タグ        未着手   学習中   習得     率
過渡現象      2       3       4      44%
静電気        5       1       3      33%
```

設計上の要点だけ書き残す。

- **`row=tag` ではなく `group=tag`。** `col=` と `row=` は対に見えるが、
  実は別種のつまみ — `col=` は「どの列を出すか」のラベル並びで、
  こちらは「何を 1 行にまとめるか」の切り替え。対の顔をさせると
  「では `row=` にラベルを並べたら？」という無い機能を期待させる。
  集約は SQL の `GROUP BY` そのものなので、その語を借りる。

- 取るのは `item_no, tags, task_todo, task_done` (memo は要らない)。
  **畳むのは純関数**にする — オフラインでも同じ関数が動き、DB 無しで
  テストでき、行数を数えるだけで合計が出る。
- **SQL で `unnest` + `count(*) FILTER` して集計しない。** タグ 3 つの
  ノートが 3 回数えられるので、合計行を同じクエリから導けず、別クエリで
  数え直す羽目になる。行を持てば起きない。
- 基底クエリのタグ自身は行から除く (全ノートに付いているので合計の複製)。
- 行は排他ではない (`#過渡現象 #難` は両方の行に乗る)。単元別と難易度別が
  同じ表で読める利点があるが、列を縦に足しても合計とは一致しない。脚注で断る。
- セルのリンクを組むには、基底クエリから task 語を**文字列レベルで**
  落とす必要がある (`stripTaskTokens`)。基底に `is:todo` が残っていると
  習得セルの `!is:todo` と矛盾して 0 件になり、セルの数字と飛んだ先の
  件数が食い違う。AST から落とす `stripTaskTerms` (docs/60 §2) は
  SQL 用で、こちらには使えない。

## 13. やらないこと

- **専用ページ `/progress?q=…`** — §2 のとおりノートに置く。
- **集計結果を本文へ焼き込む** — §2。git 履歴が埋まり、静かに古くなる。
- **表からチェックを押す** — §9。
- **`tag=` / 引用符付きの全キー形式** — §3。検索文法を二重に持たない。
- **ライブプレビューでの集計** — エディタのライブプレビュー
  ([docs/70](./70-編集ライブプレビュー計画.md)) は `MarkdownView` を通らず、
  回路図だけが専用の `POST /api/circuits` を叩いている。同じ口は作らない。
  フェンス本文は数行で、打っている最中に表が見えて嬉しい物ではない。
  編集中は素のテキストとして見え、表示タブで集計される。
- **「この検索の表をノートにする」ボタン** — フェンス数行を手で書けば済む。
- **検索結果を埋め込む汎用フェンス** — 一覧・件数・特性表 (`#bjt` の
  性能表) も同じ形でノートに置ける筋は見えているが、この表 1 つで型を
  確かめてから。汎用化を先に作らない (YAGNI)。

## 14. 承知しておく制約

- 列はラベルの文字列一致なので、**ノート側で表記を揃える必要がある**
  (`学習済み` と `学習ずみ` は別の列)。揃っていなければ `—` で出るので、
  静かに間違うのではなく目に見える形で失敗する (§4)。
- チェックを学習以外に使うノート (買い物リスト等) が同じ検索に入ると
  行に混ざる。docs/56 §8 と同じで、用途タグで括るのが前提。
- 表のノートを開くたびに集計クエリが 1 本走る。`/item` は元から
  `force-dynamic` なのでキャッシュの心配は無いが、**アクセス順の一覧では
  表のノートが常に先頭に来る** (`RecordAccess` が `accessed_at` を進める)。
  毎日開くダッシュボードなので実害はなく、むしろ都合がよい。
- **表のノート自身も検索にヒットしうる。** チェックを 1 つでも書けば
  (`- [ ] 今週やる`) 自分の表に 1 行混ざる。行 = ノートなので目に見えて
  気づけるが、気になるなら検索式で除ける (`!#進捗表`)。§12 の集計側は
  数字に紛れて気づけないので、あちらは `excludeItemNo` で構造的に除く。
- **Ver3 (マルチユーザ) では `user_id` の条件が必須になる。** 現在の DB は
  単一テナントで `Item` に所有者列が無いため、この検索は「DB 全体」を
  引いている。同じ性質は `listTags()` にもあるが、**公開できるノートの
  中に他人のノートの番号とタイトルが出る**この機能は影響が大きい。
  行レベル所有 (README Ver3) を入れるときの確認箇所として書き残す。
- デモ ([docs/38](./38-デモモード計画.md)) は独立した DB なので、デモの
  ノートに置いた表は種データを映す。毎時のリセットで巻き戻る。
