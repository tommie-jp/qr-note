# 速度計測ログ計画

検索表示の高速化 (docs/118) は「着手前と後で同じ方法で測る」ことを前提に
しているが、§5 の本番計測は PC が DevTools・iPhone が「体感」で、iPhone には
Mac 無しでインスペクタを繋げない。アプリ自身に**サーバとブラウザの両方で
時間と量を 1 行ずつ記録させ、/logs で読める**ようにして、本番・iPhone でも
同じ数字で前後を比べられるようにする。

決めたこと (2026-10-28):

- 記録は `[計測]` で始まる 1 行 (`種別 key=値 key=値 …`、順序固定)。
  /logs の「コピー」で手元へ持ち出し、表計算に貼れる形にする (§1)
- 控えは warn/error とは**別のリングバッファ** (`perf`、200 件)。/logs の
  既定表示には混ぜず、`/logs?perf=1` でだけ出す (§1-3)。打鍵ごとに 1 行
  積む計測が、肝心の警告を押し流してはいけない
- 切替は `/logs?perf=1` の「計測を始める / 止める」(実行時の切替。§1-4)。
  サーバの段階も、ブラウザの観測も、立っているときだけ動く。切っていれば
  今と同じ (起動行だけ)。再起動・配布で止まる
- 測るのは 4 つの場面: 検索 (打鍵→差し替え)、ノートを開く、オフライン同期、
  起動。それぞれサーバの段階とブラウザの観測を**同じ 1 行に**まとめる (§2・§3)
- 転送にかかる時間はアプリからは見えないので、本番の nginx に時間付きの
  アクセスログを足す (§4)
- ノート本文や検索語の全文は行に載せない (§1-5)

## 0. 何が判れば十分か

docs/118 の見立ては「DB もサーバも速く、転送量とブラウザの描画が重い」。
本番と iPhone でそれを確かめ、§1 (フォルダーペイン)・§2 (同期)・§3 (prefetch)
を入れるたびに効き目を見るには、検索 1 回について次が要る。

| 知りたいこと | どこで測るか |
| --- | --- |
| サーバが結果を組むのに何 ms か (vps1 の CPU で) | サーバ: `loadSearchResults` の段階 (§2-1) |
| 応答が届き始めるまで・届き切るまで | ブラウザ: RSC 要求の resource timing (§3-1) |
| 何バイト運んだか (gzip 後 / 展開後) | ブラウザ: resource timing (§3-1)、nginx (§4) |
| 差し替えの描画に何 ms か・DOM が何ノードか | ブラウザ: commit 後の時刻と DOM の数 (§3-1) |
| 裏で何本 prefetch が走ったか | ブラウザ: 打鍵からの resource entry の数 (§3-1) |

同期は「何 MB を何秒で、サーバのメモリをどれだけ使って」(§2-3・§3-3)、
ノートは「DB・集計・本文描画のどこが重いか」(§2-2・§3-2)、起動はいまの
`[起動]` 行で足りている (§3-4)。

## 1. 器 — 行の形・控え・表示・切替

### 1-1. 行の形

```text
[計測] 検索 q="抵抗" panes=3 view=compact 件数=21/48 全体=624ms 応答開始=120ms
       受信=310ms 描画=180ms RSC=145KB/1200KB prefetch=63 DOM=8143
       サーバ=23ms(検索=3 特性=0 サムネ=2 プレビュー=12)
[計測] ノート id=019a… 全体=410ms 応答開始=90ms 受信=200ms 描画=110ms
       サーバ=35ms(読込=4 一覧=6 添付=3 集計=20) 本文=12KB 画像=3 回路=1/1
[計測] 同期 結果=200 全体=1900ms 応答開始=350ms 受信=1300ms 解析=120ms
       保存=130ms 転送=10800KB/10800KB 件数=1148 回路=455
       サーバ=(db=40 json=90 gzip=0 rss=312MB)
[計測] 同期 結果=304 全体=80ms
[計測] 遅いSQL 時間=120ms 文="SELECT ..."(先頭 200 文字)
```

(実際は 1 計測 = 1 行。上は紙面の都合で折り返している)

- 先頭は `[計測]` と**種別** (検索 / ノート / 同期 / 起動 / 遅いSQL)。
  種別ごとに key の並びを固定する — 読むときは「どこで急に増えたか」を
  左から右へ追う (`[起動]` 行と同じ考え)。表計算に貼るときは空白で区切る
- 時間は `123ms`、量は `145KB` の整数。`ms` を付けるのは目で読むためで、
  集計するときは `scripts/perfSummary.mjs` (§6-3) が剥がす
- 立っていない印は `未了` (bootTiming の `msOrPending` と同じ。0ms と
  書くと意味が反対になる)
- 組み立ては純関数 `formatPerfLine(kind, fields)` (`src/lib/logging/perfLine.ts`)
  に集め、サーバもブラウザも同じ関数で書く。key の順序は種別ごとの配列で
  持ち、知らない key は末尾に回す

### 1-2. 控え (サーバ側)

`logging/buffer.ts` に 3 本目のバッファ `perf` を足す。`LogSource` に
`'perf'` を足すのではなく、`LogEntry` に `kind: 'log' | 'perf'` を足す —
計測行にも「サーバで測った / iPhone で測った」の区別 (`source` と `device`)
は要る。

- `pushPerfLine(text)` … サーバの段階を積む。同時に `console.log` で stdout
  にも同じ行を出す (`docker compose logs app | grep '^\[計測\]'` で、
  200 件を超えた分も集計できる)。**warn/error の包みは通らない**
  (通すと server バッファにも積まれて二重になる)
- `pushBrowserLogs()` は `ClientLogItem` の `kind` が `'perf'` なら perf
  バッファへ振る。送る側 (`clientPayload.ts`) の形に `kind?: 'perf'` を足し、
  受ける側の検算で `'perf'` 以外は捨てる
- `recentLogs()` は今までどおり log だけ。`recentPerfLines()` を別に足す。
  `clearLogBuffer()` は 3 本とも消す (調査の「消してから再現」は計測でも同じ)

### 1-3. 表示 (/logs)

- 既定の /logs は変えない (計測行は出さない)。見出しの脇に「計測」への
  リンクを足し、`/logs?perf=1` で計測行だけを新しい順に並べる。バッジは
  `計測` 1 種類 + 端末 (サーバ / iPhone / PC)
- 「コピー」は計測ページでは `formatPerfLinesForCopy()` — 1 行 1 計測で、
  先頭に時刻 (`10/28 21:03:11`) を付けた素の行。既定ページの 2 行形式
  (`[level] source 時刻` + 本文) は混ぜない
- 「消去」はページごと。計測ページの消去は計測行だけ (`/api/logs/clear?perf=1`)、
  既定のページの消去は警告・エラーだけを消す。片方を消すともう片方の調査の
  証拠まで消える形にしない
- コピーの時刻は `10/28-21:03:11` (日付と時刻の間を `-`)、検索語の中の空白は
  `_` に潰す。空白で区切ったときに列がずれないため

### 1-4. 切替

**実行時に /logs?perf=1 のボタンで切り替える** (`POST /api/logs/perf`、本文は
`{ enabled: boolean }`)。値はプロセスの中 (`logging/perfSwitch.ts` の
`isPerfLogEnabled()`) に持つので全端末に効き、再起動・配布で止まる。既定は
環境変数 `PERF_LOG` (`"1"` なら起動直後から計測)。

計画の初版は環境変数だけで切り替える形だったが、実装で改めた (2026-10-28)。
本番で環境変数を変えるには compose.yaml と vps1 の `.env` を直して作り直す
必要があり、測るたびにその手間が掛かる。計測は「測る期間だけ立てる」もの
なので、押して立てて押して止める形のほうが合う。

- サーバの段階 (§2) は、立っていなければ `startPhases()` が何もしない
  計時器を返す (呼び出し側に if を配らない)
- ブラウザの観測 (§3) は、root layout が `PerfReport` と `PerfMarks` を
  **描くかどうか**で決める (`AppSideEffects` に `perf: boolean` を渡す)。
  立っていなければ観測のコードも Observer も動かない
- 各端末は**読み込み直してから**測り始める (`PerfReport` は root layout が
  描くので、ソフトな遷移では現れない)。ボタンを押した端末は自分で読み込み直す
- Prisma の遅い SQL (§2-4) だけは client を作る時点で `PERF_LOG` を読む
  (ログ設定は後から変えられない)。本番の compose.yaml は `PERF_LOG` を渡して
  いないので、**本番では遅い SQL は出ない**。段階の時間 (`検索=` など) が DB の
  代わりの目安になる

常時 ON にしない理由: ブラウザ側は打鍵ごとに 1 行をサーバへ送る
(Beacon とはいえ iPhone の回線を 1 本使う) し、PerfMarks の props が RSC に
数十バイト乗る。測る期間だけ立てて、終わったら戻す。

### 1-5. 載せないもの

- ノートの本文・検索語の全文。検索語は 20 文字で切る (`q="抵抗"`)、ノートは
  id と本文の**長さ**だけ
- 遅い SQL (§2-4) は文の先頭 200 文字だけで、**パラメータは載せない**
  (本文の断片や検索語が入る)
- /logs はログイン必須・デモでは 404 のまま。計測ページも同じ門番を通す

## 2. サーバ側 — 段階の計時

### 2-1. 検索 (`loadSearchResults`)

`src/lib/logging/phase.ts` に小さな計時器を置く:

```ts
const t = startPhases(isPerfLogEnabled())   // 計測していなければ no-op
const result = await t.time('検索', () => searchItems(...))
...
t.done()                           // { totalMs, phases: { 検索: 3, ... } }
```

`Promise.all` で並べている 4 本 (検索・特性・ゴミ箱・進捗) はそれぞれ
`t.time()` で包み、合計ではなく**各々の時間**を残す (並列なので全体は
最大値に近い)。その後の回路図サムネ・数式・プレビューも 1 段階ずつ。
`loadSearchResults` の戻り値に `perf: PerfPhases | null` を足し、
`HomeResults` が次の 2 つに使う:

- `pushPerfLine()` で**サーバの行**を積む (`[計測] 検索/サーバ` に q・panes・
  view・件数・全体・検索・特性・サムネ・プレビュー)
- `<PerfMarks kind="検索" server={perf} />` (client component、何も描かない)
  を結果の中に置く。ブラウザは RSC で届いた props をそのまま自分の行の
  `サーバ=` に写す (§3-1)。サーバの行とブラウザの行を時刻で突き合わせる
  手間が消える

`page.tsx` の `listTags()` と `SearchFolders` の 3 本 (フォルダー集計・
ゴミ箱・登録パターン) も同じ計時器で `[計測] 検索/固定部` に 1 行。
docs/118 §1 で fallback を殻にしたあと、ここが伸びていないかを見る。

**測れないもの**: RSC の直列化と react-markdown の描画 (プレビュー・自動ノート
の本文) は React が木を描く中で起きるので、段階としては切り出せない。
nginx の `$upstream_response_time` (§4) からこの行の `全体=` を引いた残りが
それにあたる。

### 2-2. ノート (`ItemDetail` / `ItemView`)

`loadDetail` の 3 本 (ユーザー・`getItem`・一覧の前後) と、`ItemView` の
`Promise.all` 3 本 (印の添付量・matrix 集計・health 集計) を同じ計時器で
包む。`planCircuits` は描画を待たないので、**本数とキャッシュ命中の数**だけ
載せる (時間ではない)。行は `[計測] ノート/サーバ id= 本文=12KB 画像=3 回路=1/1 全体= 読込= 一覧= 添付= 集計=`。
`ItemView` の末尾に `<PerfMarks kind="ノート" id={itemId} server={perf} />`。

全画面 (`/item/[id]`) と 3 ペインの横取り (`@detail`) は同じ `ItemDetail` を
通るので、1 か所で両方が取れる。

### 2-3. 同期 (`/api/sync/items`)

route handler で `loadOfflineSyncPayload` (さらに中の `findMany` と回路図) と
`JSON.stringify` を計時し、docs/118 §2-A の gzip・§2-B の ETag が入ったら
その段階も足す。加えて `process.memoryUsage()` の rss と heapUsed を**応答を
組んだ直後**に読む — vps1 (2GB) で 10MB の文字列と gzip を同時に積んだときの
山がこれで見える (`docker stats` を横で見張らずに済む)。

- `[計測] 同期/サーバ 件数= 回路= rss= heap= サーバ=…(db= json=)`
- 応答に `Server-Timing: db;dur=40, json;dur=90` を付ける。route が
  `apiOk` の応答のヘッダに書き足す (`respond.ts` は変えない)。段階の名前は
  ASCII に限る (`formatServerTiming` が日本語の名前を落とす)。ブラウザは
  resource timing の `serverTiming` から読んで自分の行に写す (§3-3)。値は
  時間だけで、秘密は含まない

### 2-4. 遅い SQL (Prisma)

`db.ts` で起動時に `PERF_LOG=1` のときだけ
`log: [{ level: 'query', emit: 'event' }]` を付け、`$on('query')` で
`duration >= SLOW_QUERY_MS` (50ms) のものを `[計測] 遅いSQL 時間= 文="…"`
として積む。文は先頭 200 文字、パラメータは載せない (§1-5)。

docs/118 §0 では手元 (24 コア) で全部 1ms 未満だったが、vps1 の CPU と
メモリで同じかは未確認。閾値を超えた物しか出ないので、何も出なければ
「DB は本番でも速い」の裏付けになる。

## 3. ブラウザ側 — 観測

`src/components/diag/PerfReport.tsx` (何も描かない、root layout で
計測中だけ置く) が観測の本体を持ち、`src/lib/logging/perf.ts`
に純関数 (resource entry の選別・数え上げ・行の組み立て) を置く。
送信は `clientCapture.ts` の待ち行列を使う (`kind: 'perf'` 付き)。
3 秒ごとの flush と `pagehide` の Beacon はそのまま借りる。

### 3-1. 検索 (打鍵 → 差し替え)

1. **開始**: `SearchNav.navigate()` が `performance.mark('qr:検索:開始')` を
   打ち、`perf.ts` の進行中の計測に `{ kind: '検索', q, t0 }` を置く
   (`AutoLoadMore` の追加読み込みも同じ口で `kind: '追加'`)
2. **サーバの段階**: 届いた `<PerfMarks kind="検索" server={…}>` が
   `useEffect` で進行中の計測へ `server` を渡す。**commit 後**に走るので、
   この時刻が「差し替えの描画が終わった時刻」でもある
3. **終了**: `PerfMarks` の effect から `requestAnimationFrame` を 1 つ挟んで
   (描画が画面に出た時刻) 行を閉じる。そのとき:
   - RSC 要求: `performance.getEntriesByType('resource')` のうち、名前に
     `_rsc=` を含み `startTime >= t0` の中で**一番大きい** entry を本体とみなす
     (他は prefetch)。`responseStart − startTime` を応答開始、
     `responseEnd − responseStart` を受信、`transferSize` / `decodedBodySize`
     を `RSC=`。Service Worker 経由で `transferSize` が 0 のときは `キャッシュ`
     と書く (0KB と書くと「何も運ばなかった」に読める)
   - prefetch: 同じ窓の残りの `_rsc=` entry の数。docs/118 §3-1 の効き目は
     これが 0 になることで確かめる
   - 描画: effect の時刻 − RSC 要求の `responseEnd`
   - DOM: `[data-results-pane]` の `querySelectorAll('*').length`
   - 長いタスク: `PerformanceObserver` の `longtask` (Chromium だけ。
     Safari は無いので `未対応`) を窓の間だけ数え、`長タスク=3/420ms`
4. 送る。key の並びは q・panes・view・件数・全体・応答開始・受信・描画・
   RSC・prefetch・DOM・長タスク・サーバ (§1-1 の 1 行目)

打ち直しで前の計測が閉じないまま次が始まったら、前の分は `中断` として
閉じる (`全体=` だけ、他は `未了`)。15 秒を超えても閉じていなかった計測は
`結果=未着` とだけ書く (開いたままのノートを押し直した・旧 URL が別の id へ
転送された、など閉じる印が来ない場合。待つと利用者の手待ちが全体に入る)。
一度届いた印 (`at`) は覚えておき、戻る/進むでルーターのキャッシュから同じ
印が描き直されても計測を閉じさせない。debounce が 300ms なので頻繁ではないが、
黙って捨てると「遅いときほど記録が残らない」になる (起動計測で踏んだ罠)。

`panes` / `view` は cookie ではなく、`PerfMarks` の props でサーバから
もらう (ブラウザで cookie を読み直さない)。

### 3-2. ノートを開く (行を押す → 本文が出る)

1. **開始**: `PerfReport` が `click` を capture で聞き、`a[href^="/item/"]`
   なら `{ kind: 'ノート', id, t0 }` を置く (`SearchResults` の
   `recordOnOpen` と同じ判定。全画面でも 3 ペインの横取りでも同じ a 要素)
2. **終了**: `ItemView` 末尾の `<PerfMarks kind="ノート" id=…>` が commit 後に
   走り、id が一致する進行中の計測を閉じる。RSC 要求の選び方は §3-1 と同じ
3. `[計測] ノート id= 全体= 応答開始= 受信= 描画= RSC= 本文= 画像= 回路= サーバ=(…)`

自動ノート (3 ペインの先頭ノート、`shell.kind === 'auto'`) は押していないので
開始が無い。`PerfMarks` は進行中の計測が無ければ何もしない。

### 3-3. 同期 (`sync.ts`)

`syncOfflineItems()` の中で、fetch の前後・`res.json()` の前後・
`saveOfflineSnapshot()` の前後を `performance.now()` で取る。転送量と
応答開始は `SYNC_ITEMS_PATH` の resource entry から (fetch の完了後に
`getEntriesByName`)。サーバの段階は同じ entry の `serverTiming`
(`PerformanceServerTiming[]`、iOS 16.4 以降で読める) から写す。
304 (docs/118 §2-B の後) は `結果=304 全体=` だけ。

`OfflineSync` 側で、印付きの添付 (`syncPinnedAssets` の件数と時間) と
暖機 (`warmOfflineShell` の時間) も `[計測] 同期/添付`・`[計測] 同期/暖機` に
1 行ずつ。暖機は版が変わった起動でだけ走るので、デプロイ直後の 1 回に
何秒・何本かかるかがここで判る。

### 3-4. 起動

`[起動]` 行はそのまま使う。計測中は `BootTimingReport` に
`always` を渡して**毎回**計測の控えへも送る。普通の条件に当たる行は今までどおり
/logs へも送る — 計測の控えにだけ送ると、版が変わった初回の行が打鍵の行に
押し流され、控えの版は「報告済み」になるので二度と出てこない。

## 4. nginx — 転送にかかった時間

アプリの計時は「応答を返し始めるまで」しか測れず、ブラウザの resource timing
は「届き切るまで」を測るが、**両方を同じ要求で並べて見られる場所が無い**。
本番の nginx に、要求ごとに上流の時間と送り終わるまでの時間を出すログを足す。

`deploy/nginx/qr.tommie.jp.conf` の `server` (443) に:

```nginx
log_format qr_perf '$time_iso8601 $status $request_method $uri '
                   'rt=$request_time urt=$upstream_response_time '
                   'bytes=$body_bytes_sent rsc=$http_rsc ua="$http_user_agent"';
access_log /var/log/nginx/qr-perf.log qr_perf;
```

- `rt` (受け取ってから送り終わるまで) − `urt` (上流が返し切るまで) が、
  回線に食われた時間。iPhone の行は UA で拾う
- `rsc=1` で RSC と HTML を分ける (打鍵は RSC、再読み込みは HTML)
- `$uri` にクエリは含まれない (`?q=` は載らない)。検索語はアプリ側の行にある
- `log_format` は `http` の文脈にしか書けないので、`server` の外 (ファイルの
  先頭、`limit_req_zone` の隣) に置く
- `/var/log/nginx/*.log` は Debian の logrotate が既に回す
- 反映は `./doDeployNginx.sh` (ドリフト検知付き。接続先は `scripts/lib/target.sh`
  の控え = vps1)。デモの conf には足さない

読むときは `ssh vps1 'sudo tail -n 5000 /var/log/nginx/qr-perf.log'` を
手元に落とし、`scripts/perfSummary.mjs` (§6-3) に食わせる。

| 伸びている所 | 疑う場所 | 対応する docs/118 の節 |
| --- | --- | --- |

## 7. やらないこと

- 外部の APM (Sentry・OpenTelemetry) — 1 人のアプリで、vps1 は常駐を
  増やせない。/logs とバッファで足りる
- `web-vitals` の導入 — LCP / INP は `[起動]` 行と `長タスク=` で代わりが
  効き、知りたいのはアプリ固有の区間 (打鍵→差し替え) で、ライブラリは
  それを測らない
- Service Worker の中の計時 — resource timing の `workerStart` と
  `transferSize` 0 (= キャッシュ) で切り分けられる
- 常時 ON とサンプリング — 測る期間だけ /logs?perf=1 から立てる
- 検索結果の HTML (再読み込み) の大きさをアプリで測る — nginx の `bytes=` で
  見る
- react-markdown の描画時間を段階として切り出す — React の木の描画の中で
  起きるので、nginx の `urt` との差で導く (§2-1)
