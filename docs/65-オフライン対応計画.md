# 65. オフライン対応計画 (読み取り専用)

電波の届かない場所 (部品棚の前・地下・移動中) でノートを**探して読める**ようにする。
Evernote の「オフラインノート」相当を、読み取り専用の範囲で実装したもの。

前段の調査は親リポジトリの `41-QR-search/docs/06-オフライン対応調査.md`。
この文書はその Level A を実装したときの設計と、実装中に踏んだ落とし穴を残す。

§1〜§6 が最初の実装 (検索と本文の閲覧)。§7〜§10 はその後に足した 3 つで、
**「圏外で読めない物」を潰しにいった回**である — 回路図・シークレット断片・
原寸の添付。§1 の表で ❌ が 2 つ減り、△ が 1 つ条件付きの ✅ になった。

## 1. できること・できないこと

| | オフライン |
| ------ | ------ |
| ノートの検索 (`#タグ` / `is:todo` / OR / NOT すべて) | ✅ |
| ノート本文の閲覧 (Markdown・数式・表・チェック) | ✅ |
| 添付のサムネ表示 | ✅ (「画像も保存」を押した分) |
| 回路図 (` ```circuitikz `) の描画 | ✅ (描画済みの SVG を運ぶ。§8) |
| シークレット断片の復号 | ✅ (鍵束の写し + 暗号文のキャッシュ。§9) |
| 原寸の画像・動画・PDF | △ (印を付けたノートは常に。他は一度開いた物だけ。§10) |
| 編集・新規作成・ゴミ箱・公開切り替え | ❌ |

**編集は対象外**。単独ユーザーでも「スマホで直した直後に PC で開く」だけで競合し、
iOS には Background Sync が無いため再送の信頼性も担保できない (docs/06 Level B)。

## 2. 全体像

```text
オンライン                                      オフライン
  layout.tsx                                     sw.js
    └ OfflineSync (ログイン中のみ)                 └ 画面の取得に失敗
        ├ sw.js を ?v=<版> で登録                      → 302 /offline?item=…
        ├ GET /api/sync/items → IndexedDB           └ /_next/static
        │    (本文・回路図・印の有無)                    → 殻から返す
        ├ 印付きノート → qr-pin-v1                  └ /api/images・/api/secrets
        │    (原寸・シークレットの暗号文)                → qr-pin-v1 を先に見て
        └ sw.js へ warm → /offline の殻を保存           qr-media/secret へ落ちる
                                                   /offline (OfflineApp)
                                                     ├ IndexedDB から検索・表示
                                                     └ 断片は Face ID で復号
                                                        (鍵束の写しも IndexedDB)
```

## 3. 決めたこと (と、その理由)

### 3-1. 検索の文法はサーバと 1 つの実装を共有する

`src/lib/search.ts` のパーサ (AST) をそのまま呼び、**葉の評価だけ**を差し替える
(`src/lib/offline/filter.ts`)。文法を書き写すと、演算子を足したときに
オンラインとオフラインで解釈が割れる — しかも気づくのは圏外だけになる。

| 語 | サーバ (items.ts) | オフライン (filter.ts) |
| ------ | ------ | ------ |
| 語 | `memo &@ 語 OR url &@ 語 OR item_no ILIKE 語%` | 正規化した部分一致 + itemNo 前方一致 |
| `#タグ` | `tags @> ARRAY[語]` | 配列の完全一致 |
| `is:todo` | `task_todo > 0` | 同じ |

PGroonga のバイグラムと部分一致は厳密には別物だが、実データ 598 件で
`#過渡現象` `2SC1815` `is:todo` `抵抗 OR コンデンサ` `#電験三種 !#難` の
5 つを突き合わせ、**件数が完全に一致**することを確認した。

並び順は `src/lib/offline/order.ts` が `sortOrder.ts` の 8 通りを写している。
**片方を直したら必ず対で直すこと** (SQL 文字列を返す関数なので共有できない)。

### 3-2. 差分同期をしない

全ノートで約 300KB (598 件・実測)。毎回まるごと置き換えれば、端末側は常に
サーバの写しになり、**消えたノートも自然に消える** — 差分にすると「消えた物を
端末からも消す」処理が別に要る。IndexedDB には 1 レコードとして入れる
(検索は毎回全件を舐めるので、分けても得がない)。

上限は 5000 件。届いたら更新の新しい順に打ち切り、`truncated` で画面が断る。

### 3-3. 本文の同期と画像の先読みを分ける

| | 量 | 契機 |
| ------ | ------ | ------ |
| 本文 | 約 300KB | 自動 (5 分間隔。`schedule.ts`) |
| サムネ | 数 MB〜十数 MB | **手動のみ**「画像も保存」 |

電波のある場所で勝手に十数 MB 落とすのは、通信量を払う人に対して失礼。
間隔を置くのは、QR シールを何枚も読む使い方で `/item/:itemNo` を開くたびに
全件を落とし直さないため。

### 3-4. 画面の遷移先は /offline に統一する

App Router の画面遷移は RSC ペイロードを取りに行くので、**圏外では別ルートへ
進めない**。取れなかった URL の場所へ別ページの HTML を返すと URL と
ペイロードが食い違って壊れるので、素直に 302 で `/offline` へ送り、元の
行き先は query で渡す (`/item/4518` → `/offline?item=4518`)。

/offline の中では `history.pushState` だけで画面を切り替える (通信ゼロ)。
URL は React state ではなく `useSyncExternalStore` で購読する
(`src/lib/offline/location.ts`。効果の中で setState すると描画が二度走る)。

### 3-5. /offline と /sw.js はログイン不要にする

`publicPaths.ts` に載せてある。理由は 2 つ:

1. **殻の保存を確実にするため。** 未ログインだと proxy.ts が 200 のまま
   ログイン案内へ差し替えるので、閉じたままだと「ノートのつもりでログイン画面」が
   キャッシュに沈む余地が残る。
2. **圏外ではログインし直せない。** セッションが切れても手元のノートは読めるべき。

/offline の HTML は**ノートを 1 件も含まない殻**なので、開けても漏れる物がない。
念のため sw.js 側でも、保存する HTML に `data-offline-shell` の目印があることを
確かめてから殻として扱う。

### 3-6. ログアウトで端末の持ち出し分を消す

`clearOfflineData()` (`src/lib/offline/db.ts`) を LogoutButton が呼ぶ。
**これが無いと 3-5 が穴になる** — /offline はログイン不要で開けるので、
消さずに残すと「ログアウトしたのに端末を触れば全ノートを読めて検索もできる」。
消すのは IndexedDB (本文) と `qr-*` の Cache Storage (添付・殻) の両方。

## 4. Serwist を採らなかった理由

Service Worker は手書き (`public/sw.js`)。Serwist / Workbox の中心的な価値は
「ビルド成果物の precache マニフェスト」だが、このアプリではそれが空振りする:

- 全ページが `force-dynamic` の SSR で、precache できる HTML がビルド後に無い
- Turbopack ビルドには per-route のチャンク表 (`app-build-manifest.json`) が
  出ない。glob の既定に倒すと `public/` (180MB: onnx / paddle-ocr) と
  `.next/static/media` (61MB: wasm) まで抱え込む
- `@serwist/turbopack` は route handler 方式で、その import が nft の
  ファイル追跡から漏れる既知の不具合を抱える ([serwist#360])。
  `output: "standalone"` は同じ追跡で Docker 用の束を組むので直撃しうる

必要なのは precache ではなく「実行時キャッシュ + 1 ルートだけの意図的な暖機」で、
それは 300 行で書ける。

[serwist#360]: https://github.com/serwist/serwist/issues/360

## 5. 実装中に踏んだ落とし穴

### 5-1. dev サーバでは Service Worker を動かしてはいけない

キャッシュは「`/_next/static/` は中身がハッシュで固定されているから取り直さ
なくてよい」を前提にしている。ところが `next dev` (Turbopack) のチャンク名は
編集しても変わらないので、その前提が崩れて**古い JS を返し続ける** —
直したはずのコードが反映されない、という追いにくい壊れ方になる (実際に踏んだ)。

`registerOfflineWorker` は `NODE_ENV === 'development'` のとき登録を解き、
殻も捨てる (一度でも本番相当を localhost で開いた人が罠にはまらないように)。

### 5-2. 暖機は新しい Worker が動き出してから

`navigator.serviceWorker.ready` は「有効な登録がある」で解決するので、
入れ替え前の**古い** active を返してくる。そこへ暖機を投げると古い版の
キャッシュ名へ書き、新しい版が activate した瞬間に掃除されて丸ごと無駄になる。
`registerOfflineWorker` が `installing → activated` を待つ。

### 5-3. フォントは HTML に出てこない

KaTeX の woff2 は CSS の `@font-face` からしか参照されず、しかも
`url(../media/…)` という**相対パス**なので、HTML を眺めても文字列としても
拾えない。保存した CSS を読み、その URL を基準に解決する必要がある。
拾い損ねると数式が代替フォントで崩れて出る。

### 5-4. 保存しただけでは配信されない

`/icon.svg` と `/manifest.webmanifest` を殻に入れたのに、fetch ハンドラに
分岐を書き忘れて圏外でヘッダの絵だけ欠けていた。**キャッシュに入れる側と
返す側は必ず対で書く。**

### 5-5. text() したあとの見出しを丸ごと写さない

`res.text()` で本文は復号済みなのに `content-encoding: gzip` を写すと、
ブラウザが平文を gzip として解こうとして画面が真っ白になる。要るのは
`content-type` だけ。

### 5-6. IndexedDB は「DB はあるのにストアが無い」状態を作れる

版が上がらない限り `onupgradeneeded` は呼ばれないので、その状態になると
`transaction` が毎回 NotFoundError で落ち、**再同期しても直らない**行き止まりに
なる。ここは捨てて作り直せるキャッシュなので、`openDb` はストアが無ければ
DB ごと消して開き直す。

### 5-7. 下ごしらえを読み込み中に始めると、ページが自分で自分を飢えさせる

**症状**: デプロイした直後の初回起動だけ、iPhone の PWA で**ヘッダーだけ出て
その下が数十秒白い**。数十秒待ってヘッダーの「QR Note」を押すと (= クライアント
遷移) 中身が出る。

**計測** (`src/lib/bootTiming.ts` を仕込んで /logs で読んだ):

```text
[起動(途中)] v0.22.67 / SW v0.22.67 / PWA / オンライン / navigate
| 要求 6ms → 応答待ち 722ms → 受信 979ms → FCP 813ms → DCL 未了 → load 未了
| SW起動 5ms | 遅い資源: sync/items 568ms(SW)
```

サーバは 1 秒かかっていない。それなのに **5 秒経っても DCL も load も来ない** —
つまり HTML のストリームが開いたまま止まっている。Next.js は本文の途中に
`self.__next_f.push(...)` のインライン `<script>` を挟むので、続きが届かない
限りそこから下は DOM にすら入らない。ヘッダーだけ見えるのはそのためで、
「白い」の正体は**未着の HTML** であって描画の失敗ではない。

**原因**: 版が変わった起動では `needsWarm` が立ち、`OfflineSync` が
マウント直後に「全ノート同期 → 印付き添付 → 暖機 (殻の全チャンク)」を撃つ。
これらは同じ Service Worker と同じ接続を通るので、**ページ自身の残りが
その後ろに並ぶ**。ページが自分で起こした通信で自分を飢えさせていた。

**直し方** (3 つとも「いまの起動を遅くしない」に揃える):

- `OfflineSync` は `onPageLoaded` で **load を待ってから**始める。
  オフラインの下ごしらえは数秒遅れても等価
- `cacheFirst` は `cache.put` を待たずに応答を返し、保存は `event.waitUntil`
  に預ける。保存は次の起動のための仕事で、いまの描画を止める理由が無い
- 暖機の取得は `WARM_CONCURRENCY` 本までにする。素の `Promise.all` は
  数十本を同時に投げる

## 7. ノート単位の「オフラインで使う」印

`items.offline_pin` (真偽値)。ノート画面のトグルで立てる
([OfflinePinToggle.tsx](../src/components/OfflinePinToggle.tsx))。

印を立てると、そのノートは**本文だけでなく添付の原寸・回路図・シークレット
断片まで**端末に置かれる。押す前に「添付 12.3 MB」と量を出すのは、これが
通信量と保存容量を払う判断だから — 押した後に判っても遅い。

その量の置き場所は、帯を畳んだときに tooltip (`title`) へ移した
([75-ノート上部圧縮計画.md](./75-ノート上部圧縮計画.md) §3)。**スマホでは実質
読めない**のを承知で畳んでいる — 量が要るのは印を付ける一瞬だけで、その 1 回の
ために全ノートの上部を 1 行分払うのは高い、という判断。

### 7-1. 端末ごとではなくノートごとに持つ

単独ユーザーの前提では「スマホで印を付けたノートは PC でも持ち出される」
ほうが期待に合い、端末を増やすたびに付け直す手間も要らない。端末ごとの
容量差は、持ち出す側 (§10 の突き合わせ) が落とせなかったときに数で断ることで
吸収する。

### 7-2. 印を立てるときに回路図を描いておく

同期の口 (§8) は**出来上がっている図を配るだけで描かない**。描かないと
「印を付けたのに圏外で図だけ出ない」になるので、
[actions.ts](../src/app/actions.ts) の `setItemOfflinePinAction` が
`renderCircuits()` を呼んで DB キャッシュを埋める。

ノートを一度でも開いていれば ItemView が描き済みだが、それに頼ると
「開かずに印だけ付けた」経路が漏れる。描画の失敗でトグルは止めない —
TeX のエラーは本文側の問題で、印を付ける操作とは別の話。

### 7-3. `updated_at` を触らない

印は読み方の設定であって本文の変更ではない。動かすと更新順の先頭に来て
嘘になるうえ、**同期は更新の新しい順に打ち切る** (§3-2) ので「印を付けた
ノートが他を押し出す」という別の嘘まで生む。生 SQL で書く理由は
`setItemPublic` と同じ (Prisma の update は `@updatedAt` を必ず打つ)。

## 8. 回路図をオフラインで出す

回路図は**サーバで描いて DB (`circuit_svgs`) にキャッシュ**してあり、
クライアントには HTML に埋め込んで渡していた — つまり **URL を持たない**ので、
Service Worker には拾いようがなかった。そこで同期の応答に相乗りさせる。

```text
/api/sync/items → { items: [...], circuits: [{ source, svg }], circuitsOmitted }
```

### 8-1. 鍵はフェンスの中身そのもの

サーバ側のキャッシュは sha256 (`circuitHash`) を鍵にしているが、それを端末で
計算すると `RENDERER_VERSION` の混ぜ方まで二重に持つことになる。
MarkdownView が引く鍵はフェンスの中身 (trim 済み) なので、そのまま鍵にすれば
写す規則がゼロで済む ([circuits.ts](../src/lib/offline/circuits.ts))。

### 8-2. 同期の口では描かない

1 枚あたり最大 10 秒 (`CIRCUIT_TIMEOUT_MS`) の TeX 描画を同期に載せると、
回路図を書き足した直後の同期だけが数十秒かかる — しかも待たされているのは
本文の同期でもある。描くのは「ノートを開いたとき」と「印を付けたとき」の
2 か所だけにして、ここは配るだけにした。まだ描かれていないフェンスは圏外で
コードブロックとして出る (オンラインで一度開けば揃う)。

### 8-3. 予算 4MB で打ち切る

本文が全件で数百 KB なのに対し、TikZ の SVG は 1 枚で数十 KB になる。上限が
無いと、増えるのは端末の保存量だけでなく **VPS (RAM 2GB) が 1 応答のために
積む文字列の量**でもある。溢れたら印付きを先に積み、`circuitsOmitted` で
画面が断る — 黙って落とすと「圏外でだけ図が出ない」という原因の掴めない差に
なる。

## 9. シークレット断片をオフラインで復号する

解錠の計算 (PRF → KEK → unwrap) は**すべて端末の中**で完結していたのに、
手順の入口で鍵束を GET していたせいで圏外では解錠だけができなかった。
足りなかったのは 2 つだけ。

| 要る物 | 置き場 |
| ------ | ------ |
| 鍵束 (検証値・包んだ鍵) | IndexedDB の `keyring` ストア |
| 断片の暗号文 | Cache Storage の `qr-secret-v1` |

### 9-1. 端末に置くのはサーバが持っているのと同じ物だけ

平文のマスターキーは書かない (それはタブのメモリだけ。`secretSession.ts`)。
包みを開けられるのは PRF 出力を出せる認証器 (Face ID) か紙の復旧キーだけで、
端末に写しがあってもその条件は 1 つも緩まない。暗号文も同じ — サーバに
置いてあるのと同じバイト列である。

### 9-2. サーバを先に見て、駄目なら写しへ落ちる

順番が逆だと、別の端末でパスキーを足した直後に「有効になっていません」と
断られる — 直し方の判らない不具合になる。サーバが答えられるなら常にそちらが
正で、写しは圏外の保険にすぎない
([secretUnlock.ts](../src/lib/secretUnlock.ts) の `readKeyring`)。

写しを更新するのは「取れたとき」だけ。初回設定とパスキーの追加の直後にも
取り直す — **これが無いと、有効にした端末が圏外へ出た途端に元へ戻る**。

### 9-3. 鍵束だけはキャッシュしない

`/api/secrets/keyring` は `/api/secrets/` にぶら下がるが、Service Worker には
通さない。中身は「いまサーバがどう思っているか」で、別の端末でパスキーを
足せば変わる。IndexedDB の写しは書き換わったことに気づける (取れたときに
必ず上書きする) が、Cache Storage に沈めると気づけない。

### 9-4. 断片は「同じ名前のまま中身が変わる」唯一の口

添付は回転すら新しい UUID で保存し直すので取り直しが要らないが、断片の編集は
**同名上書き**である (docs/51 §9)。保存したら端末の写しを捨てる
(`forgetCachedUrl`) — 捨てないと圏外で編集前の中身が復号され、しかも復号は
成功するので古いと気づけない。

### 9-5. 圏外では編集を出さない

`/offline` の `MarkdownView` には `allowSecretEdit` を渡さない。断片の保存は
サーバへの書き込みで、圏外では必ず失敗する。

## 10. 印付きノートの持ち出し

### 10-1. 棚を分ける

| 棚 | 中身 | 捨てる条件 |
| ------ | ------ | ------ |
| `qr-shell-<版>` | `/offline` の殻 | 版が変わったら丸ごと |
| `qr-media-v1` | 見たついでに貯まった添付 | 600 件を超えたら古い順 |
| `qr-pin-v1` | 印付きノートの持ち出し | **印を外したときだけ** |
| `qr-secret-v1` | 断片の暗号文 | (名前が UUID で不変) |

印の棚を `qr-media-v1` と混ぜてはいけない。あちらは上限 600 件で古い順に
捨てるので、混ぜると「オフラインで常に使う」と言われた添付が、**別のノートを
眺めただけで押し出される**。Service Worker は印の棚を先に見る (`pinnedFirst`)。

### 10-2. 出来事ではなく突き合わせで揃える

「印を付けたら落とす・外したら消す」と書くと、取りこぼしが永久に残る。印を
外した瞬間に圏外だった、別の端末で外した、添付を差し替えた、ノートごと消した
— どれも起こるうえ、この棚は期限で腐らないので消し残りは誰にも気づかれない。

そこで毎回、印付きノートから**あるべき URL の集合**を作り直し、棚と突き合わせる
([pinCache.ts](../src/lib/offline/pinCache.ts))。**消すのが先** — 容量の
限られた端末で先に落とすと、外した印の分が残ったまま新しい分を入れられずに
詰まる。

### 10-3. ここだけは画面側が Cache Storage へ書く

サムネの先読み (§3-3) は「ただ fetch するだけ」で保存は sw.js に任せている —
規則が 1 か所にあればずれようがないため。印の棚はそうしない。**入れる物と
消す物をこちらが決める**必要があり、fetch の副作用では「余りを消す」が
書けないからである。sw.js 側はこの棚を読むだけにしてある。

### 10-4. ここだけは自動で通信量を使う

サムネの全件先読みを手動にしているのと矛盾して見えるが、印は「このノートは
圏外でも原寸まで要る」と利用者が 1 件ずつ選んだ結果で、断りは既に取れている。
逆に、選んだのに毎回 `/offline` を開いてボタンを押させるなら印の意味がない。

### 10-5. 永続化は押されたときだけ申し入れる

`navigator.storage.persist()` は Firefox だと確認バーが出る。画面を開いた
副作用として撃つと「何もしていないのに許可を求められた」になるので、
`/offline` の「印の分を保存」からだけ呼ぶ。真下に保存量が出ている場面なので、
聞くなら筋が通る。
