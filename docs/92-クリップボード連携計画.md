# クリップボード連携計画

iPhone と Windows の間で、コピーした画像 (と文字) を QR-Note を経由して受け渡す。
想定する使い方は次の 1 往復。

1. iPhone で写真を撮り「コピー」する
2. iPhone の QR-Note でコピー内容を取り込む (添付になる)
3. Windows の QR-Note でその画像をコピーする
4. 他のアプリ (X の投稿など) に貼り付ける

専用の同期機構は作らない。**ノートが箱、添付が中身**で、既存のノートを
そのまま「共通クリップボード」として使う。足すのはクライアント側のボタン 2 つで、
サーバ (API・テーブル・vps2 の常駐) は触らない。

## 0. なぜ

- iPhone と Windows にはクリップボード共有の純正手段がない。Universal Clipboard
  は Apple 同士、Windows のクラウド クリップボードは Windows と Android 同士。
- 半分はすでに動いている。
  - エディタの `paste` は画像ファイルを添付アップロードに流す
    (`MemoEditorInner.tsx` の `paste` ハンドラ → `insertFiles`。当時のパス。現在は `src/components/editor/hooks/useAttachmentInsert.ts`)
  - 詳細画面は原寸画像を `<img>` で描く (`ZoomableImage.tsx`)。Windows では
    右クリック →「画像をコピー」が効き、保存形式が WebP でも Chrome は
    ビットマップとして載せる。`ZoomableImage` は contextmenu を潰していない
  - 逆方向も無料。iPhone は `<img>` 長押し →「コピー」が OS 側で効く
    (docs の iOS 長押し共有と同じ理屈)
- 足りないのは「手数」と「大きさ」。iPhone は編集画面を開いて本文を長押しする
  必要があり、Windows は詳細画面の原寸を右クリックするしかない。写真を PNG の
  まま貼ると 10MB の上限に当たる (§8)。

## 1. まず 0 行で試す

実装の前に、今の経路で 1 往復して「使い物になる手数か」を見る。

1. 「📋 クリップ」のような固定ノートを 1 枚作る
2. iPhone: 写真アプリで「コピー」→ QR-Note でそのノートを編集 → 本文を長押し
   →「ペースト」→ 更新
3. Windows: 同じノートを開く → 画像を右クリック →「画像をコピー」→ X の投稿欄に
   貼り付け

ここで分かること: iPhone の paste が写真を何の形式・何 MB で渡してくるか
(スクショは PNG 確定、写真は PNG か JPEG)、X が原寸 PNG を受け付けるか。
§3・§4 の縮小まわりの定数はこの実測で決める。

## 2. 方針

- 専用テーブル・API・同期・通知は作らない (§9)
- 追加はクライアント側の 2 点。**取り出し**「画像をコピー」(Phase 1) と
  **取り込み**「クリップボードから取り込む」(Phase 2)
- クリップボード上の画像形式は **PNG に統一**する。Chrome の
  `navigator.clipboard.write` が受ける画像は `image/png` だけで、iOS の paste も
  PNG で来ることが多い
- 文字も同じ取り込みボタンで扱う (画像が無ければ `text/plain` を本文に挿入)。
  「コピー内容」が画像でも文字でも押すボタンは 1 つ
- 両ボタンは iPhone・Windows の両方で動く形にする。片方向専用にしない

## 3. Phase 1 — 「画像をコピー」ボタン (取り出し)

Windows 側で、ノート内の画像を PNG としてクリップボードに載せる。

- **置き場所**: `ZoomableImage` の脇。`VideoPlayer` の共有ボタンと同じ作法で、
  画像の下の操作列に小さく出す
- **出す条件**: `typeof ClipboardItem !== "undefined"` かつ
  `navigator.clipboard?.write` がある。判定は `VideoPlayer` の `canShare` と同じく
  `useSyncExternalStore` で SSR 時は false (水和ずれを避ける)
- **流れ**:
  1. click の**同期部**で `new ClipboardItem({ "image/png": pngPromise })` を作り
     `navigator.clipboard.write([item])` を呼ぶ。`ClipboardItem` には Promise を
     渡せる (Chrome 可、Safari はむしろこの形が必須)
  2. `pngPromise` = `fetch(src)` (同一オリジン、Cookie は既定で付く)
     → `createImageBitmap` → canvas → `toBlob("image/png")`
  3. 結果表示は `CodeBlock` のコピーボタンと同じ「コピーしました / 失敗」の一時表示
- **縮小はしない** (原寸)。X の 5MB 制限に当たるかは §7 で実測し、必要なら
  `COPY_MAX_EDGE` 定数 1 つで長辺を落とせる余地だけ残す
- **アニメ (GIF・アニメ WebP)** は PNG にすると 1 コマの静止画になる。最初は
  そのまま (1 コマ) でよい。判定して隠すのは URL 拡張子だけでは無理
  (アニメ WebP は拡張子で分からない) なので追わない
- 新規ファイル:
  - `src/lib/clipboardImage.ts` (当時のパス。現在は
    `src/lib/clipboard/clipboardImage.ts`) — 純粋関数。`canWriteImage()`、
    `toPngBlob(blob)` (canvas 依存部は差し替え可能に薄く分ける)
  - `src/components/CopyImageButton.tsx` — ボタン本体

## 4. Phase 2 — 「クリップボードから取り込む」ボタン (取り込み)

iPhone 側で、写真アプリなどでコピーした画像を 1 タップで添付にする。

- **置き場所**: エディタの下部バー、添付ボタンの隣 (`useBottomBarSlot` の口)
- **出す条件**: `navigator.clipboard?.read` がある (iOS 13.4 以降・Chrome)
- **流れ**:
  1. click の**同期部**で `navigator.clipboard.read()` を呼ぶ。先に `await` を
     置かない (ユーザー操作の扱いが切れて NotAllowedError)。iOS は「ペースト」の
     吹き出しを出し、そのタップが許可になる
  2. items から `image/*` を探す。あれば `getType` で Blob →
     `new File([blob], "clipboard-<日時>.png", { type })` → 既存の `insertFiles`
     に流す (alt は空、OCR は既定どおり)
  3. 画像が無ければ `text/plain` → `insertText` で本文に挿入
  4. 両方無ければ「クリップボードに画像も文字もありません」
- **大きさ対策**: `uploadTooLargeMessage` に当たる画像は、送る前に
  `fitWithin` (今は `secretImage.ts` (当時のパス。現在は `src/lib/secret/image.ts`) にある) +
  `canvas.toBlob("image/jpeg", 0.9)`
  で長辺 2048 程度に落とす。**WebP にしない** — iOS の `toBlob("image/webp")` は
  PNG/JPEG に化ける (`uploads.ts` の注記。当時のパス。現在は
  `src/lib/uploads/sniff/video.ts`。実機報告)。OCR は保存後の画像を
  読むので縮小の影響は受けない。上限以下の画像は触らない (再圧縮で劣化させない)
- **Windows でも同じボタンが動く** (Chrome は許可ダイアログ)。Windows → iPhone の
  逆方向にも使える
- 新規ファイル:
  - `src/lib/clipboardRead.ts` (当時のパス。現在は `src/lib/clipboard/clipboardRead.ts`)
    — items の選別 (`image/png` 優先 → 他の `image/*`
    → `text/plain`)。純粋関数にしてテスト対象にする
  - `src/lib/shrinkImage.ts` (当時のパス。現在は `src/lib/images/shrinkImage.ts`) —
    `fitWithin` を `secretImage.ts` から移して共有
  - `src/components/editor/ClipboardImportButton.tsx` — ボタン本体

## 5. Phase 3 (任意) — 固定ノートへの導線

一覧から「📋 クリップ」ノートの編集画面を 1 タップで開く。

- ノートの itemNo を `user_settings` (`userSettingStore`、row-tint と同じ汎用
  key-value) に持ち、一覧の下部バーに「クリップへ」を出す
- `read()` はユーザー操作が要るので、開いた直後の**自動取り込みはできない**。
  「開く → 取り込む」の 2 タップが下限
- Phase 1・2 が使い物になってから決める。最初はやらない

## 7. 検証

### 実機

1. iPhone 写真アプリ → コピー → 取り込む → Windows Chrome → コピー → X に貼り付け
   → 投稿プレビューに画像が出る
2. 12MP の写真 (PNG で 10MB 超) が上限で止まらず、縮小されて入る
3. スクショ (PNG) と、Safari で長押しコピーした画像も同じ経路で入る
4. 文字をコピーして取り込むと本文に入る
5. X が原寸 PNG を受け付けるか。弾かれる・縮められるなら `COPY_MAX_EDGE` を入れる
6. iPhone 側でもコピーボタンが出るが、長押しコピーと重複するだけで害はないか

### 単体テスト (vitest)

- `clipboardRead`: `image/png` 優先、`image/jpeg` だけなら拾う、画像が無ければ
  `text/plain`、何も無ければ null
- `shrinkImage`: 上限以下は元の File をそのまま返す、超えたら `fitWithin` の寸法で
  JPEG になる (canvas は jsdom に無いので `toBlob` 部分を差し替えて試す)
- `clipboardImage`: `ClipboardItem` が無い環境で `canWriteImage()` が false
- `CopyImageButton` / `ClipboardImportButton`: 非対応環境では描かれない、
  成功・失敗の表示が切り替わる

### E2E (Playwright, chromium)

- `context.grantPermissions(["clipboard-read", "clipboard-write"])` を付ける
- 取り込み: `page.evaluate` で小さな PNG を `navigator.clipboard.write` してから
  ボタンを押し、本文に `![](/api/images/…)` が入ることを見る
- コピー: ボタンを押した後 `page.evaluate` で `navigator.clipboard.read()` し、
  `image/png` が取れることを見る
- 起動と認証はローカル E2E の手順どおり (localhost 必須、テスト認証 env)

## 8. 落とし穴 (先に分かっていること)

- **iOS の `read()`** は click の同期部で呼ぶ。`await` が先だと NotAllowedError
- **Chrome の `write()`** は `image/png` 以外を入れると DOMException。JPEG・WebP は
  まず PNG に描き直す
- **`ClipboardItem` には Promise を渡す**形にする。Safari は同期部で item が
  できていないと拒むし、Chrome もこの形を受ける
- **EXIF は落ちる**。Chrome も WebKit もクリップボードで再エンコードする。
  位置情報が消えるので SNS 投稿にはむしろ好都合。向きは画素に焼き込まれる
- **iOS の paste PNG は大きい**。12MP で 20〜30MB になり `MAX_IMAGE_BYTES`
  (10MB) に当たる。判定は送信前なので黙って失敗はしないが使えない → §4 の縮小
- **X の画像上限は 5MB**。原寸 PNG は超えることがある → §7 で実測
- **アニメは静止画になる** (PNG は 1 コマ)
- **暗号化 (シークレット) ブロック内の画像にはコピーを出さない。**
  当初「暗号文なので `ZoomableImage` には落ちない」と書いていたが**誤り**で、
  復号した断片の中身は Blob URL の画像として `MarkdownView` から
  `ZoomableImage` に渡る (docs/51 §3, docs/53 §5)。断片は隠すときに
  `URL.revokeObjectURL` まで呼んで画素を残さないようにしているのに、その平文を
  OS のクリップボード (iOS の Universal Clipboard・Windows の履歴・同期先) へ
  1 タップで送れては元も子もない。`canCopyImage` が `blob:` を弾く
- **vps2 への負荷なし**。全部クライアント側で完結する

## 9. やらないこと (最初は)

- 専用の同期・push 通知・開いた直後の自動取り込み (`read()` にユーザー操作が要る)
- Web Share Target (iOS Safari が非対応)
- 文字と画像以外の形式 (HTML・ファイル一般)
- 一覧のサムネからのコピー (Phase 1 は詳細画面の原寸だけ)
- アニメを動いたまま渡すこと

### 計画から変えたところ

- **描き直しを 1 本にまとめた** (`src/lib/imageCanvas.ts` (当時のパス。現在は
  `src/lib/images/imageCanvas.ts`) を新設)。§3 の
  「png へ変換」、§4 の「上限を超えたら縮める」、そして既存のシークレット画像
  (docs/51 §9) は、どれも「読む → 収める大きさを決める → 描く → 書き出す」で
  同じだった。`redrawImage(blob, { type, quality, maxEdge, background })` の
  1 本にして、`secretImage.ts` もその上に載せ直した (挙動は変えていない)。
  `fitWithin` はここへ移し、テストも `imageCanvas.test.ts` (当時のパス。現在は
  `src/lib/images/imageCanvas.test.ts`) へ移した。
- **縮小をペーストにも掛けた。** 計画では取り込みボタンだけだったが、本文への
  ペーストも同じクリップボード由来で、同じ 20〜30MB の PNG が来る。ボタンなら
  通ってペーストなら「大きすぎます」で止まるのは説明がつかない。
  `insertFiles` に `shrinkOversized` を足し、ペーストと取り込みの 2 経路だけ
  true にした。ファイル選択・ドロップは原本を指しているので既定の false のまま。
- **GIF は縮めない。** canvas に描き直すとコマ 1 枚の静止画になる。動くものを
  黙って止めるくらいなら「大きすぎます」で断るほうがよい (`canShrink`)。
  アニメ WebP は静止 WebP と MIME で区別できないので、そちらは諦めている。
- **縮めた後にもう一度測る。** 桁違いに大きい PNG は長辺を落としても収まらない
  ことがありうる。収まらなければ従来どおり断る (`fitToLimit`)。
- **コピーボタンは拡大表示の中に置いた。** 本文の画像の下に常時出すと、画像の
  多いノートがボタンだらけになる。拡大表示の右下 (回転ボタンの隣) なら、
  画像を選んでから押す流れになり、覆いは押して初めて作られるので SSR とも
  無縁になる。`allowRotate` と違い**公開ビューでも出す** — 回転は書き換えだが
  コピーは読むだけなので、出さない理由がない。
- **取り込みボタンは別部品にしなかった。** `EditToolbar` の他 13 個と同じ
  帯の中のボタン 1 つなので、そこに直接置いた。判断は `clipboardRead.ts` (当時のパス。現在は
  `src/lib/clipboard/clipboardRead.ts`)
  (どの形式を採るか) に寄せてあり、部品側は取得と挿入だけを持つ。
- **JPEG の下地を白で塗る。** JPEG は透過を持てず、塗らないと透明部分が黒く
  沈む。
- **断られたときの文を言い換える。** `NotAllowedError` の素のメッセージは
  環境ごとに違ううえ英語なので、`clipboardReadErrorMessage` で日本語にする。
  iOS はペーストの吹き出しを閉じただけでもここに来る。

### レビューで直したもの

実装後の `/code-review` で 6 件。うち 3 件は挙動の不具合だった。

1. **復号したシークレット画像にコピーボタンが出ていた** (§8 に追記したとおり)。
   `canCopyImage` を足し、`blob:` には出さないようにした。
2. **縮小中は「更新」が通ってしまった。** `fitToLimit` を待つ間、本文には何も
   置かれず `busy` も立たないため、20〜30MB の写真を縮めている数秒のあいだに
   更新すると、画像の入っていない本文が保存されてから記法だけが後追いで挿さる。
   プレースホルダと `setUpload` を待つより**前**へ動かして塞いだ。
   取り込みボタン側にも `clipboardBusy` を足した — iOS の read() は
   ペーストの吹き出しが押されるまで返らず、そこも同じ窓だった (二重押しも防ぐ)。
3. **コピーの同期例外でボタンが「…」のまま固まりえた。** `new ClipboardItem` も
   `write` も同期で投げうるので、`copyImageToClipboard` を async にして必ず
   reject で返るようにした。失敗の印も時間で消すようにした。
4. 使われていない定数 (`NO_MAX_EDGE`) を消し、`shrunkFileName` の理由づけの
   説明が実際と違っていたのを直した。

### 残り

- **X への実投稿はまだ**。原寸 PNG が 5MB の制限に当たるかは投稿してみないと
  分からない。弾かれる・縮められるなら `clipboardImage.ts` (当時のパス。現在は
  `src/lib/clipboard/clipboardImage.ts`) に長辺の上限
  (`COPY_MAX_EDGE`) を足す。
- iOS の写真が実際に何 MB の PNG で来るかは測っていない。縮小が効いていることは
  上限を超えたときにしか見えないので、普段使いでは分からない。
