# リファクタリング前プロファイル計画 (速度とメモリの基準値)

<!-- markdownlint-disable MD013 -->

全体リファクタリングの前に、速度とメモリの**基準値**を 1 組そろえる。
リファクタリングは挙動を変えない約束なので、合格の目安は「悪化しない」。
フェーズごとに同じ手順で測り直し、どのフェーズで数字が動いたかを追う。

速度の計測は既存の仕組み ([docs/119](119-速度計測ログ計画.md)・[docs/120](120-計測テスト自動化計画.md)・[docs/121](121-QR-Noteベンチマーク計画.md)) をそのまま使う。
この計画で足したのは、メモリの記録 (§2)、重い処理のピーク (§3)、ブラウザ側の採取 (§4)、ビルドの計測 (§5) の 4 つ。

## 1. 条件

| 項目 | 値 |
| --- | --- |
| 基準のコミット | タグ `perf-base-20261117` (= v0.23.139。§2 のメモリの記録を含み、その直後の依存の更新 (mermaid 12・svgo 4・onnxruntime-web 1.31.1 など) は含まない) |
| 手元の機械 | Intel Core Ultra 9 285K (24 スレッド) / 48GB、WSL2 |
| 手元の DB | 2026-11-16 時点の手元の DB (ノート 1,528 件・回路 634 件)。本番からの複製 (`./doCopyDBfromVPS2.sh --yes`) は自動モードに止められ、未実施 (§7) |
| 計測用サーバ | 作業ツリーから作った `qr-search-app:perf` を 3301 番で起動。本番と同じ `--memory 1600m` |
| 回数 | 各項目 6 回。1 回目は暖機として捨て、残り 5 回の中央値・最小・最大 |

計測用サーバの立て方は [docs/118 §0-1](118-検索表示高速化計画.md) と同じで、管理者の口 (ベンチ) を叩くために `-e ADMIN_USER=e2e` と `--memory 1600m` を足す。

```bash
docker build -t qr-search-app:perf .
HASH=$(node -e "const b=require('bcryptjs'); process.stdout.write(Buffer.from(b.hashSync('e2e-test-pass',10)).toString('base64'))")
PW=$(grep '^POSTGRES_PASSWORD=' .env | cut -d= -f2-)
docker run -d --name qr-measure --network qr-search_default --env-file .env \
  -e APP_ENV= -e DATABASE_URL="postgresql://qr:${PW}@db:5432/qr" \
  -e BASIC_AUTH_USER=e2e -e BASIC_AUTH_HASH_B64="$HASH" -e ADMIN_USER=e2e \
  -e WEBAUTHN_RP_ID=localhost -e WEBAUTHN_ORIGIN=http://localhost:3301 \
  --memory 1600m -p 127.0.0.1:3301:3000 qr-search-app:perf
```

生データは `perf-baseline/` (git 管理外) に JSON で残し、要約だけをこの文書に書く。

## 2. サーバのベンチのメモリ (本体に追加)

メニュー「ベンチマーク」の「サーバを計測」([docs/121](121-QR-Noteベンチマーク計画.md)) に次を足した。
画面の表に「メモリ」列と「メモリの推移」が出て、コピーにも `メモリ.*` の行が入る。

- 項目ごとの前後: RSS の前→後、ヒープと external の増減、最大 RSS (`process.resourceUsage().maxRSS`) の伸び。GC の時機に揺れるので目安
- 周回の推移: 開始・本計測後と、本計測の後に全項目をさらに 1 回ずつ 4 周回した後の RSS。**周回のたびに伸び続けるならリークを疑う**
- コンテナ全体: cgroup v2 の `memory.current`・`memory.peak`・`memory.max`。TeX の描画は子プロセスなので、`process.memoryUsage()` には入らずこちらに入る

コードは `src/lib/diag/memorySample.ts` (採取)・`serverBench.ts` (前後と周回)・`formatBench.ts` (表示とコピー)。
古い保存 (欄の無い JSON) もそのまま読める。周回の分だけ「サーバを計測」の所要は約 2 倍になる (手元で数秒)。

- 回をまたいだ上昇 (383 → 449) は、ヒープが増えていないので今のところリークとは見ない。リファクタリング後に同じ 6 回で比べる

## 3. 重い処理のピーク (`scripts/profilePeakMemory.sh`)

処理ごとに新しいプロセスで `scripts/peakMemoryTask.ts` を流し、`/usr/bin/time -v` の最大 RSS (子孫を含む一番大きいプロセス) を取る。
材料はすべて固定で、DB には触れない。**本番では流さない** (TeX 1 本で約 400MB あり、同居のコンテナを圧迫する)。

```bash
./scripts/profilePeakMemory.sh perf-baseline/peak-memory.json 6
```

| 処理 | 材料 | ピーク RSS (中央値・最小〜最大) | 所要 |
| --- | --- | ---: | ---: |
| 読み込みだけ (基準) | import のみ | 105MB (103〜108) | — |
| 回路の解析 | 見本 × 10・50 図 | 114MB (113〜114) | 33ms |
| サムネ生成 | 4032×3024 JPEG 3.2MB | 217MB (215〜219) | 274ms |
| TeX の描画 | circuitikz 1 枚 | 381MB (379〜385) | 1,088ms |
| ZIP の読み取り | 1MB × 64 項目 | 337MB (334〜349) | 1,235ms |

TeX と ZIP は、それだけで基準から +230〜280MB 使う。
本番の平常時 (§6 で取る cgroup の値) にこれが重なっても 1,600MB に収まるかを、本番の数字が揃ったら確かめる。

## 4. ブラウザ側 (`scripts/profileBrowser.ts`)

Playwright で計測用サーバを開き、決まった 7 段を 6 回流す (1 回目は捨てる)。

```bash
npx tsx scripts/profileBrowser.ts perf-baseline/browser.json 6
```

- 所要は、文書の始まりから**最後に DOM の中身が変わった時刻**まで。load の後、DOM の変化が 0.8 秒止まるまで待って決める
- `networkidle` は使わない (ノートの画面は接続を張りっぱなしにするので来ない)。`requestIdleCallback` も使わない (速い PC では一覧の API が返る前に空き、殻だけを測ってしまった)
- Script・Layout・Style は CDP `Performance.getMetrics` の値で、文書ごとの累計。毎段 goto で開き直すので、段の値はその文書の値
- ヒープと DOM ノード数は `HeapProfiler.collectGarbage` の後
- 構成は PC (1600×1000・3 ペイン) と iPhone 相当 (390×844・1 ペイン・CPU 4 倍の絞り)。表示はどちらも小 (`view=compact`)

## 6. 本番で取る

§2 のメモリの記録は v0.23.139 から入っている。本番には v0.23.140 (2026-11-17) で配布した。次をお願いする。
本番は依存の更新を含む版になるので、手元の基準 (§2〜§5) とは依存の分だけ条件が違う。

1. PC からメニュー「ベンチマーク」→「サーバを計測」を 1 回 (所要は手元の数倍の見込み)
2. iPhone (Wi-Fi) で「この端末を計測」を 1 回
3. iPhone (キャリア) で「この端末を計測」を 1 回
4. 画面の「コピー」を貼ってもらう
5. vps1 で `free -m` と `docker stats --no-stream` (ssh は自動モードで止められるので、ユーザーが流す)
   - 2026-11-17 以降は 1 の「サーバを計測」が計測前に同じ値を取り、ベンチマーク画面の「ホストとコンテナ」とコピーに出す (手で流さなくてよい)。docker.sock は渡さず、ホストの cgroup v2 を read-only でマウントして読む (`src/lib/diag/containerStats.ts`)。名前は doDeploy.sh が配布のたびに書く `host-info/containers.tsv` から引く

本番では §3 (ピーク) は流さない。本番の余裕は「本番の cgroup の平常値 + §3 の TeX・ZIP の上乗せ」で見積もる。
結果は §6-1。

### 6-1. 本番の結果 (2026-11-17、v0.23.140)

vps1: Intel Core (Broadwell) 3 スレッド / 1,962MB、ノート 1,604 件 (回路 635 件)。
サーバの計測は配布の約 2 分後 (起動 114 秒) に 1 回。端末は iPad・iPhone (Wi-Fi・キャリア)・PC (有線) で 1 回ずつ。

**注意: 計測の時点で、同居の `kick-app` が CPU を 130% (3 スレッドのうち 1.3 本分) 使っていた。** サーバの速度は、その取り合いを含んだ値として読む。

| 検索「コンデンサ」 | 6.8ms | 1.9ms | 3.6 倍 |
| 検索「オペアンプ」 | 8.7ms | 2.6ms | 3.3 倍 |
| 検索 (全件) | 5.4ms | 1.4ms | 3.9 倍 |
| 回路の解析 (実ノート 20 件) | 35.6ms | 6.7ms | 5.3 倍 |

- 「検索 全件」は全端末で `未了` (応答開始・受信・描画が取れていない)。計測テスト側の取りこぼしで、リファクタリングとは別の課題
- この表はアプリ内の遷移 (クライアント側) を測っている。§4 (毎段 goto で開き直す) とは測り方が違うので、直接は比べない

#### 本番のメモリの余裕

| 見積もり | 値 |
| --- | ---: |
| app の平常 (cgroup、ベンチ中のピーク) | 508MB |
| + TeX 1 本 (§3、子プロセスごと) | +約 380MB |
| + ZIP の読み取り (§3、基準からの上乗せ) | +約 230MB |
| 3 つが重なった最悪 | 約 1,120MB |

- コンテナの上限 1,600MB には収まる
- **縛りはコンテナの上限ではなくホスト**。使える残りは 1.2GiB で、スワップは既に 713MiB 使っている。上の最悪が重なると、ホストの残りはほぼ尽きてスワップに落ちる
- 平常時 (約 450MB) と 1 つの重い処理 (+230〜380MB) までなら余裕がある。リファクタリングで常駐のメモリを増やす変更 (記憶の追加・事前読み込み) は、この余裕を食う前提で数字を見る

## 7. 残り・注意

- 手元の DB は本番の複製ではない (件数はほぼ同じ)。前後の比較は手元どうしで行うので支障はないが、本番と揃えて取り直すなら `./doCopyDBfromVPS2.sh --yes` をユーザーが流し、§2〜§4 を測り直す
- 依存の更新 (mermaid 12 ほか) は基準の後に入った。リファクタリングの 1 回目の測り直しの前に、依存の更新だけを入れた状態で §2〜§4 を 1 周測り、基準を取り直すとよい (依存による差とリファクタリングによる差を分けるため)
- 手元は 24 コア / 48GB なので、手元の絶対値は本番の代わりにならない。手元の数字は前後の比較に、本番の数字は絶対値の確認に使う

## 8. 前後の判定

| 結果 | 判定 |
| --- | --- |
| 中央値の差が基準の最小〜最大の幅の中 | 変化なし |
| 幅を超えて 10% 未満の悪化 | 記録して先へ進む |
| 幅を超えて 10% 以上の悪化 | そのフェーズを取り込む前に原因を調べる |
| ベンチ 6 回の周回の RSS が基準 (最後 449MB) より伸び続ける、またはブラウザの往復のヒープが伸び続ける | リークの疑いとして止める |

測り直しはリファクタリングのフェーズごとに §2〜§5 を 1 周、本番 (§6) は全体の最後に 1 回。
