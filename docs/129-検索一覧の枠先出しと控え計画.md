# 検索一覧の枠先出しと控えの計画

<!-- markdownlint-disable MD013 -->

検索結果を下へ送ったとき、「さらに表示」が出て止まるのをやめる。件数は 1 ページ目で分かるので、
続きのノートの**空の枠**を先に並べてスクロールできるようにし、枠が画面に近づいたら中身を取りに行く。
あわせて、一覧の控えを端末に残し、ノートのハッシュが変わっていなければ前の物をそのまま出す。

## 0. 現状 (2026-11-17、v0.23.148)

- 件数は 1 ページ目の応答 (`meta.total`) に入っている。件数だけを別に引く要求は要らない
- 一覧の控え (`lib/client/listStore.ts` の `listCache`) は**メモリだけ** (30 検索ぶん)。
  再読み込みや PWA の起動で消え、毎回「検索結果を読み込み中…」から始まっていた
- 30 秒を過ぎるか書き込みの後は、読み進めた所まで本文ごと取り直していた (304 なし)
- 取り直しが届くと、中身が同じでも全ノートを作り直し、全行を描き直していた
- ノートにハッシュの列は無い。`updated_at` だけでは足りない (ゴミ箱と印は `updated_at` を動かさない)

## 1. 枠の先出し

1 ページ目が届いたら、読み込み済みの先に空の枠を並べる。

| 項目 | 決めたこと |
| --- | --- |
| 枠の数 | `min(残り件数, 上限)`。上限はハンバーガーメニューの「一覧の枠」(端末ごと) で、なし・20・50・100・200・500 件。既定 100 件 |
| 枠の高さ | 行の見積もり (`itemRowDecor.ts` の `ROW_SKIP_OFFSCREEN_CLASS`) と同じ。小 2.25rem・中 3.5rem・大 7.5rem・画像 8rem |
| 枠のまとまり | ページ (20 件) ごとの塊 (`[data-placeholder-page]`)。割り付けは `components/search/placeholderPlan.ts` |
| 読み込み | 塊が画面に入ったら、入っている中で最後のページまでを 1 回で引く (`listStore` の `loadThrough`)。読み込み中に先を頼まれたら、済んでから続けて読む |
| 読み始めの門 | **見えている枠はすぐ埋める**。1 画面先の先読みは、利用者が下へスクロールしてから (docs/118 §2 の門と同じ。`useScrollArmed.ts` に分けて AutoLoadMore と共有) |
| API | `/api/items?page=N&through=M` で N〜M ページをまとめて返す。続きのページからの幅は 50 ページ (1000 件) まで (`MAX_RANGE_PAGES`) |
| 一覧の形 | 控えは「先頭から連続した配列」のまま。飛び飛びにすると前後ナビ・画像ビューア・スライドショー・一括選択を全部直すことになる |
| 最初の 1 画面 | 「検索結果を読み込み中…」の下に 12 件ぶんの枠を出す (件数はまだ分からない) |
| なし (0) | 今までの「さらに表示」(AutoLoadMore) だけの一覧 |

上限を置くのは、一気に末尾まで送られたときの転送量のため。応答はノート本文を含む。

末尾の「さらに表示 (残り n 件)」は残すが、枠と一緒に置く。IntersectionObserver が効かない環境の受け皿と、
残り件数の表示を兼ねる。`[data-auto-load-more]` の目印と画像ビューアの → からの頼み (`LOAD_MORE_EVENT`) も枠の側で受ける。

## 2. 変わっていないノートは描き直さない・送らない

- **ノートのハッシュ** (`lib/client/listReuse.ts`): DTO の JSON の FNV-1a。取り直しが届いたとき、
  同じハッシュのノートは前の `Item` をそのまま使う。全部同じなら一覧の中身ごと前の物を使い、
  プレビュー・数式も作り直さない
- **ETag と 304** (`lib/route/compress.ts` の `apiOkPagedGzip`): 本文の sha1 を ETag に付ける。
  端末は 1〜N ページをまとめて引いた応答の ETag を覚え (`ListValue.etag` / `etagThrough`)、
  同じ範囲の取り直しで `If-None-Match` に添える。同じなら 304 で本文を運ばない。
  nginx の gzip は ETag を弱い印 (`W/`) にするので、比べるときは外す
- 続きを足した後は範囲が変わるので ETag を添えない (次の取り直しで新しい範囲の ETag を覚える)
- 薄く出すのは「別の検索の結果」か「書き込みで古くなった結果」だけにした。
  30 秒の期限切れや端末の控えを確かめる間は薄くしない (`useListResults.ts` の `isDimmed`)

## 3. 控えを端末に残す

- `lib/client/listPersist.ts`。IndexedDB の `qr-search-offline` に `lists` ストアを足した (版 3)
- 残すのは新しく使った順に 10 検索、1 検索 5 ページ (100 件) まで。ページを切り詰めたら ETag は捨てる
- 控えが動いてから 1.5 秒待って書く。読み戻しより先には書かない
- 起動直後に読み戻し、**時刻 0 (期限切れ) で控えに入れる**。画面に出たら必ず ETag を添えて確かめる
  (別の端末の書き換えを拾うため)。最初の取得は読み戻しを 300ms まで待つ (`listHydration.ts`)
- 読み戻した物は外部入力として検める。30 日より古い物・未来の時刻は読まない
- 消し方はオフラインの写しに揃える: ログアウトで消す (`clearOfflineData`)、デモでは残さない
- 本文は既にオフラインの写しとして同じ DB に平文で置いているので、置く物の種類は増えない

## 4. 見送り (測ってから判断)

- id と版だけ先に引き、端末に同じ版があれば本文を取らずに枠を埋める案。往復が 1 回増える場合があり、
  オフラインの写しと一覧の DTO の形も違う (docs/123 §11-2)。§2・§3 の本番の数字を見てから
