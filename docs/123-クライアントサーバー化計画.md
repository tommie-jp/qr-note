# クライアントサーバー化計画

画面の描画をサーバ (React Server Components) からクライアントへ移し、サーバは
JSON API でデータだけを返す構成 (従来の C/S 方式) にする。2026-10-29 の調査で、
現状は「主要画面 (検索・ノート) はサーバ描画、周辺 (認証・画像・設定・同期) は
JSON API、オフライン画面だけが端末描画」の混在と分かった。体感速度の見立ては
「初回起動は少し遅くなり、操作中は速くなる」(§0-2)。

決めたこと (2026-10-29):

- **Next.js は捨てない。** 殻 (ルーティング・認証の proxy・公開ノートの SSR・
  OGP) と API の置き場として残し、画面の中身を client component に移す。
  フロントエンドを別物 (Vite・Expo) に替えるのはこの計画の後の話で、API が
  揃っていれば替えられる (§9-1)
- **端末の写しを第一の読み出し元にする** (ローカルファースト寄り)。同期
  (api/sync/items) が IndexedDB に持っている全ノートから先に描き、サーバの
  応答で差し替える。往復を待たないのが体感の改善の正体 (docs/118 §0-12)
- **描画部品は増やさない。** NoteBody / MarkdownView は "use client" を付けない
  同形の部品で、公開ビューの SSR とクライアント描画の両方から今までどおり呼ぶ
- **Server Actions は全部 JSON API に置き換える** (§2)。他クライアント
  (ネイティブ・CLI・MCP) から叩けないため
- **ライブラリは足さない。** 状態は既存の externalStore (useSyncExternalStore)、
  検証は既存の lib/validation、封筒は route/respond.ts の apiOk を広げる (§9-2)
- **各 Phase の進退は docs/120 の計測で決める** (§6)。Phase 3 (ノート画面) の
  数字が基線より悪ければ、そこで止めて見直す

### 0-2. 基線 (v0.23.84、docs/118 §0-14・docs/122 §10)

| 項目 | 実測 |
| --- | --- |
| 起動の応答待ち | PC 164〜189ms・iPhone 116〜145ms |

縮まないのはブラウザ描画。Markdown 解析を端末に移す分だけ描画は増える
(iPhone は PC の約 3 倍遅い)。

## 1. 読み取り API

### 1-1. 封筒と門番 (共通)

- 封筒は既存の `{ success, data, error }` (`lib/route/respond.ts`)。ページ付きの
  応答のために `meta: { total, page, pageCount }` を足す `apiOkPaged()` を同じ
  ファイルに足す。既存の `apiOk` の形は変えない (35 本の呼び手を触らない)
- 門番は `guardRequest()` (`lib/route/guard.ts`)。未ログインは **401** (画面の
  GET のように案内へ差し替えない。api/sync/items と同じ理由: SW のキャッシュに
  案内が「データ」として沈む)
- 読み取りも `denyCrossSite()` を通す。ノート本文が出る口はすべて第三者ページ
  からの読みを断つ (docs/18 §9)
- 入力は `lib/validation.ts` (`parseSort`・`isValidItemId`・`MAX_TEXT_LENGTH`) で
  検証し、形式不正は 400 + `BAD_REQUEST_MESSAGE`
- `Cache-Control: no-store`。端末側のキャッシュは §3 のストアが持つ

### 1-2. DTO

`lib/api/itemDto.ts` (新規) に **1 つの `ItemDto`** を置き、同期 (`OfflineItem`、
`lib/offline/item.ts`) もこれに寄せる。今は同期の形と `Item` (Prisma) の 2 つが
あり、C/S 化で 3 つ目を作ると写しと API の形が割れる。

```ts
interface ItemDto {
  itemId: string
  memo: string
  title: string          // 派生列 (並べ替え用。表示は memoSummary を通す)
  tags: string[]
  taskTodo: number
  taskDone: number
  createdAt: string
  updatedAt: string      // 書き込みの base にも使う (§2-2)
  accessedAt: string
  pinned: boolean
  isPublic: boolean
  deletedAt: string | null
}
```

- `Item` → `ItemDto` の変換は `toItemDto(item)` 1 本。Date は ISO 文字列
- 検証 (端末側・写しの読み戻し) は `OfflineItem` の `isOfflineItem` を
  `isItemDto` に改名して流用 (`lib/offline/item.ts` の型述語がそのまま使える)
- サーバ専用の列 (`circuit_fences` 別表、埋め込みベクトル) は載せない

### 1-3. エンドポイント

| 口 | 返すもの | 今の実装 (サーバ側はそのまま呼ぶ) |
| --- | --- | --- |
| `GET /api/items?q=&page=&sort=` | `ItemDto[]` + meta、`extras` (下記) | `loadSearchResults()` (`lib/search/pageData.ts`) |
| `GET /api/items/:itemId` | `ItemDto` | `getItem()` (`lib/items/read.ts`) |
| `GET /api/items/:itemId/render` | `{ circuits, matrices, health }` | `planCircuits` / `buildMatrices` / `buildHealthCharts` (ItemView の OwnerNoteBody が呼んでいるもの) |
| `GET /api/items/:itemId/neighbors?q=&sort=` | 前後のノート id | `findListNeighbors()` |
| `GET /api/tags` | `TagCount[]` | `listTags()` |
| `GET /api/folders` | 件数とフォルダーのタグ | `countFolderTotals()`・`lib/search/folderTags.ts` |
| `GET /api/trash?q=&page=&sort=` | ゴミ箱の `ItemDto[]` + meta | `trash/page.tsx` が呼んでいる検索 |
| `GET /api/items/:itemId/history` | 版の一覧 | `settings/history` の読み出し |

`extras` は `loadSearchResults` が検索と並べて引く付属情報で、**同じ 1 応答に
載せる** (別口にすると往復が増える):

```ts
interface SearchExtras {
  props: ItemPropsResult          // タグ検索のときだけ
  progress: TaskProgress          // チェック状態の検索のときだけ
  trashCount: number
  trashedMatches: number
  registerHref: string | null
  circuitThumbs: Record<itemId, svgHash[]>   // SVG 本体は載せない (§1-4)
  mathSummaries: Record<itemId, string>
}
```

`notePreviews` (一覧のプレビュー) と `mathTexts` は載せない。memo から端末で
作れる (memoSummary と同じ流儀)。サーバで作っている理由は RSC で HTML を
運ぶためだったので、C/S では要らない。

### 1-4. 回路図の SVG

一覧の RSC が重い原因の 1 つが行に埋めた SVG (docs/118 §0-3 の 4)。C/S では
**SVG を hash で別に配る** (docs/118 §2-4 で様子見にした案をここで採る):

- `GET /api/circuits/:hash` … `circuit_svgs` から 1 枚。`Cache-Control:
  public, max-age=31536000, immutable` (hash が鍵なので不変)。ログイン必須は
  変えない (guardRequest)
- 既存の `POST /api/circuits` (編集のライブプレビュー用) はそのまま
- `/api/items` の `circuitThumbs` は hash の一覧だけ。端末は手元の写し
  (同期で受けた `OfflineCircuit`、鍵はフェンスの中身) → 無ければ `/api/circuits/:hash`
  の順で引く

| Server Action | 口 | 本体 (そのまま呼ぶ) |
| --- | --- | --- |
| `updateItemAction`・`updateMemoAction` | `PUT /api/items/:itemId` `{ memo, tags?, base }` | `saveItemIfUnchanged()` |
| `toggleMemoTaskAction` | `PATCH /api/items/:itemId/tasks` `{ line, checked }` | `modifyMemo()` |
| `recordHealthAction` | `POST /api/items/:itemId/health` | 同上 (health の追記) |
| `recordAccessAction` | `POST /api/items/:itemId/access` | `recordItemAccess()` |
| `assignNoteNumberAction` | `POST /api/items/:itemId/number` | `nextFreeNoteNumber()` + 保存 |
| `bulkTagAction` | `POST /api/items/tags` `{ itemIds, add, remove }` | tags.ts の本体 |
| `trashItemsAction` 他 3 本 | `POST /api/trash` `{ op: 'trash'\|'restore'\|'purge'\|'empty', itemIds }` | trash.ts の本体 |
| `setItemPublicAction` | `PUT /api/items/:itemId/public` `{ isPublic }` | `setItemPublic()` |
| `setItemOfflinePinAction(s)` | `PUT /api/items/pin` `{ itemIds, pinned }` | `setItemOfflinePin()` |
| `commitNoteAction`・`restoreNoteVersionAction`・`backfillHistoryAction` | `POST /api/items/:itemId/history` `{ op, version? }` | history.ts の本体 |
| `setPaneModeAction`・`setViewModeAction` | 既存 `/api/settings/pane-mode`・`view-mode` | 変更なし |
| `setSortAction`・`setTrashSortAction` | `PUT /api/settings/sort` (新規) | cookie → user_settings へ |
| benchmark 3 本 | `POST /api/diag/bench`・`GET /api/diag/bench` | benchmark.ts の本体 |

- 本体のロジックは `lib/items/*` に既にあるので、route.ts は「門番 → 検証 →
  本体 → 封筒」の 20〜40 行で済む。`src/app/actions/*.ts` は Phase 5 で削除
- `_revalidate.ts` (`revalidateItem` / `revalidateLists`) は公開ノートの SSR
  にだけ残す (`setItemPublic` と `PUT /api/items/:itemId` の公開ノートの保存で
  `revalidatePath('/item/<id>')`)。それ以外の無効化は端末のストアが担う (§3-3)
- 書き込みはすべて `denyCrossSite()` + `denyIfDemoMode()` (デモで断るものは
  今の action の判断を写す)

### 2-2. 編集競合

`PUT /api/items/:itemId` の `base` は端末が最後に見た `updatedAt`。
`saveItemIfUnchanged` が `rejected` を返したら **409** で現在の `ItemDto` を
`data` に載せて返す。端末は docs/87 の競合画面にそのまま流す (今は action の
戻り値で分岐している所を、status 409 の分岐に替える)。

## 3. 端末側のデータ層

### 3-1. API クライアント (`lib/client/api.ts`、新規)

- `apiGet<T>(path, { signal })` / `apiSend<T>(method, path, body)`。封筒を剥がし、
  `success: false` は `ApiError(status, error)` で投げる
- 401 は `location.assign('/login-required?next=…')`。proxy.ts の画面 GET の
  振る舞いと揃える
- 連打の中止は `AbortController`。検索窓は打鍵ごとに前の要求を中止する
- 文字列以外は受け取らない: 応答は `isItemDto` 等の型述語で検証してから
  ストアへ入れる (外部データを信用しない)

### 3-2. ストア (`lib/client/store/`、新規)

既存の `createNotifier` / `createExternalStore` (`lib/prefs/externalStore.ts`) で
組む。ライブラリは足さない (§9-2)。

| ストア | 持つもの | 読み手 |
| --- | --- | --- |
| `itemsStore` | `Map<itemId, ItemDto>` と取得時刻 | ノート画面・一覧の行・編集画面 |
| `searchStore` | `Map<key, { itemIds, total, page, pageCount, extras, at }>`、key = `q\|sort` | 一覧・ページ送り |
| `tagsStore` / `foldersStore` | タグ一覧・フォルダー集計 | フォルダーペイン・検索窓の補完 |
| `renderStore` | `Map<itemId, { circuits, matrices, health }>` | NoteBody の付属 |
| `circuitSvgStore` | `Map<hash, svg>` | 一覧のサムネ・本文の図 |

- 読みは **写し → ストア → API** の順。写しは `snapshotDb.ts` の IndexedDB
  から起動時に 1 回 `itemsStore` へ流し込む (同期の受け取りと同じ経路)
- 取得は stale-while-revalidate: ストアにあれば即返して裏で `apiGet`、届いたら
  差し替えて通知。無ければ待つ
- 書き込みは write-through: 応答の `ItemDto` を `itemsStore` と IndexedDB の
  写しの両方へ入れる。`searchStore` は当該 key を捨てる (再取得は次に見たとき)

### 3-3. 無効化の規則

| 起きたこと | 捨てる / 直す |
| --- | --- |
| ノートの保存・タスク切替・health 追記 | `itemsStore[id]` を応答で置換、`renderStore[id]` を捨てる、`searchStore` を全部捨てる |
| ゴミ箱・復元・完全削除 | `itemsStore[id]` を置換 / 削除、`searchStore` を全部捨てる、`foldersStore` を捨てる |
| タグ一括 | 対象 id を置換、`searchStore`・`tagsStore`・`foldersStore` を捨てる |
| 同期の 200 (版が変わった) | `itemsStore` を写しで全置換、`searchStore` を全部捨てる |
| 同期の 304 | 何もしない |

「全部捨てる」で足りる。検索結果の件数は数百で、再取得は 1 往復。細かい差分
更新は YAGNI (必要になったら key 単位に絞る)。

### 3-4. 端末の検索 (打鍵の即時結果)

`lib/offline/filter.ts` をそのまま使う (サーバと `search/parse.ts` を共有)。
打鍵 → 端末の結果を即描く → `/api/items` が届いたら差し替える。並び順は
`lib/offline/order.ts` で揃える。端末は部分一致、サーバはバイグラム全文
(filter.ts の冒頭) で**件数がずれうる**ので、サーバの結果が届くまでは件数の
表示を薄くする (今の SearchResults の「反映待ち」と同じ見せ方)。

## 4. 画面の移行

### 4-1. ノート画面 (Phase 3)

- `ItemView.tsx` (server) の中身を `components/item/NoteScreen.tsx` ("use client")
  へ移す。`itemsStore.get(itemId)` → `NoteBody` へ。`circuits / matrices /
  health` は `renderStore` (`/api/items/:id/render`) から。届くまでは
  MarkdownView の省略時の挙動 (フェンスはコードブロックのまま。OfflineNote
  と同じ) で先に出す
- `OwnerNoteBody` の `onToggleTask` / `onRecordHealth` は action の bind から
  `apiSend('PATCH', …)` に替える。NoteBody の props の型は変えない
- `item/[itemId]/page.tsx` と `(search)/@detail/(.)item/[itemId]/page.tsx` は
  **ログイン済みなら `<NoteScreen itemId/>` を返すだけ**にする。`guardItemPage`
  (旧 id の 308) はサーバに残す
- 非ログイン (公開ノート) は今の `PublicItemView` の SSR のまま。`ItemDetail`
  の分岐をここで切る
- `ItemListNavSection` (前後のノート) は `/api/items/:id/neighbors`
- `RecordAccess` は `POST /api/items/:id/access`
- **バンドル**: `NoteBody` 一式 (react-markdown・remark/rehype・KaTeX・
  fence-kit 群) が初回の JS に入る。`next/dynamic` で `NoteScreen` を分け、
  検索一覧だけの起動では読まない。KaTeX と fence-kit は MarkdownView の中で
  使う所だけ `dynamic` にする (今は静的 import)
- 罠: `thumbnail.ts` の定数を client から import すると sharp が降りて 500
  (memory)。定数は別ファイルに分けてある前提を守る

### 4-2. 検索一覧 (Phase 4)

- `HomeResults.tsx` (server) → `components/search/SearchResultsClient.tsx`。
  `searchStore` から `itemIds` → `itemsStore` で行を組む。`ItemList` は既に
  client なので props の出どころが変わるだけ
- `SearchNav.tsx` の `router.replace` を `window.history.replaceState` に替える。
  App Router の `router.replace` は RSC ペイロードを取りに行く (これが往復の
  正体)。`useSearchParams` は replaceState に追随する (Next 15 以降)。
  OfflineApp の `location.ts` と同じ作法
- `AutoLoadMore` は `page+1` を `searchStore` に追加して行を**足す** (今の
  「1〜N ページを描き直す」をここで解く。docs/118 §2-3 の段階 B が自然に
  済む)
- `circuitThumbs` は hash → `circuitSvgStore`。`notePreviews` は端末で
  `memoSummary` から
- `PullToRefresh` は `searchStore` を捨てて再取得 (ページの再読み込みをやめる)
- `page.tsx` は `requireUser()` と殻 (SearchForm・Provider 群) だけ残す。
  `listTags` もやめて `tagsStore` から (検索窓の補完が数十 ms 遅れて付く。
  許容)

### 4-3. フォルダーペイン・ゴミ箱・履歴・設定 (Phase 4・6)

- `SearchFolders.tsx` → `tagsStore` / `foldersStore`
- `trash/page.tsx` → `/api/trash` と `POST /api/trash`
- `settings/history` → `/api/items/:id/history`
- `settings/*` のその他 (passkeys・secrets・server・import・benchmark) は
  **今のまま** (既に API 主体か、管理画面で速さが要らない)

### 4-4. 編集画面 (Phase 6)

`MemoEditor` は既に client。`edit/[itemId]/page.tsx` の `getItem` を
`itemsStore` に、`updateItemAction` を `PUT /api/items/:id` に替える。
`NoteSaveForm` の `useActionState` は `fetch` + state に。`UnsavedGuard` は
変更なし。

### 4-5. 残す SSR

| 画面 | 理由 |
| --- | --- |
| 非ログインの `/item/[itemId]` (PublicItemView) | 公開リンク・OGP カード (docs/90・OGP の記録)。HTML が返ることに依存 |
| `/print/[itemId]` | 印刷は 1 枚の HTML が都合よい |
| `/about`・`/docs/*`・`/login-required`・`/offline` の殻 | 静的 |
| `metadata.ts` の OGP | クローラは JS を実行しない |

### 4-6. オフライン画面の統合 (Phase 7)

本線が写しから描くようになると、`components/offline/*` の役割は「圏外で殻を
出す」だけになる。`OfflineApp` を捨て、Service Worker が `/`・`/item/*` の
ナビゲーションを圏外では**キャッシュした殻**で返す (今は `/offline` 1 枚だけ)。
本線の `NoteScreen` / `SearchResultsClient` が `apiGet` の失敗を「写しのまま
表示 + 圏外の印」に倒せば、オフライン画面と本線が 1 本になる。
`OfflineNote` の読み取り専用の制約 (編集の導線を出さない) は `navigator.onLine`
と直前の `apiGet` の失敗で切り替える。

## 5. Service Worker と起動

- 起動の順: 殻 (HTML + JS、SW キャッシュ) → IndexedDB の写しを `itemsStore` へ
  → 画面を描く → `/api/items` / `/api/items/:id` で差し替え。**写しがあれば
  サーバを待たずに最初の画面が出る**
- 写しが無い初回 (新しい端末) は API を待つ。ここだけは今より 1 往復遅い
- `sw.js` の precache に `NoteScreen` の chunk を含める (版ごとに 1 回)
- 同期 (5 分おき、`schedule.ts`) はそのまま。304 なら何もしない、200 なら
  §3-3 の全置換

## 6. 計測と合否

docs/120 の計測テスト (12 段) を各 Phase の前後で PC 3 ペインと iPhone 2 ペインで
回す。比べるのは「区分=測定」の行。

| 項目 | 合格の目安 |
| --- | --- |
| 起動の応答待ち + 最初の描画 (写しあり) | 基線の 1/2 以下 (サーバを待たないので) |
| 起動 (写しなし・新しい端末) | 基線の +30% 以内 |
| 検索語の変更 → 一覧の差し替え | 即時 (端末の結果) 50ms 以内、サーバの結果の差し替えは基線以内 |
| ノートを開く (写しあり) | iPhone で 100ms 以内 (本文のみ。回路図は後から) |
| 表示モード・ペイン切替 | 現状維持 (既に端末先行) |
| 初回の JS (gzip) | Phase 3 で測って上限を決める。目安は +300KB 以内 |
| サーバの CPU (検索 1 回) | 基線の 1/3 以下 (RSC の組み立てが無くなる) |

Phase 3 の後で「ノートを開く」が iPhone で基線より遅ければ、Markdown 解析の
重さが見立てより大きいということ。その場合は `/api/items/:id/render` に
**描画済み HTML** を載せる段 (サーバ描画の部分復活) を足して測り直す。

## 7. セキュリティ (security.md の点検表に沿う)

- 全 route に `guardRequest` (401)、本文が出る口に `denyCrossSite`、書き込みに
  `denyIfDemoMode` の判断を action から写す
- 入力検証は `lib/validation.ts` と `lib/route/parse.ts` (`parseJsonBody`)。
  memo は `MAX_TEXT_LENGTH`、`itemId` は `isValidItemId`、`sort` は `parseSort`
- 本文は `readBodyBounded` で上限 (Next の proxy の 10MB 複製の罠は ZIP 取り込み
  の記録どおり。JSON の本文は 64KB で足りる)
- エラー文は封筒の `error` に定型文だけ。内部の例外はサーバログへ
- レート制限は nginx (docs/120 の「未反映」のまま。この計画で `/api/items`
  に `limit_req` を足す)
- 秘密は増えない。`/api/items` は `auth/publicPaths.ts` に**載せない**
  (公開ノートは SSR の経路だけ)
- 完了前に security-reviewer を 1 回通す (Phase 1・2・5 の後)

## 9. 判断と却下した案

### 9-1. フロントエンドを完全に分離する (Vite SPA + 別の API サーバ)

やらない (今は)。認証 (proxy.ts と cookie)・Service Worker・公開ノートの SSR・
OGP を作り直すことになり、見返りは「Next.js への依存が消える」だけ。この計画
で API と client component に分けておけば、後で殻を替えるときに移すのは
`src/app/**/page.tsx` の薄い殻だけになる。

### 9-2. TanStack Query / SWR を入れる

入れない。stale-while-revalidate と無効化は §3 の規則で足り、既存の
`externalStore` で書ける。依存を増やすと初回の JS が太る (この計画の最大の
リスクが JS の増加)。無効化の規則が §3-3 の表で収まらなくなったら再考。

### 9-3. Server Actions を残す

残さない。Next.js の中からしか呼べず、API として他クライアントに出せない。
中身のロジックは `lib/items/*` にあるので、route.ts の殻を足す工数は小さい。

### 9-4. GraphQL / tRPC

要らない。口は 20 本、形は `ItemDto` 1 つ。REST + 封筒で足りる。

### 9-5. サーバ描画の HTML を API で返す

Phase 3 の計測が悪かったときの逃げ道として §6 に残す。最初からやると「端末が
描く」が崩れ、公開ビューとの描画経路も 2 本のままになる。

## 10. リスク

1. **初回 JS の増加。** Markdown 一式が端末へ。`dynamic` 分割と SW の precache
   で版ごとに 1 回にする。上限は Phase 3 で測って決める (§6)
2. **iPhone の描画。** 端末での Markdown 解析が PC の 3 倍かかる。Phase 3 で
   止まれる構造にしてある (§8)
3. **描画経路の 2 本化。** 公開ビュー (SSR) と `NoteScreen` (client) が
   `NoteBody` を共有する前提。`NoteBody` / `MarkdownView` に "use client" と
   server-only の import を**入れない**規則を README に明記する
4. **端末とサーバの検索の差。** 部分一致 vs バイグラム。即時結果は「仮」と
   見せ、サーバの結果で必ず差し替える (§3-4)
5. **編集競合。** 409 + 現在の DTO で docs/87 の画面へ。`base` を落とすと
   上書きになるので、PUT の検証で `base` を必須にする
6. **PGroonga 索引の消失** (memory)。API 化とは独立だが、端末の検索が先に出る
   ようになると**サーバの検索が seq scan に落ちても気づきにくくなる**。
   サーバー情報画面の索引チェックは残す
7. **写しの肥大。** 11MB の JSON を起動ごとに IndexedDB から `Map` へ。数百件
   なら数十 ms。数千件になったら `itemsStore` を遅延読み (id ごと) に変える
8. **vps のメモリ。** サーバは軽くなる方向。`/api/circuits/:hash` の immutable
   キャッシュで nginx 側の負担も減る
