# 検索候補計画 (最近の検索・登録パターン・キーワード補完)

検索窓に候補を出して、打つ手間を減らす。作るのは 3 つ。

1. **最近の検索** — 直近に検索した語。窓が空のときに出す。
2. **登録パターン** — 自分で登録した検索式。同じく窓が空のときに出す。
3. **キーワード補完** — `i` まで打つと `is:todo` `is:done` を候補に出す。

覚える数と出す数は分ける。1 と 2 はそれぞれ **10 件覚えて、最初は 5 件ずつ出す**。
残りは末尾の「もっと表示」を押したときに出す (合わせて最大 20 行)。

どれも [SearchForm.tsx](../src/components/SearchForm.tsx) に既にあるタグ補完
ドロップダウン (`#` を打ちかけたときの候補) の上に乗せる。新しい UI を足すのでは
なく、**あのドロップダウンを「候補の種類が混ざる 1 つの listbox」へ一般化する**。
↑↓ / Enter / Escape / mousedown で確定、`active === -1` の間は Enter が検索送信、
という作法はそのまま流用できる。

## 1. いつ何を出すか

| 窓の状態 | 出すもの |
| --- | --- |
| 空 (フォーカス中) | 登録パターン 5 件 → 最近の検索 5 件 → 「もっと表示」 |
| `#…` を打ちかけ | タグ候補 (既存) |
| それ以外の語を打ちかけ | キーワード候補 (`is:todo` / `is:done`) |

登録パターンを上に置く。数が少なく、自分で選んで置いた物だから。

**どちらの組も最近使った順** (新しい物が上)。登録パターンは当初「並びが
動かないほうが筋肉記憶が効く」として登録順のままにしていたが、10 件持てて
5 件しか出ない今は、よく使う物が畳まれた向こう側に沈む方が困る。

「もっと表示」は畳んでいて、かつ出していない候補があるときだけ出す。押すと
両方を上限 (10 件ずつ) まで開く。**listbox の option にはしない** — 候補では
なく操作なので、↑↓ で拾えると Enter が「もっと表示という語で検索」になる。

候補の型は種類 + 挿入する値 + (補完のときだけ) 置換範囲を持つ 1 つの
`Suggestion` にまとめる。確定処理の違いはここだけ:

- タグ / キーワード … トークンの範囲を置換する (途中まで打った語の続き)
- パターン / 最近 … **クエリ全体を差し替える** (打ちかけの語は捨てる)

窓にフォーカスしただけでも候補を出す。そのぶん「打ち終わったタグ 1 つだけが
候補に残る」形 (`#抵抗` に対して候補も「抵抗」) は抑える — 選んでも何も
変わらないのに結果を覆い、窓を触るたびに出てくるため。`matchTags` 側で
完全一致を落とさないのは、`#ab` に対する候補が `[ab, abc]` のとき Tab が
`#abc` まで走ってしまうから。抑えるのはドロップダウンを開くかどうかの判断側。

## 2. 使ったことの記録は「意思表示」のときだけ

いちばん効く設計判断がここ。この検索窓は debounce 300ms で
**打ちながら検索する** (`scheduleSearch`) ので、`navigate` のたびに記録すると

```text
電 / 電験 / 電験三 / 電験三種
```

とプレフィックスのごみが並び、5 件の枠が 1 回の検索で埋まる。記録するのは
次の 3 つだけにする。debounce の `navigate` では記録しない。

1. **明示送信** — Enter / 検索ボタン (`handleSubmit`)
2. **候補の確定** — タグ・キーワード・パターンを選んだとき
3. **結果のノートを開いたとき** — その時点の `q`
4. **タグ (#…) を押したとき** — リンク先のタグ

3 がいちばん質が高い。「結果に満足したクエリ」だけが残るため。この窓は
打つそばから結果が出る作りで、Enter を押さずにそのまま結果を叩く使い方が
主なので、3 が無いとほとんど記録されない。

3 の実装は [SearchNav.tsx](../src/components/SearchNav.tsx) の `SearchResults` に
`onClickCapture` を 1 つ置き、`a[href^="/item/"]` に当たったときだけ記録する。
結果一覧 (小・大・画像モード) をまとめて包んでいる唯一の client component が
ここで、モードごとに配って回らずに済む。

4 は [RecordTagSearch.tsx](../src/components/RecordTagSearch.tsx) が document で
受ける。タグのリンクは一覧の行・画像タイル・詳細ページ・メモ本文の 4 か所に
あって、どれも Server Component が描くので、結果一覧の中だけを見ていると
詳細ページやメモ本文のタグが漏れる。記録する語は**押した時点の URL ではなく
リンク先**から取る (`tagSearchQuery`) — タグを押すのは「そのタグで探したい」
であって、今の検索を認めたわけではないため。ページ送りや一覧への戻り
(`buildSearchUrl` は page / sort を足す) は同じ `/?q=` でも拾わない。

記録の入口は `recordQueryUse` 1 つ。**登録パターンなら最近使った順の先頭へ
動かすだけで、最近の検索には足さない**。足すと ★ に出ている物が 🕐 の枠を
見えないまま食う (表示では登録済みを引くので、10 件のうち何件かが常に
空振りになる)。代わりに ★ を外したときにその場で履歴へ入れる — 行が 🕐 に
変わって見えているのに、閉じて開いたら消えている、を避けるため。

保険としてプレフィックスの掃除も入れる。新しく記録する語の**前方一致になって
いる古い記録は消す** (`電験` を記録したら `電` を消す)。逆は消さない —
長い語を覚えている状態で短く検索し直すのは、それ自体が新しい検索だから。

## 3. 置き場所: 当初は localStorage (§7 でサーバへ移した)

> この節は最初の設計の記録。**現在の置き場はサーバ (DB)** で、経緯と設計は
> [§7](#7-置き場所をサーバへ移す-ユーザ毎共通) にある。

最近の検索も登録パターンも localStorage に置く。

- 検索のたびに DB へ書くのは重すぎる。最近の検索は端末ごとに違ってよい
  (スマホでは部品番号、PC では調べ物、という差がそのまま出るのが自然)。
- このアプリには localStorage の型が既にある
  ([drawPrefs.ts](../src/lib/draw/drawPrefs.ts) / [memoDraft.ts](../src/lib/memoDraft.ts))。
  読み出しは信用せず検算してから使う、書けなくても機能が死なない、という
  作法もそこに揃っている。

cookie にはしない。並び順 (`sortMode.ts`) や表示モード (`viewMode.ts`) が
cookie なのは**サーバが描画前に読む必要がある**からで、候補はフォーカスして
初めて要る値なので、その理由が無い。

登録パターンだけは端末をまたぎたくなる可能性があるが、それは実際に不便を
感じてから DB へ昇格させる (YAGNI)。移行のとき困らないよう、保存形式は
「クエリ文字列の配列」だけにしておく。

読むのは**ドロップダウンを開くとき**にする (マウント時ではない)。記録は別の
component (`SearchResults`) からも起きるので、開くたびに読み直せば必ず新しい。

## 4. 登録: 最近の検索を ☆ で昇格させる

登録の導線は「最近の検索の行に ☆ を置き、押すとパターンになる」だけにする。
検索窓の周りにボタンを増やすと 320px 幅で破綻するし、「登録画面を開いて
検索式を手で打つ」導線は、実際に打った式をそのまま登録できる ☆ より遠い。

パターンの行には ★ を出し、押すと登録を外す。これで管理画面は要らない。

☆ / ★ は `role="option"` の中の `<button tabIndex={-1}>` にする。listbox の
option に対話要素を入れるのは ARIA 的には行儀が悪いが、行そのものは
mousedown で確定できるままで、キーボード操作は listbox のものが生きる。

### 持てる数は「出し切れる数」に収める (SAVED_LIMIT = 10)

登録の上限を**画面に出せない数まで**広げてはいけない。出ないまま保存された
パターンは、**外す導線が ★ の行にしか無いので二度と消せなくなる**。☆ を押しても
画面は何も変わらないので、利用者から見れば「押しても効かない」。

「もっと表示」で 10 件まで開けるので、上限 10 なら必ず画面に出せる = 必ず外せる。

畳んでいる間は登録済みでも隠れる物があるが、最近の検索から引くのは
**表示分ではなく登録パターン全部**にする (`splitSuggestions`)。これで
「🕐 の行は必ず未登録」が畳んでいる間も成り立ち、☆ が空振りしない。
同じ理由で「満杯かどうか」も出ている ★ の数ではなく登録一覧の長さで見る。

満杯のときは ☆ を `disabled` にして、理由を `title` に出す — 黙って何も
起きないのが最悪の応答なので。

### 押しても行は並び替えない

☆ を押した行を ★ の欄へ移すと、下の行が 1 つずつ繰り上がる。指が同じ場所を
続けて叩くと**隣の検索語を登録してしまう**。押した後は ★/☆ と 🕐 の表示だけ
差し替え、並べ直すのは次に開いたときにする。

## 5. キーワード補完

[tagComplete.ts](../src/lib/tagComplete.ts) と同じ形の純関数として
`keywordComplete.ts` に切る (DB 非依存・カーソル位置から文脈を求める)。

- 候補は定数配列 `SEARCH_KEYWORDS = ['is:todo', 'is:done']` の前方一致。
  今後フィルタが増えても配列への追記だけで済む。
- `i` の 1 文字から出す。`active === -1` の間は Enter がそのまま検索送信に
  なるので、候補が出ているだけでは入力の邪魔をしない。`is` まで必須にすると
  発見性が落ちる (この機能の目的は「そんな構文があると気づく」ことでもある)。
- 出さない場面: 引用符の内側 (`"is:…"` はリテラル検索)、`#` で始まるトークン
  (タグ補完の担当)、トークンが空のとき、既に候補と完全一致しているとき。
- 語の境界は tagComplete と共通の `isTokenBoundary` で揃える。`!is:todo` や `(is:todo|…)` の
  ように演算子の直後でも補完が効く必要があるため。

置換の実体 (範囲を置き換えてキャレット位置を返す・必要なら空白を足す) は
タグ補完と同じなので `queryComplete.ts` に括り出して両方から使う。

## 7. 置き場所をサーバへ移す (ユーザ毎共通)

§3 で「最近の検索は端末ごとに違ってよい」と決めたが、実際に使うと逆だった。
同じ人が iPhone と PC を行き来するので、**片方で登録したパターンがもう片方に
無い**のがそのまま不便になる。最近の検索も同じで、スマホで調べた部品番号を
PC で開き直すことのほうが多い。

書き込みが重いという心配も当たらなかった。記録の契機は §2 で「意思表示」の
ときだけに絞ってあり、打鍵ごとの検索からは呼んでいない。1 回の検索につき
高々 1 回しか書かないので、DB に置いても頻度は高くない。

### 全ユーザ共通ではなく、ユーザ毎

履歴は「その人が何を探しているか」そのものなので、利用者が増えたときに
混ざってはいけない。`user_name` で仕切る。

`User` 表は作らない。`sessions.user_name` / `webauthn_credentials.user_name` が
既に名前の文字列で運用しており (docs/29 §11)、そこへ揃える。

**誰のものかを決めるのはセッションだけ**。リクエストの本文で名乗らせると、
ログインさえしていれば他人の履歴を読み書きできてしまう。

### 1 クエリ = 1 行

JSON を 1 列に持つと、2 台から同時に登録したときに後から書いたほうが相手の
登録を消す。行に割れば衝突する範囲がそのクエリだけで済む。並びは `used_at`
の降順が表す (同時刻なら `id` の大きいほう = 後から入れたほうが先)。

### 意味づけは 1 か所に置く

前方一致の掃除・上限・「登録は履歴より強い」は
[searchQueries.ts](../src/lib/searchQueries.ts) の純関数が決める。サーバの
書き込みもクライアントの楽観更新も同じ `applyQueryUse` を通るので、手元と
サーバの答えが食い違わない。

サーバは読んで・計算して・書き戻すのをトランザクションの中でやる。往復の間に
別の端末が触っても、消し合いにはならない。

### 口と呼び方

| ルート | 動作 |
| -------- | ------ |
| `GET /api/search-queries` | 2 つのリストを最近使った順で返す |
| `POST /api/search-queries` | 「使った」の記録 |
| `PUT /api/search-queries` | localStorage からの引き取り (一度だけ) |
| `PUT /api/search-queries/saved` | ☆ で登録。満杯なら 409 |
| `DELETE /api/search-queries/saved` | ★ で解除 (同時に履歴へ入る) |

読むのは**検索窓にフォーカスしたとき**の 1 回だけ。候補はドロップダウンを
開いて初めて要る値なので、描画のたびに引く理由が無い (§3 と同じ判断)。

書きは fire-and-forget + 楽観更新にする。★ を押した手応えを往復待ちにしない
ため、手元を先に動かして、返ってきた正本で置き換える。記録の POST には
`keepalive` を付ける — 結果のノートを開いた瞬間にも呼ばれるので、付けないと
遷移でブラウザに要求を捨てられる。

**サーバから新しい値が届いても、開いている一覧は組み直さない**。並びが指の
下で動くと、続けて押した指が隣の検索語を登録してしまう (§4 の「押しても行は
並び替えない」と同じ理由)。閉じているときだけ開く。

### 失敗したときの振る舞い

localStorage 版の割り切りをそのまま引き継ぐ。**候補が出ない・記録が残らない
だけで、画面にエラーは出さない**。検索そのものは候補と無関係に動く。
ただし黙って消えると原因が追えないので `console.warn` は残す。

応答は検算してから使う。サーバを無条件に信じて型の合わない値を描画側へ流すと
そこで落ちる (localStorage を信じなかったのと同じ理由で、経路が変わっても
「外から来た値」であることは変わらない)。

### デモは覚えない

デモは共有アカウント (docs/38-デモモード計画.md) なので、履歴を持たせると
訪問者どうしで検索語を見せ合うことになる。かといって 403 にすると画面が
エラーを抱えるので、**空を返して「何も覚えていない」として振る舞う**。
候補が出ないだけで検索は動く。

### localStorage からの引き取り

引き取るのは**登録パターンだけ**。最近の検索は数回検索すれば貯まり直すが、
登録パターンは利用者が自分で選んで置いた物なので、黙って消えると困る。

1 回のリクエストでまとめて送る。1 件ずつ登録させると、途中で満杯になったとき
にどこまで入ったのか分からず、localStorage を消してよいか判断できない。

送れたら localStorage の鍵は消す。**利用者ごとの済み印は持たない** — 鍵を
消してしまえば、同じ端末で別の人がログインしても引き取る物が残っていない。
送れなかったら鍵は残す (消してから失敗すると、登録したパターンがどこにも
無くなる)。

**デモには送らない。** 鍵を残してやり直せるのは圏外や 500 のような
*一時的な* 失敗のときだけで、デモは「覚えない」(上節) が変わらない以上、
何度送っても同じ空の応答が返る。当初は「200 だが登録パターンが空なら
鍵を残す」で断りを見分けていたが、これだとデモでは検索窓を開くたびに
送り直す無限ループになる。デモかどうかを知っているのはサーバだけなので、
`isDemo` を検索ページから `SearchForm` へ降ろし、送る前に降りる。
鍵は消さずに残す — デモを離れて本番で開いたときに引き取れる。

全員の端末が通り終わったら
[searchQueryLegacy.ts](../src/lib/searchQueryLegacy.ts) ごと削除する。
