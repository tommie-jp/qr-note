# 検索候補計画 (最近の検索・登録パターン・キーワード補完)

検索窓に候補を出して、打つ手間を減らす。作るのは 3 つ。

1. **最近の検索** — 直近に検索した語を 3 件。窓が空のときに出す。
2. **登録パターン** — 自分で登録した検索式を 3 件。同じく窓が空のときに出す。
3. **キーワード補完** — `i` まで打つと `is:todo` `is:done` を候補に出す。

どれも [SearchForm.tsx](../src/components/SearchForm.tsx) に既にあるタグ補完
ドロップダウン (`#` を打ちかけたときの候補) の上に乗せる。新しい UI を足すのでは
なく、**あのドロップダウンを「候補の種類が混ざる 1 つの listbox」へ一般化する**。
↑↓ / Enter / Escape / mousedown で確定、`active === -1` の間は Enter が検索送信、
という作法はそのまま流用できる。

## 1. いつ何を出すか

| 窓の状態 | 出すもの |
| --- | --- |
| 空 (フォーカス中) | 登録パターン 3 件 → 最近の検索 3 件 |
| `#…` を打ちかけ | タグ候補 (既存) |
| それ以外の語を打ちかけ | キーワード候補 (`is:todo` / `is:done`) |

登録パターンを上に置く。固定の並びなので筋肉記憶が効き、最近の検索のように
中身が入れ替わらないため。

候補の型は種類 + 挿入する値 + (補完のときだけ) 置換範囲を持つ 1 つの
`Suggestion` にまとめる。確定処理の違いはここだけ:

- タグ / キーワード … トークンの範囲を置換する (途中まで打った語の続き)
- パターン / 最近 … **クエリ全体を差し替える** (打ちかけの語は捨てる)

窓にフォーカスしただけでも候補を出す。そのぶん「打ち終わったタグ 1 つだけが
候補に残る」形 (`#抵抗` に対して候補も「抵抗」) は抑える — 選んでも何も
変わらないのに結果を覆い、窓を触るたびに出てくるため。`matchTags` 側で
完全一致を落とさないのは、`#ab` に対する候補が `[ab, abc]` のとき Tab が
`#abc` まで走ってしまうから。抑えるのはドロップダウンを開くかどうかの判断側。

## 2. 最近の検索: 記録するのは「意思表示」のときだけ

いちばん効く設計判断がここ。この検索窓は debounce 300ms で
**打ちながら検索する** (`scheduleSearch`) ので、`navigate` のたびに記録すると

```text
電 / 電験 / 電験三 / 電験三種
```

とプレフィックスのごみが並び、3 件の枠が 1 回の検索で埋まる。記録するのは
次の 3 つだけにする。debounce の `navigate` では記録しない。

1. **明示送信** — Enter / 検索ボタン (`handleSubmit`)
2. **候補の確定** — タグ・キーワード・パターンを選んだとき
3. **結果のノートを開いたとき** — その時点の `q`

3 がいちばん質が高い。「結果に満足したクエリ」だけが残るため。この窓は
打つそばから結果が出る作りで、Enter を押さずにそのまま結果を叩く使い方が
主なので、3 が無いとほとんど記録されない。

実装は [SearchNav.tsx](../src/components/SearchNav.tsx) の `SearchResults` に
`onClickCapture` を 1 つ置き、`a[href^="/item/"]` に当たったときだけ記録する。
結果一覧 (小・大・画像モード) をまとめて包んでいる唯一の client component が
ここで、モードごとに配って回らずに済む。タグリンクは `/?q=%23…` なので
当たらない — タグを叩いたのは「今の検索が良かった」合図ではないので、
これは意図どおり。

保険としてプレフィックスの掃除も入れる。新しく記録する語の**前方一致になって
いる古い記録は消す** (`電験` を記録したら `電` を消す)。逆は消さない —
長い語を覚えている状態で短く検索し直すのは、それ自体が新しい検索だから。

## 3. 置き場所: localStorage

最近の検索も登録パターンも localStorage に置く。

- 検索のたびに DB へ書くのは重すぎる。最近の検索は端末ごとに違ってよい
  (スマホでは部品番号、PC では調べ物、という差がそのまま出るのが自然)。
- このアプリには localStorage の型が既にある
  ([drawPrefs.ts](../src/lib/draw/drawPrefs.ts) / [memoDraft.ts](../src/lib/memoDraft.ts))。
  読み出しは信用せず検算してから使う、書けなくても機能が死なない、という
  作法もそこに揃っている。

cookie にはしない。並び順 (`sortMode.ts`) や表示モード (`viewMode.ts`) が
cookie なのは**サーバが描画前に読む必要がある**からで、候補はフォーカスして
初めて要る値なので、その理由が無い。

登録パターンだけは端末をまたぎたくなる可能性があるが、それは実際に不便を
感じてから DB へ昇格させる (YAGNI)。移行のとき困らないよう、保存形式は
「クエリ文字列の配列」だけにしておく。

読むのは**ドロップダウンを開くとき**にする (マウント時ではない)。記録は別の
component (`SearchResults`) からも起きるので、開くたびに読み直せば必ず新しい。

### 読めなかったときは書かない

localStorage の読みは信用しない、という作法をそのまま持ってくると
「壊れていたら `[]` として扱う」になるが、**ここでは書き込みが読んだ値への
追加・削除**なので、それだけでは足りない。壊れた値を `[]` と読んで書き戻すと、
利用者が登録したパターンが 1 クリックで全部消える (drawPrefs.ts は色と太さの
まるごと上書きなので、この危険が無かった)。

そこで読み出しを 2 つに分ける:

- `readQueries` … 未保存なら `[]`、**壊れている / 読めないなら `null`**
- `loadQueries` … 表示用。`readQueries(…) ?? []`

書き手 (`recordRecentQuery` と ☆ の処理) は `readQueries` を使い、`null` なら
書かずに諦める。壊れた値を握り潰すのは変わらないが、`console.warn` は残す —
黙って消えると「覚えたつもりが消えている」の原因が追えない。

## 4. 登録: 最近の検索を ☆ で昇格させる

登録の導線は「最近の検索の行に ☆ を置き、押すとパターンになる」だけにする。
検索窓の周りにボタンを増やすと 320px 幅で破綻するし、「登録画面を開いて
検索式を手で打つ」導線は、実際に打った式をそのまま登録できる ☆ より遠い。

パターンの行には ★ を出し、押すと登録を外す。これで管理画面は要らない。

☆ / ★ は `role="option"` の中の `<button tabIndex={-1}>` にする。listbox の
option に対話要素を入れるのは ARIA 的には行儀が悪いが、行そのものは
mousedown で確定できるままで、キーボード操作は listbox のものが生きる。

### 持てる数 = 出す数 (SAVED_LIMIT = SUGGEST_COUNT = 3)

登録の上限を表示数より多くしてはいけない。4 件目を登録すると、それは ★ の欄に
出ないまま保存され、**外す導線が ★ の行にしか無いので二度と消せなくなる**。
☆ を押しても画面は何も変わらないので、利用者から見れば「押しても効かない」。

上限と表示数を揃えれば「★ の欄に居る = 登録済み」が常に成り立つ。最近の検索の
側は登録済みを除いて出す (`splitSuggestions`) ので、🕐 の行の ☆ は必ず未登録を
意味する。満杯のときは ☆ を `disabled` にして、理由を `title` に出す —
黙って何も起きないのが最悪の応答なので。

### 押しても行は並び替えない

☆ を押した行を ★ の欄へ移すと、下の行が 1 つずつ繰り上がる。指が同じ場所を
続けて叩くと**隣の検索語を登録してしまう**。押した後は ★/☆ と 🕐 の表示だけ
差し替え、並べ直すのは次に開いたときにする。

## 5. キーワード補完

[tagComplete.ts](../src/lib/tagComplete.ts) と同じ形の純関数として
`keywordComplete.ts` に切る (DB 非依存・カーソル位置から文脈を求める)。

- 候補は定数配列 `SEARCH_KEYWORDS = ['is:todo', 'is:done']` の前方一致。
  今後フィルタが増えても配列への追記だけで済む。
- `i` の 1 文字から出す。`active === -1` の間は Enter がそのまま検索送信に
  なるので、候補が出ているだけでは入力の邪魔をしない。`is` まで必須にすると
  発見性が落ちる (この機能の目的は「そんな構文があると気づく」ことでもある)。
- 出さない場面: 引用符の内側 (`"is:…"` はリテラル検索)、`#` で始まるトークン
  (タグ補完の担当)、トークンが空のとき、既に候補と完全一致しているとき。
- 語の境界は tagComplete と共通の `isTokenBoundary` で揃える。`!is:todo` や `(is:todo|…)` の
  ように演算子の直後でも補完が効く必要があるため。

置換の実体 (範囲を置き換えてキャレット位置を返す・必要なら空白を足す) は
タグ補完と同じなので `queryComplete.ts` に括り出して両方から使う。
