# 問題集を回すための学習進捗計画

[docs/58-CBT問題集計画.md](58-CBT問題集計画.md) で作った `quiz` フェンスを、
問題集として**繰り返し回せる**ようにする。docs/58 が「1 問を解く」までなら、
こちらは「9 問を最後まで回し、弱いところへ戻ってくる」ための道具立て。

要望は 4 つ:

1. 全問題の学習済み % を見たい
2. 全く分からない問題は、解答せずに解説だけ読みたい
3. 「問 1 の次は問 2」の**次/戻る**が欲しい (ブラウザの履歴とは別物)。
   学習済みの問題は飛ばしたい
4. 学習はしたが自信がない問題を、後から拾い直したい

**どれも専用のテーブル・API を作らない。** 正本はメモ本文という docs/58 §1 の
原則をそのまま守り、既にある道具 (チェックボックス docs/55、`is:todo` 検索
docs/56) の組み合わせで済ませる。

## 1. 自信の度合いは「2 つ目のチェック」で持つ (要望 4)

理解度を 0〜100 の数値で入れる案から始めたが、採らない。

- 自己評価に 100 段階の分解能はない (SRS はどれも 3〜4 段階に落ち着いている)
- 数値で持つと「低い順に並べる」ために検索側へ数値フィールドと並べ替えが要る。
  段階なら**既存の検索がそのまま絞り込みに使える**

そこで、ノートに**チェックを 2 つ**置く。

```markdown
- [ ] 学習済み        ← 解いた / 解説を理解した
- [ ] 自信あり        ← もう間違えないと思える
```

これだけで 3 つの状態が、既存の文法だけで区別できる (**コード変更ゼロ**):

| 状態 | チェック | 検索 |
| --- | --- | --- |
| 未着手 | どちらも空 | `#過渡現象 !is:done` |
| 解いたが自信なし | 学習済みのみ | `#過渡現象 is:todo is:done` |
| 習得済み | 両方 | `#過渡現象 !is:todo` |
| 回す対象 (未着手 + 自信なし) | — | `#過渡現象 is:todo` |

**極性を「達成したら付ける」に揃えるのが要点。** `- [ ] 要復習` のように
「悪いときに付ける」向きにすると、自信のある問題が未チェックのまま残り、
`is:todo` が永久に真になる。単語帳の回転 (docs/56) も要望 3 のスキップも
`is:todo` に乗っているので、この 1 か所で全部が壊れる。

タグ (`#要復習`) で持つ案も採らない。iPhone で毎回打つのが重く、
チェックなら**閲覧画面でそのまま押せる** (docs/55)。

## 2. 進捗率の表示 (要望 1)

検索結果の件数行に、**チェック状態で絞り込んでいるときだけ**進捗を足す。

```text
「#過渡現象 is:todo」の検索結果: 6 件
チェック完了 3 / 9 (33%)   [====------]
```

- **分母** … 同じ検索から `is:todo` / `is:done` を取り除き、
  「チェックを 1 つ以上持つ」で絞った件数 (= 進捗管理の対象)。
  チェックの無いノートを分母に入れると、混ざった瞬間に率が嘘になる。
- **分子** … そのうち**全部チェックしたノート** (`task_todo = 0`)。
  「一部だけ付いた」を済みに数えないので、§1 の 3 状態と食い違わない。

問題集専用ではなく、単語帳など「タグで括った集合」すべてに効く。

### 検索式からチェック語を取り除く (search.ts)

分母は「今の検索からチェックの条件だけ外したもの」なので、AST から task の葉を
落とす純関数 `stripTaskTerms` を置く。葉が消えて空になったノードは
`combine` が畳み、`!` の被演算子が消えたら否定ごと落とす (`capTerms` と同じ作法)。
何も残らなければ null = 絞り込みなし。

これを分母・分子それぞれの条件と AND する。SQL は `buildWhereFrom` に条件を
1 つ足すだけで、既存の WHERE 組み立てをなぞる。

### 出さない場面

- チェック語を含まない検索 (`#過渡現象` だけ) では出さない。
  常時出すと、チェックを使っていないノート群にも 0% が並ぶ
- 分母が 0 のときも出さない (0/0 に意味がない)

## 3. 解答せずに解説を読む (要望 2)

`QuizCard` の状態を 2 値 (未解答 / 解答済み) から 3 値にする。

```ts
type QuizState =
  | { kind: 'unanswered' }
  | { kind: 'answered'; choice: number }
  | { kind: 'revealed' }   // 降参して解説を開いた
```

- 選択肢の下に「解説を見る」を置く。**未解答のときだけ**出す
- 押すと正解と解説が開き、選択肢は押せなくなる。正解には ○ を付け、
  × は付けない (選んでいないので不正解の選択肢が存在しない)
- 知らせの文面は「正解は (3)」。○/× の判定は出さない
- 「やり直す」で未解答へ戻すのは今までどおり

**CBT らしさ (解答前は隠す) は壊れない。** 隠す目的は「うっかり目に入らない」
ことで、意図して押した 1 つのボタンはそれに当たらない。ただし選択肢と
見た目を分ける (選択肢は枠付きボタン、こちらは控えめな文字リンク調) —
並べて置くと 6 番目の選択肢に見える。

保存しないのも今までどおり (docs/58 §3)。

## 4. 一覧の中を「次/戻る」で移る (要望 3)

### 独立した順序は作らない

「問 1 の次は問 2」を本文のリンクや専用の順序テーブルで持つ案は採らない。
学習済みをスキップする要件が満たせないうえ、問題を足すたびに書き換えが要る。

**「いま見ている検索結果の中を移動する」と捉える。** README の運用が既に
`#過渡現象 is:todo` を開いて回す形なので、スキップは `is:todo` が
やってくれる — 専用のロジックが要らない。

### 検索状態をノートの URL に載せる

一覧からノートを開くとき、検索語と並び順を URL に持たせる。

```text
/item/42?q=%23過渡現象+is%3Atodo&sort=itemNo
```

- 組み立ては `searchUrl.ts` の `buildItemUrl`。`buildSearchUrl` と同じく
  既定値 (空クエリ / `sort=updated`) は省いて短く保つ
- `q` があるときだけ前後ナビを出す。QR シールから直接開いたノート
  (文脈が無い) には出さない
- 並び順を URL にも載せるのは、検索ページと同じ `resolveSort`
  (URL → cookie → 既定) をノート側でも通すため。cookie だけを見ると、
  `?sort=` 付きの共有リンクから入ったときに一覧と順序が食い違う

### 前後の求め方 (items.ts)

**押した時点で毎回クエリを評価し直す**のが要点。開いている間にチェックを
付けたら、`is:todo` の一覧からそのノートは消えている — それでも「次」は
正しく次のノートを指さなければならない。

そこで、検索条件に**今のノート自身を OR で足してから**並べる。

```sql
WITH ordered AS (
  SELECT item_no,
         lag(item_no)  OVER (ORDER BY <並び順>) AS prev,
         lead(item_no) OVER (ORDER BY <並び順>) AS next
  FROM items
  WHERE (deleted_at IS NULL) AND ((検索条件) OR item_no = <現在>)
)
SELECT prev, next FROM ordered WHERE item_no = <現在>
```

- 一覧に残っているときは、OR を足しても結果は変わらない
- 一覧から外れたときは、**その並び順での本来の位置に差し込まれる**ので
  前後が求まる
- 返るのは 1 行だけ。全件を JS へ持ち出して添字を探す必要がない
- 並び順は `orderByClause` (sortOrder.ts) をそのまま使う。あれは自前の定数しか
  返さないので `Prisma.raw` に通してよい (buildOrderBy と同じ理由)

ノートが未登録 (QR シールだけ貼った番号) でも動く。`item_no = <現在>` に
一致する行が無いので前後とも null になり、ナビは出ない。

### 承知しておく限界: 並び順のキーが動くと位置も動く

上の工夫が吸収するのは**集合から外れること**だけで、**並び順のキーそのものが
変わること**は吸収できない。

- **更新順 (既定)** — チェックを押すと `toggleMemoTaskAction` が `upsertMemo` を
  通り、Prisma の `@updatedAt` が `updated_at` を進める。そのノートは一覧の
  先頭へ移るので、同じ応答の `revalidatePath` で描き直した前後ナビは
  **先頭に居る前提の前後** (「前」が無くなる) になる。
- **アクセス順** — 開くだけで `accessed_at` が進む (RecordAccess)。通り過ぎた
  ノートが先頭へ移るので、「前」を押すと 1 つ手前ではなく最初に開いた
  ノートへ飛ぶ。

これはナビの不具合というより**一覧そのものが読んでいる最中に並び替わる**ことの
影響で、ナビは一覧に正直に従っている。

**順番に回す用途では番号順 (`sort=itemNo`) を使う。** `item_no_num` は
何をしても動かないので、チェックを付けても前後は狂わない。問題集のように
「問 1 → 問 2 → …」と辿るものは番号順が本来の並びでもある。

`toggleMemoTaskAction` が `updated_at` を進めないようにする手もある
(`trashItems` / `setItemPublic` が生 SQL で `@updatedAt` を避けているのと同じ
作法)。ただしチェックは本文の変更でもあるので、更新順の意味を変える判断は
この計画では行わない。

### 見た目

本文の下 (タイムスタンプの下) に「← 前」「次 →」。問題を解き終えて
下まで読んだところに次があるのが自然な流れ。行き先が無い側は
**押せないまま場所だけ取る** — 端に着くたびにボタンが動くと押し間違える。

リンク先にも同じ `q` / `sort` を載せる (連鎖して回れるように)。

## 5. 実装ステップ (TDD)

1. `search.ts` の `stripTaskTerms` / `queryHasTaskTerm` — 純関数。
   task 語だけの検索・AND/OR/NOT の中の task 語・引用リテラル (`"is:todo"` は
   残る) をテスト。
2. `searchUrl.ts` の `buildItemUrl` — 既定値の省略・エンコードをテスト。
3. `items.ts` の `countTaskProgress` / `findListNeighbors` — DB 統合テスト
   (`RUN_DB_TESTS=1` のときだけ走る既存の枠に足す)。
4. `QuizCard` の 3 値化 — 純関数 `choiceClassOf` / `markOf` に state を渡す形へ。
   SSR で見えるのは初期表示までなので、テストは「降参ボタンが出る」
   「正解と解説は出ていない」に絞る (docs/58 の「テストの届く範囲」と同じ)。
5. 一覧 → ノートのリンクに検索状態を載せる (`ItemList` → `ItemRow` /
   `ImageMasonry`)。
6. `/item` に前後ナビ。
7. ドキュメント (検索ヘルプ・メモ記法) と実機確認。

## 6. 今回やらないこと

- **理解度の数値 (0〜100) とその並べ替え** — §1 のとおり 2 段階で始める。
  足りなくなってから考える。
- **ノートを跨いだ成績集計 (9 問中 N 問正解)** — docs/58 §6 のまま。
  quiz の解答は保存しないので、集計するなら保存方式から決め直しになる。
- **編集からノートへ戻ったときの文脈の維持** — `/edit` を経由すると `q` が
  落ちて前後ナビが消える。編集は回転から外れる寄り道なので許容する。
- **共有 URL から検索語を落とす** — 一覧から開くとアドレスバーは
  `/item/42?q=%23健康+is%3Atodo` になる。公開ノート (docs/22) の URL を
  ここからコピーして渡すと、相手に自分の検索語が渡る。`history.replaceState`
  で消す手はあるが、消した URL でチェックを押すと `revalidatePath` の
  描き直しで**前後ナビ自体が消える**ので採らない。公開ノートを人に渡すときは
  `/item/<番号>` だけを送る、で運用する。
- **前後ナビのキーボードショートカット (← →)** — 主な使い場所が iPhone。
