# 51. 部分暗号化計画 (シークレット断片)

ノートの機微部分 (住所・パスワードなど) だけをクライアント側で暗号化して
保存し、サーバ管理者にも読めなくする。本文・タグは平文のまま残すので、
全文検索 (docs/04)・タグ検索 (docs/06) は今まで通り動く。

処理フローは挿入画像と同型: 断片を別レコードに保存し、本文には参照だけを
書く。表示時にクライアントが取得して復号する (画像をクライアントで
表示するのと同じ流れ)。

## 1. 目的と脅威モデル

**守る**: vps2 の root・DB・pg_dump を「受動的に覗く」相手から、
シークレット断片の中身を守る。バックアップが漏れても断片は読めない。

**守らない** (方式上の割り切り):

| 守らないもの | 理由 |
| --- | --- |
| メタデータ (件数・日時・サイズ) | 暗号化しても行の存在は見える |
| 断片の前後の文脈ラベル | 「〇〇銀行 パスワード: 🔒」の平文部分は見える。検索性との交換条件 |
| 能動的な攻撃者 | 管理者が改竄 JS を配信すれば鍵は抜ける。Web 配信型 E2EE の宿命 |

「ラベルごと隠したいノート」はこの方式の対象外。必要になったら本文全部を
1 断片に入れればノート単位暗号化 (D 案) として使える — この計画は D 案を
特殊ケースとして内包する。

## 2. なぜノート単位でなく断片単位か

ノート単位で暗号化すると、memo 平文から作る派生キャッシュ
(tags / props / thumb / embedding / CircuitSvg) を全部塞ぐ必要があり、
検索もクライアントに移すことになる。断片単位なら検索面 (memo 本文と
tags 列) が平文に残るため、**既存の検索・一覧・タグ集計に手を入れない**。
派生キャッシュ対策は「断片に入れたものだけ」に局所化される (§5)。

## 3. 記法 — 画像記法に相乗りする

```text
![ラベル](/api/secrets/<UUID>)
```

当初は独自記法 (`!secret[…](…)`) を予定したが、**画像記法に相乗りする形へ
変更した** (実装時の判断)。このアプリは音声・動画・PDF・テキストも既に
画像記法で本文へ入れており、[MarkdownView.tsx](../src/components/MarkdownView.tsx)
の `imgRenderer` が src を見て描き分けている。同じ仕組みに乗せれば、
パーサ・サニタイズ・GC・本文置換のどれにも新しい経路が要らない。

自動リンク化の心配も無い — `![…](…)` は画像記法であってリンクではないため、
独自記法にする動機だった「押すと暗号文が開く」は起こらない。

- ラベル (alt) は平文で本文に残る (検索に掛かる)。URL の UUID が Secret 行の主キー。
- 断片がインライン (パスワード 1 行) でもブロック (markdown 数段落 + 画像)
  でも記法は 1 種類。復号後の mime を見て表示側が描き分ける。
- 保存名は**拡張子を持たない**ので、画像・音声の名前判定
  (`isValidImageName` 等) とは決して取り違えない = 一覧サムネ・画像検索・
  OCR の対象に紛れ込まない。
- 正本は [secrets.ts](../src/lib/secrets.ts)。[メモ記法.md](./メモ記法.md)
  にも追記した。

## 4. データモデル

実装は [schema.prisma](../prisma/schema.prisma) の `Secret` / `SecretKeyring` と
`WebAuthnCredential.secretKeyWrap`。

```prisma
model Secret {
  name      String   @id            // UUID (拡張子なし)
  mime      String                  // 復号後の種別。暗号化しないメタデータ
  data      Bytes                   // 暗号エンベロープ (§7)
  createdAt DateTime @default(now())
}
```

- **Image テーブルには入れない**。`saveImage()`
  ([imageStore.ts](../src/lib/imageStore.ts)) を通すと thumb / embedding が
  自動生成される — 平文由来の派生物がサーバに残ったら台無しになる。
  フラグで分岐するより、テーブルごと分けてパイプラインを構造的に分離する
  方が塞ぎ忘れが起きない。
- 断片内の画像は、暗号化した画像バイト列を別の Secret 行として保存し、
  断片本文 (markdown) から `/api/secrets/<UUID>` で参照する。入れ子は
  この 1 段だけ。
- `mime` は暗号化しない。管理者には「これは画像だ」までは見える (§1 の
  メタデータの割り切り)。表示側が描き分けに使う。
- **名前を決めるのはクライアント**。画像 (サーバが UUID を振る) とは逆だが、
  エンベロープの AAD が名前に縛られる以上、封をする時点で名前が要る (§7)。
  トラバーサル対策は書式検算 (`isValidSecretName`) が担う。
- DB に置くので pg_dump 一発の設計 (schema.prisma の Image の思想) は
  そのまま。暗号文ごとバックアップに乗る。

## 5. 派生キャッシュの禁止事項

断片の中身から作られるものは、一切サーバに送らない・置かない。

| 派生物 | 通常ノート | 断片内 |
| --- | --- | --- |
| tags / props | memo 平文から抽出 (今のまま) | ラベルのみ対象。中身は対象外 |
| サムネ / embedding | saveImage() が自動生成 | 作らない (§4 の分離で構造的に不可能) |
| CircuitSvg キャッシュ | circuit_svgs に保存 | **送らない**。ローカルにだけキャッシュ |

CircuitSvg は [circuitCache.ts](../src/lib/circuitCache.ts) への保存を
断片描画パスでは呼ばない。描画結果 (SVG) は平文そのものだから。

## 6. 鍵管理

### PRF とは

WebAuthn の PRF (Pseudo-Random Function) 拡張。認証器 (Secure Enclave /
iCloud キーチェーン) がクレデンシャルごとに内部秘密を持ち、渡した入力
(salt) に対して 32 バイトの決定的な出力を返す。CTAP2 の hmac-secret が
土台。同じパスキー + 同じ salt なら常に同じ出力、秘密は端末から出ない。
出力はクライアント JS だけが受け取り、サーバには渡らない。つまり
**Face ID から暗号鍵を導出できる** — パスフレーズを覚えずに済む。

### 構成

PRF 出力は**クレデンシャルごとに違う** (端末ごとではない)。iCloud
キーチェーンで同期されたパスキーは iPhone / iPad / Mac で**同一の
クレデンシャル**なので、どの端末でも同じ PRF 出力が得られる。別の値に
なるのは別クレデンシャルのとき — 例: 別のパスキーを登録し直した、
保存先プロバイダが違う (1Password など)、ハードウェアキー。

そのため断片を PRF 出力で直接暗号化はできない (クレデンシャルを足す・
失うたびに読めなくなる)。ランダムなマスターキー (MK) を 1 つ立て、
各パスキーの鍵でラップして持つ:

```text
パスキー (PRF, salt="qr-search-secret-v1")
  → 32B 出力 → HKDF → KEK (クレデンシャルごと)
  → KEK で MK をラップ
  → wrapped MK をサーバに保存
断片: AES-256-GCM(MK) で暗号化
```

- wrapped MK は `webauthn_credentials` に nullable 列で持つ
  ([schema.prisma](../prisma/schema.prisma))。サーバにあるのはラップ済み
  だけで、MK 平文はクライアントのメモリにしか存在しない。
- 新しいパスキーを追加するときは、解錠済みの端末 (または復旧キー) で
  MK を得て、新クレデンシャルの KEK でラップし直して登録する。
- **復旧キー = MK そのものを base32 で紙に印字** (52 文字程度)。全端末の
  パスキーを失っても断片を取り戻せる。これを作らずに運用開始しない —
  MK を失うと全断片が永久に読めない。
- 解錠状態はタブのメモリ (module state) に持つ。再読込したら Face ID で
  解錠し直す。面倒なら non-extractable CryptoKey を IndexedDB に置く
  緩和もあるが、初版はメモリのみ (KISS)。
- **退避路**: PRF 非対応環境が出たら、パスフレーズ → Argon2id → KEK の
  ラップ行を 1 つ足すだけで共存できる (MK 構成の利点)。着手前に手持ちの
  iPhone Safari で PRF が動くことをテストページで確認する (iOS 18+ で
  対応だが、パスキーの保存先プロバイダで挙動差がある)。

### 環境ごとの解錠経路

| 環境 | 経路 | 備考 |
| --- | --- | --- |
| iPhone / iPad / Mac | iCloud 同期パスキー | 同一クレデンシャル |
| Win / Linux (Chrome 系) | QR (hybrid) で iPhone に委譲 | PRF 通過は**要確認** |
| Windows 常用時 | 別パスキー登録 + MK 再ラップ | 下記の注を参照 |
| どれも駄目なとき | 復旧キーの直接入力 | 常設の最終手段 |

注: Windows Hello の PRF 対応は OS 世代差がある。確実なのは
1Password / Google パスワードマネージャ / YubiKey (hmac-secret)。
別パスキーの追加登録は、解錠済み端末か復旧キーで MK を得てから
その場でラップし直す (§6 構成の通り)。

## 7. 暗号仕様

- WebCrypto AES-256-GCM。エンベロープは `version(1B) || iv(12B) || 暗号文`。
  iv は毎回ランダム。
- **AAD に断片の name と mime を入れる** (`secretContext()`)。GCM は中身の
  改竄は検知するが、管理者がブロブ A と B を丸ごと入れ替えるのは検知できない
  (「銀行のパスワード」欄に別の値が出る)。AAD で縛れば、すり替えは復号失敗に
  なる。**mime も縛るのが要点** — mime は暗号化しないメタデータなので、
  `data` はそのままに mime だけを書き換えると、画像の生バイト列が
  「復号に成功した markdown」として描画側へ渡ってしまう。同じすり替えの
  一種なので、名前と同じ扱いにする (secretContent.test.ts が回帰を守る)。
- 断片ごとの DEK は**立てない**。MK で直接暗号化する (KISS)。ブロブは
  小さく件数も少ないので、MK ローテーションは全断片の再暗号化で足りる。
  DEK ラップ層を挟んでもローテーションの手間はほぼ同じで、複雑さだけ増える。

## 8. 保存フロー — 平文は memo を経由しない (最重要)

「本文に平文で書いてから選択して暗号化」は採らない。暗号化前に自動保存が
走った時点で平文がサーバに届き、**一度でも pg_dump に乗ると過去の
バックアップに平文が残り続ける**。

1. エディタのツールバーの「秘密」(南京錠) でダイアログを開く
   ([EditToolbar.tsx](../src/components/EditToolbar.tsx))。
2. ダイアログ内で入力 (markdown / 画像添付)。この内容は memo の state に
   一切触れない ([SecretDialog.tsx](../src/components/secret/SecretDialog.tsx))。
3. クライアントで暗号化 → `PUT /api/secrets/<UUID>` → 本文には
   `![ラベル](/api/secrets/<UUID>)` だけを挿入。
4. 既存ノートの平文を後から断片化した場合、**移行前のバックアップには
   平文が残る**ことを承知しておく (気にするなら古いダンプの整理まで含めて
   移行)。

断片に貼る画像は**クライアントで canvas に描き直してから**暗号化する
([secretImage.ts](../src/lib/secretImage.ts))。サーバが復号できない以上
sharp の変換 (docs/26) に頼れないため。副産物として EXIF (撮影場所・日時) も
落ちる。長辺は 2048px に収める。

画像だけでなく**録音・録画・お絵かき・OCR・スキャンもダイアログから使える**
(docs/53-シークレット挿入拡張計画.md)。どれもバイト列はブラウザで作られ、
暗号化してから断片として保存される。スキャンだけは読み取った文字を入れる
だけで、書誌・商品情報の取得はしない (コードを外部へ送ることになるため)。

## 9. 表示・編集フロー

- 未解錠: 「🔒 ラベル」のプレースホルダ。押すまで**暗号文すら取りに行かない**
  (肩越しの覗き見対策であり、鍵が無いときに認証器を何度も呼ばないため)。
  実装は [SecretBlock.tsx](../src/components/secret/SecretBlock.tsx)。
- 押すと (必要なら Face ID で解錠して) 取得・復号して展開。中身が
  markdown なら通常 memo と**同じ描画パイプライン** (同じサニタイズ) を通す。
  断片内の画像参照は復号して Blob URL に差し替える。
- 「隠す」で畳み、Blob URL も解放する。施錠 (設定画面) でも同じ後始末が走る。
- パスワード用途向けに「コピー」ボタン (肩越し対策)。**60 秒でクリップボードを
  消す** — クリップボードは OS の履歴機能 (Windows のクラウド同期履歴、Apple の
  Universal Clipboard、拡張機能) を通じてアプリの外へ出ていくため。
- 入力欄は `spellCheck={false}` + Grammarly 除外の印を必ず付ける。ブラウザの
  拡張スペルチェックは**打った文字をそのまま自社サーバへ送る** — サーバ管理者に
  読ませないための機能が、自分のブラウザから第三者へ漏らしては元も子もない。
- 編集は**エディタ側**で行う。カーソルがシークレット記法の上にある状態で
  「秘密」を押すとその断片が開き、保存で**同名上書き**する
  (`secretAtCursor` / `findSecretNotation`)。画像 (docs/49 §1) と逆の選択なのは
  意図的: 配信を `no-store` にするので immutable キャッシュ問題がなく、
  同名なら本文のトークンが不変で CodeMirror の undo 履歴と干渉しない。

## 10. API と認可

実装は [src/app/api/secrets](../src/app/api/secrets)。門番は 3 つ共通で
`denySecretRequest` (デモ拒否 → ログイン → クロスサイト拒否)。

- `GET /api/secrets/[name]` — **ログイン必須**。公開ノート (publicAt) に
  参照が書かれていても、未ログイン閲覧者には暗号文すら配らない。
  `Cache-Control: no-store` + `X-Content-Type-Options: nosniff`。
  復号後の種別は `X-Secret-Mime` で返す (本文は octet-stream)。
- `PUT /api/secrets/[name]` — 新規も編集も同じ口 (upsert)。名前は UUID の
  書式だけを受ける。CSRF と大きさは画像と同じ `checkUploadRequest` を通す。
  **base64 にせず生のバイト列で運ぶ** (数 MB を 33% 太らせない)。
- `GET/POST/PUT /api/secrets/keyring` — 鍵束の状態取得・初回設定・包みの追加。
  流れるのは**包んだ鍵と検証値だけ**で、マスターキーの平文は現れない。
  POST は既に設定済みなら 409 (検証値の上書きは既存断片を読めなくする)。
- デモモードでは機能ごと出さない (鍵をデモ利用者間で共有できないため)。
  設定画面も `notFound()` に倒す。

## 11. GC (未実装)

本文から参照が消えた Secret 行の回収は、画像 GC
([20-画像GC計画.md](./20-画像GC計画.md)、未実装の sweep) と同じ方針に
乗せる。参照の抽出規則は `allSecretNames()` が正本。SQL で探すときは
`position()` を使う — LIKE は PGroonga に乗っ取られる (docs/49 §3 と同じ注意)。
GC を実装するまで孤児は残るが、暗号文なので残っても漏洩にはならない。

## 12. 既存平文の断片化 (移行)

コピペではなく、エディタの選択範囲から変換する。

1. CodeMirror で範囲選択 → ツールバーの「秘密」。
2. ダイアログが選択内容を引き継いで開く (ラベルを付ける)。
3. クライアントで暗号化 → 選択範囲が記法に置き換わる。

§8 の「平文は memo を経由しない」は**新規作成の話**。既存平文はもう
サーバとバックアップにあるので、この経路で新たな漏れは増えない。

**平文の痕跡の掃除は初版では自動化していない** (承知のうえの割り切り):

- **画像を含む範囲**: 選択範囲に `/api/images/` の参照があると、ダイアログが
  「通常の画像はサーバに平文のまま残る」と警告する。隠したい画像は
  ダイアログの「画像を追加」で貼り直し、本文側の旧参照は手で消す。
  旧 Image 行の自動削除 (thumb / embedding ごと消す) は今後の課題。
- **circuitikz を含む範囲**: `circuit_svgs` に平文由来の SVG が残る。断片の
  中の circuitikz は初版では描画せずコードブロックのまま出すので、**新しく
  キャッシュが作られることはない** (残るのは移行前に描いた分だけ)。
- それでも**移行前の pg_dump には平文が残る** (§8)。気にするなら古い
  ダンプの整理までを移行作業に含める。

## 14. 承知しておく制約

- 断片の中身は全文検索に一切掛からない。ラベルの付け方が検索性のすべて。
  後から中身も探したくなったら、件数が少ない前提でクライアント復号総なめを
  足す (別計画)。
- 断片内の画像は画像検索 (docs/25) の対象外。サムネもないので一覧の
  画像モードにも出ない。
- 過去のバックアップに移行前の平文が残る (§8)。
- 能動的な改竄 JS には無力 (§1)。受動的な覗き見までを守る道具と割り切る。
- MK と復旧キーを両方失うと全断片が永久に読めない。復旧キーの印字を
  運用開始の前提条件にする。
- 解錠はタブのメモリだけに残る。**再読込のたびに Face ID が要る**
  (localStorage に置けば楽になるが、置いた時点で「端末を開けば読める」に
  落ちるので採らない)。
- 断片は ENEX エクスポート (docs/28) では暗号文のままになる。持ち出すときは
  先に復号して貼り直すこと。
- 印刷 (`/print`) やノートの共有では断片は開かれない (プレースホルダのまま)。
- **復号した本文は mermaid と同じレンダラを通る**。`MermaidDiagram` は
  `dangerouslySetInnerHTML` を使っており (mermaid の `securityLevel: "strict"`
  頼み)、そこにサニタイズ回避の不具合が出た場合、被害が「ノートの改竄」から
  「解錠中のマスターキーの窃取」まで広がる。§1 の「能動的な改竄には無力」の
  範囲内だが、この機能の追加で影響が一段重くなったことは意識しておく。
