# サーバクリップボード計画

Windows と iPhone の間で、OS のクリップボードの中身 (文字・画像) を QR-Note の
サーバを経由して受け渡す。ハンバーガーメニューに「サーバへコピー」と
「サーバからペースト」の 2 行を足す。

想定する使い方は次の 1 往復。

1. Windows の他のアプリで文字 (または画像) をコピーする
2. Windows の QR-Note → メニュー →「サーバへコピー」
3. iPhone の QR-Note → メニュー →「サーバからペースト」
4. iPhone の他のアプリに貼り付ける

逆方向 (iPhone → Windows) も同じ 2 行で動く。

## 0. なぜ

- iPhone と Windows にはクリップボード共有の純正手段がない (docs/92 §0)
- docs/92 (クリップボード連携) で**ノートを箱にする**経路は本番で動いている
  (v0.23.5)。拡大表示の「コピー」と編集画面の「貼り付け」の 2 つで、画像の往復は
  iPhone 実機で確認済み
- 足りないのは**手数とノートの汚れ**。受け渡しのたびにノートを開いて更新し、
  受け取ったら消す。文字 1 行を渡すのに添付やノートの履歴 (git) が増える
- そこでノートを介さず、**利用者ごとに 1 枠 (スロット) をサーバに持つ**。
  同期も通知も要らない。受け取る側がメニューを開いたときに取りに行けば足りる

## 1. 決めたこと

### 1-1. 1 枠・上書き・期限つき

- 利用者 (userName) ごとに**1 行**。送るたびに上書きする。履歴は持たない
  (vps2 のメモリ事情。1 枠・上書きなら表が育たない)
- 中身は**文字か画像のどちらか 1 つ**。両方は載せない (OS のクリップボードが
  画像に出所の URL を text/plain で添えることがあるが、docs/92 と同じく画像を
  優先して文字は捨てる)
- **10 分で期限切れ** (`CLIPBOARD_TTL_MS`)。クリップボードにはパスワードが乗る
  ことがあるので、サーバに残り続けさせない。読む口が期限切れを「無い」と答え、
  そのとき行を消す (lazy)。常駐の掃除役は置かない
- 手で消す口 (DELETE) も置く。メニューの行に小さく「消す」を出す

### 1-2. 文字も画像も 1 つの表 `clipboard_slots` に置く

当初の助言では「文字は user_settings、画像は専用表」としたが、**1 つの表にまとめる**。

- user_settings の `readUserSetting` は value だけを返し `updatedAt` を出さない。
  期限の判定に `updatedAt` が要るので、文字のためだけに読み口を増やすことになる
- 文字と画像で置き場が分かれると、メニューの行は「どちらに何があるか」を 2 回
  聞くことになる
- 1 行 1 利用者の表なら、文字用の列と画像用の列を同じ行に持てて、読む口は 1 つで済む

```prisma
// サーバ経由のクリップボード (docs/114)。利用者ごとに 1 行、上書きのみ。
// 文字 (text) か画像 (mime + data) のどちらか一方だけが入る。両方 null はない
// (無いときは行ごと消す)。期限の判定は読む側 (clipboard/slot.ts の isSlotExpired)
model ClipboardSlot {
  userName  String   @id @map("user_name")
  text      String?
  mime      String?
  data      Bytes?
  updatedAt DateTime @updatedAt @map("updated_at")

  @@map("clipboard_slots")
}
```

### 1-3. 上限

| 何 | 上限 | 定数 |
| --- | --- | --- |
| 文字 | 64KB | `MAX_CLIPBOARD_TEXT_BYTES` (新) |
| 画像 | 10MB | `MAX_IMAGE_BYTES` (添付と同じ) |

- 文字: クリップボードの文字は数 KB が普通。JSON 本文で受けるので小さく保つ
- 画像: 添付と同じ門 (Content-Length の事前検査 `checkUploadRequest`) を通す

画像は**送る側で上限を超えていれば縮める** (docs/92 §4 の `shrinkImageFile`、長辺
2048 の JPEG)。iOS で写真をコピーすると PNG で 20〜30MB になるため。上限以下なら
触らない。

### 1-4. デモでは出さない・断る

デモは共有アカウントなので、1 枠が利用者全員で共有される。メニューの行を出さない
だけでなく、API も `guardRequest(request, { demo: 'deny' })` で塞ぐ (photo-meta と同じ)。

### 1-5. 撮影情報 (EXIF) は追わない

OS のクリップボードから `clipboard.read()` で取れる画像は、ブラウザが再エンコード
した PNG で EXIF を持たない (docs/92 §8)。受け取る側も canvas で PNG に描き直して
から OS に載せる。サーバに置かれる 10 分間だけを守る理由はない。

### 1-6. シークレットの中身を送れる口になる

docs/92 の「コピー」は `blob:` (復号したシークレット断片) を弾いている。こちらの
入口は **OS のクリップボード**なので、利用者が長押しでコピーした復号済みの画像を
「サーバへコピー」すれば、平文が 10 分だけサーバの DB に置かれる。

これは**利用者が自分で選んだ操作**なので止めない。緩和は 1-1 の期限と「消す」。
メニューの行の説明文に「10 分で消えます」と書いて、残らないことを伝える。

## 2. API

すべて `guardRequest(request, { demo: 'deny' })` を通す (デモ → 未ログイン →
クロスサイトの順)。応答は `apiOk` / `apiFail` の封筒。

| メソッド | パス | 本文 | 応答 |
| --- | --- | --- | --- |
| GET | `/api/clipboard` | なし | `{ slot }` (メタ。無ければ null) |
| PUT | `/api/clipboard` | JSON `{ text }` | `{ slot }` (保存後のメタ) |
| DELETE | `/api/clipboard` | なし | `{ slot: null }` |
| GET | `/api/clipboard/data` | なし | 画像の生バイト |
| PUT | `/api/clipboard/data` | 画像の生バイト | `{ slot }` |

メタの形は `{ kind: 'text' | 'image', bytes, updatedAt, text? }`。文字は
64KB 以下なので本文ごとメタに同梱する (受け取る側が押した瞬間に同期で
`writeText` できる。§3-3)。

`/api/clipboard/data` の GET は `Content-Type` に保存した mime、
`Cache-Control: no-store` を付ける。無い・期限切れ・文字のときは 404。
PUT は `Content-Type: image/*` の生バイトを受ける。

- GET は期限切れなら行を消して `slot: null`。期限の判定は `isSlotExpired(updatedAt, now)`
  の 1 か所 (純粋関数)
- PUT (文字) は `parseJsonBody` で `text` が文字列か・空でないか・64KB 以下かを見る。
  **知らない形は畳まず 400** (photo-meta と同じ理由)
- PUT (画像) は `checkUploadRequest` で Content-Length を先に見てから本文を読み、
  `sniffImageFormat` で中身が png / jpg / webp / gif のいずれかであることを確かめる。
  申告の Content-Type は信じない (保存する mime は中身から決める)。それ以外は 400
- 書き込みは `upsert`。文字を入れるときは `mime` と `data` を null にし、画像を入れる
  ときは `text` を null にする (1-1 の「どちらか 1 つ」を表の形ではなく store で守る)
- `responseContracts.test.ts` に 5 本の口を登録する (封筒の形の検査)

## 3. 画面

### 3-1. 置き場所

ハンバーガーメニュー (`AppHeaderMenu`)。ログイン中かつ非デモの先頭、
`RowTintMenuItem` の**前**に 2 行で置く。設定ではなく操作なので、設定の行
(選択色・撮影情報) より上。

```text
┌─────────────────────────────┐
│ ⇧ サーバへコピー                │ ← OS のクリップボード → サーバ
│ ⇩ サーバからペースト  文字 120 字 │ ← サーバ → OS のクリップボード
│    ・3 分前 ・消す               │
│   10 分で消えます。送るときは    │
│   クリップボードの読み取りを     │
│   許可してください               │
└─────────────────────────────┘
```

- 名前は利用者の言葉 (コピー・ペースト) を残し、方向を「サーバへ / サーバから」で
  補う。OS のコピー・貼り付けと取り違えないため
- 2 行目の右に**いま何があるか**を出す: 「文字 120 字」「画像 1.2MB」「なし」と
  「3 分前」。押す前に何が来るか分かる。中身が無いときはペーストの行を disabled
- メニューは開いている間だけ中身を描く (`HeaderMenu`)。開くたびに GET で読み直す
  ので、layout には何も足さない (photo-meta の `savedInThisTab` のような控えも
  要らない)

### 3-2. 「サーバへコピー」の流れ

```text
click (同期部)
  ├ navigator.clipboard.read() を呼ぶ  ← await を先に置かない (iOS が NotAllowedError)
  └ busy を立てる
await 以降
  ├ pickClipboardEntry(items)         ← docs/92 の選別 (画像優先 → text/plain)
  ├ null → 「クリップボードに画像も文字もありません」
  ├ 文字 → PUT /api/clipboard { text }
  └ 画像 → 10MB 超なら shrinkImageFile → PUT /api/clipboard/data (生バイト)
終わったら
  ├ 行に「送りました (文字 120 字)」を一時表示し、ペースト行のメタを更新
  └ 失敗は clipboardReadErrorMessage で言い換えて赤字
```

- `clipboard.read` が無い環境 (Firefox・secure context 外) は押した時点で
  「この環境ではクリップボードを読めません」。行は出しておく (後から生えると
  メニューが跳ねる。useEditorClipboard と同じ判断)
- iOS は read() で「ペースト」の吹き出しを出す。そのタップが許可になる。
  吹き出しを閉じると NotAllowedError で、言い換えの文が出る
- Windows の Chrome は初回だけ許可ダイアログ

### 3-3. 「サーバからペースト」の流れ

```text
click (同期部)
  ├ 文字: navigator.clipboard.writeText(meta.text)
  └ 画像: copyImageToClipboard('/api/clipboard/data')
          ← docs/92 の関数そのまま。同期部で ClipboardItem (Promise 入り) を作り
             write を呼び、中で fetch → PNG に描き直す。Cookie は同一オリジンで付く
終わったら
  ├ 「コピーしました」を一時表示 (CodeBlock のコピーボタンと同じ作法)
  └ 失敗は赤字
```

- 文字はメニューを開いたときの GET で**本文ごと**手元にある。押した瞬間に
  同期で `writeText` できるので、iOS でも許可の問題が出ない
- 画像は `copyImageToClipboard` が PNG 以外を描き直す。Chrome の `write` は
  `image/png` しか受けない (docs/92 §8)
- 受け取っても**自動では消さない**。PC と iPhone の両方で受け取りたいことがある。
  消すのは期限か「消す」

### 3-4. 「消す」

ペースト行の末尾に小さく。DELETE を呼び、メタを「なし」に戻す。

1. Windows で文字をコピー → サーバへコピー → iPhone でサーバからペースト → メモ

2. iPhone で文字をコピー → 逆方向
3. iPhone 写真アプリで写真をコピー (PNG 20MB 超) → 縮んで入る → Windows で X の
   投稿欄に貼れる
4. Windows で画像をコピー → iPhone で LINE などに貼れる
5. 10 分放置 → ペースト行が「なし」になり disabled
6. 「消す」→ 即「なし」
7. iOS で「ペースト」の吹き出しを閉じる → 「読み取りが許可されませんでした」
8. デモで メニューに行が無く、`/api/clipboard` が 403
9. 送信中に二度押ししても 1 回しか送られない (busy)

## 7. 落とし穴 (先に分かっていること)

- **`clipboard.read()` と `write()` は click の同期部で呼ぶ。** 先に await を挟むと
  iOS が NotAllowedError (docs/92 §8、shareFile.ts の transient activation)
- **Chrome の `write()` は `image/png` だけ。** `copyImageToClipboard` が描き直す
- **iOS の写真は PNG で 20〜30MB。** 送る側で `shrinkImageFile`
- **`prisma migrate` が PGroonga 索引を落とすことがある。** `\di` を前後で
- **Next の proxy は本文を 31MB まで複製する** (next.config.ts)。10MB の画像は
  通るが、Content-Length の無い送信 (chunked) は `checkUploadRequest` を素通りする。
  `fetch` に Blob を渡せば Content-Length は付く
- **メニューは閉じると行ごと捨てられる。** 送信中に閉じられても fetch は進むが、
  結果の表示先が無い。次に開いたときの GET で結果 (メタ) が見えるので、それでよい
- **文字数は code point で数える。** `String.length` は絵文字で 2 になる

## 8. やらないこと

- 履歴・複数枠・端末の識別。1 枠で足りる
- プッシュ通知・同期。開いたときに取りに行く
- 文字の `text/html`。ノートは markdown なので素の文字だけ (docs/92 と同じ)
- `clipboard.read` の無い環境向けの貼り付け欄 (textarea)。欲しくなってから
- 暗号化。通信は HTTPS、スコープは userName、期限は 10 分。これ以上はノート全体
  暗号化 (41-QR-search/docs/25) の話
- ノートへの取り込み。それは docs/92 の「貼り付け」の役目で、こちらは OS の
  クリップボードを運ぶだけ

## 9. 実装の記録 (2026-10-25)

### 9-1. 計画から変えたこと

- **`bytes` 列を足した。** メニューを開くたびに「画像 1.2MB」を出すので、最大 10MB の
  `data` を読まずに大きさを知るため。文字は UTF-8 のバイト数を入れる
- **本文は読みながら数える** (`src/lib/route/boundedBody.ts`)。Content-Length を
  申告しない送信 (chunked) や嘘の申告は事前検査を素通りし、`arrayBuffer()` /
  `json()` で全部読むと 1 人でメモリを食い尽くせる (セキュリティレビューの指摘)。
  画像は 10MB、文字は 64KB を JSON で最大に膨らませた長さ (6 倍 + 枠) で打ち切る
- **期限切れの行は書くときにもまとめて消す。** 読まれない枠は読み出しの掃除が働かず、
  平文が残るため。常駐の掃除役は置かないままで、書くついでに 1 回の `deleteMany`
- **期限切れの削除は「見た版」だけ消す。** `userName` だけで消すと、見つけてから
  消すまでの間に別の端末が書き直した新しい中身を消してしまう (`updatedAt` 一致)
- **NUL を含む文字は 400。** PostgreSQL の text に入らず、保存で 500 になる
- 受け取った後に自動では消さない、デモは 5 口とも 403、の方針は計画どおり

### 9-2. 確かめたこと

- vitest: 純粋部・store・route・送受信ロジック・表示の描き分け。
  `read()` / `writeText()` を同期部で呼ぶこと、10MB 超の画像だけ縮めること、
  GIF は縮めないこと、chunked の巨大本文を読み切らないことを固定した
- Playwright (chromium・ローカル dev): 文字と画像の往復、「消す」、開き直しの予告、
  空のクリップボードの断り。`e2e/server-clipboard.spec.ts`
- 移行はローカルに `prisma migrate deploy` で当て、前後で PGroonga 索引
  (`items_memo_pgroonga_idx`) が残ることを `\di` で確認した

`clipboard_slots` ができ、PGroonga 索引も残っている。未ログインの

## 10. ファイル全般・ドロップへの拡張 (2026-10-25)

v0.23.52 の後に、枠へ置けるものを文字と画像からファイル全般へ広げた。

### 10-1. 受ける形式

このアプリが添付として扱える形式をすべて受ける。判定は中身の署名で、順と部品は
添付の保存口 (attachments/store.ts) と同じ。`src/lib/clipboard/slotFile.ts`。

| 種類 | 形式 | 上限 |
| --- | --- | --- |
| 画像 | png・jpeg・gif・webp・avif・heic・tiff | 10MB |
| 動画 | mp4・mov・webm | 30MB |
| 音声 | mp3・m4a・wav・webm | 10MB |
| PDF | pdf | 10MB |
| テキスト | txt・csv・md・s1p・s2p | 10MB |

- テキストには署名が無いので、`X-File-Name` ヘッダ (URL エンコード) の拡張子で判定する。
  名前は保存せず、判定にだけ使う
- 受けないもの: HTML・SVG (スクリプトを埋め込める)・zip・実行ファイル。名前を偽っても
  中身の署名で弾く。保存した mime がそのまま配信の Content-Type になるので、ここが
  XSS を防ぐ要。配信には `Content-Security-Policy: sandbox` も付ける
- 種類は mime から決まる (`kindOfMime`)。表に列は足していない。メタに `mime` を載せた

### 10-2. 変換

- **写真**: HEIC・TIFF はサーバで JPEG に変換して置く (`normalizeImageForTransfer`)。
  添付の保存は WebP に寄せるが、枠から取り出した写真は LINE・X・Windows のアプリへ
  貼るので、読めないことのある WebP にはしない。向きは画素に焼き、透過は白で埋める
- **10MB を超える写真**はクライアントで長辺 2048 の JPEG に縮めてから送る
  (クリップボード由来もファイル選択も同じ)。GIF・動画・PDF など縮められない物の
  上限超えは、送る前にクライアントで断る
- 受け取って OS のクリップボードへ載せるときの PNG への描き直しは、docs/92 の
  `copyImageToClipboard` のまま。JPEG・WebP・AVIF の写真もこれで貼れる

### 10-3. 受け取り

ブラウザからクリップボードに載せられるのは文字と画像だけ。動画・音声・PDF・テキストの
ファイルは「サーバから保存」のリンク (`download` 属性) にする。JS を挟まないので
iOS のユーザー操作の扱いに依らない。画像には貼り付けのほかに「保存」のリンクも出す。
保存名は `clipboard-日時.拡張子` で、元の名前は残さない。

**iPhone ではリンクにしない (v0.23.54 の修正)。** `download` 付きのリンクは、ホーム画面から
起動した PWA では効かず、動画ファイルそのものへ同じ画面で遷移する。standalone には戻る
ボタンが無く、アプリへ戻れなくなった (実機の報告)。iOS では共有シートを開く
(`SaveSlotFile.tsx`)。動画プレイヤーの共有と同じ二段構えで、1 回目に取得し、許可が
切れたら「もう一度」で手元のバイト列を同期で共有に渡す。PC・Android はリンクのまま。
判定は `shouldOfferShare` (files 付き share が使える + `navigator.standalone` がある)。

### 10-4. 送り方

- 「ファイルを選んで送る」の行 (写真・動画・音声・PDF・テキストを選べる)
- **メニューへのドロップ**。ファイルを引いてきた間だけ点線の枠を出す (`types` に
  `Files` があるときだけ反応し、文字や別タブのリンクは無視する)。複数ファイルは、
  先頭だけ黙って送らず「1 つずつ送ってください」と断る (`pickDroppedFile`)

### 10-5. メモリ

動画 30MB を DB の bytea で置くので、送受信 1 回で数十 MB の一時領域を使う
(本文の連結・Prisma の引数・配信時の複製)。vps は空きが少ないため、同時に何本も
流れる使い方は想定しない。レート制限はまだ無い。

### 10-6. 確かめたこと

vitest (形式判定・変換・上限・送受信・表示・ドロップの判定) と Playwright 16 本
(動画の送信と保存で同じバイト列が落ちる・PDF と日本語名の csv・TIFF が JPEG に
なって貼れる・zip を断る・ドロップ 4 通り)。iPhone 実機は未確認。
