# 予定カレンダー計画 (1 イベント 1 ノート)

> **2026-11-03 の検討で §1 の記法・§3 の置き場・§4 の追加の流れが変わった。**
> 最小仕様と実装計画は [docs/126](126-予定カレンダー仕様メモ.md)。差分は同 §0。

iPhone アプリ SaiSuke2 のようなスケジュール帳を QR-Note の中に作る。
**予定 1 件をノート 1 枚**にし、`/calendar` ページが `date=` プロパティを持つ
ノートを月のマス目に並べる。予定に写真・PDF・音声・お絵かき・シークレット・
QR・公開リンク・git 履歴・全文検索が、何も足さずに付いてくるのが狙い。

きっかけは別リポジトリの検討メモ
`~/60-tommie-schedule/docs/01-構成検討.md` (2026-11-03)。そこでは単体の
PWA (FastAPI + SQLite + FullCalendar) を本命にしていたが、「写真などいろいろ
入れたい」という要望は QR-Note のノートがそのまま満たすので、こちらを先に試す。

**QR-Note に統合する方針で確定 (2026-11-03)。** 単体アプリ案は採らない。

決めたこと (2026-11-03):

- 正本はノート本文。予定の日時はプロパティ行 (`date=2026-11-05 start=10:00`)
  で書き、新しいテーブルは作らない (docs/77 §1・docs/83 §1 と同じ理由)
- 月表示のために**派生列を 3 つ足す** (`event_start` / `event_end` /
  `event_repeat`)。プロパティの JSON には範囲検索が効かず、これが無いと
  月を開くたびに全ノートを舐める
- 月のマス目は自前で描く (docs/83 §6 の「ライブラリを足さず SVG で」と同じ)。
  週・日の時間軸表示が要るようになったら、そのとき FullCalendar を検討する
- 祝日はノートにしない。サーバで計算して月表示に重ねる層にする
- 繰り返し予定は RFC 5545 の RRULE をそのまま `repeat=` に書く。展開は
  `rrule` パッケージに任せる

## 1. ノートの形

```text
# 歯医者 (定期検診)

#予定 #通院
date=2026-11-05 start=10:00 end=11:00
repeat=FREQ=MONTHLY;BYDAY=1WE

受付で保険証。前回のレントゲン ↓
![](image.jpg)
```

プロパティ行の規則は docs/08 のまま (行全体が `キー=値`、空白なし、キーは
英字始まり)。新しい記法は増やさず、**キーの約束だけ決める**。

| キー | 値 | 意味 | 省略時 |
| --- | --- | --- | --- |
| `date` | `YYYY-MM-DD` | 予定の日 (これがある行を持つノートが「予定」) | 予定ではない |
| `start` | `HH:MM` | 開始時刻 (JST) | 終日 |
| `end` | `HH:MM` | 終了時刻 (JST) | `start` + 1 時間。`start` 無しなら終日 |
| `until` | `YYYY-MM-DD` | 複数日の最終日 | `date` と同じ日 |
| `repeat` | RRULE (`FREQ=WEEKLY;BYDAY=MO`) | 繰り返し。`date` が初回 | 1 回きり |
| `skip` | `YYYY-MM-DD` (複数行可) | 繰り返しのうち休む回 | 無し |

- 値に空白を入れられない (docs/08) ので、時刻は `start=10:00` のように分ける。
  `date=2026-11-05 10:00` とは書けない
- `#予定` タグは**必須ではない**。`/calendar` の既定の検索式が `#予定` な
  だけで、タグを変えればカレンダーを分けられる (`#予定 #仕事` など)。
  部品ノートに `date=` を書いても、タグが無ければ既定のカレンダーには出ない
- 繰り返しの「この回だけ別の内容」は、`skip=` で休ませて別ノートを 1 枚切る。
  `until` と `repeat` を両方書いたときは、各回が `until − date` 日間続く
- 時刻は JST 固定 (`lib/datetime.ts` の表示と同じ)。UTC 保存の kick とは違い、
  本文に書くのは人が読む時刻なので JST のまま

## 2. 派生列 — 範囲検索のため

`items` に 3 列足す。tags / props / task_todo / circuit_fences (docs/122 §1)
と同じ「正本は memo、`derivedFromMemo` (`items/write.ts`) が保存のたびに
作り直す」型。

| 列 | 型 | 中身 |
| --- | --- | --- |
| `event_start` | `timestamptz NULL` | `date` + `start` (無ければ 00:00 JST) |
| `event_end` | `timestamptz NULL` | `until` or `date` + `end` (終日なら翌日 00:00 JST、半開区間) |
| `event_repeat` | `text NULL` | `repeat` の値そのまま。無ければ NULL |

- 索引は `event_start` に 1 本 (`WHERE event_start IS NOT NULL` の部分索引)。
  Item のコメントにある「数百件の seq scan で足りる」は、SaiSuke2 の使い方
  (細かい用事も全部) をすると年 500〜1,000 ノート増えて崩れるので、最初から張る
- 月を引く条件: `event_start < 月末 AND (event_end > 月初 OR event_repeat IS NOT NULL)`
  に検索式 (`buildWhere`) を AND する。繰り返しのノートは全部拾い、展開して
  月に当たる回だけ残す (繰り返しは数十件が上限だろうから、ここは全件でよい)
- `date` が読めない (`date=来週`) ときは 3 列とも NULL にし、予定として出さない。
  黙って落とすのは docs/08 の「値は緩く受けて判断は人に委ねる」と同じ姿勢だが、
  編集画面の注意行 (後述 §4) で気づけるようにする
- 移行 `prisma/migrations/<日時>_add_item_event_columns`。**適用後に `\di` で
  PGroonga の索引が残っているか見る**
- バックフィル `scripts/backfillEventColumns.ts` + `doBackfill.sh events`。
  docs/122 §1-3 と同じ形 (全件を読み、違う行だけ生 SQL で UPDATE、冪等)。
  既存ノートに `date=` はほぼ無いはずなので、実質は新規保存分だけ

## 3. `/calendar` ページ

| 部位 | 中身 |
| --- | --- |
| 上 | 検索式 (既定 `#予定`)、月送り、今日 |
| 中 | 7 列の月のマス目。各日に予定の題名 (ノートの `title` 列) を文字で並べる。SaiSuke2 の月表示がこれ |
| 日をタップ | その日の予定の一覧 (題名・時刻・サムネ 1 枚) と「+」 |
| 予定をタップ | `/item/<id>` を開く (3 ペイン検索の器が使えるなら右ペインに) |

- 描画は自前 (`components/calendar/MonthGrid.tsx`)。7 列の grid と、予定の
  チップだけなので小さい。健康グラフ (docs/83 §6) と同じ判断
- データは `lib/calendar/calendarQuery.ts` (DB を触るのはここだけ、
  `searchItemRows` を共有) → `lib/calendar/expandEvents.ts` (繰り返しの展開、
  DB 非依存の純関数、`rrule` を使う) → ページ
- 上限は `CALENDAR_ROW_LIMIT = 200` (`items/limits.ts`)。SQL 側で月に絞るので、
  1 か月 200 件を超えることは個人利用では無い
- 週・日の時間軸表示は作らない (§8)。必要になったら FullCalendar
  (`@fullcalendar/react` + daygrid / timegrid / rrule、MIT) に乗り換える。
  その場合もデータの経路 (§2 の列と展開) はそのまま使える

## 4. クイック追加 — 日付をタップして題名だけ打つ

SaiSuke2 の「日をタップ → 題名を打つ → 保存」に負けないことが要点。
iPhone で `date=2026-11-05` を手打ちさせてはいけない。

- 月表示の「+」は `/new?draft=<本文>` を開く。`/new` は今は採番して
  `/edit/<id>` へ送るだけ (docs/27) なので、`draft` をそのまま
  `/edit/<id>?draft=` へ引き継ぎ、**エディタが空のときだけ初期本文にする**
  (DB には書かない。「更新」で初めて行ができる、という docs/27 の約束は保つ)
- ひな型は `# \n\n#予定\ndate=2026-11-05\n` で、カーソルは 1 行目の題名に置く
- 編集画面の下に**予定の注意行**を出す: `date=` があって 3 列が組めない
  (`date=来週`、`start=25:00`) ときに「予定として出ません」と 1 行。
  健康の記録欄 (docs/83 §7) と同じく、本文を書き換える部品ではなく読むだけの部品
- 日付・時刻の変更は本文を直す。SaiSuke2 のドラッグ移動は作らない (§8)

## 5. 祝日 — ノートにせず層にする

`@holiday-jp/holiday_jp` 2.5.2 (2026-09 更新、内閣府のデータ表に基づく) を
サーバで呼び、月表示の日付に祝日名を重ねる。

- ノートにしない理由: 年 17 件 × 何年分ものノートが検索・同期・履歴に混ざる
  割に、本文に書くことが無い
- データ表方式なので、収録範囲を超えた年は空になる。年に 1 度、翌々年が
  出るかを確かめる (別リポジトリ `60-tommie-schedule/docs/01` §祝日の自動設定
  に、内閣府 CSV と Python の `jpholiday` を突き合わせた記録がある。
  2020〜2027 年は全件一致だった)
- 手元検証は未。採用前に 2026〜2028 年を内閣府 CSV と突き合わせる
  (`date-holidays` 3.38.0 が代案)

## 6. オフライン

Phase 1 ではオンライン専用。`/calendar` はオフラインの入口 (docs/65) に載せない。

同期 (`offline/syncItems.ts`) はノート本文を端末に持っているので、
`expandEvents` が純関数なら端末側でも同じ月表示が組める (props は本文から
再抽出できる)。繰り返し展開の `rrule` が端末にも降りる点だけが重さの増分。
これは Phase 3 で、オフライン検索 (`offline/filter.ts`) と同じ「文法は 1 つの
実装を共有する」型で入れる。

## 7. 一覧への溢れ

`#予定` のノートが年に数百枚増えると、検索の既定一覧・最近閲覧・タグ補完に
予定が混ざる。

- 最初は何もしない。混ざって困るかは使ってみないと分からない
- 困ったら `user_settings` (docs/88 の汎用 key-value) に「一覧から隠すタグ」を
  持ち、既定の検索式に `-#予定` を補う。検索式に `#予定` を明示したときは隠さない
- オフラインの同期は全件を 1 クエリで引く (Item のコメント) ので、件数が
  効いてくるのはここが先。docs/124 の差分同期が入れば問題は消える

## 8. やらないこと

- 週・日の時間軸表示、ドラッグでの移動・伸縮 (必要になったら FullCalendar)
- Google カレンダー・CalDAV との同期。iCal (.ics) の書き出しは、展開済みの
  予定を並べるだけなので後から足せる
- 予定専用のテーブル・画面。ノートの一枚として扱い、一覧・検索・公開・QR・
  履歴・エクスポートは既存の経路をそのまま通す
- 1 か月 1 ノートに日付行を並べる第 2 の入力源 (docs/83 の健康と同じ型)。
  軽い予定 (「17:00 ゴミ出し」) に 1 ノートが重いと分かったら足す。
  `/calendar` は両方を集められる形にしておくが、最初から 2 系統は作らない
