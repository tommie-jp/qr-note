# 検索表示高速化計画

検索結果の表示が PC でも iPhone でも遅い。初版 (2026-10-28 午前) は curl と
DevTools の計測から「DB もサーバも速く、転送量とブラウザの描画が重い」と
見立てた。同じ日の夜に速度計測ログ (docs/119) で検索・追加読み込み・ノート・
同期を段階ごとに測り直したところ、**サーバの CPU を回路フェンスの解析が
食っている**ことが分かり、順番を組み替えた。

決めたこと (2026-10-28 改訂):

- 一番先に §1 (回路フェンスの解析を覚えておく) をやる。一覧の段階で最も
  重く、同期では Node を 2 秒止めて、その間の検索をすべて待たせている
- 次に §2 (打鍵のたびに続けて走る「追加」を止める)。1 回の検索が 2〜3 回の
  要求になり、後の要求ほど大きい
- フォルダーペイン (§3)・同期の転送 (§4)・行の prefetch (§5) は初版の
  計画のまま、順番だけ後ろにずらす
- 検索結果のサーバキャッシュは**作らない** (§7)。測り直しても DB の検索は
  3〜29ms で、縮める余地がない
- 前後の比較は docs/119 の行で行う。手順は §0-1

## 0. 計測

### 0-1. 手順

docs/119 の計測は本番ビルドで行う (`next dev` では数秒おきに全体を
読み直してしまい、測れない)。手元の作業ツリーを別タグでビルドし、
`PERF_LOG=1` で起動直後から計測を立てて 3301 で起こす。

```bash
docker build -t qr-search-app:perf .
HASH=$(node -e "const b=require('bcryptjs'); process.stdout.write(Buffer.from(b.hashSync('e2e-test-pass',10)).toString('base64'))")
PW=$(grep '^POSTGRES_PASSWORD=' .env | cut -d= -f2-)
docker run -d --name qr-measure --network qr-search_default --env-file .env \
  -e APP_ENV= -e PERF_LOG=1 -e DATABASE_URL="postgresql://qr:${PW}@db:5432/qr" \
  -e BASIC_AUTH_USER=e2e -e BASIC_AUTH_HASH_B64="$HASH" \
  -e WEBAUTHN_RP_ID=localhost -e WEBAUTHN_ORIGIN=http://localhost:3301 \
  -p 127.0.0.1:3301:3000 qr-search-app:perf
# サーバの行
docker logs qr-measure 2>&1 | grep '計測'
# 片付け
docker rm -f qr-measure && docker rmi qr-search-app:perf
```

操作は Playwright で流す。`http://e2e:e2e-test-pass@localhost:3301/login` で
入り、cookie `panes` と `view=compact` を置いて次を繰り返す。

1. `/` を開いて読み込みを待つ
2. 検索窓 (`input[type="search"][name="q"]`) に `抵抗`・`コンデンサ`・
   `オペアンプ` を 1 文字ずつ打ち、それぞれ 3 秒待つ
3. 一覧の 2 件目を押す

ブラウザ側の行 (応答開始・受信・RSC・prefetch・DOM) は stdout に出ないので
`/logs?perf=1` から読む。iPhone の代わりは幅 390・高さ 844、CDP で
CPU 4 倍遅く (`Emulation.setCPUThrottlingRate`) した 1 ペインで測った。

本番では /logs?perf=1 の「計測を始める」から同じ操作を PC と iPhone で行う
(docs/119 §6-1 の手順 6)。

### 0-3. 読み取れること

1. **サーバの時間の大半は回路フェンスの解析。** 一覧の `回路=` は DB の
   `検索=` の 10〜40 倍。中身は `extractCircuitFences` が本文全体を描画と
   同じパーサ (`createNoteParser`) で構文解析する処理で、ノート 1 件
   あたり 3〜5ms かかる。DB から SVG を引く部分は数 ms
2. **同期はサーバ全体を 2 秒止める。** 同じ解析を 583 件に掛けるため。
   CPU だけを使う同期処理なので、その間はほかの要求が一切進まない。
   計測では、同期と重なった検索の応答開始が 1.6 秒になった。端末を
   開くたび (5 分おき) に起きる
3. **1 回の検索が 2〜3 回の要求になる。** 1 ページ 20 件では画面の 2 倍
   (先読みの距離) が埋まらず、追加読み込みがすぐ続く。追加は 1〜N ページを
   まとめて描き直す作りなので、後の要求ほど大きい。`コンデンサ` の 1 回で
   RSC は 57 + 185 + 333 = 575KB (gzip 後) を運んだ
4. **回路図の多い検索は 1 ページ目から重い。** SVG を行に埋め込んでいる
   ため (docs/68 §3)。`オペアンプ` は 20 件で 149KB、`抵抗` の 5 倍
5. **3 ペインの重さはフォルダーペイン。** 2 ペインとの差は RSC で
   100KB / 1MB、DOM で 5,200。初版 §1 の見立てどおり
6. **DB は速い。** `検索=` は 3〜29ms。キャッシュで縮む余地はない

読み取れること:

1. **本番では回路図サムネの解析が手元の 10 倍以上重い。** 20 件で 0.5〜1.4 秒。
   vps1 の CPU が手元より遅く、本番の検索結果には本文の長い教科書の頁
   (37KB 前後) が多い。1 件あたり数十 ms になる。サーバの時間のほぼ全部がここ
2. **同期の直後なのに記憶が効いていなかった。** 同期は 490 件を解析した後
   だったが、検索の `回路=` は冷えたままだった。Next が同期の口とページを
   別々に束ねるので、モジュールの変数に置いた記憶が 2 つあった。記憶を
   globalThis に置き直した (§1-2)。手元では、同期の後の初めての検索の
   `回路=` が 86〜121ms から 5〜10ms になった
3. **3 ペインはフォルダーが重い。** RSC が展開後 2.1〜2.2MB、DOM が 1.1〜1.3 万。
   タグが手元より多い (1,581 種) ぶん §3 の効き目は大きい
4. `受信=` が長いのは、RSC が流しながら届くため。サーバが回路図を解析して
   いる間も受信が続くので、`全体=` はほぼ「サーバ + 転送」になる
5. 手順はノートを開く段で途切れた。3 ペインでは一覧の領域にノート側の釦も
   入っていて、それを押して全体の読み込み直しになった。押すのを行の
   題名リンクに限り、途切れたら次の読み込みで計測を止めるよう直した
   (docs/120 §2)。iPhone はまだ流していない

次の手: 冷えた解析が 1 件数十 ms かかるので、記憶だけでは配布直後と
初めて出るノートが重いまま残る。§1-B (書き込み時に派生列へ) か、起動時に
裏で記憶を温める案を、記憶の共有を配布した後の本番の数字で選ぶ。

## 2. 検索の直後に続く追加読み込みを止める

## 4. オフライン同期の転送を軽くする

§1 でサーバの時間は片付くが、転送は 10.5MB の非圧縮のまま残る。

- Next.js は Route Handler の JSON を圧縮しない (計測で `転送=` の
  2 つの値が同じ)。本番の nginx も既定 (`gzip_proxied off`) で上流の応答を
  圧縮しない
- iPhone の回線では 10.5MB が数十秒かかり、その間の打鍵と帯域を取り合う

### 4-1. 段階 A: 圧縮して返す

`src/lib/route/respond.ts` に `apiOkCompressed(data, request)` を足す。
`Accept-Encoding` に gzip があれば `zlib.gzipSync` した本文に
`Content-Encoding: gzip` と `Vary: Accept-Encoding` を付ける。使うのは
`app/api/sync/items/route.ts` だけ。docs/119 の `Server-Timing` に
`gzip` の段階を足す。

rss は手元で 522〜635MB まで上がった。gzip でさらに積むので、本番の
`同期/サーバ` の rss を見て、vps1 で苦しければ `zlib.createGzip()` の
ストリームに替える。

テスト (`route.test.ts`): gzip 付きの要求は `Content-Encoding` が付き、
展開すると素の応答と同じ JSON。無しは `Content-Encoding` が無い。

期待値: 10.5MB → 約 2.2MB。

### 4-2. 段階 B: 変化が無ければ 304

応答に ETag を付け、`If-None-Match` が一致したら 304 で返す。ETag は
本文を組む**前**に安いクエリ 1 本で決める。

```sql
SELECT count(*) FILTER (WHERE deleted_at IS NULL)              AS live,
       max(updated_at)                                         AS updated,
       max(accessed_at)                                        AS accessed,
       max(deleted_at)                                         AS deleted,
       count(*) FILTER (WHERE offline_pin AND deleted_at IS NULL) AS pinned
FROM items
```

これに `circuit_svgs` の件数を足して文字列にする。ゴミ箱と印は
`updated_at` を触らないので、`max(updated_at)` だけでは拾えない
(trash.ts、docs/65 §7-3)。

- `OfflineSyncPayload` に `etag` を足す。`syncOfflineItems()` は保存済みの
  etag を `If-None-Match` に載せ、304 なら保存を触らずに今の写しを返し、
  `{ changed: false }` を添える (OfflineApp の「変更はありません」)
- 304 でも `LAST_SYNC_ATTEMPT_KEY` は書く

テスト: route (一致で 304・本文なし・no-store のまま)、sync.ts (304 で
保存を呼ばない)、ETag の純関数。

期待値: 変化が無い開き直しは数百バイトの 304 だけになる。

### 4-3. 段階 C: 差分だけ送る (様子見)

A・B の後も、ノートを 1 件直すと次の同期は 2.2MB 丸ごとになる。

突き合わせ用、gzip 後 20KB)、変わったノートの回路図を返し、端末は純関数
`mergeSnapshot(current, delta)` で写しを作り直す。docs/65 §3-2 が差分同期を
しないと決めた前提 (本文は数百 KB) は崩れているので、そこに追記してから
進める。

検討の発端は「DB に変化がなければキャッシュを返す」だった。測り直しても
DB の検索は 3〜29ms で、サーバの時間の大半は回路フェンスの解析だった
(§0-3)。解析は本文が同じなら結果も同じなので、§1 で**解析の結果だけ**を
覚える。検索結果を丸ごと覚えるより無効化が要らない (本文の hash が鍵) 分
単純で、同期にも同じものが効く。

後で検索結果のキャッシュが要るなら、Next.js 16 の `use cache` を
`loadSearchResults` に付けて `cacheTag('items')` を貼り、書き込みの
Server Action で `updateTag('items')` を呼ぶか、DB のトリガーで版番号の表を
持つ。どちらも `max(updated_at)` では代用できない (§4-2 と同じ罠)。

## 8. 順番と検証

1. §1-A を実装し、§0-1 の手順で測り直す。見るのは一覧と追加の `回路=`、
   同期の `サーバ=`、同期中の検索の応答開始、遅い SQL の行
2. §2-A を実装し、1 回の検索が 1 要求になること・RSC の合計を見る
3. 配布して本番の /logs?perf=1 で PC と iPhone の「前後」を取る。
   vps1 の CPU では §1 の差がもっと大きく出るはず
4. §3 → §4-A・§4-B → §5 の順に入れ、それぞれ同じ手順で測る
5. 本番の行を見て §1-B・§2-B・§2-C・§4-C を判断する

vps1 の CPU・メモリはまだ確認できていない (ssh が自動モードで許可され
なかった)。本番の行の `同期/サーバ` の rss と、`nproc; free -m` を
控えて突き合わせる。

## 9. やらないこと

- 検索結果のサーバキャッシュ (§7)
- 回路フェンスを正規表現で探す (描画とずれる。extractFences.ts の冒頭)
- フォルダーペインを layout へ移す (§3-3)
- 自動ノートの作り直し (§6)
- 同期の間隔 (5 分) を変える。間隔より 1 回の重さが問題
- vps1 のプラン変更。§1・§4 の後の本番の行を見てから判断する

## 10. 表示モードの切替の往復を消す (方針待ち)

§0-11 のとおり、切替が体感で遅い理由は回線 1 往復で、サーバの処理ではない。

| 案 | 内容 | 効き目 | 手間 |
| --- | --- | --- | --- |
| A. 何もしない | 先読み 39 本の削減だけ (済) | 小。往復は残る | 0 |
| B. 押した瞬間に替える | 行の描き方をクライアントが持つ | 往復の待ちが消える | 大。行を4モードの部品に分ける |
| C. 隣を先に描く | 4 モードぶん描いて表示だけ切り替える | 同上 | 大。DOM と RSC が膨らみ §3 を戻す |
| D. 押した直後に「切替中」の見た目を出す | 釦に待ちの印を付ける (すでに押した釦は回る) | 体感のみ | 小 |

C は §3 で削った DOM と転送量を戻すので採らない。B が本筋だが、行の描き方を
サーバ部品からクライアント部品に動かす作りの変更になる。着手前に利用者に
方針を決めてもらう。
