# 検索表示高速化計画

検索結果の表示が PC でも iPhone でも遅い。手元で本番ビルドを計測したところ、
DB もサーバの描画も速く (検索クエリは 1ms 未満、応答開始まで 10〜15ms)、
遅さの正体は**転送量とブラウザ側の描画**だった。重い順に 3 つあり、
この計画はそれぞれを実装の粒度まで落とす。

決めたこと (2026-10-28):

- 検索結果のサーバキャッシュは**作らない** (§4)。計測上、効く場所がない
- 着手順は §1 (フォルダーペイン) → §2-A・§2-B (同期の圧縮と「変化なし」の
  304) → 本番で計測 → §3-1 (行の prefetch) → §2-C (差分同期) は計測を見て判断
- 計測の手順を §0 に残し、着手前と後で同じ方法で測る

## 0. 計測 (2026-10-28)

本番イメージ `qr-search-app:latest` を手元の DB (ノート 1,148 件、本文 5.5MB、
回路図 SVG 592 枚 6.4MB) に繋いで別ポートで起動し、curl と Playwright で測った。
ローカルは 24 コアなので、サーバ側の時間は本番 (vps1) ではこれより伸びる。
転送量とリクエスト数は本番でも同じ。

### 0-1. 手順

```bash
# 計測用に本番イメージを 3301 で起こす (同じ DB、資格情報だけ上書き)
HASH=$(node -e "const b=require('bcryptjs'); process.stdout.write(Buffer.from(b.hashSync('e2e-test-pass',10)).toString('base64'))")
PW=$(grep '^POSTGRES_PASSWORD=' .env | cut -d= -f2-)
docker run -d --name qr-measure --network qr-search_default --env-file .env \
  -e APP_ENV= -e DATABASE_URL="postgresql://qr:${PW}@db:5432/qr" \
  -e BASIC_AUTH_USER=e2e -e BASIC_AUTH_HASH_B64="$HASH" \
  -e WEBAUTHN_RP_ID=localhost -e WEBAUTHN_ORIGIN=http://localhost:3301 \
  -p 127.0.0.1:3301:3000 qr-search-app:latest

# ログインして cookie を取り、ペイン構成ごとに HTML と RSC の大きさ・時間を測る
curl -s -o /dev/null -u e2e:e2e-test-pass -c cj http://localhost:3301/login
URL='http://localhost:3301/?q=%E6%8A%B5%E6%8A%97'
for p in 1 2 3; do
  curl -s -o /dev/null -b cj -b "view=compact; panes=$p" \
    -w "panes=$p DOC %{size_download}B ttfb=%{time_starttransfer}\n" "$URL"
  curl -s -o /dev/null -b cj -b "view=compact; panes=$p" \
    -H 'RSC: 1' -H 'Accept-Encoding: gzip' \
    -w "panes=$p RSC-gz %{size_download}B\n" "$URL"
done
curl -s -o /dev/null -b cj -H 'Accept-Encoding: gzip' \
  -w "sync %{size_download}B %{time_total}s\n" \
  http://localhost:3301/api/sync/items
docker rm -f qr-measure
```

ブラウザ側は Playwright で `http://e2e:e2e-test-pass@localhost:3301/login` へ
入り、`performance.getEntriesByType('navigation')` と `'resource'` を読む。
打鍵から結果の差し替えまでは `[data-results-pane]` の textContent の変化を待つ。

## 1. フォルダーペインのタグ一覧を絞り、二重描画をやめる (PC・3 ペイン)

### 1-1. 何が重いか

- `FolderPane` がタグ 1,236 件を全部 `Link` で描く。HTML で 1.3MB、RSC で
  1MB、DOM で 2,480 ノード
- `(search)/page.tsx` が `SearchFolders` を Suspense で後送りし、その fallback
  にも同じ `tags` を渡しているので、**同じ 1,236 行が 2 回**描かれる
  (fallback と本体)
- 打鍵のたびに page が描き直され、この一覧が RSC で毎回送り直される
  (3 ペインの打鍵 1 回 = gzip 後 145KB、うち約 100KB がこの一覧)
- 画面に入った行から prefetch が走る (76 要求)

### 1-2. 出すタグを絞る

フォルダーは「よく使う入口」であって、タグの全目録ではない (全目録は検索窓の
補完が既に持つ)。次の 2 つを満たすタグだけ並べる。

- **2 ノート以上**に付いている (`FOLDER_TAG_MIN_COUNT = 2`)
- 数字だけのタグではない (旧番号 `#1003`。docs/107 §4-5 で本文へ移した物で、
  フォルダーとして辿る意味がない)

手元のデータではこれで 1,236 件 → 約 37 件になる。絞った残りは
「ほか N 件のタグは検索窓の補完から」と 1 行で断る (黙って減らすと
「タグが消えた」に見える。`searchItemProps` の omitted と同じ考え)。

判定は純関数 `folderTags(tags: TagCount[]): { shown: TagCount[]; hidden: number }`
を `src/lib/search/folderTags.ts` に置き、`FolderPane` ではなく呼び出し側
(`page.tsx` の fallback と `SearchFolders`) で通す。`FolderPane` は渡された物を
並べるだけに保つ (テストが素のまま通る)。`listTags()` 自体は変えない —
検索窓の補完は全件が要る。

### 1-3. fallback に一覧を渡さない

fallback の目的は「ペインの有無で一覧の幅が跳ねない」ことだけで
(globals.css の `body:has([data-folder-pane])`)、中身は要らない。fallback を
`<FolderPaneShell />` (`data-folder-pane` を持つ空の `aside` + `PaneResizer`)
にして、タグは本体でだけ描く。`SearchFolders` の DB 読みは合計 1ms 未満
(`countFolderTotals` 0.6ms・`listQueries` 小) なので Suspense を外す選択肢も
あるが、構造を変えずに済む fallback の差し替えで足りる。

### 1-4. 打鍵ごとの送り直しは残す

一覧を `(search)/layout.tsx` へ移せば searchParams の変化で送り直されなく
なるが、開いているフォルダーの印 (`aria-current`) が `query` に依存して
いるので、印だけ client へ分ける作り直しになる。§1-2 で一覧が 37 件に
なれば送り直しは数 KB で、割に合わない。**やらない**。

## 2. オフライン同期を軽くする (iPhone・PC 共通)

### 2-1. 何が重いか

`OfflineSync` は画面を開き直して 5 分経っていれば `/api/sync/items` を撃ち、
全ノートと描画済み回路図を丸ごと受けて IndexedDB を置き換える (docs/65 §3-2)。
いまそれが 10.8MB で、しかも**圧縮されていない**:

- Next.js は Route Handler の `NextResponse.json` を圧縮しない (実測。
  ページの HTML と RSC は gzip で返っている)
- 本番の nginx も `gzip_proxied` が既定 (off) なので、上流の応答を圧縮しない
- Caddy (ローカル・デモの compose) も `encode` を書いていない

読み込み完了後に始める (docs/65 §5-7) ので白画面にはならないが、
iPhone の回線では 10.8MB が数十秒かかり、その間の打鍵・遷移と帯域を取り合う。

### 2-2. 段階 A: 圧縮して返す

`src/lib/route/respond.ts` に `apiOkCompressed(data, request)` を足す。
`Accept-Encoding` に gzip があれば `zlib.gzipSync` した本文に
`Content-Encoding: gzip` と `Vary: Accept-Encoding` を付けて返し、
無ければ今までどおり。`Cache-Control: no-store` は変えない。
使うのは `app/api/sync/items/route.ts` だけ (他の API は小さい)。

同期の口は 10MB の文字列を一度メモリに積む作りで、gzip も同じ桁を積む。
vps1 のメモリに収まるかは §5 の本番計測で `docker stats` を見る。
収まらなければ `zlib.createGzip()` のストリームに切り替える。

テスト (`route.test.ts`): `Accept-Encoding: gzip` 付きは `Content-Encoding`
が付き、展開すると素の応答と同じ JSON。無しは `Content-Encoding` が無い。

期待値: 10.8MB → 2.2MB。

### 2-3. 段階 B: 変化が無ければ本文を送らない (ETag)

同期の多くは「前回から何も変わっていない」はずで、そのときに 2.2MB を
送るのも無駄になる。応答に ETag を付け、クライアントが `If-None-Match` で
送り返したら 304 で返す。

ETag は本文を組み立てる**前**に安いクエリ 1 本で決める (本文を組んでから
ハッシュすると、DB 読みと JSON 化は毎回払うことになる):

```sql
SELECT count(*) FILTER (WHERE deleted_at IS NULL)              AS live,
       max(updated_at)                                         AS updated,
       max(accessed_at)                                        AS accessed,
       max(deleted_at)                                         AS deleted,
       count(*) FILTER (WHERE offline_pin AND deleted_at IS NULL) AS pinned
FROM items
```

これに `circuit_svgs` の件数を足して文字列にする
(`"<live>-<updated>-<accessed>-<deleted>-<pinned>-<svgs>"`)。
それぞれ、ノートの追加・編集 / 開いた順 (オフラインの並びに使う) /
ゴミ箱と復元 (updated_at を触らない。trash.ts) / 印 (docs/65 §7-3 で
updated_at を触らない) / 描画済み回路図の増加、を拾う。永久削除は
live の減少で拾える。取り込み (ZIP・ENEX) も updated_at が動くので拾える。

クライアント側:

- `OfflineSyncPayload` に `etag: string` を足す (無い古い保存は「無し」扱い)。
  `parseSyncPayload` は文字列でなければ落とす
- `syncOfflineItems()` は `loadOfflineSnapshot()` の etag を `If-None-Match` に
  載せ、304 なら保存を触らずに今の写しを返す。戻り値に
  `{ changed: boolean }` を添える (OfflineApp の「今すぐ同期」が
  「変更はありません」と言えるように)
- 304 でも `LAST_SYNC_ATTEMPT_KEY` は書く (いまと同じ)

テスト: route (ETag 一致で 304・本文なし・no-store のまま)、sync.ts
(304 で保存を呼ばない・写しを返す)、ETag を作る純関数 (値の並びと
null の扱い)。

期待値: 変化が無い開き直しは数百バイトの 304 だけになる。

### 2-4. 段階 C: 差分だけ送る (計測を見て判断)

A と B の後も、ノートを 1 件直すたびに次の同期は 2.2MB 丸ごとになる。
iPhone でまだ重ければ、`?since=<前回の syncedAt>` で変わった分だけ返す。

- 返すのは `greatest(updated_at, accessed_at) > since` のノート、
  `deleted_at > since` の id (removed)、生きている全 id の一覧 (永久削除を
  端末側で突き合わせて落とす。1,148 件で約 40KB、gzip 後 20KB)、
  変わったノートに含まれる回路図
- 端末側は純関数 `mergeSnapshot(current, delta)` で写しを作り直す
  (`src/lib/offline/merge.ts` + テスト)。保存の形 (snapshot ストアの 1 レコード)
  は変えない
- `since` には端末の時計を使わない。前回の `syncedAt` (サーバ時刻) を返す
- 初回・etag 無し・`truncated` のときは今までどおり全件

docs/65 §3-2 が「差分同期をしない」と決めた理由 (単純さ) は、本文が数百 KB
だった頃のもの。前提が崩れたことを §3-2 に追記したうえで進める。

## 3. 一覧の後ろで走る通信を減らす

### 3-1. 行の prefetch を止める

一覧の行 (`ItemRowCompact` / `ItemRowCard` の `Link`) は画面に入るたびに
`/item/<id>` を prefetch し、1 検索で 63 要求出ている (21 行 × 最大 3 回)。
`/item` は動的経路なので prefetch で届くのは loading 境界までで (Next 16 の
`prefetch="auto"`)、押したときの本文は結局その場で取る。つまり prefetch で
縮むのは待ち画面が出るまでの時間だけで、iPhone (hover が無い) では
ほぼ効かない。行の `Link` に `prefetch={false}` を付ける。

タグのリンク (`rowParts.tsx`) と検索窓の候補 (`SearchForm.tsx`、既に
`prefetch={false}`) も同じ扱いにする。フォルダー行は §1-2 で 37 件になる
ので既定のまま。

テスト: 単体では prefetch の有無は見えないので、§0 の手順で
「1 検索あたりの /item への要求数」が 0 になることを確かめる。

### 3-2. 自動ノート (2・3 ペイン) は様子見

先頭ノートを毎回描く分は RSC で約 10KB (gzip 後) と小さい。ただし
サーバでは `ItemView` が本文の描画と表・健康グラフの DB 読みを打鍵ごとに
やっているので、vps1 の CPU では効いているかもしれない。§5 の本番計測で
2 ペインと 1 ペインの TTFB を比べ、差が出たら次の計画にする。

### 3-3. 打鍵ごとの RSC はこのまま

1 ペイン 38KB・2 ペイン 50KB (gzip 後) で、打鍵の debounce 300ms
(useSearchDebounce.ts) も効いている。これ以上は本文のプレビュー (docs/71) を削る話になるので
やらない。

## 4. 検索結果のサーバキャッシュはやらない

検討の発端は「DB に変化がなければキャッシュを返す」だった。計測上、
検索クエリは 1ms 未満、サーバの応答開始は 10〜15ms で、キャッシュで
縮むのはこの十数 ms だけになる。転送量 (§1・§2) と要求数 (§3) が桁で
大きいので、そちらを先に片付ける。

もし後で要るなら、Next.js 16 の `use cache` を `loadSearchResults` に付け
`cacheTag('items')` を貼り、無効化は (a) 書き込みの Server Action で
`updateTag('items')` を呼ぶか、(b) DB のトリガーで版番号の表を持ち、毎回
1 行読んでキャッシュのキーに混ぜる。(b) はスクリプトや直接 SQL の編集も
拾えるが、どちらも `max(updated_at)` では代用できない (ゴミ箱と印は
updated_at を触らない。§2-3 と同じ罠)。

## 5. 順番と検証

1. §1 を実装し、§0 の手順で 3 ペインの HTML / RSC / DOM を測り直す
2. §2-A・§2-B を実装し、同期の転送量 (初回 2.2MB・2 回目 304) を測る
3. 配布して本番で測る。測り方は docs/119-速度計測ログ計画.md の行
   (/logs?perf=1 で計測を始め、PC と iPhone で同じ操作をする)。検索 1 回の
   転送量・prefetch の本数・サーバの段階、同期の転送量と rss がそこに並ぶ
   (2026-10-28 に実装。iPhone でも Mac 無しで数字が取れる)
4. §3-1 を実装し、/item への要求数が 0 になることを確かめる
5. iPhone でまだ重ければ §2-C

vps1 の CPU・メモリは今回確認できていない (ssh が自動モードで許可されな
かった)。本番計測のときに `nproc; free -m` を控え、docs/23 の見積もりと
突き合わせる。

## 6. やらないこと

- 検索結果のサーバキャッシュ (§4)
- フォルダーペインを layout へ移す (§1-4)
- 同期の間隔 (5 分) を変える。間隔より 1 回の重さが問題
- vps1 のプラン変更。転送量を減らしてから判断する
